Governor Limits

The complete cheat sheet — every limit that matters, why it exists, how to measure your usage, and the concrete pattern that fixes each violation.

Why limits exist

Salesforce is multitenant: your code runs on servers shared with thousands of other companies. Governor limits are the platform's enforcement of fair resource use — a runaway loop in your org must not slow down anyone else's.

Limits are per-transaction, and a transaction is bigger than you think

Other limits worth knowing

Async & scheduling

  • 250,000 async executions per 24 h (or 200 × licences, whichever is greater)
  • 100 scheduled Apex jobs
  • 5 concurrent batch jobs; 100 in the flex queue
  • Batch: up to 50 M records via QueryLocator; scope 1–2,000
  • 10 concurrent long-running (>5 s) synchronous requests

API & integration

  • API calls per 24 h: 15,000 (Enterprise) + 1,000/licence, tiered by edition
  • Bulk API 2.0: 150 M records/24 h
  • Composite: 25 subrequests; Composite Graph: 500 nodes
  • Platform Events: publishing and delivery allocations per 24 h by edition
  • Callout endpoint must be in Remote Site Settings or a Named Credential

Storage

  • Data storage: 2 KB per record (most objects)
  • File storage separate from data storage
  • Recycle Bin: 15 days, 25× your storage in records

Email

  • Single emails to external addresses: 5,000/day (org)
  • Mass email: 5,000 external recipients/day
  • 10 Messaging.sendEmail calls per transaction
  • Emails from tests are never actually sent

Measuring your usage

System.debug('SOQL   : ' + Limits.getQueries()       + '/' + Limits.getLimitQueries());
System.debug('Rows   : ' + Limits.getQueryRows()     + '/' + Limits.getLimitQueryRows());
System.debug('DML    : ' + Limits.getDmlStatements() + '/' + Limits.getLimitDmlStatements());
System.debug('DMLRows: ' + Limits.getDmlRows()       + '/' + Limits.getLimitDmlRows());
System.debug('CPU    : ' + Limits.getCpuTime()       + '/' + Limits.getLimitCpuTime());
System.debug('Heap   : ' + Limits.getHeapSize()      + '/' + Limits.getLimitHeapSize());
System.debug('Callout: ' + Limits.getCallouts()      + '/' + Limits.getLimitCallouts());
System.debug('Async  : ' + Limits.getQueueableJobs() + '/' + Limits.getLimitQueueableJobs());

// Defensive guard before an expensive operation
if (Limits.getQueries() >= Limits.getLimitQueries() - 10) {
    // stop and hand off to an async job instead of blowing up
    System.enqueueJob(new ContinueProcessingQueueable(remainingIds));
    return;
}
🚫
You cannot catch a LimitException System.LimitException is deliberately uncatchable — the platform must be able to kill a runaway transaction. Measure and prevent; you cannot recover.

Reading the debug log

  • Setup → Debug Logs → New, set the trace flag on your user, with Apex = FINEST.
  • At the bottom of every log, the CUMULATIVE_LIMIT_USAGE block lists final consumption of every limit.
  • LIMIT_USAGE_FOR_NS shows usage per namespace — useful for blaming a managed package.
  • The Developer Console's Execution Overview → Limits tab shows the same data graphically.
  • Logs are capped at 20 MB and truncated; raise log levels selectively rather than everything at FINEST.

The four patterns that keep you safe

1 · Query once, map it

Map<Id, Account> parents = new Map<Id, Account>(
  [SELECT Id, Tier__c FROM Account
   WHERE Id IN :accountIds]);

for (Contact c : Trigger.new) {
  Account a = parents.get(c.AccountId);
  if (a != null) c.Tier__c = a.Tier__c;
}

2 · Collect, then commit

List<Task> toInsert = new List<Task>();
for (Opportunity o : Trigger.new) {
  if (o.Amount > 100000) {
    toInsert.add(new Task(WhatId = o.Id,
      Subject = 'Review large deal'));
  }
}
if (!toInsert.isEmpty()) insert toInsert;

3 · Stream, don't load

// heap-safe: 200 at a time
for (List<Account> chunk :
     [SELECT Id, Name FROM Account]) {
  for (Account a : chunk) { /* ... */ }
  update chunk;
}

4 · Escalate to async

// >10k records? Batch Apex.
// Callout needed? Queueable.
// Nightly? Schedulable.
Database.executeBatch(new MyBatch(), 200);
🧮
A sizing rule of thumb Under ~1,000 records: synchronous is fine. 1,000–10,000: Queueable, or synchronous with careful bulkification. Over 10,000: Batch Apex. Over 1 M: Batch Apex with a tuned scope size and, if it must run regularly, off-peak scheduling.

Interview questions

1 Why do governor limits exist? (Don't say "to stop bad code".)Easy

Because the platform is multitenant. Your code runs on infrastructure shared with thousands of other companies, so a runaway loop in your org would degrade everyone else's. Limits are enforced fair resource sharing, not a code-quality tool. Every limit traces back to that single architectural fact — which is exactly the connection interviewers are listening for.

2 List the limits you'd expect a developer to know from memory.Easy

100 SOQL queries (200 async) · 50,000 query rows · 150 DML statements · 10,000 DML rows · 6 MB heap (12 MB async) · 10 s CPU (60 s async) · 100 callouts with a 120 s cumulative timeout · 200 records per trigger invocation · 50 M records in Batch Apex · 20 SOSL searches · 50 future calls.

3 Your trigger is perfectly bulkified but still throws "Too many SOQL queries: 101". Explain.Hard

Limits are per transaction, not per component. Everything in that save shares one budget: validation rules, your trigger, other triggers on the same object, record-triggered flows, managed package code, roll-up recalculations and any triggers those cascade into.

So a flow that queried 95 times leaves you 5. The real fix is governance: consolidate to one trigger per object and one flow per timing, remove duplicated logic, and move non-urgent work async. Diagnose with the CUMULATIVE_LIMIT_USAGE and LIMIT_USAGE_FOR_NS blocks in the debug log, which attribute usage per namespace.

4 Which limits improve in asynchronous context, and which don't?Medium

Improve: SOQL queries 100 → 200, heap 6 MB → 12 MB, CPU time 10 s → 60 s.

Unchanged: DML statements (150), DML rows (10,000), query rows (50,000), callouts (100).

The genuinely different one is Batch Apex, where each 200-record chunk is its own transaction with a completely fresh set of limits — which is why it scales to 50 million records rather than just doubling your budget.

5 How do you fix "Apex CPU time limit exceeded"? It's the hardest one.Hard

CPU time measures your own computation — it excludes database and callout waiting, so it's almost always your loops. Common causes and fixes:

  • Nested loops (O(n²)) → replace the inner loop with a Map lookup.
  • List.contains() in a loop → use a Set.
  • Schema.getGlobalDescribe() called repeatedly → cache it in a static.
  • Heavy string concatenation or JSON in loops → use String.join, build once.
  • Too much automation stacked on one object → consolidate, then move work async (60 s instead of 10 s).

Measure with Limits.getCpuTime() checkpoints rather than guessing.

6 When do you move from synchronous to Batch Apex?Medium

Rough sizing: under ~1,000 records synchronous is fine; 1,000–10,000 use Queueable or careful synchronous bulkification; over 10,000 use Batch Apex; over a million, tune the scope size and schedule it off-peak.

The other trigger for Batch regardless of count is heap — if each record carries large text or you must hold a big Map, the fresh limits per chunk matter more than the record count.

7 What causes UNABLE_TO_LOCK_ROW and how do you avoid it?Hard

Two transactions trying to update the same record — most often the same parent. Inserting child records locks the parent for master-detail roll-ups, so parallel Data Loader batches containing children of the same account collide.

Fixes: sort the input file by parent Id so each batch touches distinct parents; switch Bulk API to serial mode; reduce batch size; avoid updating a shared "counter" record; and in Apex use FOR UPDATE deliberately rather than accidentally holding locks across a long transaction.

8 How do you read limit usage from a debug log?Medium

At the bottom of every log the CUMULATIVE_LIMIT_USAGE block lists final consumption of every limit for the transaction, and LIMIT_USAGE_FOR_NS breaks it down per namespace — which is how you prove a managed package consumed your queries. The Developer Console's Execution Overview → Limits tab shows the same data graphically, and the Timeline tab shows where CPU went. Set the Apex log level to FINEST only for the class you're investigating, since logs cap at 20 MB and truncate.

Quick check

1. A well-bulkified trigger still fails with "Too many SOQL queries: 101". Most likely reason?
Limits are per transaction, shared by everything that runs in it. Consolidating automation on the object is usually the real fix.
2. Which limit is doubled in asynchronous context?
SOQL goes 100 → 200 and heap 6 MB → 12 MB (CPU goes 10 s → 60 s). DML statements and query rows stay the same.
3. You must process 2 million records. What's the design?
QueryLocator handles up to 50 M records and each chunk gets fresh limits. A SOQL for loop still caps at 50,000 rows per transaction.
