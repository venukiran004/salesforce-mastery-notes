Branching Strategy

How to map git branches onto Salesforce orgs without losing work: the models that actually survive contact with declarative admins, the metadata that will not merge, the gates that belong on each branch, and how hotfixes get back into main without silently reverting a release.

🔗
Where this sits Deployment & DevOps covers the tooling — CLI, packaging, change sets, pipelines. This page is only about branch topology: which branches exist, what each one means, which org it maps to, and how changes travel between them.

Why Salesforce branching is different

Every git branching model you have read about assumes three things that are not true on this platform. Understand the differences and the strange parts of Salesforce branching stop looking arbitrary.

Normal software assumesOn SalesforceConsequence
A branch can be built and tested in isolationCode only compiles and tests inside an orgEvery branch needs an org to validate against. Branches are cheap; orgs are not
All changes arrive through gitAdmins make changes in a UI, in an orgBranches drift from reality. Retrieval and back-propagation are part of the strategy, not an afterthought
Source files merge cleanlySome metadata is a single large XML file that many people touchProfiles, layouts, flows and translations conflict constantly — see the merge problem
Production is a deployment targetProduction is also a source of truth people edit directlyYou need a defensible answer to "who changed this, and is it in git?"
Rollback means redeploy the old buildThere is no transactional rollback of a deploymentForward-fix is the norm; your branch model must make hotfixes fast
🧭
The one principle that decides everything else A branch should mean exactly one thing. Either a branch represents an org's current state (org-based) or it represents a unit of work (feature-based). Teams get into trouble when a branch means both — "develop is the dev org, but also where features queue up, but also what we release from". Pick one meaning per branch and write it down.

Mapping branches to orgs

The spine of any Salesforce strategy is the branch ⇄ org mapping. Everything else is detail.

The standard four-tier mapping
Long-lived branches map to persistent orgs. Short-lived branches map to disposable orgs.
1️⃣
main always equals production If someone has to ask "is main what's live?", your strategy has already failed. main is deployed to production and nothing else; every production release is a tagged commit on it. That single invariant is what makes hotfixes, audits and rollbacks tractable.

The four models

1 · Org branching (branch per environment)

A long-lived branch for each org: dev → int → uat → main. Changes are promoted by merging one environment branch into the next.

Works when

  • The team is mostly admins and declarative work
  • Releases are scheduled and move as one block
  • You need the simplest possible mental model

Breaks when

  • You need to ship part of what's in UAT — cherry-picking becomes the normal case, which it should never be
  • Branches drift: merges become enormous and conflict-ridden
  • Nobody can answer "what's actually in this release?"

2 · GitFlow (feature → develop → release → main)

Feature branches merge into develop; a release/* branch is cut and stabilised; it merges to main and back into develop. hotfix/* branches come off main.

Works when

  • You release on a cadence — fortnightly or monthly
  • UAT needs a frozen scope while development continues
  • Multiple teams contribute to one release
  • You need an auditable "what shipped when"

Costs

  • The most moving parts of any model
  • Forward-merging hotfixes is a discipline people forget
  • Long-lived release branches re-introduce drift

This is the default for most Salesforce programmes, because the frozen-UAT-scope requirement is close to universal and the platform gives you no feature-flag mechanism for free.

3 · Trunk-based with short-lived branches

One long-lived branch (main). Feature branches live hours or days, merge behind a flag, and deploy continuously.

Works when

  • A mature, mostly-developer team with real test coverage
  • Package-based development with versioned artefacts
  • You can hide incomplete work behind feature flags
  • You genuinely want to deploy several times a week

Breaks when

  • Admins click-build in a shared sandbox with no flag discipline
  • Business stakeholders need a fixed UAT scope to sign off
  • Test coverage is thin, so merging is scary and branches quietly get long

4 · Package-based (branch per package)

The repo holds several unlocked packages; each has its own directory, its own version history, and often its own release train. Branches target a package rather than an environment.

📦
The endgame, not the starting point Package-based development is where the platform is heading and it genuinely solves drift and dependency problems. It also demands clean modular boundaries, dependency discipline and strong test coverage. Most orgs should get org-based GitFlow working reliably first, then decompose into packages — doing both migrations at once is how programmes stall for a year.

Always carry the ticket id in the branch name. It is how a deployment gets traced back to a requirement eighteen months later during an audit, and it lets delta tooling and release notes be generated automatically.

✂️
The real cause of merge pain is branch lifetime Almost every horrible Salesforce merge traces back to a branch that lived for six weeks. Metadata conflicts grow superlinearly with branch age because so much of it lives in shared files. One story per branch, merged within days, prevents more pain than any tooling you can buy.

The metadata that will not merge

Some metadata is fundamentally hostile to parallel work. Knowing which, and what to do about it, is the difference between a strategy that works and one everybody bypasses.

MetadataWhy it conflictsMitigation
ProfilesOne giant XML listing every object, field and tab permission. Two people touching unrelated features both rewrite itStop versioning profiles. Use permission sets and permission set groups; keep profiles minimal and manage them manually in each org. Add them to .forceignore if you can
Page layoutsField order is positional; two additions collide on the same linesPrefer Dynamic Forms; assign layout ownership per team; expect manual conflict resolution
FlowsA flow is one XML blob with generated element positions. A text merge produces a corrupt flowTreat flows as binary: never merge, take one side wholesale. One owner per flow per release; split big flows into subflows so two people aren't in the same file
Custom labels & translationsAll labels in one file; translations in one file per languageAppend-only conventions, alphabetical ordering, and resolve by taking both sides
Picklist value setsShared global value sets rewritten by anyone adding a valueAppend-only; never reorder; review carefully
package.xmlEveryone edits the same manifestGenerate it from the diff instead of hand-maintaining it — see delta deployments
Record types & picklist assignmentsBuried inside object XML and profile XML simultaneouslySource-format decomposition helps; permission sets help more
CPQ / Field Service configIt is data, not metadata — git does not see it at allA scripted, version-controlled data migration. See Field Service deployment
 
# Treat flows and other generated XML as unmergeable: take one side, never blend
# .gitattributes
*.flow-meta.xml      merge=ours -diff
*.labels-meta.xml    merge=union        # append-only files can safely take both sides
*.translation-meta.xml merge=union

# .forceignore — keep hostile metadata out of version control entirely
# (make sure every org's profiles are then managed deliberately, not forgotten)
**/profiles/**
**/*.profile-meta.xml
**/settings/**
**/reports/unfiled$public/**
🌊
A text-merged flow is a corrupt flow Git will happily merge two flow XML files line by line and produce something that deploys, loads in the builder, and behaves wrongly — missing connectors, duplicated elements, orphaned decisions. Configure the merge driver above, agree one owner per flow per release, and if two people must change the same flow, they do it sequentially rather than in parallel.

Config drift and back-propagation

The hardest problem in Salesforce branching is not merging — it is that your orgs change without git. An admin fixes a validation rule in production on Friday. Your main branch no longer matches production, and the next deployment silently reverts their fix.

Drift, and the loop that closes it
ControlWhat it does
Scheduled drift detectionA nightly job retrieves key metadata from production and diffs it against main, failing loudly if they differ. This is the single highest-value piece of automation in a Salesforce pipeline
Setup Audit Trail reviewWeekly: who changed what in production outside a release. Cheap, and it names the behaviour rather than the person
Locked-down productionRemove Modify All Data and metadata-edit permissions from humans; deployments happen as a service account. The honest version of "don't change prod"
A sanctioned fast pathAdmins will need to change things urgently. Give them a documented route — a hotfix branch and a 20-minute pipeline — or they will use production directly and you will never see it
Back-propagation disciplineAnything that lands in main out of band merges down into develop and every open release/* branch the same day

Hotfixes without losing the fix

A production defect cannot wait for the release train. The flow is fixed, and the last step is the one people skip.

  • Branch from main, never from develop — develop contains unreleased work that must not go live.
  • Fix it, with a test that fails without the fix. A hotfix with no test is how the same defect ships twice.
  • Validate against production (a check-only deployment with the relevant tests) so the real deployment is a quick deploy of an already-validated build.
  • Deploy to production and tag it — v2026.04.1. The tag is your rollback reference and your audit record.
  • Merge the hotfix branch back into main if you worked on a separate branch.
  • Forward-merge main into develop AND every open release/* branch. Miss this and the next release ships the old broken code over the top of your fix — the classic "we fixed that twice" incident.
# Hotfix, end to end
git switch main && git pull
git switch -c hotfix/ABC-789-quote-total-rounding

# ... fix + test ...
git commit -am "Fix rounding on quote grand total (ABC-789)"

# Validate against production before you deploy anything
sf project deploy start --dry-run --target-org prod \
  --test-level RunSpecifiedTests --tests QuoteTotalsTest

# Real deploy, then tag what went live
sf project deploy start --target-org prod \
  --test-level RunSpecifiedTests --tests QuoteTotalsTest
git switch main && git merge --no-ff hotfix/ABC-789-quote-total-rounding
git tag -a v2026.04.1 -m "Hotfix: quote total rounding"
git push origin main --tags

# THE STEP EVERYONE FORGETS — get the fix into unreleased lines
git switch develop && git merge --no-ff main && git push
git switch release/2026.05 && git merge --no-ff main && git push
🔁
Make the forward-merge mechanical Do not rely on memory. Add a CI job that fails whenever main contains commits absent from develop or from any open release/* branch. It turns a discipline problem into a red build, which is the only kind of reminder that works.

Release branches, freezes and tags

StepWhat happens
Cutrelease/2026.04 is created from develop. From this moment its scope is frozen; develop reopens for the next cycle immediately
StabiliseOnly bug fixes for in-scope items land on the release branch. Each fix also merges back to develop

🏷️
Tags are your only real rollback story There is no transactional rollback on the platform, so "roll back" means "deploy the previous known-good state and manually undo what cannot be redeployed" — destructive changes, data, picklist values. A tag per release makes the first half trivial. Write down, per release, which changes are not reversible; that list is what turns a rollback decision from a guess into a judgement.

Pull requests and the gates on each branch

Branch protection is where a strategy stops being a diagram and starts being enforced.

Target branchRequired checksReview
feature/*Lint, Jest for LWC, Apex static analysis (scanner/PMD), fast unit tests in a scratch orgNone — it's yours
developDelta validation deploy to the integration org, full local test run, scanner clean at your agreed severity1 reviewer
release/*Validation deploy against production, specified-tests run, migration dry run1 reviewer + release manager
mainEverything above, plus drift check against production and an up-to-date-with-main requirement2 reviewers, linear history, no direct pushes — ever

What to actually review in a Salesforce PR

Code

  • Bulkification: no SOQL or DML in loops
  • Sharing keywords (with sharing / without sharing) deliberate, not accidental
  • FLS and CRUD enforcement where required
  • Tests that assert behaviour, not just run it, and don't use SeeAllData
  • No hard-coded Ids — see why

Metadata

  • Did a profile sneak into the diff?
  • Flow changes: one owner, deliberate version, not text-merged
  • Field-level security changes reviewed as a security change
  • Destructive changes listed explicitly — nothing gets deleted by surprise
  • Anything that is data rather than metadata, and how it will be migrated

Delta deployments

Deploying the whole repo to production is slow, risks reverting drift, and makes every deployment a full-org risk. Deploying only what changed between two commits is the norm for mature pipelines.

# What changed between the last release tag and HEAD?
git diff --name-only v2026.03.0..HEAD -- force-app/

# Generate a manifest and a destructive manifest from the diff
# (sfdx-git-delta is the common community plugin for this)
sf sgd source delta --to HEAD --from v2026.03.0 --output-dir delta --generate-delta

# Validate just the delta against production, then quick-deploy the validated build
sf project deploy start --dry-run --manifest delta/package/package.xml \
  --post-destructive-changes delta/destructiveChanges/destructiveChanges.xml \
  --target-org prod --test-level RunLocalTests

sf project deploy quick --use-most-recent --target-org prod
Full deploymentDelta deployment
SpeedSlow — grows with the orgProportional to the change
Drift behaviourOverwrites undocumented production changesLeaves untouched metadata alone — kinder, but hides drift
Risk profileWhole-org blast radius every timeScoped to the change
Confidence that git = orgHigh (it enforces it)Lower — you need separate drift detection

The mature answer is delta deployments plus scheduled drift detection: fast releases, with a separate mechanism that tells you when the org and git have diverged, instead of papering over it on every deploy.

Feature flags on Salesforce

Flags are what make short-lived branches and trunk-based development possible: merge incomplete work safely because it is switched off. The platform gives you three good mechanisms.

MechanismBest forNotes
Custom PermissionPer-user and per-profile rolloutCheckable in Apex, flows, formulas and component visibility. The cleanest option for a progressive rollout
Custom Metadata TypeEnvironment-level on/off, deployableQueryable without a SOQL limit cost; the setting travels with your release
Hierarchy Custom SettingOrg / profile / user overrides at runtimeEditable in production without a deployment — which is both the feature and the risk
 
// A flag check that works in Apex, and the same flag drives
// component visibility and flow entry conditions
public with sharing class FeatureGate {

    // Custom Metadata: environment-level, ships with the release
    private static Map<String, Boolean> cache = new Map<String, Boolean>();

    public static Boolean isOn(String featureName) {
        if (!cache.containsKey(featureName)) {
            Feature_Flag__mdt flag = Feature_Flag__mdt.getInstance(featureName);
            cache.put(featureName, flag != null && flag.Is_Enabled__c);
        }
        return cache.get(featureName);
    }

    // Custom Permission: per-user rollout, no deployment needed to widen it
    public static Boolean isOnForMe(String customPermissionName) {
        return FeatureManagement.checkPermission(customPermissionName);
    }
}
🧹
Flags are debt with an expiry date Every flag is a branch in your code that must be tested in both states. Put a removal ticket in the same sprint you add the flag, and review live flags every release. An org with forty stale flags is harder to reason about than the long-lived branches you were avoiding.

A working pipeline, by branch

# .github/workflows/ci.yml — the shape of it
name: CI

on:
  pull_request:
    branches: [develop, "release/**", main]

  static-analysis:
    # Fast, no org needed — run on every PR
    # sf scanner run --target force-app --severity-threshold 3
    # npm run lint && npm run test:unit  (LWC Jest)

    # Delta validation against the right org for the target branch
    # develop     -> integration sandbox, RunLocalTests
    # release/**  -> PRODUCTION, dry-run, RunLocalTests
    # main        -> PRODUCTION, dry-run + drift check

  drift-check:
    # Nightly on main: retrieve from prod, diff against the branch,
    # fail loudly if the org and git have diverged

The principle: the gate matches the blast radius of the target branch. A feature PR should get an answer in two minutes. A PR into main should be slow, thorough and boring.

Advanced

Choosing a strategy: the five questions

Do not start from a diagram. Answer these, and the model is usually determined:

  • Does the business need to sign off a frozen scope? Yes → you need release branches. This single answer rules out trunk-based for most enterprises.
  • Who makes changes — admins in a UI, or developers in an IDE? Mostly admins → optimise for retrieval and drift detection, not for merge elegance.
  • How often must you ship? Monthly → GitFlow. Weekly or faster → short-lived branches plus flags, or you'll spend your life merging.
  • How good is your test coverage, honestly? Thin coverage makes merging frightening, which makes branches long, which makes merging worse. Fix coverage before adopting a model that depends on confidence.
  • How many sandboxes do you actually have, and of what type? Your branch topology cannot exceed your org topology. One full sandbox refreshed every 29 days constrains everything downstream.

Migrating an existing org onto a branch model

The common real task: a five-year-old org with no version control. Sequence that works:

2 · Convert & ignoreConvert to source format; .forceignore the hostile metadata (profiles, settings, unfiled reports)Decomposed source is what makes diffs and merges legible
3 · Read-only pipelineCI that validates PRs but deploys nothing; nightly drift detection onBuilds trust and surfaces the real change volume before you block anyone
4 · One tier at a timeAutomate deployment into integration, then UAT, then production lastProduction automation last, when the pipeline has earned it

6 · DecomposeCarve out unlocked packages where boundaries are cleanThe payoff phase — and only safe once everything above is boring

Branching for declarative-only teams

A team of admins with no developers still needs a strategy, but a different one. The branch is a record of what was changed, not a development workspace:

  • Changes are made in a dev or config sandbox, then retrieved into a branch by the pipeline, not hand-written.
  • The PR exists for the review conversation and the audit trail — the diff is evidence, not craft.
  • Scope discipline matters even more: one admin per conflict-prone component per release.
  • Change sets may still be the deployment mechanism while git provides history and review. That's a legitimate intermediate state, not a failure.

What a strategy cannot fix

Structural problems

  • Not enough sandboxes, or the wrong types
  • No test coverage, so nothing can be validated cheaply
  • One monolithic org serving five unrelated business units
  • Config living as data (CPQ, Field Service) with no migration tooling

Behavioural problems

  • Production edits treated as normal because the sanctioned path is slow
  • "Urgent" used to bypass review weekly
  • Nobody owning the release, so forward-merges never happen
  • Branches kept open for months because stories are too big

If you recognise more than two of these, the branching model is not your bottleneck. Fix the bottleneck, then adopt the model — in that order, or the model gets blamed and abandoned.

Worked example: a fortnightly train

  • Monday, week 1 — release/2026.04 cut from develop, deployed to UAT. develop reopens immediately for the next cycle.
  • Week 1 — devs work on feature/* branches off develop, each with a scratch org. PRs into develop need static analysis, a delta validation against integration, and one review.
  • Week 1, Thursday — a UAT defect on in-scope work. bugfix/* off release/2026.04, merged to the release branch and immediately merged back into develop.
  • Week 2, Tuesday — production defect, unrelated. hotfix/* off main, validated against production, deployed, tagged v2026.03.1. main forward-merged into develop and release/2026.04 the same day.
  • Week 2, Wednesday — release dry run: validation-only deploy of the delta against production, plus a rehearsal of the config-data migration.
  • Week 2, Thursday evening — merge release/2026.04 → main, quick-deploy the validated build, tag v2026.04.0, merge main → develop, delete the release branch.
  • Friday — drift check green, release notes generated from the ticket ids in the merge commits, retro on anything that needed a manual step.

Interview questions

1 Why can't you just use GitFlow as written on Salesforce?Medium

You can use the topology, but three platform realities change the practice. Branches can't be built in isolation — code only compiles and tests inside an org, so every meaningful gate needs an org to validate against. Changes arrive outside git, because admins click-build directly in orgs, so retrieval and drift detection are first-class parts of the model rather than edge cases. And some metadata won't merge — profiles, layouts and flows are large shared XML files, so you need ignore rules, merge drivers and ownership conventions that a normal codebase never needs.

2 What's the single most important invariant in your branch model?Easy

main equals production. Nothing else is deployed there, every release is a tagged commit on it, and nobody pushes to it directly.

That one rule is what makes hotfixes safe (branch from main and you can't accidentally ship unreleased work), makes rollback meaningful (deploy the previous tag), and makes audit questions answerable. Once main and production diverge, every other guarantee in the pipeline becomes a guess.

3 Walk me through a production hotfix.Medium

Branch from main — never develop, which holds unreleased work. Fix it with a test that fails without the fix. Validate against production with a check-only deployment and specified tests, then deploy (ideally a quick deploy of that validated build) and tag it.

Then the step people skip: forward-merge main into develop and into every open release/* branch, same day. Miss it and the next release deploys the old broken code over your fix. I'd automate a CI check that fails when main contains commits missing from those branches, because discipline alone doesn't survive a busy month.

4 Two developers changed the same flow on different branches. What happens?Hard

Git will merge the XML line by line and produce a flow that deploys but is subtly broken — missing connectors, duplicated elements, generated coordinates interleaved. It will pass a deployment and fail in behaviour, which is the worst possible outcome.

Prevention: mark flow files unmergeable in .gitattributes so a conflict is forced rather than auto-merged; assign one owner per flow per release; and split large flows into subflows so two streams of work aren't in the same file. If two people genuinely must change one flow, they do it sequentially — second person rebases and reapplies in the builder.

5 Should profiles be in version control?Medium

Generally no. A profile is one enormous XML file describing permissions across every object, field and tab, so two unrelated features both rewrite it and you get constant meaningless conflicts. Worse, people learn to resolve those diffs carelessly — and then do the same on a conflict that mattered.

The pattern: keep profiles minimal (login hours, defaults), move everything else to permission sets and permission set groups, which are small, purposeful and mergeable, and .forceignore the profiles. The tradeoff is that profile changes are then managed deliberately per org, so that has to be documented rather than forgotten.

6 How do you handle an admin who changed production directly?Hard

Detect, capture, then remove the incentive. Detect with a nightly job that retrieves production metadata and diffs it against main, failing loudly — plus a weekly Setup Audit Trail review. Capture by retrieving the change into a config/* branch and PR-ing it into main like any other change, then merging down to develop and open release branches so the next deployment doesn't revert it.

Then the actual fix: people bypass the process when the process is slow. Give admins a sanctioned fast path — a hotfix branch with a twenty-minute pipeline — and lock down metadata-edit permissions in production only once that path genuinely works. Locking the door before building the corridor just moves the problem somewhere you can't see it.

7 Delta or full deployments?Medium

Delta for speed and a scoped blast radius: generate the manifest from the diff between the last release tag and HEAD, validate it, then quick-deploy. Full deployments get slower as the org grows and overwrite undocumented production changes — occasionally useful, rarely what you want every release.

The catch is that delta deployments hide drift rather than steamrolling it, so the mature setup is delta deployments plus scheduled drift detection. You get fast releases and a separate honest signal about whether git still describes the org.

8 When would you choose trunk-based development?Hard

When three things are true: the team is mostly developers with real test coverage, you have working feature flags so incomplete work can merge switched off, and the business does not require a frozen scope signed off in UAT. Package-based development makes it considerably more practical, since each package is a versioned artefact you can choose not to promote.

In most enterprise Salesforce programmes at least one of those fails — usually the UAT sign-off requirement — so GitFlow with release branches is the honest answer. Adopting trunk-based without flags just produces long-lived branches with a trunk-based label on them.

9 How do you branch for a six-month programme running alongside BAU?Hard

A long-lived project/* branch with its own org, and a mandatory scheduled merge from develop — weekly at minimum, in the sprint plan, with someone's name on it. The failure mode is always the same: the merge is deferred because it's painful, which makes it more painful, until re-integration becomes its own project with its own budget.

Better, where the domain allows: decompose the programme's work into unlocked packages so it ships incrementally behind flags instead of accumulating on a branch. If that's not possible, at least keep the programme's changes narrow and own the conflict-prone components explicitly, because profiles, layouts and flows are where a six-month branch actually dies.

10 Your repo has no version control today. What's your first week?Hard

Baseline first: retrieve production into main, accept that it's ugly, tag it, and convert to source format with the hostile metadata in .forceignore. Trying to make the baseline beautiful is how this exercise burns three months.

Then a read-only pipeline — PR validation that deploys nothing, plus nightly drift detection. That builds trust and shows you the real volume and shape of change before you block anybody's work. Automating deployment comes tier by tier afterwards, production last, and locking down production edit rights comes last of all, once the sanctioned fast path is genuinely fast.

Quick check

1. You branch a hotfix from develop instead of main. What's the risk?
develop contains everything merged for future releases. Hotfixes always branch from main, which equals production.
2. Why are flow files treated as unmergeable?
Git will cheerfully interleave two flow definitions. The result passes deployment and fails in behaviour — the worst kind of bug. Force a conflict and take one side.
3. After deploying a hotfix to production, what must happen the same day?
Otherwise the next release deploys the old code over your fix. Automate a check that fails when main has commits missing downstream.
4. Cherry-picking is your normal way to assemble a release. What does that tell you?
Routine cherry-picking means scope isn't controlled at the branch level. Use release branches (choose what merges) or feature flags (ship it off) instead.
5. Delta deployments are fast and low-risk. What do they fail to give you?
Full deployments enforce git-as-truth by overwriting. Delta deployments don't, so pair them with scheduled drift detection.
