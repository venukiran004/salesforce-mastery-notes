Integration Patterns & Approach

The six canonical patterns, the technology that implements each one, and a repeatable method for designing any integration from a blank page.

The six patterns

Almost every Salesforce integration is one of six shapes. Naming the pattern first — before choosing a technology — is what separates a design from a guess.

Pattern map: direction × timing

1 · Remote Process Invocation — Request and Reply

Shape

Salesforce calls a remote system, waits for the response, and uses the result immediately — often storing it or blocking the user's action based on it.

Implement with: Apex HTTP callout (REST), WSDL2Apex (SOAP), External Services, or a Flow HTTP callout action.

Design considerations

  • The user is waiting — set an aggressive timeout (5–15 s)
  • Counts against 100 callouts / 120 s per transaction
  • Cannot follow DML in the same transaction
  • What happens if the remote system is down? Define the fallback before you build
  • Consider caching the response in Platform Cache
🎯
Use case A rep clicks "Validate Address". Salesforce calls a postal API and populates the standardised address before the record saves. The rep must see the result now, so it has to be synchronous.

2 · Remote Process Invocation — Fire and Forget

Shape

Salesforce notifies a remote system and continues without waiting. The remote system may act later; Salesforce doesn't need the answer to complete its work.

Implement with: Platform Events (best), Outbound Messages (no-code + retry), Queueable/@future callouts, or a record-triggered Flow on an asynchronous path.

Why it's usually the right default

  • The user isn't blocked by a slow third party
  • Failures don't roll back the Salesforce transaction
  • You can retry independently
  • Multiple consumers can subscribe with no extra work
🎯
Use case On Closed Won, publish Order_Placed__e. The ERP, the billing platform and the analytics pipeline each subscribe. Adding a fourth consumer next year needs zero changes in Salesforce.

3 · Remote Call-In

Shape

The external system initiates: it creates, reads, updates or deletes Salesforce data.

Implement with: standard REST/SOAP API, Apex REST for custom logic, Composite API to bundle operations, Bulk API for volume, or publishing a Platform Event into Salesforce.

Design considerations

  • Use a dedicated integration user with a least-privilege permission set — never an admin
  • Prefer upsert by External Id so calls are idempotent and replay-safe
  • Watch the daily API request allocation
  • Version your Apex REST endpoints (/v1/orders) so you can evolve them
  • Return meaningful HTTP status codes and error bodies

4 · Batch Data Synchronisation

Shape

Large volumes moved on a schedule, in either direction. Latency of minutes or hours is acceptable.

Implement with: Bulk API 2.0 (in/out), Batch Apex + callouts (out), an ETL/iPaaS tool (Informatica, MuleSoft, Talend, Jitterbit), or CDC for a delta-based feed.

Design considerations

  • Delta not full load — filter on SystemModstamp > lastRunTime
  • Use External Ids for matching, never Name
  • Run off-peak; consider deferring sharing recalculation
  • Disable/bypass triggers for the migration user if the logic isn't needed
  • Plan for partial failure: capture failed rows and reprocess
  • Sort by parent Id to avoid UNABLE_TO_LOCK_ROW

5 · UI Update Based on Data Changes

Shape

The browser updates in real time when data changes elsewhere — without the user refreshing.

Implement with: Platform Events or CDC subscribed via lightning/empApi in an LWC; LMS for same-page component sync.

Design considerations

  • Never poll on a timer — it burns API calls and scales badly
  • Filter events client-side to what this user cares about
  • Unsubscribe in disconnectedCallback
  • Handle reconnection and replay after a dropped connection

6 · Data Virtualisation

Shape

Salesforce displays external data live, on demand, without ever storing it.

Implement with: Salesforce Connect (OData, Cross-Org, custom Apex adapter), or an LWC that calls out and renders the result.

Design considerations

  • Every page view hits the external system — how fast and how reliable is it?
  • No triggers, flows or full reporting on external objects
  • Callout allocations apply per hour
  • If the source is down, the page shows an error

A repeatable integration approach

Work through these eight steps in order. Most failed integrations skipped steps 1–3 and jumped straight to code.

The eight-step method
  • Define the business outcome — not "integrate with SAP" but "a rep must see live credit limits so they stop quoting customers who are on hold". Write the acceptance criteria first.
  • Identify the systems, direction and system of record — which system owns each field? Two-way sync without a clear owner is how you get infinite update loops and data corruption.
  • Quantify volume, frequency and latency — 50 records a day or 5 million a night? Must it be under a second, or is an hour fine? These numbers eliminate most options immediately.
  • Choose the pattern from the six above. Say it out loud: "this is fire-and-forget, outbound."
  • Choose the technology that implements that pattern, and check it against your limits.
  • Design the security — Named Credential, OAuth flow (JWT for server-to-server), a dedicated integration user with a least-privilege permission set, and no secrets in code.
  • Design failure handling — retry with backoff, idempotency via External Id or event UUID, an error log object, and a dead-letter path for what can never succeed.
  • Design monitoring — how will you know at 3am that it broke? Error log reports, email alerts, an integration health dashboard, and correlation ids in every payload.

The design checklist

Data

  • Field-level mapping document (both directions)
  • External Id on every synced object
  • Data type and picklist value alignment
  • Timezone and date format handling
  • What happens on delete? Soft delete or ignore?
  • Initial data load plan, separate from the ongoing sync

Resilience

  • Idempotency — is replaying a message safe?
  • Retry policy and maximum attempts
  • Circuit breaker if the remote system is down
  • Error log object + alerting
  • Loop prevention on bidirectional syncs (flag field or commit-user check)
  • Reconciliation report to catch silent drift

Security

  • Named Credentials, never hard-coded secrets
  • JWT or Client Credentials for server-to-server
  • Dedicated integration user, least privilege
  • Encrypt sensitive fields at rest if required
  • Log who called what, and when
  • IP restrictions where practical

Operations

  • Runbook: how to replay a failed batch
  • Sandbox endpoints separate from production (Custom Metadata)
  • Load test at realistic volumes
  • Version your endpoints
  • Document the contract and share it with the other team
  • Track API allocation consumption over time

Anti-patterns to avoid

❌ Common mistakes

  • Synchronous callouts in triggers — couples the user's save to a third party's uptime
  • Polling on a timer instead of subscribing to events
  • Two-way sync with no system of record — guaranteed conflicts and loops
  • Matching on Name instead of an External Id
  • Full data loads every night when a delta would do
  • Hard-coded endpoints and secrets instead of Named Credentials + Custom Metadata
  • Using an admin account as the integration user
  • Swallowing errors — silent failure is worse than a loud one
  • No idempotency — a retry creates a duplicate order
  • Building it all in Apex when a Named Credential + External Service would do

✅ Signs of a good design

  • You can name the pattern in one sentence
  • Replaying any message is harmless
  • The remote system going down degrades gracefully
  • Failures land in a log with enough context to reprocess
  • Adding a new consumer needs no change to the publisher
  • Secrets live in Named Credentials only
  • Sandbox and production differ only by configuration
  • There's a dashboard someone actually looks at
  • The contract is documented and versioned

Worked example: end-to-end design

📋
The requirement "When a Salesforce Opportunity is Closed Won, create the sales order in SAP, store the SAP order number back on the Opportunity, and let service agents see live order status on the Account. About 400 orders a day; SAP occasionally goes down for maintenance."
  • Outcome — no manual re-keying of orders; agents answer "where is my order?" without leaving Salesforce.
  • Systems & direction — Salesforce → SAP (create order, outbound) and SAP → Salesforce (status, read). SAP is the system of record for orders; Salesforce owns the opportunity.
  • Volume & latency — 400/day outbound (tiny); order status read on demand; SAP has planned downtime, so the outbound path must tolerate failure.
  • Patterns — outbound order creation is Fire and Forget (with a callback for the order number). Live status display is Data Virtualisation.
  • Technology — a record-triggered Flow publishes Order_Ready__e; an Apex trigger on that event enqueues a Queueable that POSTs to SAP via a Named Credential and writes back the SAP number. For status, a Salesforce Connect OData external object SAP_Order__x with an Indirect Lookup to Account.
  • Security — JWT Bearer flow into SAP via an External Credential; a dedicated SAP Integration user in Salesforce with a least-privilege permission set.
  • Resilience — the Queueable retries 3 times with growing delay on 5xx; the SAP call carries the Opportunity Id as an idempotency key so a retry never double-creates; permanent failures write an Integration_Error__c record.
  • Monitoring — a report on Integration_Error__c created today, an email alert to the integration team, and a dashboard component showing failure count by day.
Closed Won→ Flow publishes event→ Event trigger → Queueable→ POST to SAP (Named Cred)→ Write back SAP order #→ Errors → log + alert

Interview questions

1 Name the six integration patterns and one example of each.Medium
  1. Request & Reply — live credit check before the Opportunity saves.
  2. Fire & Forget — publish an event when an order ships.
  3. Remote Call-In — the web store creates a Lead through the REST API.
  4. Batch Data Synchronisation — nightly 2 M product load via Bulk API.
  5. UI Update on Data Change — console refreshes via empApi + Platform Event.
  6. Data Virtualisation — SAP invoices shown live through Salesforce Connect.
2 What three questions decide the pattern?Easy

Who initiates? (inbound or outbound) · Does the caller need the answer now? (synchronous or asynchronous) · How many records, how often? (real-time or batch).

Answer those three and the pattern — and usually the technology — falls out. Everything else is detail. The mistake juniors make is starting from the technology ("we'll use Apex callouts") before answering these.

3 Why is Fire & Forget usually the better default over Request & Reply?Medium

Because it decouples you from someone else's uptime and latency. The user isn't blocked by a slow third party; a remote failure doesn't roll back the Salesforce transaction; you can retry independently; and additional consumers can subscribe later with no change to the publisher.

Only use Request & Reply when the answer genuinely changes what happens next in the current transaction — a credit check that blocks the save, an address validation the user must see.

4 Design a two-way sync between Salesforce and an ERP. What worries you most?Hard

The first question is which system is the system of record for each field. Without that agreed field-by-field, you get update loops and silent data corruption — this is the answer interviewers want.

Then: loop prevention (filter on commitUser in CDC, or a flag field); conflict resolution (last-write-wins, or source-of-truth per field); idempotency via External Ids; a reconciliation job to catch drift; and a correlation id in every payload so you can trace one record's journey across both systems.

5 When do you introduce middleware instead of point-to-point?Medium

Point-to-point is fine for 1–3 stable integrations owned by one team. Introduce middleware (MuleSoft, an iPaaS, an ESB) when: the number of connections is growing — n systems point-to-point needs n(n−1)/2 links; you need complex transformation or orchestration; different teams release on different cadences; you need central monitoring, throttling and retry; or you must mediate protocols (SOAP ⇄ REST ⇄ files). The cost is an extra hop of latency and a platform to run.

6 What does "idempotent" mean here, and how do you achieve it?Medium

Processing the same message twice produces the same result as processing it once — essential because networks time out and event delivery is at-least-once.

Inbound: upsert on an External Id rather than insert. Outbound: send an idempotency key (the record Id or a UUID) the receiver checks. Event subscribers: de-duplicate on EventUuid, or make the action naturally repeatable — set a status rather than increment a counter.

7 Name five integration anti-patterns you'd flag in a design review.Hard
  1. Synchronous callouts in triggers — couples the user's save to a third party.
  2. Polling on a timer instead of subscribing to events.
  3. Two-way sync with no system of record — guaranteed loops and conflicts.
  4. Matching on Name instead of an External Id.
  5. Hard-coded endpoints and secrets rather than Named Credentials plus Custom Metadata.
  6. An admin account as the integration user, and swallowed errors with no log or alert.
8 How would you monitor an integration in production?Medium

Log every permanent failure to an Integration_Error__c object with the payload, status code, correlation id and timestamp. Build a report and dashboard on today's errors, and an email alert or Slack notification when the count crosses a threshold.

Add: AsyncApexJob monitoring for failed Queueable/Batch jobs, the Outbound Message delivery queue if used, API usage tracking against the daily allocation (GET /limits), and a scheduled reconciliation job comparing record counts between systems — because the failure mode nobody catches is the one that fails silently.

Quick check

1. A rep must see a live credit score before the Opportunity can be saved. Which pattern?
The answer is needed to complete the current action, so the call must be synchronous.
2. Four different systems all need to know when an order ships. Best design?
Pub/sub decouples the publisher from consumers — adding a fifth system later requires no Salesforce change.
3. 12 million historical invoices, viewed rarely, owned by SAP. What do you do?
Rarely-read, high-volume, externally-owned data is the textbook case for virtualisation: no storage cost and never stale.
