Debugging & Troubleshooting — 100 Scenarios

Reading logs properly, the tools beyond them, debugging production without logs, async and events, and the "works in sandbox" problems that are really data, permissions or drift.

📚
How to use this Answer out loud in ninety seconds, then open the answer. Concepts on Debugging & Troubleshooting and its Advanced section.

Reading logs (1–20)

1 Which part of a debug log do you read first?Easy

CUMULATIVE_LIMIT_USAGE — the actual SOQL, DML, CPU and heap consumed, broken down per namespace.

It tells you which limit you are near and whether the consumption is yours or a managed package's. Everything else is detail by comparison.

2 You need to know which automation ran on a save.Easy

CODE_UNIT_STARTED/FINISHED gives you the execution tree: every trigger, flow, validation rule and package unit, in order, with timings.

It routinely reveals automation nobody documented — which is why reading the log beats reasoning from configuration.

3 The log is truncated before the interesting part.Medium

Logs are capped and the UI truncates sooner. Lower the levels: set everything to NONE except the one category you need.

Everything at FINEST produces a half-log that answers nothing — and slows the transaction enough to change the behaviour you are investigating.

4 What log levels for a limits problem?Medium

APEX_PROFILING=FINEST, everything else NONE. That gives you the cumulative limits without the noise.

For "which automation ran": WORKFLOW=FINER plus APEX_CODE=FINE. For query plans: DATABASE=FINEST.

5 A query returns 3 rows and takes 4 seconds.Medium

SOQL_EXECUTE_BEGIN/END gives you rows and elapsed time — so this is a selectivity problem, not a volume one. The optimiser scanned to find those three rows.

Run the Query Plan tool: cost above roughly 1 means a table scan.

6 You cannot see your own log.Easy

No trace flag for that user, it expired, or the log storage filled and older logs were purged.

Also check whether the code actually ran as you — async and event-driven work often runs as a different user.

7 A platform event subscriber produces no log.Medium

It runs as the Automated Process user, so your trace flag catches nothing.

Set the trace flag on that user. This is one of the most common wasted hours in Salesforce debugging.

8 How do you prove a managed package is the problem?Medium

LIMIT_USAGE_FOR_NS and the cumulative section break consumption down by namespace.

Isolate further by disabling your own logic and re-measuring, so the evidence is clean. A log naming their namespace is what gets a support case taken seriously.

9 A flow's behaviour is unclear from the log.Medium

WORKFLOW=FINER gives element-by-element execution, showing which decision branch was taken.

Verbose, but it is the only way to see inside a flow's logic without adding temporary log records.

10 Your System.debug output is missing.Easy

APEX_CODE is below DEBUG level, or the statement is in a branch that did not execute.

Also note System.debug itself costs CPU and heap — leaving verbose debugging in production code is a real cost.

11 How do you find a specific transaction's log?Medium

By user and timestamp — and if you logged Request.getCurrent().getRequestId() in your own error record, by matching that correlation id.

That correlation id is why instrumentation beats log-hunting.

12 The log shows a trigger running twice.Medium

Usually a workflow field update re-firing the save path, a roll-up recalculation saving the parent, or an after-save flow updating its own record.

The execution tree shows which. Then guard by record Id rather than with a blunt static boolean.

13 Log storage keeps filling up.Easy

Trace flags left on, at high levels, for many users. Logs are capped org-wide and older ones are purged.

Set trace flags deliberately with short expiry, and delete them when finished.

14 You need a log for a user you cannot impersonate.Medium

Set a trace flag on that user and ask them to reproduce — you do not need to log in as them to capture their log.

Login As is for reproducing behaviour; trace flags are for capturing it.

15 A log shows "skipped frames".Medium

Output was dropped because the log exceeded its size budget mid-transaction. What you are reading is incomplete.

Reduce the levels and reproduce rather than drawing conclusions from a partial log.

16 Validation rules do not appear where you expect.Medium

They run after before-triggers and before after-triggers — and a workflow field update re-fires triggers without re-running validation by default.

The execution tree shows the real order, which is frequently not the one people assume.

17 A batch job's log is enormous.Medium

Each execute is its own log. Lower the levels, reduce the scope for the debug run, and target a single chunk rather than the whole job.

For ongoing visibility, your own job-log records beat trying to read batch logs.

18 How do you compare two transactions?Medium

Capture both logs at the same levels and diff the cumulative limits and the execution tree.

That is how you answer "why is it slow for this record and not that one" — the difference is almost always in what automation fired.

19 Do debug logs affect behaviour?Medium

Yes — high log levels add real overhead, which can change timing and occasionally mask or create a limit problem.

So a transaction that only fails without logging is plausible, and a transaction that only fails with it is also possible.

20 What is the method, in order?Hard

Reproduce (as the right user, with the right data, through the right entry point) → isolate (bisect by disabling automation) → measure (cumulative limits and query plan) → fix → write the failing test first.

The step people skip is the first: half of all "unreproducible" bugs reproduce immediately once you stop testing as a system administrator.

Tools beyond logs (21–40)

21 A report times out. Which tool?Easy

The Query Plan tool in the Developer Console — paste the equivalent SOQL and read the cost and which index (if any) is used.

Cost above roughly 1 means a table scan, which tells you to change the filter rather than the report.

22 You need to step through Apex.Medium

Apex Replay Debugger in VS Code — free, replays a debug log with real breakpoints, stepping and variable inspection.

Post-mortem rather than live, since it needs a log. The licensed Interactive Debugger gives you live breakpoints in a sandbox.

23 A collection is unexpectedly empty.Medium

Developer Console checkpoints capture full object state at a line — far more useful than guessing from debug statements.

Heap dumps are the right tool for "what is actually in this structure at this moment".

24 "The org is slow." Which tool?Easy

The Lightning Usage App — EPT by page, browser, user and over time.

It frequently shows one browser or one geography rather than a platform problem, which changes the investigation entirely.

25 You need to know who exported a report last month.Medium

Event Monitoring — report export events are among its most valuable log types, and it is the only retrospective answer.

Without it you cannot answer the question at all, which is worth knowing before an incident.

26 An error happened in production and the log has expired.Hard

You need instrumentation you built in advance: a structured error log published as a platform event so the record survives rollback.

Capture class, method, message, stack, record Id, correlation id, quiddity and a limit snapshot. That answers most incident questions without a log.

27 A bug only happens from the mobile app.Medium

Request.getCurrent().getQuiddity() tells you the invocation context — AURA, REST, BATCH_APEX, SYNCHRONOUS and so on.

Log it on every error and "it only fails from X" becomes a provable statement rather than a theory.

28 You need to test a snippet quickly.Easy

Execute Anonymous in the Developer Console or the CLI — but note it runs with sharing by default, which differs from a class's default.

So a query that works there may behave differently inside your code.

29 An LWC is slow and you suspect the server.Medium

Browser devtools: the network tab shows Aura/Apex call count, payload size and timing — which usually reveals too many calls rather than one slow one.

Then component instrumentation on the page to attribute the rendering cost.

30 Setup Audit Trail — when is it the right tool?Easy

"What changed in configuration, and who changed it" — the first question when something worked yesterday and does not today.

Review it weekly as a habit, not just during incidents, so drift is caught before it causes one.

31 You need per-test coverage and failure stacks.Easy

The Developer Console Tests tab, or the CLI's test results — both give you per-class coverage and the failure stack without leaving your workflow.

For CI, JUnit output so the pipeline names the failing test.

32 Salesforce Optimizer — what is it good for?Medium

Org-wide hygiene: unused fields, too many layouts, excessive components per page, inactive rules.

Treat it as a backlog rather than a to-do list, prioritised by what affects users or blocks change.

33 Health Check — what does it tell you?Easy

How your security settings compare with a baseline, scored. Run it quarterly — the score drifts downward as "temporary" relaxations accumulate.

Each regression should be a ticket with a justification or a fix.

34 You need to alert on a condition in real time.Medium

Real-Time Event Monitoring with a Transaction Security policy — block or notify on a large export, an unexpected login region.

Start in notify mode to measure false positives before blocking anything, or you will cause business disruption.

35 A scheduled job stopped and nothing errored.Medium

Query CronTrigger for NextFireTime and state — a deployment or an abort can leave a schedule broken.

And add a heartbeat: the job writes a completion record, and a separate check alerts if none appeared today.

36 How do you monitor async failures programmatically?Medium

Query AsyncApexJob on a schedule for Failed and Aborted, and alert. The Apex Jobs UI is for humans and nobody looks at it.

NumberOfErrors gives a count, never a cause — your own error log supplies that.

37 You need production debugging for one user only.Medium

A custom permission that switches on verbose logging in your own framework, assigned to that user.

That gives you production tracing without logging for everyone, and without relying on catching a trace flag at the right moment.

38 A managed package's internals are opaque.Medium

You get cumulative totals per namespace and nothing more. Isolate by disabling your logic, measure the difference, and raise it with the vendor.

Debugging inside a managed package is not available to you — do not spend hours trying.

39 Which tool for "why can't this user see the record"?Medium

Login As, then the sharing chain — and querying the object's share table with its RowCause to see what grants exist.

That field turns sharing archaeology into a lookup.

40 What should every org have before an incident?Hard

Structured error logging via platform events, correlation ids, limit snapshots at thresholds, async job monitoring with alerts, drift detection, and Apex exception emails going to a monitored address.

Each is roughly a day's work, and together they change every future incident from an investigation into a lookup.

Debugging production (41–60)

41 Your error log is empty exactly when it matters.Hard

You wrote it with DML, so it was rolled back with the failing transaction. This is the single most common logging mistake.

Publish a platform event instead — event publication survives rollback, and a subscriber writes the durable record.

42 What belongs in a production error record?Medium

Class, method, message, stack trace, record Id, correlation id, quiddity, running user, and the limit snapshot at failure.

That set answers most incident questions without a debug log — which is exactly when you cannot get one.

43 An intermittent failure you cannot reproduce.Hard

Intermittent usually means concurrency, data shape or ordering: lock contention, a null only in old data, async arriving out of order, or a limit approached under load.

Correlate occurrences — same user? same hour? same record type? "Random" is usually "a condition we have not characterised".

44 A user reports an error with no details.Medium

Ask for the time, the record and what they clicked — then find it by user and timestamp, or by correlation id if your UI surfaces one.

Showing a correlation id in the error message is a small change that makes support dramatically faster.

45 The error email went to a developer who left.Easy

Set the Apex exception recipients to a monitored distribution list, and build real alerting off your error log.

Single-person notification is a guaranteed future gap, and one of the most common findings when an org changes hands.

46 How do you debug without affecting users?Medium

Trace flags are per user, so target the affected user rather than enabling broadly — and keep levels low to avoid changing timing.

For anything structural, reproduce in a sandbox with production-shaped data.

47 A failure happens once a week at random.Hard

Look for a weekly trigger: a scheduled integration, a batch overlapping with interactive usage, or a particular record with unusually many children.

Correlate by hour and by record. Weekly patterns almost always have a weekly cause.

48 The business asks what caused an incident.Medium

Answer with evidence: the correlation id, the log record, the cumulative limits, the audit trail entry — not a theory.

If you cannot produce evidence, say so and describe what instrumentation you are adding so the next one is answerable.

49 An integration failed silently overnight.Hard

Alert on absence, not just errors: a feed that normally delivers 5,000 records and delivered zero should page someone.

Most monitoring only catches failures, and silence is the more dangerous failure mode.

50 You need to find which records were affected.Medium

From your error log's record Ids, or by querying for the state the failure would have left — which is why logging the record Id matters.

A count of failures without record Ids leaves you unable to remediate.

51 A production incident needs containment first.Hard

Stop the bleeding before diagnosing: flip the bypass switch, pause the job, open the circuit breaker, freeze the user if it is an access issue.

Diagnosing while data continues to diverge makes the repair larger.

52 How do you avoid making it worse?Medium

Preserve evidence before changing anything, make one change at a time, and know what each change reverses.

The classic incident mistake is three simultaneous fixes, after which nobody knows what worked.

53 A bypass switch would have helped. You do not have one.Medium

Then your options are a deployment under pressure or deactivating metadata by hand — both slow and risky.

Build the switch afterwards: a hierarchy custom setting checked at the top of every handler, flippable per user without a deployment.

54 How do you write a useful post-incident note?Medium

What happened, the evidence, the immediate containment, the root cause, what made it hard to detect, and what you changed so it is detectable next time.

The detection gap is the most valuable part and the most commonly omitted.

55 An error is user-facing and unhelpful.Easy

An unhandled exception surfaces internal class names — unhelpful and an information leak.

Catch, log the detail with a correlation id, and show a message written for the user. In Aura/LWC that means AuraHandledException.

56 You need to replay failed work.Medium

Store enough in the error or dead-letter record to reconstruct the operation, and provide a button or batch to re-submit selected rows.

Replay must be idempotent, because some of what you replay may have partially succeeded.

57 A cascade of automation ran for hours unnoticed.Hard

Each async hop is its own transaction, so the loop is invisible in any single debug log.

Add a durable counter and alert on it — a static guard cannot span transactions, and this class of incident is only detectable with instrumentation.

58 How do you debug a flow failure in production?Medium

The error email or your fault-path log record gives you the failing element and $Flow.FaultMessage; then reproduce with that record's data as that user.

WORKFLOW=FINER shows element-by-element execution when you can reproduce.

59 A failure only affects one user.Medium

Their data shape or their permissions: more related records, a larger territory, a record-type-specific path, or missing FLS.

Reproduce as them with their data. "Works for me" is almost always a permissions or data-shape difference.

60 What is the most under-built debugging capability?Hard

Structured, rollback-surviving error logging with correlation ids — most orgs have none, so every production incident starts from zero.

It is about a day's work and it changes the character of every subsequent investigation.

"Works in sandbox" (61–80)

61 A query is fast in sandbox and times out in production.Hard

Data volume changed the query plan: a filter that was selective in the sandbox is not in production, so the optimiser abandoned the index.

Run the Query Plan tool against production — the statistics are per tenant.

62 Code works in sandbox and fails on a production load.Medium

Data shape: skew, a mega-account with tens of thousands of children, or nulls that do not exist in the sandbox.

Lock contention and the concurrent long-running request limit also only appear under real concurrency.

63 A feature deployed fine and does not work.Medium

Missing data: custom setting rows, Custom Metadata, queue members, picklist assignments per record type, package configuration.

Metadata deployed; configuration data did not. Seed it with an idempotent post-deployment script.

64 Production has automation your sandbox does not.Medium

A flow added directly in production, a validation rule, or a package upgraded on one side only — classic config drift.

Drift detection would have told you. Capture the difference into a config/* branch and merge it down.

65 Tests pass and users get access errors.Medium

Tests run in system mode, so they never exercised sharing or FLS.

Use System.runAs with a minimum-access profile plus the permission set under test — that is the test that finds this before users do.

66 An integration works in sandbox and fails in production.Medium

Different endpoint, different credentials, real latency, real rate limits — and sandbox mocks hide all of them.

Also check the API allocation: production has different volume, and a polling integration can exhaust it.

67 A scheduled job runs in sandbox and not production.Medium

The schedule was never created in production — schedules are not metadata in the way people assume.

Run an idempotent scheduler setup method as a documented post-deployment step and verify CronTrigger.

68 A page is slower in production.Medium

More related records per parent, more components added by other teams, more packages, and unselective reports over larger data.

Measure with EPT and component instrumentation in production rather than extrapolating from a sandbox.

69 A test passes in sandbox and fails in production deployment.Medium

It depends on org data (SeeAllData), on a profile name that differs, on a Custom Metadata row, or on a picklist value.

Make tests self-sufficient: create what they need and inject configuration rather than relying on deployed rows.

70 Production has a managed package your sandbox lacks.Medium

Then your CPU and limit measurements are wrong, and its triggers will run on your saves.

Install packages at matching versions in every environment — otherwise sandbox testing proves something about a different org.

71 A sandbox refresh "broke" everything.Medium

The refresh reset config data, schedules, named credentials and integration users — and hard-coded Ids now point at nothing.

A scripted post-refresh checklist fixes this repeatably. See post-refresh.

72 You cannot reproduce a production issue at all.Hard

Work through the differences systematically: data volume, data shape, permissions, entry point, concurrency, installed packages, and drift.

One of those seven is nearly always the answer, and the list is faster than guessing.

73 A Full sandbox would have caught it.Medium

For volume, selectivity and migration behaviour, yes — those only reproduce with production-shaped data.

That is the argument for using the Full sandbox for performance testing and migration rehearsal rather than everyday UAT.

74 The same code behaves differently for two users.Medium

Sharing, FLS, record type, locale, timezone, or a permission-gated branch.

Log the running user and the quiddity on every error, and reproduce as the affected user.

75 A date is wrong for some users only.Hard

Timezone. Datetime is stored in UTC and rendered in the user's zone; Date has none.

Write down all the relevant zones — user, org, operating hours, remote system — before changing any code.

76 Behaviour differs between the UI and the API.Medium

Different automation applies (assignment rules, auto-response), different running user, and validation scoped to exclude integration users.

Log the quiddity so this becomes provable rather than suspected.

77 It worked yesterday and nothing was deployed.Hard

Something changed that is not a deployment: data volume crossing a threshold, a package upgrade, a config change in production, a certificate expiry, or an API version retirement.

Setup Audit Trail and drift detection answer the configuration half; volume growth answers much of the rest.

78 A deployment reverted someone's production fix.Hard

Config drift. The fix existed in production and not in your branch, and a full deployment overwrote it.

Add nightly drift detection and a sanctioned fast path. See drift.

79 How do you make sandboxes more representative?Medium

Matching package versions, a seeded config-data script, a sandbox template with realistic data shape, and deployment from the pipeline rather than by hand.

A sandbox nobody deploys to is a snapshot of whenever it was last touched.

80 What is the honest limit of sandbox testing?Hard

Volume, concurrency, real integrations, real user permissions and drift. Those five cannot be fully reproduced, which is why production instrumentation matters.

Plan for detection in production, not just prevention in a sandbox.

Method & judgement (81–100)

81 Where do you start on an unfamiliar bug?Medium

Reproduce it — as the right user, with the right data, through the right entry point. Everything else is faster once you can.

If you cannot reproduce, work the seven differences: volume, shape, permissions, entry point, concurrency, packages, drift.

82 How do you bisect a problem?Medium

Disable automation one layer at a time using bypass switches, or compare against a stripped-down configuration (the diagnostic policy idea, applied generally).

Halving the search space beats inspecting everything, and it is why bypass switches are worth building before you need them.

83 Should you optimise before measuring?Easy

No. On this platform the CPU-versus-waiting distinction alone changes the fix entirely, and the slow thing is rarely the suspected one.

Measure, change one thing, re-measure.

84 You have a theory and no evidence.Medium

Test the theory cheaply before acting on it — a query, a log, a count. Theories are free and fixes are not.

Acting on an untested theory is also how an incident gains a second cause.

85 A fix works but you do not know why.Medium

Keep investigating — a fix you cannot explain will recur, and you have no idea what else it affected.

Write the mechanism down once you have it; that note is what prevents the same investigation in six months.

86 What do you do after fixing a bug?Easy

Write the failing test first, then confirm it passes — so the defect cannot return silently.

And note what made it hard to detect, which is usually a more valuable output than the fix itself.

87 A stakeholder wants an answer before you have one.Medium

Give them the state honestly: what you know, what you are checking, when you will next update, and the containment already in place.

Speculating under pressure produces a wrong answer that then has to be retracted.

88 Two problems look like one.Medium

Separate the symptoms before diagnosing — reports timing out and batch jobs failing on locks have different causes even when they appear together.

Conflating them is how investigations stall.

89 How do you debug something you cannot see into?Hard

Instrument the boundary: log what goes in and what comes out, with a correlation id, and infer from the difference.

That is the only approach for managed packages, external systems and the optimisation engine.

90 You inherit code with no logging.Medium

Add observability before changing behaviour — you cannot improve what you cannot see, and you will not know whether a change helped.

Structured error logging, limit snapshots and a correlation id first.

91 How much logging is too much?Medium

When it costs real CPU and heap, or produces volume nobody can use. Log at thresholds and on errors, with sampling for trends.

Comprehensive logging gives you noise and a storage problem; threshold logging gives you signal.

92 A bug report says "it's broken".Easy

Get the specifics: who, when, what record, what they clicked, what they expected, what happened.

Most "unreproducible" bugs become reproducible with those six answers, and asking is faster than guessing.

93 How do you know when to stop investigating?Medium

When you can explain the mechanism and the fix addresses it. Stopping at "the symptom went away" leaves you with a recurrence you will not connect.

If time forces you to stop early, say so explicitly and record what is still unknown.

94 A fix requires a data repair.Medium

Scope it precisely from your error log's record Ids, rehearse it in a sandbox, run it in batches, and verify counts afterwards.

And make the repair idempotent, because you will probably run it twice.

95 The same bug class keeps recurring.Medium

Fix the pattern, not the instance: a review checklist item, a static analysis rule, or a framework change that makes the mistake impossible.

Recurring bugs are a process signal rather than a coding one.

96 How do you prioritise multiple live issues?Medium

By irreversibility and blast radius: security exposure, then data integrity (silent corruption is worse than visible downtime), then blocked revenue work, then the rest.

Not by who escalated most loudly.

97 You are the only person who can debug this.Medium

That is a risk to fix, not a status to enjoy. Document the mechanism, add the instrumentation that makes it diagnosable, and walk someone through it.

Single points of knowledge fail at exactly the wrong moment.

98 A vendor says the problem is yours.Medium

Produce evidence: the cumulative limits attributing CPU to their namespace, the request and response, the correlation id.

Evidence moves support cases; assertions do not.

99 What is the most common debugging mistake?Hard

Testing as a system administrator with developer-shaped data — which hides permissions, sharing, FLS and volume problems simultaneously.

Closely followed by reading the clock instead of the cumulative limits, and by changing three things at once.

100 One habit that most improves debugging?Hard

Building rollback-surviving structured logging with correlation ids before you need it.

Every other technique depends on having evidence. With it, most incidents become a lookup; without it, every one starts from nothing.
