Postman — 100 Scenarios

Auth flows and token handling, environments and secrets, chaining and data-driven runs, the Salesforce APIs worth having in a collection, Newman in CI, and troubleshooting what the response is actually telling you.

📚
How to use this Answer out loud in ninety seconds, then open the answer. Concepts on Postman In Detail and its Advanced section.

Authentication (1–18)

1 You get 401 on every request despite a fresh token.Easy

You are calling login.salesforce.com instead of the instance_url returned with the token. That is the single most common Postman-against-Salesforce mistake.

Capture instance_url into an environment variable in the token request's test script and use it as your base URL.

2 Which auth flow should you use for interactive testing?Easy

Postman's OAuth 2.0 helper with authorization code + PKCE — it opens a browser, you log in as yourself, and it stores the token.

That also means you are testing with your permissions, which is useful to remember when something works for you and not for the integration user.

3 You need to test as the integration user, not yourself.Medium

Authenticate as that user — JWT bearer or client credentials tied to it — rather than as an admin.

Most "works in Postman, fails in production" issues are permission differences between you and the integration user.

4 A vendor asks for the username-password flow.Medium

Avoid it: it stores a credential, bypasses MFA and is being actively restricted on the platform.

Use JWT bearer or client credentials. If you have legacy collections using it, treat migrating them as remediation work.

5 How do you do JWT bearer in Postman?Hard

Postman's sandbox cannot sign RS256 natively, so the practical approach is to generate the assertion outside Postman (a small script or your CI) and store it as a short-lived environment variable, then POST it to the token endpoint.

For day-to-day interactive work, authorization code + PKCE is far less friction.

6 Your token expires mid-run.Medium

A collection-level pre-request script that checks a stored expiry and refreshes a minute before it lapses.

Store token_expires_at when you obtain the token, and compare against Date.now() — never refresh on every request, which is wasteful and rate-limits you.

7 Where should the refresh token live?Medium

In an environment variable of type secret, or Postman's vault — never in the collection, which gets exported, committed and shared.

An exported collection containing a refresh token is a credential leak with a long life.

8 You accidentally committed a collection with a token.Hard

Treat it as compromised: revoke the token from the Connected App immediately, then rotate the client secret or certificate.

Removing it from the repo is not sufficient — git history retains it, and revocation is the only action that actually closes it.

9 How do you avoid posting to production by mistake?Medium

Separate environments per org, with the environment name visible, and a naming convention that makes production obvious (PROD — DO NOT RUN).

Some teams also add a pre-request guard that fails the request if the base URL looks like production and a flag is not set.

10 A Connected App's IP restrictions block Postman.Medium

Your workstation is not in the permitted range. Either relax IP relaxation on that Connected App for testing, or test from a permitted network.

Document the exception rather than leaving it relaxed permanently.

11 400 invalid_grant on the token request.Medium

Usually a mismatch: wrong login URL for the org type (test.salesforce.com for sandboxes), wrong consumer key, expired assertion, or a user who cannot log in from there.

The response body usually names the reason — read it rather than guessing.

12 Your sandbox token works and production fails.Easy

Different login host, different Connected App, different user. Sandboxes use test.salesforce.com and have their own consumer key.

Parameterise the login URL and consumer key per environment so switching is a dropdown rather than an edit.

13 What OAuth scopes should the app request?Medium

The minimum — an API scope plus refresh_token/offline_access if you need refresh. full is almost never justified.

Scopes are a control a reviewer checks, and an over-scoped test app often becomes the production app.

14 A request works in Postman and fails from your app.Medium

Compare exactly: headers (content type, authorization), the base URL, the API version, and crucially the authenticated user.

Postman's "Code" view gives you the equivalent request in your language, which usually reveals the difference.

15 You need to test MFA-protected behaviour.Medium

Interactive flows prompt for MFA in the browser; server-to-server flows (JWT, client credentials) bypass it by design.

Which is exactly why those flows need certificate rotation, IP restrictions and minimal scopes as compensating controls.

16 How do you share a collection with a partner safely?Medium

Share the collection plus an environment template with empty secret values, and document how they obtain their own credentials.

Never share a working environment. A collection with example requests and error cases answers more partner questions than documentation.

17 Postman stores your token but requests still fail intermittently.Medium

Likely the token being refreshed in one environment while requests use another, or a stale instance_url after an org migration.

Re-capture both access_token and instance_url together in the same script.

18 Should Postman be your source of auth truth?Easy

No — it is a client. The authoritative configuration is the Connected App or External Client App, and your pipeline's secrets.

Keep the collection in version control alongside the code it tests, with secrets injected at runtime.

Environments & variables (19–34)

19 What belongs in an environment versus the collection?Easy

Environment: anything org-specific — base URL, login URL, consumer key, tokens, test record Ids. Collection: the requests, scripts and structure.

That split is what lets one collection run against five orgs.

20 You need a value available to every request.Easy

A collection variable for non-secret defaults (API version), an environment variable for anything org-specific.

Globals work but are invisible when debugging — avoid them for anything that matters.

21 How do you pin the API version?Easy

A variable ({{apiVersion}}) used in every URL, so bumping it is one change and you can test two versions by switching.

Hard-coding v62.0 in forty requests is how collections drift out of date.

22 A variable is not resolving.Easy

Scope: the environment is not selected, or a collection variable of the same name is shadowing it, or it was set as an "initial" value and never given a current one.

The variable inspector shows the resolved value and its source — check there rather than guessing.

23 Initial versus current value — why does it matter?Medium

Initial values are shared when you export or sync; current values stay local. That is the mechanism that keeps secrets out of shared collections.

Put secrets in current values only, and leave the initial value blank.

24 You need test record Ids that differ per org.Medium

Environment variables, ideally populated by a setup request that queries for them rather than hard-coded by hand.

Hard-coded Ids break after every sandbox refresh, which is the same problem as hard-coding them in Apex.

25 How do you run the same collection against five orgs?Easy

Five environments, one collection. Switch the environment and run.

If that does not work, something org-specific has leaked into the collection — usually a hard-coded URL or Id.

26 A secret must not appear in the run log.Medium

Mark the variable as secret type so it is masked, and never log it in a script with console.log.

In CI, inject it via --env-var from the pipeline's secret store rather than committing an environment file.

27 Where do you set the base URL?Easy

From the token response's instance_url, captured into an environment variable — not typed by hand.

That way an org migration or a My Domain change does not require editing every request.

28 You need per-request dynamic values.Easy

Postman's dynamic variables ({{$guid}}, {{$timestamp}}, {{$randomInt}}) — useful for unique external ids and idempotency keys.

A fresh GUID per request is exactly what you want when testing an idempotent endpoint.

29 How do you keep collections in version control?Medium

Export the collection and an environment template as JSON, commit them beside the code they test, and inject real secrets in CI.

That way the API contract and the implementation move together, and a contract change shows up in a diff.

30 A teammate's run behaves differently.Medium

Different environment values, a different authenticated user, or local current values that were never shared.

Diff the resolved variables, and confirm which user each token belongs to — that accounts for most divergence.

31 You need to clean up records a run created.Medium

Accumulate created Ids into an environment variable and finish with a teardown request that deletes them.

Non-negotiable against a shared sandbox: a scenario that leaves records behind makes the next run non-deterministic.

32 Variables are getting out of hand.Easy

Name them consistently with a prefix by purpose (sf_, test_, tmp_), and unset temporary ones in teardown.

An environment with 60 half-remembered variables is as unmaintainable as any other configuration.

33 How do you document a collection?Easy

Descriptions on the collection, each folder and each request — Postman renders them as documentation, which partners can read.

Include the auth setup steps and an example of each error case; those are the questions you will otherwise answer repeatedly.

34 Should the collection mirror your API or your use cases?Medium

Use cases, organised in folders — a partner wants "submit an order end to end", not an alphabetical list of endpoints.

Then a reference folder with the individual calls for people who need them.

Scripts, tests & chaining (35–54)

35 You need to pass a created Id to the next request.Easy

In the Tests tab, parse the response and pm.environment.set('account_id', body.id), then reference {{account_id}}.

That is the basis of every multi-step scenario.

36 A test passes when it should fail.Medium

Usually it asserts something trivially true — a status code of 200 when the body contains an error, or no assertion at all.

Assert on the content: body.success, the created Id, the specific field value.

37 How do you assert on response time?Easy

pm.expect(pm.response.responseTime).to.be.below(2000) — useful as a smoke check that an endpoint has not regressed.

Keep the threshold realistic for the environment, or it becomes a flaky test everyone ignores.

38 You need conditional flow in a run.Medium

pm.execution.setNextRequest('Request name') to branch or loop — which is how you poll an async job until it completes.

Guard the loop with a counter, or a failing job spins forever.

39 How do you poll a Bulk API job to completion?Medium

A folder: create job → upload data → close → a status request that re-queues itself via setNextRequest until the state is Complete or Failed, with an attempt cap.

Then assert the job's record counts, which is the actual outcome.

40 You need the same setup for many requests.Easy

Folder-level pre-request scripts, or a collection-level script that applies to everything.

Duplicating the same auth-refresh script in thirty requests is how collections become unmaintainable.

41 A script needs to make its own HTTP call.Medium

pm.sendRequest — typically used in a pre-request script to fetch a token.

It is asynchronous, so set your variables inside the callback; code after the call runs before the response arrives.

42 How do you test an error response deliberately?Medium

Send a knowingly invalid request and assert the status code and the error body shape — your API's error contract is part of its contract.

Error cases are where integrations actually break, and they are the ones nobody puts in a collection.

43 Data-driven testing with a CSV.Medium

The Collection Runner accepts a CSV or JSON data file and runs the request once per row, with columns available as variables.

Ideal for validating a range of inputs — including the bad ones, with expected status codes per row.

44 How do you assert on a nested JSON field?Easy

const b = pm.response.json() then navigate it, with optional chaining for anything that may be absent.

And assert the absence case explicitly, rather than letting an undefined comparison pass quietly.

45 A run fails on the third request every time.Medium

State from the previous run: a record that still exists, a variable not reset, or data the teardown did not remove.

Make each run self-sufficient — create what it needs, clean up at the end.

46 How do you verify idempotency in Postman?Medium

Send the identical upsert or request twice with the same external id or idempotency key, and assert the second call updated rather than created — same record count, same Id.

That is the single most valuable test for any integration endpoint.

47 You need to test pagination.Medium

Follow nextRecordsUrl in a loop with setNextRequest, accumulating a count, and assert the total matches totalSize.

Not handling pagination is one of the most common integration bugs, and this test catches it.

48 A script is 200 lines.Medium

Move shared logic into a collection-level script or a small library stored in a variable, and keep per-request scripts to assertions and capture.

Scripts are code: the same readability rules apply.

49 How do you keep tests from being flaky?Medium

No dependence on existing data, no dependence on timing without polling, realistic response-time thresholds, and a teardown that always runs.

Flaky API tests get disabled, which costs you the coverage entirely.

50 You want to mock a Salesforce response.Medium

Postman mock servers return saved example responses — useful for developing a client before the endpoint exists, or for demonstrating a contract.

Base the examples on captured real responses, or you will build against a shape Salesforce never produces.

51 Monitors — are they worth using?Medium

For a lightweight external uptime and contract check on a few key endpoints, yes — they run on a schedule and alert on failure.

They are not a substitute for in-org monitoring of your own integrations, which see far more than an external caller.

52 How do you avoid consuming your API allocation in testing?Medium

Run full suites against sandboxes, keep production runs to a small smoke set, and check /limits as part of the suite.

An enthusiastic data-driven run against production can consume a noticeable share of the daily allocation.

53 A request needs a file upload.Medium

Form-data with a file part — and note the file path is local, so a shared collection will not find it unless the file is in the working directory.

For CI, keep the fixture file in the repo next to the collection.

54 Should Postman tests replace Apex tests?Easy

No — different jobs. Apex tests prove your logic; Postman proves the deployed endpoint, the auth and the contract.

Run both in CI at different stages: unit tests before deployment, the collection after.

Salesforce APIs in practice (55–76)

55 What is the first request to put in any collection?Easy

GET /services/data — it lists available API versions and is the quickest confirmation that auth works and the base URL is right.

Then GET /limits, which tells you daily API calls remaining, storage and async usage.

56 An integration starts failing at 4pm daily.Medium

Check /limits — almost certainly daily API allocation exhaustion, usually from a polling job.

Postman is the fastest way to confirm it, and the number makes the case for replacing polling with events.

57 How do you discover an object's fields quickly?Easy

GET /sobjects/Account/describe — field names, types, picklist values and relationships, faster than hunting in Setup.

It is also how you confirm what the authenticated user can see, which differs from what you see as an admin.

58 A SOQL query returns 400 MALFORMED_QUERY.Easy

URL encoding. Spaces, commas and quotes in the query string need encoding — Postman does most of it, but a hand-edited URL breaks.

Put the query in the params table rather than typing it into the URL bar.

59 A query returns only 2,000 records.Easy

That is the batch size; follow nextRecordsUrl for the rest, and check done and totalSize.

A client that ignores nextRecordsUrl silently processes a fraction of the data — a very common bug.

60 You need to create a parent and children in one call.Medium

POST /composite/graph (or sObject Tree) with reference ids linking children to the parent, all-or-none per graph.

Test it in Postman before coding it — the reference syntax is fiddly and the error messages are terse.

61 You need to update 200 records in one request.Easy

PATCH /composite/sobjects with up to 200 records and an allOrNone flag, returning per-record results.

That is the shape most integrations should use rather than 200 individual calls.

62 How do you test an upsert by External Id?Medium

PATCH /sobjects/Account/External_Id__c/ABC123 — then run it twice and assert the second call updated rather than created.

201 then 204 (or an equivalent) is the signal. That is your idempotency proof.

63 A Bulk API 2.0 job in Postman.Medium

Create the job (POST /jobs/ingest), PUT the CSV to the content URL, PATCH the state to UploadComplete, then poll the job status.

Worth scripting as a folder with a polling loop; it is also the fastest way to understand the sequence before coding it.

64 You need to read across several objects in one call.Medium

POST /graphql — the client shapes its own read query, with FLS and sharing applied.

Testing it in Postman first is the easiest way to iterate on the query shape before putting it in a component.

65 How do you call your own Apex REST endpoint?Easy

/services/apexrest/your/path with the same bearer token.

A 404 usually means the class is not exposed to the user's profile, the URL mapping differs from what you expect, or the namespace is missing.

66 Your custom endpoint returns 403.Medium

Apex class access on the authenticated user's profile or permission sets — distinct from object permissions.

This is the most common cause of "works for me, fails for the integration user" on a custom endpoint.

67 You need to test what a guest user can reach.Hard

Call the site's public endpoints without an authorization header, from an incognito-equivalent context.

That is the real test of guest exposure, and it frequently returns more than the team expected.

68 How do you test a platform event publish?Medium

POST /sobjects/My_Event__e with the payload — it publishes like any other insert.

Then verify the subscriber's effect by querying the records it should have created, since the publish response tells you nothing about consumption.

69 Can you subscribe to events from Postman?Medium

Not comfortably — streaming needs a long-lived CometD or gRPC connection, which is not Postman's model.

Use a dedicated client for subscription testing, and use Postman for publishing and for verifying the outcome.

70 A response is 201 but nothing was created.Hard

Check the body: a composite or collection request can return an overall success with per-record failures inside.

Always assert the inner results, not just the HTTP status — this is exactly the bug that reaches production unnoticed.

71 You get 403 REQUEST_LIMIT_EXCEEDED.Easy

Daily API allocation exhausted, org-wide. Check /limits and find the consumer.

Nothing in your request is wrong — this is a capacity problem, and tuning the request will not help.

72 You need to inspect what your own integration is sending.Medium

Point it at a Postman mock server or a request-capture endpoint and compare with what you intended.

Frequently the integration sends a subtly different header, encoding or payload shape than the Postman request that worked.

73 The official Salesforce collection — worth using?Easy

Yes as a reference: it covers the platform APIs with working examples and saves you assembling them.

Fork it and keep your own trimmed version for your project, rather than navigating hundreds of requests you do not use.

74 How do you verify an API version migration?Medium

Run the same collection with {{apiVersion}} switched and diff the responses — which is why the version belongs in a variable.

Pay attention to field availability and error shapes, which are where version differences usually bite.

75 A field is missing from the response.Easy

FLS for the authenticated user, or you did not request it.

Describe the object as that user to confirm. "The API is dropping my field" is almost always a permission difference.

76 How do you test a long-running operation?Medium

Kick it off, capture the job or request id, then poll with setNextRequest and an attempt cap until it resolves.

Asserting immediately after kicking off an async operation is a guaranteed flaky test.

Newman & CI (77–90)

77 How do you run a collection in CI?Easy

newman run collection.json --environment env.json --env-var "secret=$SECRET" --reporters cli,junit.

JUnit output so the pipeline shows which endpoint broke rather than a wall of console text.

78 When in the pipeline should the collection run?Medium

After deployment, as a smoke test: does auth work, do the endpoints respond, is the contract unchanged, are limits healthy.

Unit tests verify the code; this verifies the deployed org.

79 Secrets in a CI run.Medium

Commit an environment template with empty values and inject the real ones with --env-var from the pipeline's secret store.

Never commit a working environment file — and mark the variables secret so they are masked in output.

80 Should a failing collection fail the build?Medium

Yes for the smoke set — if the deployed endpoints do not work, the deployment is not successful.

Use --bail to stop on the first failure when the suite is a gate, and keep the smoke set small enough to be reliable.

81 The CI run is slow.Medium

Separate a fast smoke folder from a comprehensive suite, and run only the smoke set on every deployment.

Feedback slower than a few minutes gets ignored, which defeats the purpose.

82 A CI run pollutes the sandbox with records.Medium

A teardown folder that always runs, deleting what the run created from an accumulated Id list.

Otherwise the sandbox degrades over weeks and the suite becomes non-deterministic.

83 How do you authenticate Newman non-interactively?Medium

JWT bearer or client credentials — the same flows your pipeline uses for the CLI. Interactive OAuth is not available.

Generate the token in a pre-request script or a prior pipeline step and pass it in.

84 The collection passes locally and fails in CI.Medium

Different environment values, a different authenticated user, missing local current values, or a file path that only exists on your machine.

Make the collection fully parameterised, and run it locally with the CI environment file to confirm.

85 How do you report results usefully?Easy

JUnit XML consumed by the pipeline, so failures appear as named test results with the request and assertion that failed.

A console dump nobody reads is the same as no reporting.

86 Should the collection live in the same repo as the code?Easy

Yes — so the contract and the implementation move together and a contract change appears in the pull request diff.

A collection in someone's Postman workspace drifts from the code within weeks.

87 How do you review a collection change in a PR?Medium

The JSON diff is readable enough for request and assertion changes, but import it to review anything structural.

What matters in review: new assertions are meaningful, no secrets added, and teardown still covers what the run creates.

88 Can Newman test the UI too?Easy

No — it is an API runner. UI testing needs a browser automation tool.

Keep the boundary clear: Newman for contracts and smoke, something else for end-to-end user journeys.

89 How do you test against a scratch org in CI?Medium

Create the org, deploy, seed data, then generate an auth token for it and pass the instance URL into the Newman run as environment variables.

Everything org-specific must come from the pipeline, which is the same discipline as any parameterised environment.

90 What belongs in the smoke set?Medium

Auth, /limits, one read, one write with cleanup, and each custom endpoint's happy path plus one error case.

Small, fast and genuinely diagnostic — if that set passes, the deployment is functional.

Judgement & troubleshooting (91–100)

91 It works for you and fails for the integration.Medium

Permissions, by a wide margin — you are an admin and the integration user is not. Then API version, headers and the base URL.

Re-run your request authenticated as the integration user; that single step resolves most of these cases.

92 A partner says your API is broken.Medium

Ask for the full request and response including headers and the correlation id, then reproduce it in Postman as their user.

Half of these resolve as a malformed request or an expired token on their side — and the other half you can now fix.

93 How do you debug an opaque 500?Medium

A 500 from your own Apex endpoint means an unhandled exception — find it in the debug log or your error log by correlation id.

And fix the endpoint to return a meaningful 4xx with a message instead; a 500 is almost always your bug.

94 You need to prove a response shape to a consumer.Easy

Save the response as an example in the collection and share the rendered documentation.

A real captured response is a far better contract artefact than a hand-written schema that drifts from reality.

95 How much should you automate versus explore?Medium

Automate the contract and the smoke set; keep exploration manual. Not every request you try needs to become a test.

A bloated suite of low-value tests slows CI and gets disabled.

96 Postman versus curl versus the CLI?Easy

Postman for exploration, documentation and sharing. curl for a quick one-off or a scripted check. The Salesforce CLI for metadata, data loads and org operations.

Use the right one; forcing all three jobs into one tool wastes time.

97 A collection has 300 requests and nobody maintains it.Medium

Split it: a small maintained smoke set in version control, and an archive for reference.

An unmaintained collection is worse than none, because people trust its requests and they no longer reflect the API.

98 What is the fastest way to onboard a new integration developer?Easy

A documented collection with working auth setup, example requests, error cases and an environment template.

It answers more questions in an hour than any written specification, and it is executable rather than aspirational.

99 Your collection is the only documentation of an API.Medium

That is better than nothing and genuinely common — so treat it as documentation: descriptions, examples, error cases, and an auth setup guide.

Also generate an OpenAPI spec if partners need one, and keep the collection as the executable companion.

100 One habit that most improves API work in Postman?Hard

Capturing instance_url and access_token together in the token request's script, and parameterising everything org-specific into the environment.

It eliminates the commonest failure (calling the login host), makes one collection work against every org, and keeps secrets out of anything you share.
