Test Classes

Coverage rules, test data factories, mocking callouts, runAs, bulk and negative tests — how to write tests that actually catch bugs instead of just hitting 75%.

Why and the rules

The deployment gate

  • 75% org-wide coverage to deploy to production
  • Every trigger needs at least some coverage
  • All tests must pass
  • Coverage is calculated org-wide, not per class

What actually matters

  • Assertions, not line count
  • Bulk behaviour (200 records)
  • Negative paths and error handling
  • Different user profiles

Test context rules

  • Tests see no org data by default
  • Data is rolled back after each test
  • Emails aren't sent
  • Callouts must be mocked
  • Async runs at stopTest()
🎯
Coverage is a side effect, not a goal for (Integer i=0; i<100; i++) myMethod(); with no assertions gives you 100% coverage and zero value. A test's job is to fail when the behaviour breaks.

Anatomy of a test class

Test execution timeline — and what startTest/stopTest actually do
The Arrange–Act–Assert shape maps exactly onto startTest / stopTest — put only the code under test between them.
@isTest
private class OpportunityDiscountServiceTest {

    /* ---------- Runs ONCE per test class, data shared by all methods ---------- */
    @testSetup
    static void makeData() {
        Account acc = new Account(Name = 'Test Account', Tier__c = 'Gold');
        insert acc;

        List<Opportunity> opps = new List<Opportunity>();
        for (Integer i = 0; i < 200; i++) {
            opps.add(new Opportunity(
                Name        = 'Deal ' + i,
                AccountId   = acc.Id,
                StageName   = 'Prospecting',
                CloseDate   = Date.today().addDays(30),
                Amount      = 10000 + i));
        }
        insert opps;
    }

    /* ---------- Positive path ---------- */
    @isTest
    static void appliesTierCapToDiscount() {
        List<Opportunity> opps = [SELECT Id, Amount FROM Opportunity LIMIT 200];

        Test.startTest();
        OpportunityDiscountService.applyDiscount(opps, 0.40);   // request 40%
        Test.stopTest();

        for (Opportunity o : [SELECT Discount__c FROM Opportunity]) {
            Assert.areEqual(0.30, o.Discount__c,
                'Gold tier should cap the discount at 30%');
        }
    }

    /* ---------- Negative path: the exception IS the expected behaviour ---------- */
    @isTest
    static void rejectsNegativeDiscount() {
        Boolean threw = false;
        try {
            OpportunityDiscountService.applyDiscount(new List<Opportunity>(), -0.1);
            Assert.fail('Expected a DiscountException');
        } catch (DiscountException e) {
            threw = true;
            Assert.isTrue(e.getMessage().contains('must be positive'),
                'Message should explain the problem, got: ' + e.getMessage());
        }
        Assert.isTrue(threw);
    }

    /* ---------- Boundary/empty input ---------- */
    @isTest
    static void handlesEmptyListGracefully() {
        Test.startTest();
        OpportunityDiscountService.applyDiscount(new List<Opportunity>(), 0.10);
        Test.stopTest();
        Assert.areEqual(0, Limits.getDmlStatements(), 'No DML should run for an empty list');
    }
}
Annotation / methodWhat it does
@isTest on the classExcludes it from the 6 MB code limit and from coverage calculations
@isTest on a methodMarks a test method (or use static testMethod void, now deprecated)
@testSetupRuns once before each test method; the data is rolled back to that state between methods. Max one per class
Test.startTest()Resets governor limits — put the code under test after it
Test.stopTest()Restores limits and forces queued async work to run
@isTest(SeeAllData=true)Grants access to real org data. Avoid — makes tests environment-dependent
@isTest(isParallel=true)Allows the test to run in parallel for faster test runs
@suppressWarningsSilences PMD/compiler warnings

Assertions

// Modern Assert class (API 55+) — preferred
Assert.areEqual(expected, actual, 'message');
Assert.areNotEqual(notExpected, actual, 'message');
Assert.isTrue(condition, 'message');
Assert.isFalse(condition, 'message');
Assert.isNull(value, 'message');
Assert.isNotNull(value, 'message');
Assert.isInstanceOfType(obj, Account.class, 'message');
Assert.fail('Should not reach here');

// Legacy System methods (still everywhere in older code)
System.assertEquals(expected, actual, 'message');
System.assert(condition, 'message');
✍️
Always pass the third argument Assert.areEqual(5, count) fails with "Expected 5, Actual 3" — useless at 2am. Assert.areEqual(5, count, 'Should create one task per open case') tells you what broke.

Test data factory

Never copy-paste record creation. One reusable factory means a new required field is fixed in one place instead of fifty test classes.

@isTest
public class TestDataFactory {

    public static Account createAccount(Boolean doInsert) {
        Account a = new Account(
            Name          = 'Test Account ' + generateUnique(),
            Industry      = 'Technology',
            BillingCity   = 'Bengaluru',
            BillingCountry= 'India');
        if (doInsert) insert a;
        return a;
    }

    public static List<Contact> createContacts(Id accountId, Integer count, Boolean doInsert) {
        List<Contact> cons = new List<Contact>();
        for (Integer i = 0; i < count; i++) {
            cons.add(new Contact(
                FirstName = 'Test',
                LastName  = 'Contact ' + i,
                Email     = 'test' + i + generateUnique() + '@example.com',
                AccountId = accountId));
        }
        if (doInsert) insert cons;
        return cons;
    }

    public static User createUser(String profileName, Boolean doInsert) {
        Profile p = [SELECT Id FROM Profile WHERE Name = :profileName LIMIT 1];
        String uid = generateUnique();
        User u = new User(
            FirstName = 'Test', LastName = 'User',
            Alias = uid.substring(0, 8),
            Email = uid + '@example.com',
            Username = uid + '@example.com.test',
            ProfileId = p.Id,
            TimeZoneSidKey = 'Asia/Kolkata', LocaleSidKey = 'en_IN',
            EmailEncodingKey = 'UTF-8', LanguageLocaleKey = 'en_US');
        if (doInsert) insert u;
        return u;
    }

    private static String generateUnique() {
        return String.valueOf(Datetime.now().getTime()) + String.valueOf(Math.abs(Crypto.getRandomInteger()));
    }
}
🏭
Factory conventions ① Always offer a doInsert flag so tests can modify before saving. ② Generate unique values for anything with a uniqueness constraint (Username, External Id). ③ Mark the class @isTest so it doesn't count toward org code size. ④ Consider a fluent builder for objects with many optional fields.

Testing security with System.runAs

@isTest
static void salesRepCannotSeeOtherRepsOpportunities() {
    User rep1 = TestDataFactory.createUser('Standard User', true);
    User rep2 = TestDataFactory.createUser('Standard User', true);

    System.runAs(rep1) {
        Account a = TestDataFactory.createAccount(true);
        insert new Opportunity(Name='Rep1 Deal', AccountId=a.Id,
                               StageName='Prospecting', CloseDate=Date.today());
    }

    System.runAs(rep2) {
        List<Opportunity> visible = [SELECT Id FROM Opportunity];
        Assert.areEqual(0, visible.size(),
            'Rep2 must not see Rep1 opportunities under a Private OWD');
    }
}

// runAs also solves MIXED_DML in tests
@isTest
static void createsUserAndAccount() {
    System.runAs(new User(Id = UserInfo.getUserId())) {
        insert TestDataFactory.createUser('System Administrator', false);
    }
    insert TestDataFactory.createAccount(false);     // no MIXED_DML error
}
📌
What runAs does and doesn't do It changes the user context for record sharing and FLS. It does not enforce object-level CRUD in all cases, and it does not reset governor limits. It only works in test methods.

Mocking callouts

Real callouts are blocked in tests. You must supply a mock, or you get "Methods defined as TestMethod do not support Web service callouts".

@isTest
public class ErpCalloutMock implements HttpCalloutMock {
    private Integer statusCode;
    private String  body;

    public ErpCalloutMock(Integer statusCode, String body) {
        this.statusCode = statusCode;
        this.body = body;
    }

    public HttpResponse respond(HttpRequest req) {
        // You can assert on the OUTGOING request too — very valuable
        Assert.isTrue(req.getEndpoint().contains('/api/invoices'), 'Wrong endpoint');
        Assert.areEqual('POST', req.getMethod());

        HttpResponse res = new HttpResponse();
        res.setStatusCode(statusCode);
        res.setHeader('Content-Type', 'application/json');
        res.setBody(body);
        return res;
    }
}

@isTest
static void syncsInvoiceSuccessfully() {
    Test.setMock(HttpCalloutMock.class,
        new ErpCalloutMock(201, '{"id":"ERP-9001","status":"created"}'));

    Test.startTest();
    InvoiceSyncService.sync(invoiceIds);
    Test.stopTest();

    Assert.areEqual('Synced', [SELECT Sync_Status__c FROM Invoice__c LIMIT 1].Sync_Status__c);
}

@isTest
static void handlesServerError() {
    Test.setMock(HttpCalloutMock.class, new ErpCalloutMock(500, '{"error":"down"}'));
    Test.startTest();
    InvoiceSyncService.sync(invoiceIds);
    Test.stopTest();
    Assert.areEqual('Failed', [SELECT Sync_Status__c FROM Invoice__c LIMIT 1].Sync_Status__c);
}
// When one test hits several endpoints, route by URL
@isTest
public class MultiEndpointMock implements HttpCalloutMock {
    private Map<String, HttpResponse> responses = new Map<String, HttpResponse>();

    public MultiEndpointMock addResponse(String urlFragment, Integer code, String body) {
        HttpResponse r = new HttpResponse();
        r.setStatusCode(code);
        r.setBody(body);
        responses.put(urlFragment, r);
        return this;                    // fluent
    }

    public HttpResponse respond(HttpRequest req) {
        for (String fragment : responses.keySet()) {
            if (req.getEndpoint().contains(fragment)) return responses.get(fragment);
        }
        HttpResponse notFound = new HttpResponse();
        notFound.setStatusCode(404);
        notFound.setBody('{"error":"no mock configured for ' + req.getEndpoint() + '"}');
        return notFound;
    }
}

// Usage
Test.setMock(HttpCalloutMock.class, new MultiEndpointMock()
    .addResponse('/oauth/token', 200, '{"access_token":"abc"}')
    .addResponse('/api/invoices', 201, '{"id":"ERP-1"}'));
// Store a real captured response as a Static Resource named "ErpInvoiceResponse"
StaticResourceCalloutMock mock = new StaticResourceCalloutMock();
mock.setStaticResource('ErpInvoiceResponse');
mock.setStatusCode(200);
mock.setHeader('Content-Type', 'application/json');
Test.setMock(HttpCalloutMock.class, mock);

// Or combine several static resources by endpoint
MultiStaticResourceCalloutMock multi = new MultiStaticResourceCalloutMock();
multi.setStaticResource('https://erp.example.com/api/invoices', 'ErpInvoiceResponse');
multi.setStaticResource('https://erp.example.com/api/customers', 'ErpCustomerResponse');
multi.setStatusCode(200);
Test.setMock(HttpCalloutMock.class, multi);

Best when the real payload is large — paste the actual production response into a static resource and your test stays faithful to reality.

@isTest
global class WeatherServiceMock implements WebServiceMock {
    global void doInvoke(
            Object stub, Object request, Map<String, Object> response,
            String endpoint, String soapAction, String requestName,
            String responseNS, String responseName, String responseType) {

        WeatherService.GetWeatherResponse_element resp =
            new WeatherService.GetWeatherResponse_element();
        resp.temperature = 28;
        resp.condition   = 'Sunny';
        response.put('response_x', resp);
    }
}

@isTest
static void readsWeather() {
    Test.setMock(WebServiceMock.class, new WeatherServiceMock());
    Test.startTest();
    Integer t = WeatherClient.getTemperature('Bengaluru');
    Test.stopTest();
    Assert.areEqual(28, t);
}

Apex Stub API — mocking your own classes

// Mock a Selector so the test never touches the database
@isTest
public class SelectorMock implements System.StubProvider {
    private List<Account> toReturn;
    public SelectorMock(List<Account> accounts) { this.toReturn = accounts; }

    public Object handleMethodCall(Object stubbed, String methodName, Type returnType,
                                   List<Type> paramTypes, List<String> paramNames,
                                   List<Object> args) {
        if (methodName == 'selectByIds') return toReturn;
        return null;
    }
}

@isTest
static void serviceUsesSelectorResults() {
    List<Account> fake = new List<Account>{ new Account(Id = TestUtil.fakeId(Account.SObjectType), Name = 'Fake') };
    AccountSelector mockSelector = (AccountSelector) Test.createStub(
        AccountSelector.class, new SelectorMock(fake));

    AccountService svc = new AccountService(mockSelector);   // dependency injection
    Assert.areEqual(1, svc.getActiveAccounts().size());
}
⚡
Why stubbing is worth it Tests that never insert records run in milliseconds instead of seconds, and they isolate the class under test from triggers, validation rules and required fields. It requires designing for injection — pass dependencies into the constructor rather than instantiating them inline.

Test patterns cheat sheet

You're testing…Pattern
A triggerInsert/update 200 records, assert the outcome; then a single-record case; then a case that should not fire
Batch Apex≤ 200 records, Database.executeBatch inside start/stopTest, assert after
QueueableSystem.enqueueJob inside start/stopTest; guard chaining with Test.isRunningTest()
Scheduled ApexSystem.schedule with a far-future cron; assert CronTrigger
A calloutTest.setMock; test 200, 4xx and 5xx responses separately
An LWC's Apex controllerCall the @AuraEnabled method directly; assert the wrapper contents
Sharing / permissionsSystem.runAs with a user on the relevant profile
A validation rule or addErrorExpect the DmlException and assert on its message
SOSLTest.setFixedSearchResults(new List<Id>{...}) — the index doesn't exist in tests
A platform eventPublish inside start/stopTest; Test.getEventBus().deliver() to force delivery
Custom metadata-driven logicInject the config via a setter/test-visible variable — CMDT rows can't be inserted in tests
 
// Generating a fake Id without inserting — handy for stubbed tests
public static Id fakeId(Schema.SObjectType sot) {
    String prefix = sot.getDescribe().getKeyPrefix();
    return Id.valueOf(prefix + '0'.repeat(12 - String.valueOf(counter).length()) + counter++);
}

Testing best practices

✅ Do

  • One logical assertion per test method — name the method after the behaviour
  • Test with 200 records for anything triggered by DML
  • Test negative paths: nulls, empty lists, invalid input, exceptions
  • Use @testSetup to keep tests fast
  • Use Test.startTest()/stopTest() around the code under test
  • Use a shared TestDataFactory
  • Test as different users with runAs
  • Mock every external dependency
  • Aim for 90%+ on business-critical classes

❌ Don't

  • SeeAllData=true (except for a handful of objects that genuinely require it, like Pricebook2 in some cases)
  • Hard-code Ids or query for real org records
  • Write assertion-free "coverage" tests
  • Depend on test execution order
  • Use System.debug instead of assertions
  • Create data in every method instead of @testSetup
  • Ignore a failing test by commenting it out
  • Forget Test.stopTest() before asserting async results
💰
The standard Pricebook exception Tests cannot see the standard Pricebook by default. Use Id pbId = Test.getStandardPricebookId(); then create your PricebookEntry against it — this is the one case everyone hits when testing Opportunity Products.

Interview questions

1 What exactly does the 75% rule require?Easy

To deploy to production you need 75% coverage org-wide (not per class), every trigger must have at least some coverage, and all tests must pass. Coverage is recalculated on the classes in the deployment plus the org total.

The follow-up they're really asking: coverage is a gate, not a quality measure. A loop calling a method 100 times with no assertions gives you high coverage and zero confidence.

2 What do Test.startTest() and Test.stopTest() actually do?Easy

Two distinct things. startTest() gives you a fresh set of governor limits, so the data you set up beforehand doesn't consume the budget of the code under test. stopTest() restores the original limits and forces any queued asynchronous work to execute synchronously — which is why assertions on Batch/Queueable/@future results must come after it. You can use them only once per test method.

3 Why avoid @isTest(SeeAllData=true)?Easy

It makes the test depend on org data, so it passes in your sandbox and fails in production — or starts failing the day someone deletes a record. Tests should be self-contained and deterministic; build data with a TestDataFactory.

The honest exception is a handful of objects tests can't create, most famously the standard Pricebook — and even there Test.getStandardPricebookId() is the correct answer rather than SeeAllData.

4 How do you test a method that makes an HTTP callout?Medium

Real callouts are blocked in tests. Implement HttpCalloutMock (or use StaticResourceCalloutMock for large realistic payloads) and register it with Test.setMock(HttpCalloutMock.class, new MyMock()) before invoking the code. For SOAP, implement WebServiceMock.

The point worth making in an interview: mocks let you test the paths a real endpoint won't give you on demand — 500s, 429s and malformed bodies. You can also assert on the outgoing request inside respond() to verify you built the right endpoint, method and payload.

5 What does System.runAs do — and what does it not do?Medium

It executes a block as another user, applying that user's record sharing and FLS, so you can prove a rep can't see another rep's opportunities. It also solves MIXED_DML in tests by letting you insert a User in a separate context.

What it does not do: reset governor limits, and it doesn't enforce object CRUD in every case. It only works inside test methods.

6 Describe a good test suite for a trigger.Medium
  1. Bulk — insert/update 200 records and assert the outcome. This is where triggers actually break.
  2. Single record — the happy path.
  3. Negative — data that should be rejected; assert the DmlException message from addError().
  4. No-op — an update that shouldn't fire the logic, asserting nothing changed.
  5. Permissions — runAs a non-admin profile.
  6. Recursion — an update that cascades, asserting the work happened exactly once.
7 What is the Stub API and why would you use it?Hard

Test.createStub() plus a class implementing System.StubProvider lets you mock your own Apex classes — typically a Selector — so the test never touches the database.

Benefits: tests run in milliseconds instead of seconds, and the class under test is isolated from triggers, validation rules and required fields on unrelated objects. The prerequisite is designing for dependency injection — pass the Selector into the Service's constructor rather than instantiating it inline.

8 Your test passes in the sandbox and fails in production. Name three likely causes.Hard
  1. Data dependency — SeeAllData or a query assuming a record exists.
  2. Different automation — a validation rule, required field or active trigger that exists in production but not the sandbox, so your test data no longer inserts.
  3. Org-wide limits — production has more automation stacked on the same object, so the transaction hits a governor limit your sandbox never reached.
  4. Also common: profile/permission differences under runAs, and a Pricebook2 or record-type Id that differs between orgs because it was hard-coded.

Quick check

1. Where do you assert the results of a Batch job in a test?
Async work queued between startTest and stopTest is executed synchronously when stopTest() is called — assert after that line.
2. Your test fails with "Methods defined as TestMethod do not support Web service callouts". Fix?
Real HTTP is never allowed in tests. A mock also lets you deliberately test 500s and timeouts, which real endpoints won't give you on demand.
3. Which gives the most confidence for a trigger?
Bulk behaviour is where triggers break. Coverage percentage tells you nothing about correctness.
