Step 1 · Set up the Connected App

Postman can't talk to Salesforce until you create a Connected App to authenticate against.

  • Setup → App Manager → New Connected App (choose "Create an External Client App" in newer orgs).
  • Basic Information — name it "Postman", add your email.
  • Tick "Enable OAuth Settings".
  • Callback URL: https://oauth.pstmn.io/v1/callback (Postman's hosted callback). Add http://localhost:1717/OauthRedirect too if you use the desktop agent.
  • Selected OAuth Scopes — add: Manage user data via APIs (api), Perform requests at any time (refresh_token, offline_access), and optionally Full access (full) for exploration.
  • Untick "Require Proof Key for Code Exchange (PKCE)" only if you hit trouble — Postman supports PKCE, so leave it on where possible.
  • Save, then wait up to 10 minutes for it to propagate. Calling too early gives confusing invalid_client_id errors.
  • Click "Manage Consumer Details" and copy the Consumer Key and Consumer Secret.
  • Manage → Edit Policies — set Permitted Users to "Admin approved users are pre-authorized" for tight control (then assign a profile/permission set), or "All users may self-authorize" for a dev org. Set IP Relaxation to "Relax IP restrictions" while testing.
⏳
The three things that waste an hour ① Not waiting 10 minutes after creating the app. ② A callback URL that doesn't match exactly (including https and no trailing slash). ③ Using login.salesforce.com for a sandbox — sandboxes need test.salesforce.com, and My Domain orgs should use their own domain URL.

What Postman needs to make any Salesforce call

Best for a dev/test workspace. No browser prompt, no user interaction. Requires nominating a "Run As" user on the Connected App (Manage → Edit → Client Credentials Flow).

The production standard for server-to-server. No password anywhere — you sign a JWT with a private key whose certificate is uploaded to the Connected App.

// Pre-request script: build and sign the JWT
// (Requires the private key in an environment variable — never commit it)
const header  = { alg: 'RS256' };
const claims  = {
    iss: pm.environment.get('consumer_key'),          // Connected App key
    sub: pm.environment.get('integration_username'),  // the user to impersonate
    aud: pm.environment.get('login_url'),             // login or test .salesforce.com
    exp: Math.floor(Date.now() / 1000) + 180
};
// Sign with jsrsasign loaded via pm.sendRequest, or generate the assertion externally
// then POST it:
POST {{login_url}}/services/oauth2/token
grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer
&assertion={{signed_jwt}}

Setup: generate a self-signed certificate, upload it to the Connected App ("Use digital signatures"), and pre-authorise the integration user's profile.

POST {{login_url}}/services/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=password
&client_id={{consumer_key}}
&client_secret={{consumer_secret}}
&username={{username}}
&password={{password}}{{security_token}}     ← password and token CONCATENATED
🚫
Blocked by default and deprecated Salesforce disables this flow in new orgs (Setup → OAuth and OpenID Connect Settings → "Allow OAuth Username-Password Flows"). It sends credentials on every call and can't use MFA. Never use it in production. Know it only because legacy integrations still do.

The security token is emailed when you reset it (Personal Settings → Reset My Security Token). It isn't needed if your IP is in a Trusted IP Range.

Saving the token automatically

Add this to the Tests tab of your token request so every other request just works:

// Tests tab of the "Get Token" request
const res = pm.response.json();

pm.environment.set('access_token', res.access_token);
pm.environment.set('instance_url', res.instance_url);
if (res.refresh_token) {
    pm.environment.set('refresh_token', res.refresh_token);
}
pm.environment.set('token_issued_at', Date.now());

pm.test('Token received', function () {
    pm.response.to.have.status(200);
    pm.expect(res.access_token).to.be.a('string').and.not.empty;
});

Step 4 · Building the requests

# CREATE
POST {{base_url}}/sobjects/Account
Authorization: Bearer {{access_token}}
Content-Type: application/json

{ "Name": "Acme India", "Industry": "Technology", "Phone": "+91 80 1234 5678" }
# → 201 { "id": "0015j00000ABCDE", "success": true, "errors": [] }

# READ (all fields)
GET {{base_url}}/sobjects/Account/{{account_id}}

# READ (specific fields — much faster)
GET {{base_url}}/sobjects/Account/{{account_id}}?fields=Id,Name,Industry

# UPDATE
PATCH {{base_url}}/sobjects/Account/{{account_id}}
{ "Industry": "Banking" }
# → 204 No Content (empty body is SUCCESS, not an error)

# UPSERT by External Id
PATCH {{base_url}}/sobjects/Account/Legacy_Id__c/A-1001
{ "Name": "Acme India" }
# → 201 created  or  204 updated

# DELETE
DELETE {{base_url}}/sobjects/Account/{{account_id}}
# → 204

# DESCRIBE — every field, picklist value and record type
GET {{base_url}}/sobjects/Account/describe

# LIMITS — check your remaining daily API calls
GET {{base_url}}/limits
# SOQL — remember to URL-encode (Postman does it if you use Params)
GET {{base_url}}/query?q=SELECT Id, Name, Industry FROM Account WHERE Industry = 'Technology' LIMIT 10

# Pagination — the response includes nextRecordsUrl when there are more
GET {{instance_url}}/services/data/{{api_version}}/query/01g5j00000ABCDEabc-2000

# Include deleted and archived records
GET {{base_url}}/queryAll?q=SELECT Id FROM Account WHERE IsDeleted = true

# SOSL
GET {{base_url}}/search?q=FIND {Acme*} IN ALL FIELDS RETURNING Account(Id,Name), Contact(Id,Name)

# Parameterised search (easier to build)
GET {{base_url}}/parameterizedSearch?q=Acme&sobject=Account&Account.fields=Id,Name&Account.limit=10

Step 5 · Pre-request scripts & tests

Every request has two script slots: Pre-request (runs before) and Tests (runs after). They're plain JavaScript.

Auto-refresh the token — put this at collection level

// Collection → Pre-request Script: refresh if the token is missing or older than 1 hour
const issuedAt = Number(pm.environment.get('token_issued_at') || 0);
const isStale  = !pm.environment.get('access_token') || (Date.now() - issuedAt) > 3600000;

if (isStale) {
    pm.sendRequest({
        url: pm.environment.get('login_url') + '/services/oauth2/token',
        method: 'POST',
        header: { 'Content-Type': 'application/x-www-form-urlencoded' },
        body: {
            mode: 'urlencoded',
            urlencoded: [
                { key: 'grant_type',    value: 'client_credentials' },
                { key: 'client_id',     value: pm.environment.get('consumer_key') },
                { key: 'client_secret', value: pm.environment.get('consumer_secret') }
            ]
        }
    }, function (err, res) {
        if (err) { console.error('Token refresh failed', err); return; }
        const json = res.json();
        pm.environment.set('access_token',   json.access_token);
        pm.environment.set('instance_url',   json.instance_url);
        pm.environment.set('token_issued_at', Date.now());
        console.log('Token refreshed');
    });
}
♻️
Set auth once, at the collection On the collection's Authorization tab choose Bearer Token with value {{access_token}}, then set every request to "Inherit auth from parent". Now one script keeps the whole collection authenticated.

Writing tests

// ---- Status and timing ----
pm.test('Status is 201 Created', () => pm.response.to.have.status(201));
pm.test('Responds under 2s',     () => pm.expect(pm.response.responseTime).to.be.below(2000));
pm.test('Is JSON',               () => pm.response.to.be.json);

// ---- Body assertions ----
const json = pm.response.json();
pm.test('Record was created', () => {
    pm.expect(json.success).to.be.true;
    pm.expect(json.errors).to.be.an('array').that.is.empty;
    pm.expect(json.id).to.match(/^001[a-zA-Z0-9]{12,15}$/);
});

// ---- Chain: save the Id for the next request ----
pm.environment.set('account_id', json.id);

// ---- Schema validation ----
const schema = {
    type: 'object',
    required: ['id', 'success'],
    properties: {
        id:      { type: 'string' },
        success: { type: 'boolean' },
        errors:  { type: 'array' }
    }
};
pm.test('Matches schema', () => pm.response.to.have.jsonSchema(schema));

// ---- Negative testing ----
pm.test('Rejects a missing required field', () => {
    if (pm.response.code === 400) {
        pm.expect(pm.response.json()[0].errorCode).to.eql('REQUIRED_FIELD_MISSING');
    }
});

// ---- Control the flow of a collection run ----
if (pm.response.code === 401) {
    postman.setNextRequest('Get Token');       // jump back
}
// postman.setNextRequest(null);               // stop the run

Newman — running collections in CI

# Install
npm install -g newman newman-reporter-htmlextra

# Export the collection and environment from Postman, then:
newman run SalesforceAPI.postman_collection.json \
  -e UAT.postman_environment.json \
  -d accounts.json \
  --reporters cli,htmlextra,junit \
  --reporter-htmlextra-export ./reports/report.html \
  --reporter-junit-export ./reports/junit.xml \
  --bail                      # stop on first failure

# Pass secrets from the CI vault rather than the environment file
newman run collection.json -e env.json \
  --env-var "consumer_secret=$SF_CONSUMER_SECRET" \
  --env-var "consumer_key=$SF_CONSUMER_KEY"
# GitHub Actions step
- name: API regression tests
  run: |
    npm install -g newman
    newman run postman/SalesforceAPI.json \
      -e postman/UAT.json \
      --env-var "consumer_secret=${{ secrets.SF_CONSUMER_SECRET }}" \
      --reporters cli,junit --reporter-junit-export results.xml

The official Salesforce collection

  • In Postman, search the public API Network for "Salesforce Platform APIs" and fork it into your workspace.
  • It ships with hundreds of pre-built requests: REST, Bulk 2.0, Composite, Tooling, Metadata, UI API, Connect, Analytics, Pub/Sub.
  • Fill in its environment template (_endpoint, _accessToken, version) and everything works.
  • Use it as a reference even if you build your own collection — it documents parameter names you'd otherwise hunt for.

Best practices

✅ Do

  • Structure the collection in folders: Auth · CRUD · Query · Composite · Apex REST · Bulk
  • One environment per org, never hard-coded URLs
  • Set auth at collection level and inherit it
  • Mark secrets as secret type, and only in Current Value
  • Write at least a status-code test on every request
  • Chain requests by saving Ids to environment variables
  • Add a description to every request — the collection becomes your documentation
  • Export collections to Git alongside the code they test

❌ Don't

  • Commit an environment file containing a real client secret
  • Use the Username-Password flow in production
  • Hard-code record Ids that only exist in your sandbox
  • Point a shared collection at production by default
  • Run destructive DELETE requests in a shared workspace without a guard
  • Ignore the daily API allocation while load testing
  • Forget to switch {{login_url}} when moving from sandbox to prod
🧰
Beyond the basics Mock servers let a front-end team build against your Apex REST contract before you've written it. Monitors run a collection on a schedule from Postman's cloud and alert you when an endpoint breaks. Postman Interceptor captures real browser traffic so you can see exactly what the Salesforce UI itself calls.

Interview questions

1 Walk me through connecting Postman to a Salesforce org from scratch.Easy

Create a Connected App with OAuth enabled, callback https://oauth.pstmn.io/v1/callback and scopes api refresh_token offline_access; wait ~10 minutes; copy the Consumer Key and Secret. In Postman create an environment holding login_url, consumer_key, consumer_secret and api_version. Run a token request, and in its Tests tab save access_token and instance_url to the environment. Set the collection's auth to Bearer {{access_token}} and have every request inherit it.

2 Your token request returns invalid_grant. Diagnose it.Medium

Most likely, in order: you're hitting login.salesforce.com for a sandbox (use test.salesforce.com or the My Domain URL); the password is missing the appended security token; the user isn't authorised for the Connected App ("Admin approved users are pre-authorized" without the profile assigned); or the username-password flow is disabled org-wide, which it is by default in new orgs. invalid_client_id instead means a wrong key or an app that hasn't propagated yet.

3 Where do you put secrets, and what's the trap?Medium

Environment variables with Type = secret, and only in the Current Value column.

The trap is Initial Value: that's the column Postman syncs and shares with your team or workspace. Put a client secret there and you've distributed it to everyone — and it ends up in the exported JSON if you commit the environment to Git. Leave Initial Value blank and inject secrets from the CI vault via newman --env-var.

4 How do you avoid re-authenticating manually before every request?Medium

A collection-level pre-request script that checks whether the token is missing or older than an hour and, if so, calls the token endpoint with pm.sendRequest() and writes the new access_token, instance_url and token_issued_at back to the environment.

Combine that with collection-level Bearer auth on {{access_token}} and "inherit auth from parent" on every request, and the whole collection stays authenticated with no manual step — which is what makes it usable in Newman/CI.

5 Explain Postman's variable scopes.Easy

From broadest to narrowest — and narrowest wins: Global (whole workspace) → Collection (travels with the collection when shared) → Environment (one per org: Dev, UAT, Prod) → Data (a CSV/JSON row in the Collection Runner) → Local (set in a script, lives for one run).

Practical use: put api_version at collection level so one edit updates every request, and org-specific URLs and credentials at environment level so switching orgs is a dropdown.

6 How do you chain requests so request B uses the Id created by request A?Medium

In A's Tests tab, capture and store it: pm.environment.set('account_id', pm.response.json().id); Then B references {{account_id}} in its URL or body.

For flow control inside a run, postman.setNextRequest('Get Token') jumps to a named request (useful for re-authenticating on a 401), and postman.setNextRequest(null) stops the run.

7 How would you use Postman in a CI pipeline?Hard

Export the collection and environment to the repo, then run Newman in the pipeline: newman run collection.json -e uat.json --reporters cli,junit --env-var "consumer_secret=$SF_SECRET". Publish the JUnit XML so failures appear as test results, and use --bail to stop on the first failure.

This gives you API regression tests for your Apex REST endpoints on every deployment — the contract your partners depend on is verified automatically rather than by someone remembering to click Send.

8 A PATCH returns 204 with an empty body and the developer says the API is broken. Response?Easy

204 No Content is the documented success response for PATCH and DELETE in the Salesforce REST API — there is deliberately no body. Only POST returns 201 with the new Id, and GET returns 200 with data.

The lesson for their tests: assert on the status code, not on body content. And open the Postman Console (Ctrl+Alt+C) to see the fully resolved request — nine times out of ten an "API problem" is an unresolved variable visible right there.

Quick check

1. Your PATCH returns 204 with an empty body. Did it work?
Assert on status codes, not body content. 200 returns a body; 204 deliberately does not.
2. Where should the Consumer Secret live in Postman?
Initial Values sync to everyone in the workspace. Secrets belong in Current Value only, marked as secret so they're masked.
3. You need the same 200 accounts created in three sandboxes. Fastest approach?
Data-driven runs are exactly this scenario — and swapping environments repoints the whole collection at another org.
