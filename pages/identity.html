Identity & Access Management

Who gets in, how they prove it, and how Salesforce acts as both a consumer and a provider of identity — SSO, MFA, Connected Apps, My Domain and session security.

🔗
Where this sits Security & Sharing answers "what can this user see once they're in". This module answers "how do they get in, and are they who they claim to be". OAuth for APIs is the machine-to-machine cousin.

The vocabulary

TermMeaning
AuthenticationProving who you are (login, MFA)
AuthorisationDeciding what you may do (profiles, permission sets, sharing)
Identity Provider (IdP)The system that authenticates the user and asserts their identity
Service Provider (SP)The application that trusts that assertion and logs the user in
SAMLXML-based assertion protocol — the enterprise SSO standard
OpenID Connect (OIDC)An identity layer on top of OAuth 2.0, JSON/JWT based — the modern choice
SCIMStandard for automated user provisioning and de-provisioning
JIT provisioningCreating or updating the user automatically from the SSO assertion at login

When the IdP certificate expires or the IdP goes down, that account is the only way back into the org.

Salesforce as the Identity Provider

Salesforce can also be the IdP — users log into Salesforce, then click into other apps without logging in again.

  • Enable it in Setup → Identity Provider, then define each downstream app as a Connected App with SAML or OIDC settings.
  • The App Launcher becomes the users' portal to all connected apps.
  • Common with Experience Cloud: customers authenticate once and reach partner tools.
  • Identity licences exist for users who only need SSO and App Launcher, not CRM.

Connected Apps — both directions

Inbound (app → Salesforce)

An external system authenticates to Salesforce via OAuth. This is the object you create for Postman, a mobile app or an integration. See OAuth flows.

Key policies: permitted users, IP relaxation, refresh-token validity, session policies.

vs

Outbound (Salesforce → app)

Salesforce asserts identity to another app via SAML/OIDC, and appears in the App Launcher.

Key settings: ACS URL, Entity Id, NameID format, custom attributes to pass.

MFA & login security

Multi-Factor Authentication

  • Mandatory for all direct Salesforce logins
  • Methods: Salesforce Authenticator, TOTP apps, security keys (U2F/WebAuthn), built-in device biometrics
  • SMS and email codes are not accepted as MFA factors
  • If your IdP enforces MFA, that satisfies the requirement for SSO users
  • Enforce with the "Multi-Factor Authentication for User Interface Logins" permission

Session security

  • Session timeout and "force logout on timeout"
  • Lock sessions to the IP they originated from
  • High Assurance sessions — require MFA to reach sensitive areas (reports, Setup, a connected app)
  • Login Flows — run a screen flow after authentication for extra verification or terms acceptance
  • Clickjack, CSRF and CSP protections

Access restrictions

  • Login IP Ranges (profile) — hard block outside the range
  • Trusted IP Ranges (network access) — inside = no verification challenge; outside = challenge, not block
  • Login Hours (profile)
  • Device activation and identity verification by email/authenticator

Monitoring

  • Login History — status, IP, browser, application, login type
  • Identity Verification History
  • Login Forensics and Transaction Security Policies (Shield) to block or alert on risky logins in real time

My Domain & org URLs

  • My Domain is mandatory. It gives your org a branded URL (acme.my.salesforce.com).
  • It's a prerequisite for SSO, Lightning components in Experience Cloud, and the modern login experience.
  • Enhanced Domains standardise the format across Lightning, Experience Cloud and Visualforce hosts.
  • Practical impact: hard-coded instance URLs (na152.salesforce.com) break. Always use URL.getOrgDomainUrl() in Apex and {{instance_url}} from the OAuth response in integrations.
// Never hard-code the instance
String base = URL.getOrgDomainUrl().toExternalForm();
String recordUrl = base + '/lightning/r/Account/' + acc.Id + '/view';

// A self-callout still needs a Named Credential — even to your own org
req.setEndpoint('callout:Self_Org/services/data/v62.0/sobjects/Account/' + acc.Id);

User provisioning & lifecycle

ApproachHow it worksBest for
ManualAdmin creates each userSmall orgs
JIT provisioningUser created/updated from the SAML assertion at first loginSSO orgs where the IdP owns the data
SCIM / User ProvisioningThe IdP pushes create, update and deactivate eventsEnterprises — the only approach that reliably handles leavers
Data Loader / APIBulk create from HR dataMigrations and onboarding waves
🚪
Deactivation, not deletion Salesforce users can never be deleted — they're deactivated, which frees the licence while preserving record ownership and audit history. Before deactivating: reassign record ownership, check they aren't the running user of a dashboard, an approver, a queue member, the owner of a scheduled job, or a Connected App's integration user. Freezing blocks login immediately without freeing the licence — use it while you work through that list.

Delegated Administration lets you give a business-unit lead the ability to create users and reset passwords for specified roles and profiles, without full admin rights.

Interview questions

1 Authentication vs authorisation — where does each live in Salesforce?Easy

Authentication = proving identity: My Domain login, SSO, MFA, login IP ranges and hours, session settings. Authorisation = what you can do once in: profiles, permission sets and groups (object and field access) plus OWD, role hierarchy and sharing rules (record access). A user can be perfectly authenticated and still see nothing — the two layers are independent.

2 Walk me through SP-initiated SAML SSO.Medium

The user hits the My Domain URL → Salesforce redirects the browser to the IdP with a SAML AuthnRequest → the IdP authenticates them (password + MFA) → the browser POSTs a signed SAML assertion back to Salesforce → Salesforce validates the signature against the uploaded certificate and maps the identity (normally the Federation ID) to a User record → a session is created.

No Salesforce password is ever used. IdP-initiated is the same but starts from the IdP's portal.

3 SSO breaks org-wide at 9am. What happened and how do you get back in?Hard

Most likely the IdP signing certificate expired — the classic overnight failure. Other candidates: the IdP is down, someone changed the Entity ID/Issuer, or a clock-skew problem invalidating assertions.

You get back in with the break-glass admin — an account excluded from SSO, with a password and MFA, stored in the vault. That's why you create one before enforcing SSO. Then upload the new certificate. Longer term: monitor certificate expiry and alert 30 days ahead.

4 Login IP Ranges vs Trusted IP Ranges.Medium

Login IP Ranges are set on the profile and are a hard block — outside the range, the user cannot log in at all. Trusted IP Ranges are org-wide network settings and only control the identity verification challenge: inside the range you skip the emailed code; outside you're challenged but not blocked.

The trap: adding an office IP to Trusted ranges doesn't restrict anything — people often think it does.

5 A user leaves the company. What's your checklist?Medium

Freeze immediately to stop login while you work. Then reassign: record ownership, open activities, dashboards where they're the running user, pending approvals, queue membership, scheduled jobs they own, and any Connected App or integration using their credentials. Check they aren't referenced in a role hierarchy gap or a Sharing rule target. Then deactivate to free the licence — users cannot be deleted, so their audit history is preserved. Ideally SCIM from the IdP triggers all this automatically.

6 What is a High Assurance session and when would you use one?Hard

A session that was established with a stronger factor — MFA, or a specific login method. You can mark a Connected App, report, or Setup area as requiring High Assurance, so a user logged in with only a password is re-challenged when they try to reach it.

Typical use: normal CRM work needs standard assurance, but exporting reports or entering Setup requires MFA. It's the step-up authentication pattern, configured under Session Security Levels.

7 Why is hard-coding na152.salesforce.com a bug?Easy

Instance names change — Salesforce migrates orgs between instances, and My Domain/Enhanced Domains changed the URL format. Hard-coded hosts break silently after a migration or a sandbox refresh.

Use URL.getOrgDomainUrl().toExternalForm() in Apex, the instance_url returned by the OAuth token response in integrations, and a Named Credential for callouts — including self-callouts back into your own org.

8 How would you let a business unit manager create users without making them an admin?Medium

Delegated Administration. Define a delegated admin group specifying which roles (and subordinates) they can manage and which profiles they may assign. They can then create and edit users, reset passwords and unlock accounts within that scope — and nothing else.

It's the correct answer to "they need to onboard their own team" and avoids the far riskier alternative of granting Manage Users, which is effectively full administrative power.

Quick check

1. Which identity value is recommended for matching SSO users?
Usernames must be globally unique across all of Salesforce and often change; the Federation ID is owned by your IdP and stays stable.
2. Can a Salesforce user be deleted?
Deactivation frees the licence while preserving ownership history and audit integrity. Freeze blocks login immediately without freeing the licence.
3. Before enforcing SSO org-wide, what must you set up?
