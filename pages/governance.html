Governance, Ecosystem & Localisation

The organisational side of Salesforce — how change is controlled, how many orgs you should have, the wider product ecosystem, and how to run one platform across many countries.

Governance & the Centre of Excellence

Every org that becomes unmaintainable got there one reasonable-sounding request at a time. Governance is the process that stops it.

A change lifecycle that scales

What a CoE owns

  • A single intake process — no side-door requests to a friendly admin
  • Prioritisation against business value, not volume of shouting
  • Design standards: naming, one automation tool per concern per object, when Apex is justified
  • Release cadence and environment strategy
  • Security review and permission model ownership
  • Documentation and a data dictionary
  • Adoption metrics and technical-debt backlog

Symptoms of no governance

  • Fifteen flows and three triggers on Account, order unknown
  • 200 profiles, nobody knows which are used
  • Fields created for one report three years ago, never populated
  • Two teams building the same integration
  • Changes made directly in production
  • Nobody can say what a field means
  • Every release breaks something unrelated

Well-Architected thinking

Salesforce publishes a Well-Architected framework. Whatever the branding, these are the questions a reviewer asks:

Trusted

Is it secure (least privilege, FLS enforced, secrets in Named Credentials), compliant (consent, retention, auditability) and reliable (error handling, retries, monitoring)?

Easy

Is it intentional (solves a stated business outcome), automated (CI/CD, tests) and resilient to change — can the next person understand and modify it?

Adaptable

Is it composable (loosely coupled, reusable) and scalable (bulk-safe, within limits at 10× today's volume)?

🏛️
The senior signal Junior answers describe what a feature does. Senior answers describe trade-offs: "Batch Apex handles the volume, but it's asynchronous so the user won't see the result immediately — if they need confirmation, we should publish a platform event and update the UI via empApi." Practise articulating the cost of your choice, not just the choice.

Single org or multi-org?

Single org

  • One view of the customer across business units
  • Shared objects, automation and reporting
  • Cheaper licences and less duplicated build
  • One release process
  • Risk: shared governor limits, shared namespace, one business unit's change affects everyone, and org-wide limits (custom objects, fields, code size) become real
vs

Multi-org

  • Autonomy and isolation per region or business unit
  • Independent release cycles and limits
  • Sometimes required by data residency or regulation
  • Cost: duplicated build and admin, no single customer view, cross-org integration, and a proliferation of near-identical solutions

Middle grounds: Divisions to partition a very large single org; Salesforce Connect cross-org adapter to read another org's data; Data Cloud to unify profiles across orgs; and unlocked packages to share a common codebase between orgs.

Managed packages and your limits A package's Apex consumes SOQL, DML and CPU in the same transaction as your code. When a well-written trigger suddenly throws "Too many SOQL queries: 101", check LIMIT_USAGE_FOR_NS in the debug log — it attributes usage per namespace and will tell you whether the package is the cause.

Irreversible settings — decide once, carefully Multi-Currency, Person Accounts, Custom Fiscal Years, Divisions and Territory Management are all extremely difficult or impossible to turn off. Prototype in a scratch or developer org, and get architectural sign-off before enabling any of them in a production org.

Interview questions

1 An org has 15 flows and 3 triggers on Account. What's your plan?Hard

Measure first — a debug log's CUMULATIVE_LIMIT_USAGE shows what's actually expensive. Then consolidate: one trigger per object with a handler; one before-save and one after-save record-triggered flow, branching internally; move same-record field updates to before-save; tighten entry criteria to "only when a record is updated to meet the condition"; and delete logic duplicated between a flow and a trigger.

Then prevent recurrence: a governance standard of one automation tool per concern per object, enforced in design review. The technical fix without the process fix just delays the same problem.

2 Single org or multi-org — how do you advise?Hard

Default to single org: one customer view, shared automation and reporting, lower cost, one release process. Justify multi-org only for genuine drivers — data residency or regulatory isolation, completely unrelated businesses with no shared customers, an acquisition with its own release cadence, or org-wide limits genuinely exhausted.

Mention the middle grounds: Divisions to partition a large org, Salesforce Connect's cross-org adapter, Data Cloud to unify profiles, and unlocked packages to share a codebase. And be explicit about the multi-org cost: duplicated build, duplicated admin and permanent cross-org integration.

3 What would you check before installing an AppExchange package?Medium

Security review status and date, customer reviews, when it was last updated, and the vendor's viability. Then technically: what objects, fields and permissions it requires; whether it installs triggers on your standard objects (a governor-limit and ordering risk); its licence model; how it's upgraded; and whether uninstalling it would delete data you need.

Always install into a sandbox first, run your regression tests, and check the debug log's LIMIT_USAGE_FOR_NS to see what it consumes in your busiest transactions.

4 Which platform settings are effectively irreversible?Hard

Multi-Currency, Person Accounts, Custom Fiscal Years, Divisions, Territory Management and enabling State & Country Picklists (reversible only with significant pain). Also, once My Domain is deployed you can't go back to instance URLs.

The right process: prototype in a scratch or Developer org, document the impact on reporting, integrations and data model, get architectural sign-off, and schedule it as its own change rather than bundling it into a release.

5 How do you run one org across 12 countries?Hard

Data: Multi-Currency with Advanced Currency Management for dated rates; State & Country picklists for clean addresses; consistent ISO codes in integrations. UI: Translation Workbench for metadata, Custom Labels for every user-facing string, per-user locale and language. Process: record types and Dynamic Forms where processes genuinely differ, resisting the urge to fork everything. Access: role hierarchy or territories aligned to geography, with restriction rules if some data must not cross borders. Operations: a release window that works across time zones, and datetime handling using formatGMT() in integrations.

6 How do you measure technical debt in an org?Medium

Make it numeric so it can be prioritised: Salesforce Optimizer for unused fields, layouts and reports; Security Health Check score; sf scanner findings; test coverage with assertion quality; automation count per object; profiles in use vs existing; users with Modify All Data; API consumption trend; and page EPT from the Lightning Usage App.

Then put the worst items in the same backlog as feature work — debt that isn't on the roadmap never gets fixed.

7 A stakeholder wants a change deployed straight to production today. Response?Medium

Separate urgency from process. Establish whether it's genuinely a production incident or just impatience. If it's an incident, use the documented hotfix path — branch from the production tag, validate with tests, deploy, then merge back so the fix isn't lost in the next release.

If it isn't, explain the cost concretely: unvalidated changes have broken unrelated automation before, and there's no rollback. Offer the next scheduled release, or a same-day validated deploy if the change is small and testable. Saying "no, because process" without offering a path is how governance gets bypassed.

Quick check

1. Which of these can you NOT turn off once enabled?
Multi-Currency, Person Accounts, Custom Fiscal Years, Divisions and Territory Management are all effectively permanent — prototype elsewhere first.
2. A managed package trigger is consuming your SOQL limit. How do you prove it?
The per-namespace breakdown separates your consumption from each installed package's, which is the evidence you need for the vendor.
3. What's the strongest argument for a single org?
Limits are actually an argument against a single org at extreme scale — the real case is the unified customer view and avoiding duplicated build and admin.
