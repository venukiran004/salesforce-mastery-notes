LWC Core — 100 Scenarios

Reactivity, lifecycle, shadow DOM, styling, conditional rendering, accessibility and performance — the things that actually go wrong in components.

📚
How to use this Answer out loud in ninety seconds, then open the answer. Concepts on LWC Core and its Advanced section.

Reactivity (1–16)

1 You push to an array and the UI does not update.Easy

LWC tracks reassignment, not mutation. this.items.push(x) mutates in place, so the framework sees no change.

Reassign: this.items = [...this.items, x]. Almost every "my UI didn't update" bug is this one rule.

2 Setting a nested object property does not re-render.Easy

Same cause. this.record.Name = 'x' mutates. Spread a new object: this.record = { ...this.record, Name: 'x' }.

For deeper nesting, spread each level — or restructure so the component holds flatter state, which is usually better.

3 Is @track still needed?Medium

Rarely. Fields are reactive automatically; @track only adds deep observation of objects and arrays.

Prefer the reassignment pattern over relying on it — it is clearer, it works everywhere, and it avoids surprising deep-mutation behaviour.

4 A getter in your template runs dozens of times.Medium

Getters referenced in the template are evaluated on every render pass. That is fine for cheap expressions and expensive for anything else.

If the getter loops a large array, parses JSON or formats a thousand dates, compute once when the data changes and store the result in a field.

5 A tracked property changes but a child does not update.Medium

You passed an object into the child and mutated it. The child's @api setter only fires on reassignment.

Pass a new object reference, or pass primitives where practical — primitives make reactivity unambiguous.

6 You need to react when a public property changes.Easy

Use an @api getter/setter pair and do the work in the setter — but keep it light and idempotent, because the setter can fire more than once.

Logic needing two properties belongs in connectedCallback, since setter order between properties is not guaranteed.

7 Setter order between two public properties is wrong.Hard

There is no guaranteed order. A setter that depends on another property already being set will intermittently see undefined.

Store the values in the setters and do the combined work in connectedCallback, or guard with a check that both are present.

8 A boolean public property receives the string "false".Medium

HTML attributes are strings. A value from a template attribute or App Builder may arrive as "false", which is truthy.

Coerce explicitly in the setter, and document the expected type. This is a common source of inverted logic in configurable components.

9 A computed class string does not update.Easy

Build it in a getter that references reactive fields, and bind class={computedClass}.

Assigning to element.className imperatively in renderedCallback works until the next render overwrites it.

10 Deleting an item from an array leaves stale UI.Medium

Reassign with a filter: this.items = this.items.filter(i => i.id !== id).

If the rows still look wrong after that, the problem is your key — see the iteration section.

11 You mutate an array returned from a wire adapter.Hard

Wire results are immutable. Mutating them throws or silently fails depending on context.

Copy before modifying: map into new objects. That is also the right place to shape the data for display rather than doing it in getters.

12 A large object in state makes rendering slow.Medium

Deep reactive observation of a big structure is expensive, and spreading it on every change copies it.

Hold only what the template needs, in a flat shape, and keep the raw payload in a non-reactive field if you must retain it.

13 You need state that does not trigger re-render.Medium

Keep it in a field that the template never references — reactivity only matters for values the template reads.

Useful for caches, timers, subscription handles and scroll positions.

14 Two components share state and drift out of sync.Medium

There is no shared store by default. Options: lift the state to a common parent, use Lightning Data Service so both wire the same record (the cache becomes the channel), or use Lightning Message Service.

LDS is the most elegant when the state is a record.

15 You need a derived value used in three places in the template.Easy

One getter, referenced three times — but remember it evaluates on every render, so keep it cheap.

If it is expensive, compute on change into a field. The template then reads a plain value.

16 How do you debug a component that re-renders constantly?Hard

Log in renderedCallback with a counter. A loop usually means you are mutating reactive state inside renderedCallback.

Guard one-time DOM work with a boolean flag, and never assign to a tracked field in that hook.

Lifecycle (17–32)

17 this.template.querySelector returns null in the constructor.Easy

The DOM does not exist yet, and public properties are not set. The constructor is for initialising fields only.

Do DOM work in renderedCallback, and data work in connectedCallback.

18 connectedCallback fires twice.Medium

It can fire again if the component is moved in the DOM or re-inserted (tabs, conditional rendering).

Make it idempotent, and tear down subscriptions, listeners and timers in disconnectedCallback.

19 An infinite loop in renderedCallback.Medium

You changed reactive state there, which triggers another render, which calls the hook again.

Guard with a flag for one-time work, or move the logic to where the data changes rather than where it renders.

20 An error in a child blanks the whole panel.Medium

No error boundary. Implement errorCallback(error, stack) in a parent to catch child errors and render a fallback.

Note it catches errors from children only — not from itself, and not from async callbacks, which need their own handling.

21 errorCallback does not catch your fetch failure.Medium

It does not catch errors thrown in promises or async callbacks. Handle those with .catch or try/catch around await.

Then set component state to render an error message, so the user sees something meaningful rather than an empty space.

22 Where should you fetch data?Easy

connectedCallback for imperative fetches, or a @wire which handles it declaratively.

Not the constructor (no properties yet), and not renderedCallback (fires repeatedly).

23 A component inside a closed accordion still fetches data.Medium

It is constructed and connected even when not visible, so its connectedCallback runs.

Lazy-load: only fetch when a public isActive property becomes true, or render the child conditionally so it is not created at all.

24 You add a window listener and it leaks.Medium

Anything added to window or document, plus setInterval and empApi subscriptions, must be removed in disconnectedCallback.

Keep the handler reference in a field so you can remove exactly what you added — an anonymous function cannot be removed.

25 You need to focus an input after render.Easy

renderedCallback with a one-time guard, using this.refs (with lwc:ref) or this.template.querySelector.

Without the guard you will steal focus on every render, which is a genuinely irritating bug.

26 A child's public method is undefined when the parent calls it.Medium

The child is not rendered yet, or it is inside a conditional branch that is currently false, so querySelector returns null.

Null-check, and call after the child exists — or better, drive the child through a property rather than reaching into it with a method.

27 Should the parent call child methods or set properties?Medium

Properties, usually — declarative, re-renders naturally and survives the child being re-created.

Public methods are for genuine imperative actions (focus, reset, validate), and each one is a contract you then have to maintain.

28 Data arrives after render and the template shows nothing.Easy

Expected — render happens first. Show a loading state with lwc:if while the data is undefined.

Three states deserve rendering: loading, error, and empty. Skipping them is the most common cause of a component that looks broken.

29 How do you know a component has been destroyed?Easy

disconnectedCallback. Use it to clean up, and set a flag so async callbacks that resolve afterwards do not try to update a dead component.

Updating state after disconnect is harmless but can mask bugs; guarding makes the intent explicit.

30 A timer keeps running after navigation.Medium

You did not clear it. Store the id and clearInterval in disconnectedCallback.

In a console app where tabs persist, leaked timers accumulate across a working day and degrade the whole page.

31 Component state resets unexpectedly.Medium

It was destroyed and re-created — conditional rendering, a tab change, or a changed iteration key causing the engine to rebuild it.

If the state must survive, lift it to the parent or persist it (per-viewer storage, or a record).

32 You need to run code once per component instance.Easy

connectedCallback with an idempotency guard, since it can fire more than once.

The constructor runs exactly once but has no properties or DOM, which usually makes it unsuitable.

Templates & rendering (33–50)

33 Rows get the wrong values after you delete one.Hard

You keyed the iteration on the index. Deleting row 2 shifts every later key, so the engine reuses the wrong DOM — input values jump to different rows.

Always key on a stable business identifier.

34 if:true versus lwc:if.Easy

lwc:if/lwc:elseif/lwc:else are the modern directives; if:true is deprecated and evaluates falsy values differently.

Migrate when you touch a template — the new form also avoids duplicating the negative condition.

35 A conditional section flickers on load.Medium

The condition is false initially and becomes true when data arrives, so the empty state renders first.

Distinguish "loading" from "empty": render a spinner while the data is undefined, and the empty state only when it is an empty array.

36 You need to render a component chosen at runtime.Medium

<lwc:component lwc:is={ctor}> with a dynamically imported constructor.

Useful for plug-in style UIs. Keep the set of possible components explicit rather than derived from user input, and handle the import failure.

37 A slot's content is not styled by the child's CSS.Hard

Slotted content lives in the parent's scope, so the child's styles do not apply to it and the child cannot query it.

Style it in the parent, or expose styling hooks the parent can set. This surprises almost everyone.

38 You need multiple insertion points for content.Easy

Named slots: <slot name="header"> and the parent supplies slot="header".

Provide sensible default content inside the slot so the component is usable without the parent filling every slot.

39 Rendering 5,000 rows is slow.Medium

A hand-rolled for:each creates 5,000 DOM subtrees. Use lightning-datatable, which handles large sets, or paginate.

Virtualisation is not something to build yourself here unless you have a very specific need.

40 You need to iterate with first/last awareness.Easy

iterator:it gives you it.first, it.last, it.index and it.value.

Useful for separators and conditional styling without precomputing flags in JavaScript.

41 Template expressions cannot call a function with arguments.Easy

Correct — templates support property access and getters only, not function calls with parameters.

Precompute in JavaScript: map the array into objects that already contain the derived values the template needs.

42 You need the index inside a nested iteration.Medium

Nested for:each works, but each level needs its own item alias and a stable key.

If the structure is complex, flatten it in JavaScript first — nested template logic becomes unreadable quickly.

43 Conditionally rendered components lose their state.Medium

lwc:if destroys and re-creates, so state goes with it.

If the state must survive, keep it in the parent, or hide with CSS instead (accepting that the component stays mounted and active).

44 How do you render raw HTML safely?Hard

lightning-formatted-rich-text, which sanitises. Never set innerHTML from user or record content — that is the classic LWC XSS.

If you need markup you control, build it with template elements rather than strings.

45 You need two different layouts in one component.Medium

Multiple templates: export several HTML files and return the right one from render().

Cleaner than one template full of conditionals when the layouts genuinely differ, and it keeps each template readable.

46 A base component's internals need styling.Hard

Shadow DOM prevents it, and piercing selectors are unsupported and break between synthetic and native shadow.

Use the component's documented styling hooks (CSS custom properties). If none exists, accept the default or build your own.

47 You need a global style to reach inside your component.Medium

static renderMode = 'light' renders without a shadow root, letting global CSS and third-party tools reach in.

It gives up encapsulation, so use it deliberately — commonly for analytics or accessibility tooling that must traverse the DOM.

48 querySelector cannot find an element in a child.Easy

this.template.querySelector only sees your own shadow tree — by design.

Communicate with the child through properties, public methods or events. Reaching into another component's DOM is a bug waiting for their next refactor.

49 What is this.refs for?Easy

With lwc:ref="name" on an element, this.refs.name gives you a direct handle — cleaner and faster than a selector.

Still only valid after render, so the same null-checking applies.

50 Styles behave differently in a community than in the app.Medium

Different theming context, and possibly different shadow DOM behaviour between runtimes.

Use SLDS styling hooks rather than hard-coded values, and test in every runtime you ship to — including dark mode if supported.

Styling & theming (51–64)

51 Your component looks wrong in dark mode.Medium

Hard-coded colours. Use SLDS styling hooks (var(--slds-g-color-surface-1, #fff)) with sensible fallbacks, so the component inherits the theme.

Fixed hex values also break in Experience Cloud and after a brand change.

52 You need consumers to be able to theme your component.Medium

Expose your own CSS custom properties on :host with defaults, and document them.

That gives consumers a supported surface instead of trying to pierce your shadow root — which will break on your next change.

53 SLDS classes do not apply inside your component.Easy

SLDS utility classes generally work, but component-specific SLDS blueprints expect particular markup structures — partial markup gives partial styling.

Prefer composing base components, which bring their own correct markup, accessibility and behaviour.

54 Why prefer base components over custom markup?Easy

You inherit accessibility, keyboard behaviour, mobile layout, validation states and every future design-system update for free.

Re-implementing lightning-input means owning all of that yourself, permanently.

55 A base component's default width breaks your layout.Medium

Wrap it in your own container and control the container's sizing with SLDS grid classes, rather than trying to restyle the component's internals.

Layout belongs outside the component; appearance belongs to its styling hooks.

56 You need a CSS file shared across components.Easy

A CSS module imported in each component's stylesheet — the supported way to share styles without global leakage.

Keep it to tokens and small utilities; a large shared stylesheet recreates the problems shadow DOM prevents.

57 Fonts and images fail to load.Medium

CSP: external resources need CSP Trusted Sites entries, and stylesheets have their own restrictions.

Bundle assets as static resources where possible — versioned, reviewable and offline-safe — rather than loading from a CDN.

58 A third-party CSS framework fights SLDS.Medium

Expect conflicts, specificity battles and an inconsistent look. Shadow DOM limits the damage but also limits the framework's usefulness.

Usually the better answer is SLDS plus targeted custom CSS. Importing a whole framework into a Salesforce UI rarely pays for itself.

59 Your component is unreadable at 200% zoom.Medium

Fixed pixel sizing and fixed-height containers. Use relative units and allow content to reflow.

200% zoom is an accessibility requirement, not an edge case, and testing it takes seconds.

60 A table overflows on a phone.Medium

Dense tables are hostile on small screens. Switch to a card layout below a breakpoint, or make the table horizontally scrollable with a visible affordance.

lightning-datatable handles some of this; a hand-built table handles none.

61 Spacing is inconsistent across your components.Easy

Use SLDS spacing utilities and spacing tokens rather than ad-hoc margins.

Consistency comes from a shared scale, not from each developer choosing a pixel value that looks right in isolation.

62 You need to hide something visually but keep it for screen readers.Medium

slds-assistive-text — visually hidden, still announced.

display: none removes it from the accessibility tree entirely, which is the opposite of what you want.

63 Your component looks different in a console app.Medium

Console apps have different available height, utility bars and tab chrome, and components are often narrower.

Test in the actual app type you ship to. Designing only against a standard record page is how components break in console.

64 How do you keep styling maintainable across 40 components?Medium

Tokens via SLDS hooks, a small shared CSS module, base components for anything standard, and no hard-coded colours or spacing anywhere.

Then a theme or brand change is a token change rather than forty edits.

Accessibility (65–78)

65 You built a clickable div. What is wrong?Easy

No keyboard operability, no focus state, no role, no accessible name — it is invisible to keyboard and screen-reader users.

If it behaves like a button, make it a button. That one change fixes four accessibility failures at once.

66 An icon-only button has no label.Easy

Add alternative-text (on base components) or aria-label. An icon alone announces as "button" with no purpose.

This is the single most common accessibility omission in custom Salesforce UIs.

67 A designer asks you to remove focus outlines.Easy

Decline, and offer to restyle them instead. Without a visible focus indicator, keyboard users cannot tell where they are.

A custom focus style that meets contrast requirements satisfies both the design and the requirement.

68 A toast confirms a save but screen-reader users miss it.Medium

Dynamic content needs an appropriate live region to be announced. Base component toasts generally handle this; hand-rolled notifications do not.

Use the platform toast, or add a live region yourself for inline status messages.

69 Validation errors are shown only in red text.Medium

Colour alone is insufficient, and the error must be programmatically associated with the field so it is announced.

Base input components do this via setCustomValidity/reportValidity — another reason to use them.

70 A modal traps keyboard users.Hard

A modal needs focus moved into it on open, focus contained within it, Escape to close, and focus returned to the trigger on close.

That is a lot to get right — strong argument for the platform modal rather than a custom one.

71 Your headings are styled divs.Easy

Screen-reader users navigate by heading structure, so styled divs remove their primary navigation mechanism.

Use real h1–h6 in a sensible hierarchy and style them, rather than the reverse.

72 Tab order jumps around the page.Medium

DOM order does not match visual order, often because of CSS reordering — or someone used positive tabindex.

Fix the DOM order; never use positive tabindex values. tabindex="0" and -1 are the only ones you should need.

73 How do you actually test accessibility?Medium

Keyboard only (no mouse), a screen reader (NVDA or VoiceOver), 200% zoom, and an automated checker like axe.

Automated tools catch perhaps a third of real issues; the keyboard pass finds most of the rest and takes two minutes per component.

74 Contrast fails in dark mode only.Medium

Check both themes — 4.5:1 for body text, 3:1 for large text and UI boundaries.

Using SLDS tokens rather than fixed colours generally gets you compliant values in both themes without separate work.

75 A status is shown only by a coloured dot.Easy

Colour alone excludes colour-blind users. Add text, an icon shape, or both.

It also improves clarity for everyone — a red dot means nothing without a legend.

76 Who is responsible for accessibility?Easy

Whoever builds the component. Treating it as a later QA pass means it is never done, because retrofitting is far more expensive than building it right.

Make it a line in the definition of done and in the PR checklist.

77 A screen reader reads the table in a confusing order.Medium

Missing table semantics — proper th elements with scope, a caption, and no layout-only tables.

If you are using a table for layout, stop; use CSS grid or SLDS grid instead.

78 Does accessibility apply to internal-only tools?Easy

Yes — your colleagues include people who use keyboards, screen readers and magnification, and in many jurisdictions it is a legal obligation for internal systems too.

It is also the cheapest usability work available: most accessibility fixes improve the experience for everyone.

Performance, security & judgement (79–100)

79 A record page feels slow and your component is suspected.Medium

Measure before accepting the blame: the Lightning Usage App for EPT, then component-level instrumentation on the page.

The slow component is frequently not the suspected one, and often the cost is the number of components rather than any single one.

80 Five components each call Apex on load.Medium

Five round trips. Consolidate into one call returning a composite payload, or use LDS so they share the cache.

This is usually the single biggest win available on a slow record page.

81 A search box fires Apex on every keystroke.Easy

Debounce — wait a few hundred milliseconds after typing stops before calling.

Without it, a fast typist generates a dozen concurrent requests and you have built a denial-of-service against your own org.

82 You deep-clone a large wire result on every render.Medium

JSON.parse(JSON.stringify(x)) on a big payload is a significant hidden cost, especially inside a getter.

Shape the data once when it arrives, into exactly what the template needs.

83 A third-party library must be loaded.Medium

Bundle it as a static resource and load with loadScript/loadStyle in renderedCallback with a one-time guard.

Versioned, reviewable, CSP-friendly and offline-safe — and re-test under Lightning Web Security, since libraries that failed under Locker often work now.

84 An API key is needed in your component.Easy

It cannot live there — client code is public. Proxy the call through Apex with a Named Credential.

A key in a component is a key in your git history and in every user's browser.

85 You hide a button for unauthorised users. Is that enough?Easy

No. The Apex method remains callable by anyone who can load the component, including guests on a public page.

Enforce CRUD, FLS and sharing server side. Client-side checks are UX.

86 A component must behave differently on mobile.Medium

@salesforce/client/formFactor tells you Small, Medium or Large, and component visibility rules can hide it entirely.

Prefer responsive CSS for layout and reserve form-factor branching for genuinely different behaviour.

87 Your component works in the app and breaks in a community.Medium

Different runtime (LWR versus Aura), different theming, guest-user context, and some APIs unavailable.

Declare the right targets, avoid app-specific APIs, and test as an authenticated and a guest community user.

88 A component needs to work offline.Hard

Offline support means the GraphQL wire adapter and supported device capabilities — not arbitrary Apex, which requires a server.

Design the data access around what is primed to the device. See offline architecture.

89 How do you make a component configurable by admins?Easy

Expose @api properties and declare them in the meta XML as design-time attributes, so App Builder shows them.

Give sensible defaults and validate the values — an admin will eventually type something unexpected.

90 You need to support an unknown object type.Medium

Take the object API name as a design attribute and use a field set or the GraphQL adapter, rather than accepting arbitrary SOQL from the client.

Generic components are useful; generic queries driven by client input are a security surface.

91 How do you test an LWC?Medium

Jest: mount the component, emit wire data, an error and an empty result in three tests, and assert the rendered DOM after awaiting a microtask.

Those three cases catch most real defects and run in milliseconds with no org.

92 A Jest test fails because of a missing module.Medium

Salesforce-specific modules need stubs — configure moduleNameMapper in the Jest config for anything not provided by sfdx-lwc-jest.

Once configured, it applies across the whole project rather than per test.

93 How much Jest coverage is worth having?Medium

Enough to cover the rendering states and the event contracts — data, error, empty, and that the right events fire with the right payloads.

Chasing 100% on template bindings is low value; covering the three states is high value.

94 Should business logic live in the component?Medium

No — keep it in Apex (testable, reusable, enforceable) and keep the component to presentation and interaction.

Logic in JavaScript cannot be reused by a flow, an integration or a trigger, and it is not where your security checks belong.

95 A component has 800 lines of JavaScript.Medium

It is doing too much. Split into a container that handles data and presentational children, and move shared helpers into an ES module.

Smaller components are easier to test, reuse and reason about.

96 Should you build a component or use a base one?Easy

Base component unless it genuinely cannot do the job. You inherit accessibility, keyboard support, mobile behaviour and future design-system updates.

Most custom re-implementations exist because nobody checked what the base component could already do.

97 An LWC or a screen flow for a guided task?Medium

Screen flow if admins should own and change the steps, and the UI needs are within its components. LWC when the interaction is bespoke or the UX must be tightly controlled.

A flow with a custom LWC screen component is often the right middle ground.

98 How do you hand a component over to another team?Medium

Documented public API (properties, methods, events) in the component's own comments, design attributes in the meta XML, Jest tests showing intended usage, and the styling hooks you expose.

The tests are the most honest documentation, because they cannot drift from the behaviour.

99 What makes an LWC production-ready?Hard

Three rendering states (loading, error, empty), server-side security enforcement, no hard-coded colours, keyboard operability and accessible names, cleanup in disconnectedCallback, debounced input, stable iteration keys, and Jest tests for the three states.

That list is about an extra hour and prevents most component defects.

100 One habit that most improves components?Hard

Rendering loading, error and empty states from the start, before the happy path.

It forces you to handle the cases that actually occur in production, and it is the difference between a component users trust and one that looks broken whenever anything is slow.
