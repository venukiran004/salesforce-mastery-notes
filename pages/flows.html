Flow Builder — in detail

Flow is now the single declarative automation tool. Every type, every element, the entry-criteria rules that decide performance, and the best practices that stop a flow org from becoming unmaintainable.

Why Flow replaced everything

Workflow Rules and Process Builder are retired — no new ones can be created, and existing ones must be migrated. Flow is the successor because it can do everything they did plus loops, screens, callouts, error handling and record deletion.

The flow types

Choosing a flow type
🖥️

Screen Flow

Collects input from a user. Surface it on a Lightning page, a record action button, the utility bar, an Experience Cloud site, or embed it in an LWC.

Use case: a guided "Log a Complaint" wizard that asks three questions and creates a Case with the right record type.

⚡

Record-Triggered Flow

Runs on create/update/delete. The workhorse — replaces Workflow and Process Builder.

Use case: when Opportunity hits Closed Won, create a Project record and notify the delivery team.

🕒

Schedule-Triggered Flow

Runs once, daily or weekly at a set time, optionally over every record matching a filter.

Use case: every night, flag Opportunities with a Close Date in the past and still open.

🔗

Autolaunched Flow

No UI, no trigger — invoked by Apex, REST, a process, another flow (subflow) or a button.

Use case: a reusable "Calculate Discount" flow called from three different places.

📡

Platform Event-Triggered Flow

Subscribes to a platform event and runs when a message is published. Always asynchronous.

Use case: an ERP publishes Order_Shipped__e; the flow updates the Order and notifies the customer.

🎼

Flow Orchestration

Chains flows into stages and steps assigned to different users, with its own work-item UI.

Use case: employee onboarding — IT provisions, HR verifies, manager approves, each in sequence.

Before-save vs after-save — the performance decision

This single choice can make a record-triggered flow 10× faster. Know exactly when to use each.

Where each flow runs in the save

Fast Field Update (before-save)

  • Only updates the triggering record
  • No DML, no extra SOQL for the record
  • Cannot: create/delete records, send email, call Apex, use screens, get related records via actions
  • $Record is editable directly
vs

Actions and Related Records (after-save)

  • Record already has an Id
  • Can create/update/delete other records, send emails, call Apex, publish events
  • Supports scheduled paths and asynchronous paths
  • $Record is read-only

Entry criteria — "When to Run the Flow"

OptionBehaviour
Every time a record is updatedRuns even if nothing relevant changed — avoid
Only when a record is updated to meet the conditionBest practice. Equivalent to ISCHANGED logic — fires only on the transition
Formula evaluates to trueFull formula power including ISCHANGED(), PRIORVALUE()

Paths

  • Immediate path — runs in the same transaction.
  • Scheduled path — runs later (X hours/days after a date field or after the trigger). Runs asynchronously as the Automated Process user by default, and gets its own limits.
  • Asynchronous path — runs immediately after the transaction commits, in a separate transaction. This is how you make a callout from a record-triggered flow.
  • Run Asynchronously path also protects the main transaction from a slow external call failing the save.

Bulkification — the #1 flow mistake

Flows are bulkified automatically between interviews, but a DML or Get inside a Loop is executed once per iteration and will blow your limits on a 200-record data load.

❌ Wrong

Loop over Contacts
  └─ Get Records (Account)     ← SOQL in loop
  └─ Assignment
  └─ Update Records            ← DML in loop
End Loop

200 contacts = 200 queries + 200 DML → Too many SOQL queries: 101.

→

✅ Right

Get Records (all Accounts) → collection
Loop over Contacts
  └─ Assignment (build record)
  └─ Add to collection variable
End Loop
Update Records (the collection)  ← ONE DML

Query once before the loop, collect inside, commit once after.

🔥
Never put these inside a Loop Get Records · Create Records · Update Records · Delete Records · Apex actions · Email actions. Build a collection inside the loop and act on it once outside.

Fault paths & error handling

Without a fault path, an error shows the user a raw, unhelpful "An unhandled fault has occurred" screen — and in a record-triggered flow it rolls back the whole transaction.

  • Drag the fault connector from any data element or action.
  • In a screen flow, route to a Screen showing {!$Flow.FaultMessage} in friendly language.
  • In an autolaunched/record-triggered flow, route to a Create Records that logs an Error_Log__c record, or send an email to the admin.
  • Add a Decision before risky elements to prevent predictable failures (null checks, empty collections).
📧
Who gets the error email? By default the flow's last modifier. Change it in Setup → Process Automation Settings → "Send Process or Flow Error Email to" → Apex Exception Email recipients. Do this on day one.

Flow best practices

✅ Do

  • One record-triggered flow per object per timing (one before-save, one after-save) — use Decisions inside to branch. Order is otherwise unpredictable.
  • Use before-save for same-record field updates.
  • Set entry criteria to "only when a record is updated to meet the condition".
  • Always add fault paths.
  • Name elements meaningfully: Get_Open_Cases, not Get_Records_0.
  • Use the Description field on every element — it's your only documentation.
  • Build reusable logic as subflows.
  • Use Custom Metadata for thresholds instead of hard-coded numbers.
  • Test with 200 records, not one.
  • Use the Debug button with "Run as another user" and rollback mode.

❌ Don't

  • DML or Get Records inside a Loop.
  • Hard-code record IDs — they change between orgs. Use Get Records by DeveloperName or Custom Metadata.
  • Build 15 flows on one object.
  • Mix Apex triggers and flows doing the same job on the same object.
  • Use a flow for high-volume batch processing — that's Batch Apex.
  • Forget to deactivate the old Workflow/Process when migrating.
  • Leave "Every time a record is updated" as the entry condition.
  • Ignore the flow's execution context — it runs in system context by default; set "How to Run the Flow" to user context when access must be respected.

Flow ⇄ Apex

Calling Apex from Flow

public class DiscountCalculator {

    public class Request {
        @InvocableVariable(required=true label='Opportunity Id')
        public Id opportunityId;
        @InvocableVariable(label='Requested Discount')
        public Decimal requestedDiscount;
    }
    public class Result {
        @InvocableVariable(label='Approved Discount')
        public Decimal approvedDiscount;
        @InvocableVariable(label='Needs Approval')
        public Boolean needsApproval;
    }

    @InvocableMethod(label='Calculate Discount'
                     description='Caps discount by account tier'
                     category='Sales')
    public static List<Result> calculate(List<Request> requests) {
        // Bulkified: Flow passes ALL records in one call
        Set<Id> oppIds = new Set<Id>();
        for (Request r : requests) oppIds.add(r.opportunityId);

        Map<Id, Opportunity> opps = new Map<Id, Opportunity>([
            SELECT Id, Account.Tier__c FROM Opportunity WHERE Id IN :oppIds
        ]);

        List<Result> results = new List<Result>();
        for (Request r : requests) {
            Result res = new Result();
            Decimal cap = opps.get(r.opportunityId)?.Account.Tier__c == 'Platinum' ? 0.30 : 0.15;
            res.approvedDiscount = Math.min(r.requestedDiscount, cap);
            res.needsApproval    = r.requestedDiscount > cap;
            results.add(res);
        }
        return results;
    }
}
📦
Invocable rules The method must be static, take a List and return a List of the same size and order. One @InvocableMethod per class. Flow calls it once per batch, so write it bulk-safe.

Worked example: Closed Won → Project

  • Type: Record-Triggered Flow on Opportunity, "A record is updated", after save (we're creating another record).
  • Entry conditions: StageName equals "Closed Won", and set "Only when a record is updated to meet the condition" so it fires once.
  • Decision: does the Account already have an active Project? Use Get Records → Decision on "record found".
  • Create Records: build Project__c with Name = Opportunity Name, Account, Start Date = TODAY(), Budget = Amount.
  • Action: Send email alert to the delivery team, and Post to Chatter on the Account.
  • Scheduled path: 7 days after close date, create a follow-up Task for the rep.
  • Fault path on Create Records → Create an Error_Log__c record with {!$Flow.FaultMessage}.
  • Debug with an existing Opportunity, then activate.

Interview questions

1 Name the flow types and give a use case for each.Easy
  • Screen Flow — a guided "Log a Complaint" wizard on a record page.
  • Record-Triggered — on Closed Won, create a Project and notify delivery.
  • Schedule-Triggered — nightly, flag Opportunities past their Close Date.
  • Autolaunched — reusable "Calculate Discount" subflow called from three places.
  • Platform Event-Triggered — an ERP publishes Order_Shipped__e; update the Order.
  • Orchestration — employee onboarding across IT, HR and the manager, in sequence.
2 Before-save vs after-save — how do you decide, and why does it matter?Medium

If you're only setting fields on the record being saved, use before-save ("Fast Field Update"). It edits $Record in memory: no extra DML, no second save, no recursion — roughly 10× faster than the equivalent after-save update.

Use after-save when you need the record's Id or must touch anything else: creating/updating/deleting other records, sending email, calling Apex, publishing events, or using scheduled and asynchronous paths. In after-save, $Record is read-only.

3 A flow fails on a 200-record data load with "Too many SOQL queries: 101". What happened?Medium

There's a Get Records (or a DML element, or an Apex/email action) inside a Loop. Flows bulkify between interviews but every element inside a loop executes once per iteration.

Fix: Get Records once before the loop into a collection, use Assignment inside the loop to build a record collection, then a single Create/Update Records after the loop. Never place data elements or actions inside a Loop.

4 How many record-triggered flows should one object have?Medium

Ideally one before-save and one after-save, branching internally with Decision elements. Salesforce does not guarantee execution order between multiple flows on the same object and timing, so several flows means unpredictable, unreproducible behaviour and repeated evaluation cost. If you must split them, use the flow's Trigger Order field (values in increments of 10) to make the order explicit.

5 A record-triggered flow must call an external REST API. How do you do it legally?Hard

Not on the immediate path — you can't make a callout after uncommitted DML. Put the HTTP callout action on the asynchronous path, which runs in a separate transaction after commit. Alternatively call an @InvocableMethod that enqueues a Queueable implements Database.AllowsCallouts, which also gives you retry logic and proper error handling. Add a fault path either way.

6 What happens if you don't add a fault path?Easy

In a screen flow the user sees a raw "An unhandled fault has occurred" screen with a technical message. In a record-triggered flow the error rolls back the entire transaction, so the user's save fails. An email goes to the flow's last modifier by default — change this in Setup → Process Automation Settings on day one. Route fault paths to a friendly screen, or to a Create Records element logging {!$Flow.FaultMessage} to an Error_Log__c object.

7 When do you stop using Flow and write Apex?Medium

Switch to Apex for: complex branching or recursive algorithms; processing thousands of records (Batch Apex); complex SOQL with joins or aggregates; callouts needing retry and custom error handling; anything requiring real unit tests and version-controlled review. Stay in Flow for simple, admin-maintainable logic, screens, and requirements that change often. The rule that matters most: never build both on the same object doing overlapping work.

8 How do you pass data between Flow and Apex?Medium

Flow → Apex: an @InvocableMethod. It must be static, take a List and return a List of the same size and order, with one invocable method per class. Flow calls it once per batch, so write it bulk-safe. Use @InvocableVariable on request/response inner-class members.

Apex → Flow: Flow.Interview.My_Flow f = new Flow.Interview.My_Flow(inputsMap); f.start(); then read outputs with f.getVariableValue('name'). Flow variables must be marked "Available for input/output".

Quick check

1. You need to set a field on the record being saved, based on other fields of the same record. Best design?
Before-save updates the in-memory record — no extra DML, no recursion, roughly 10× faster than an after-save update of the same record.
2. A flow errors on a data load of 200 records with "Too many SOQL queries: 101". Most likely cause?
Elements inside a Loop run once per iteration. Move Get Records before the loop and use a collection.
3. A record-triggered flow must call an external REST API. How?
You cannot make a callout after uncommitted DML in the same transaction. The asynchronous path runs after commit, which is exactly what's needed.
