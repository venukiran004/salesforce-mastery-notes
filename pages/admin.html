Admin Essentials

The declarative core: how data is modelled and related, how duplicates are stopped, how records are routed and approved, and how a lead becomes cash — end to end.

Objects & fields — the foundation

Standard objects

Ship with the platform: Account, Contact, Lead, Opportunity, Case, Campaign, User, Task, Event. You can add fields but not delete the object.

Custom objects

You create them; API name always ends in __c. Get a tab, page layouts, reports and full API access automatically.

Field types worth knowing

TypeNotes / gotchas
Text / Text Area (Long / Rich)255 / 131,072 chars. Long Text Areas are not filterable in reports and cost heap in Apex.
Picklist / Multi-selectMulti-select is stored semicolon-separated; avoid it — it's painful in reports, SOQL (INCLUDES) and integrations.
Number / Currency / PercentCurrency respects multi-currency; percent stores 0.5 as 50%.
FormulaCalculated on read, never stored, always current. Can't be used in ORDER BY efficiently and isn't indexed unless deterministic.
Roll-Up SummaryCOUNT/SUM/MIN/MAX on children — requires Master-Detail. Max 25 per object.
Lookup / Master-DetailSee Relationships.
Auto NumberRead-only sequence, e.g. INV-{0000}. Not a true unique key across deletes.
External IDMarks a field as a foreign key from another system — enables upsert by that field. Max 25 (7 pre-Spring '20 orgs) per object; automatically indexed.
Encrypted / ShieldClassic encrypted text masks in UI; Shield Platform Encryption encrypts at rest but blocks some filtering.
🔑
External ID + Upsert = the integration superpower Mark Legacy_Id__c as External ID and Unique, then an external system can PATCH /sobjects/Account/Legacy_Id__c/A-1001 — insert or update without ever knowing the Salesforce ID.

Relationships

Relationships are how objects connect. Choosing the wrong type is one of the most expensive mistakes in a data model, because converting Lookup ⇄ Master-Detail later is restricted and sometimes impossible.

The relationship family

Lookup vs Master-Detail — the table you must know

AspectLookupMaster-Detail
Parent required?Optional (can be made required)Always required
Delete behaviourChild stays (field cleared), or optionally blocks deleteCascade delete — children die with the parent
OwnershipChild has its own Owner fieldNo Owner field — inherits from master
Sharing / securityIndependentInherited from the master record
Roll-up summary❌ Not allowed✅ Allowed (up to 25)
ReparentingAllowed by defaultDisallowed unless "Allow reparenting" is ticked
Limit per object40 lookups2 master-detail
Required on layoutNoYes — must be populated at insert
⚠️
Conversion rules You can convert Master-Detail → Lookup only if no roll-up summaries exist on the master. You can convert Lookup → Master-Detail only if every existing child record has that field populated. Plan the model before loading data.

Other relationship types

  • Self relationship — a lookup from an object to itself (Account → Parent Account).
  • Hierarchical — special self-lookup available only on User (the Manager field).
  • External Lookup — child (standard/custom/external) → parent external object, matched on the External Object's External ID.
  • Indirect Lookup — child external object → parent Salesforce object, matched on a custom External ID field. See Salesforce Connect.
🎯
Use case A recruitment app: Job Posting and Candidate are many-to-many, so create a Job Application junction with two master-detail fields. Now you can roll up "Number of Applicants" onto Job Posting, and deleting a Job Posting cleans up its applications automatically.

Record types, page layouts & Dynamic Forms

Record types let one object behave differently for different business processes — different picklist values, different page layouts, different sales processes.

How a user's screen is assembled
  • Page Layout — controls field placement, related lists, buttons. Also controls required/read-only at layout level only.
  • Compact Layout — the highlights panel at the top of a record and mobile cards.
  • Dynamic Forms — replaces the monolithic layout with individually placed fields in Lightning App Builder, each with its own visibility rule. The modern approach.
  • Lightning Record Pages — assign by app, record type and profile; add component visibility filters.

Validation rules

A validation rule fires on save and blocks the record when its formula evaluates to TRUE (think: "error if true").

/* Block closing an Opportunity with no Amount */
AND(
  ISPICKVAL(StageName, "Closed Won"),
  OR(ISBLANK(Amount), Amount <= 0)
)

/* Only allow discount > 20% for managers */
AND(
  Discount__c > 0.20,
  NOT($Permission.Approve_Large_Discount)
)
📐
Useful functions ISCHANGED(), PRIORVALUE(), ISNEW(), ISBLANK(), REGEX(), $User.ProfileId, $Permission.X, $Setup.MyCustomSetting__c.Field__c. ISCHANGED and PRIORVALUE only work in validation rules, workflow and record-triggered flows — not formula fields.

Duplicate rules & matching rules

Two objects working as a pair. The matching rule defines how to detect a duplicate; the duplicate rule defines what to do about it.

Duplicate management flow

Matching rule

  • Choose fields and a matching method per field: Exact or Fuzzy (fuzzy handles "Bob"/"Robert", "Inc."/"Incorporated", typos).
  • Fields are combined with AND/OR logic; a rule can have up to 10 fields.
  • Standard matching rules exist for Account, Contact and Lead — activate them and they're ready.
  • Activation builds a matching index in the background, so it isn't instant.

Duplicate rule

SettingWhat it does
Record-level actionAllow (with optional alert) or Block the save
Alert textCustom message shown to the user
ReportTicking "Report" logs matches so you can report on duplicates
ConditionsOnly run the rule when e.g. Lead Source = Web
Bypass sharing rules"Compare with all records" vs only records the user can see
OperationsRun on Create and/or Edit
⚠️
Big gotchas ① Duplicate rules do not run for records created by Apex/API by default — they do run for API inserts, but not for Database.insert with DmlOptions.duplicateRuleHeader.allowSave = true. ② They don't apply to records created by Lead Convert unless configured. ③ Only one duplicate rule per object runs per operation — order matters.
// Saving through Apex while respecting/overriding duplicate rules
Database.DMLOptions opts = new Database.DMLOptions();
opts.duplicateRuleHeader.allowSave = true;         // save even if flagged
opts.duplicateRuleHeader.runAsCurrentUser = true;  // apply sharing of running user

Lead l = new Lead(LastName='Kumar', Company='Acme');
Database.SaveResult sr = Database.insert(l, opts);

// Detect duplicates without saving
Datacloud.FindDuplicatesResult[] results =
    Datacloud.FindDuplicates.findDuplicates(new List<Lead>{ l });
for (Datacloud.FindDuplicatesResult r : results) {
    for (Datacloud.DuplicateResult dr : r.getDuplicateResults()) {
        for (Datacloud.MatchResult mr : dr.getMatchResults()) {
            System.debug('Matched ' + mr.getMatchRecords().size() + ' records');
        }
    }
}
🎯
Use case Marketing uploads 5,000 leads weekly from three vendors. Activate the standard Lead matching rule on Email (exact) OR First+Last+Company (fuzzy), set the duplicate rule to Allow with alert + Report so uploads don't fail, then work the Duplicate Record Sets report to merge weekly.

🏆
Modern default Use Custom Metadata Types for anything an admin configures that should move between orgs, and Hierarchy Custom Settings only when you need per-user/per-profile values (classic example: trigger bypass switches).

Queues, public groups & ownership

  • Queue — a holding area that can own records (Lead, Case, custom objects, Order). Members pull work from it. Also used as an approver.
  • Public Group — a bundle of users/roles/other groups. Cannot own records; used in sharing rules, list view visibility and folder access.
  • Queue vs Group: queues own records, groups grant access.

Assignment rules

Automatically route new Leads or Cases to the right owner (user or queue).

  • One active rule per object — a rule contains many ordered rule entries.
  • First match wins — entries are evaluated in order and evaluation stops at the first match.
  • Each entry sets an owner (user or queue) plus an optional email template.
  • Default owner — if nothing matches, the record goes to the Default Lead Owner / Default Case Owner set in Support Settings.
Entry pointDoes the rule run?
Lightning UI (checkbox "Assign using active assignment rule")Only if ticked (layout can force it on)
Web-to-Lead / Email-to-Case✅ Always
API / Apex❌ Not by default — you must pass the header
FlowVia the "Assignment Rules" option on the record-create/update element
 
// Firing assignment rules from Apex
Database.DMLOptions dmo = new Database.DMLOptions();
dmo.assignmentRuleHeader.useDefaultRule = true;   // use the active rule
// or target a specific rule:
// AssignmentRule ar = [SELECT Id FROM AssignmentRule WHERE SobjectType='Lead' AND Active=true LIMIT 1];
// dmo.assignmentRuleHeader.assignmentRuleId = ar.Id;
dmo.emailHeader.triggerUserEmail = true;          // send the notification email

Lead l = new Lead(LastName='Rao', Company='Globex', Country='India');
l.setOptions(dmo);
insert l;
🧭
Related routing features Auto-Response Rules send an acknowledgement email to the lead/contact (also first-match-wins). Escalation Rules re-assign or notify when a Case ages past a threshold. Omni-Channel is the modern, skills-based alternative for real-time work routing.

Web-to-Lead

Generates an HTML form you host on your website; submissions create Lead records directly in Salesforce.

Web-to-Lead end to end
<form action="https://webto.salesforce.com/servlet/servlet.WebToLead?encoding=UTF-8" method="POST">
  <input type="hidden" name="oid"        value="00D5j000000XXXX">  <!-- your Org ID -->
  <input type="hidden" name="retURL"     value="https://example.com/thank-you">
  <input type="hidden" name="lead_source" value="Web">
  <input type="hidden" name="recordType" value="0125j000000YYYY">

  <label>Last Name</label>  <input name="last_name"  maxlength="80" required>
  <label>Company</label>    <input name="company"    maxlength="40" required>
  <label>Email</label>      <input name="email"      maxlength="80" type="email">
  <label>Budget</label>     <input name="00N5j00000ZZZZ">      <!-- custom field id -->

  <input type="submit" value="Submit">
</form>

Setup steps

  1. Setup → Web-to-Lead → Enable
  2. Create Form, pick fields
  3. Set default lead creator & auto-response
  4. Give the HTML to your web team
  5. Add reCAPTCHA to stop spam

Limits & gotchas

  • 500 leads/day; overflow is emailed, not lost
  • Field names use the API field ID for custom fields
  • No authentication — anyone can POST, so validate and use reCAPTCHA
  • Only Lead fields; can't create Contacts

Email-to-Case

Turns inbound email into Cases, threading replies onto the same Case.

Standard Email-to-CaseOn-Demand Email-to-Case
Agent required?✅ Email agent installed behind your firewall❌ Nothing to install
Attachment sizeLarger (agent handles it)Limited by email service (25 MB)
Email stays on your server?✅ Yes❌ Routed through Salesforce
RecommendedOnly for strict compliance needs✅ Default choice
  • Enable Email-to-Case in Setup and choose On-Demand.
  • Create a routing address — e.g. support@yourcompany.com. Salesforce gives you a long generated address.
  • Forward your real mailbox to that generated address (verify the forwarding).
  • Set defaults — case origin, priority, record type, and the assignment rule to run.
  • Thread replies — modern orgs use Lightning Threading (header-based); legacy used a thread token in the subject.
  • Handle the extras — auto-response rules for acknowledgements, and Email Message records store the body/attachments.
🎯
Use case Support receives 300 emails a day. Email-to-Case creates the Case, an assignment rule routes billing emails to the Finance queue, an auto-response sends a ticket number, and an escalation rule pings a manager if a P1 case is untouched for 2 hours.
⚠️
Gotcha Email-to-Case runs as the Automated Process user. Anything you build on top (triggers, flows) must not assume a real running user, and field-level security is not applied the way it is for a UI save.

Approval process

A structured, multi-step sign-off with locking, history and escalation — far beyond what a flow alone gives you.

Anatomy of an approval process

The four action buckets

Initial Submission

Runs on submit. Usually locks the record and sets Status = "Pending".

Final Approval

All steps approved. Set status, unlock, notify, fire outbound message.

Final Rejection

Rejected. Set status back, unlock, notify submitter.

Recall

Submitter withdraws. Unlock and reset.

Each bucket can run: Field Update, Email Alert, Task, Outbound Message. (Flows can be triggered indirectly via a field update.)

Key configuration choices

OptionMeaning
Approver typeManager field · queue · specific user(s) · related user field · let submitter choose
Multiple approversUnanimous (all must approve) or First response
Record editabilityAdmins only, or admins + the current approver
Reject behaviourReject the whole request, or go back one step
Delegated approverAllow an assigned delegate to approve on someone's behalf
RecallAllow submitters to recall their own request
 
// Submit a record for approval from Apex
Approval.ProcessSubmitRequest req = new Approval.ProcessSubmitRequest();
req.setObjectId(opp.Id);
req.setComments('Auto-submitted: discount above threshold');
req.setProcessDefinitionNameOrId('Discount_Approval');
req.setSkipEntryCriteria(false);
Approval.ProcessResult result = Approval.process(req);
System.debug(result.isSuccess() + ' → ' + result.getInstanceStatus());

// Approve / reject a pending work item
Approval.ProcessWorkitemRequest wi = new Approval.ProcessWorkitemRequest();
wi.setWorkitemId(workItemId);
wi.setAction('Approve');          // 'Approve' | 'Reject' | 'Removed'
wi.setComments('Looks good');
Approval.process(wi);
📊
Objects behind the scenes ProcessInstance (one per submission), ProcessInstanceStep (completed steps), ProcessInstanceWorkitem (the pending approval). Query these to build "My Pending Approvals" components or approval-cycle-time reports.

Standard objects — a real end-to-end process

This is the process every Salesforce professional should be able to narrate. It ties the standard objects together.

Lead → Cash (Sales Cloud)

Step by step

  • Campaign — marketing runs a webinar. Attendees become Campaign Members.
  • Lead — an unqualified person + company in one record. Web-to-Lead creates it; an assignment rule routes it.
  • Qualification — the rep works the Lead (Tasks, calls). Lead Status moves Open → Working → Qualified.
  • Conversion — one click creates Account (the company), Contact (the person) and optionally Opportunity (the deal). Existing Accounts/Contacts can be matched instead of duplicated. Custom Lead fields must be mapped or the data is lost.
  • Opportunity — the deal, with Amount, Close Date and Stage. Stages drive the Probability and the forecast.
  • Products & Price Books — add Opportunity Line Items from a Price Book to build the Amount from real products.
  • Quote — a formal, versioned offer; sync a quote back to the Opportunity so amounts match.
  • Approval — discount above 20%? An approval process locks the record until a manager signs off.
  • Closed Won — creates an Order or Contract for fulfilment/billing.
  • Service — post-sale issues arrive as Cases via Email-to-Case, routed by assignment rules, escalated by escalation rules, and answered with Knowledge articles.
🔁
Lead conversion gotchas — classic interview material ① Field mapping must be configured per Lead field, and data types must match. ② Triggers fire on Lead (update), Account, Contact and Opportunity in the same transaction — watch your limits. ③ Use Trigger.isUpdate && lead.isConverted && !oldLead.isConverted to detect a conversion. ④ Converted Leads become read-only and are hidden from list views by default.

New→ Assignment rule → Queue→ Agent accepts (Omni-Channel)→ Working / Escalated→ Solution + Knowledge article→ Closed→ CSAT survey

Interview questions

1 How do you model a many-to-many relationship, and what decides the "primary" side?Medium

Create a junction object with two master-detail fields, one to each parent. The first master-detail you create becomes the primary: it controls the junction record's look and feel, its ownership and its sharing, and the junction appears under that parent by default. Deleting either parent deletes the junction records. Classic example: Job Posting ⇄ Candidate joined by Job Application.

2 Walk me through lead conversion. What are the traps?Medium

Conversion creates an Account, a Contact and optionally an Opportunity, or matches existing ones. The Lead becomes IsConverted = true and read-only.

Traps: ① custom Lead fields are lost unless explicitly mapped, and the data types must match; ② triggers fire on Lead, Account, Contact and Opportunity in one transaction, so limits are shared; ③ validation rules on the target objects can block conversion with confusing messages; ④ detect it in Apex with lead.isConverted && !oldLead.isConverted; ⑤ converted leads disappear from most list views by default.

3 Matching rule vs duplicate rule — which does what?Easy

The matching rule defines how to detect a duplicate — which fields to compare and whether each uses exact or fuzzy matching. The duplicate rule defines what to do about a match: Allow with an alert, or Block, plus conditions, which operations it runs on, and whether matches are logged for reporting. You always need both, and only one duplicate rule per object runs per operation.

4 Custom Setting vs Custom Metadata Type vs Custom Label — pick one for each scenario.Medium
  • "Integration endpoint that must differ per environment and deploy with the code" → Custom Metadata Type (records deploy, no SOQL limit consumed, relationships supported).
  • "Let an admin disable a trigger for one integration user during a data load" → Hierarchy Custom Setting (Org → Profile → User resolution, cached, no SOQL).
  • "Error message shown to users that must be translated into French" → Custom Label.

The key discriminator: only Custom Metadata records travel with a deployment; Custom Setting definitions deploy but their data does not.

5 A record saves and you have a validation rule, a before trigger and a before-save flow. What order do they run in?Hard

Before-save flow → before trigger → validation rules. Precisely: system validation (step 3) → record-triggered flows configured for "fast field update" (step 4) → before triggers (step 5) → system and custom validation rules re-run against whatever those set (step 6) → duplicate rules (step 7) → save (step 8).

The practical consequence: a value your before-save flow or before trigger writes is subject to validation rules, which surprises people who expect validation to run first. Full sequence on the Triggers page.

6 Leads created by an integration aren't being routed to queues. Diagnose it.Medium

Assignment rules do not run for API or Apex inserts unless the caller sets the header. In the UI there's a checkbox; through the API you must pass Database.DMLOptions.assignmentRuleHeader.useDefaultRule = true (or a specific rule Id). Web-to-Lead and Email-to-Case always run them. Also check: is the rule active (only one can be), does a higher-ordered entry match first (first match wins), and is the queue's object type correct?

7 Record Type vs Page Layout vs Dynamic Forms — how do they interact?Medium

Record Type represents a business process variant; it filters picklist values and, combined with the user's Profile, determines which Page Layout is assigned. The layout controls field placement, related lists and buttons. Dynamic Forms supersede the monolithic layout in Lightning: fields are placed individually in App Builder, each with its own visibility rule, so you stop creating a new record type purely to hide fields.

8 Queue or Public Group — which do you use, and why?Easy

Queues own records — use one when work needs to sit in a shared bucket until someone takes it (unassigned Cases, Leads), or when you need a group as an approver. Public Groups grant access — they can't own anything, and are used in sharing rules, list view visibility and folder sharing. If the requirement contains the word "assign", think queue; if it contains "let them see", think group.

9 Web-to-Lead is dropping leads on a big campaign day. What's happening and what do you do?Hard

Web-to-Lead is capped at 500 leads per 24 hours. Beyond that, extra submissions are sent to the default lead creator by email rather than created as records — so they look "lost". Options: request a limit increase from Salesforce, or move to the REST API / middleware posting Leads directly, which has no such cap. Either way add reCAPTCHA (the endpoint is unauthenticated), set an assignment rule, and use duplicate rules in "Allow with alert + Report" mode so bulk submissions never hard-fail.

Quick check

1. You need a roll-up summary of child records. What must be true?
Roll-up summaries require Master-Detail. With Lookup you'd use a trigger, a record-triggered flow, or the Rollup Helper style approach.
2. Config values must move from sandbox to production with the deployment. Best choice?
Only Custom Metadata Type records deploy along with metadata. Custom Setting definitions deploy, but their data does not.
3. Leads inserted through Apex aren't being routed to queues. Why?
The UI has a checkbox; the API needs the header explicitly. Web-to-Lead and Email-to-Case always run them.
