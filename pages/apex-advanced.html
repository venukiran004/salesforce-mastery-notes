Advanced Apex

Wrapper classes, dynamic Apex, JSON, interfaces, custom exceptions, design patterns and the best-practice rules that separate demo code from production code.

Wrapper classes

A wrapper class (also called a container class) is a custom Apex class that groups together different data types into a single object — typically an sObject plus extra fields that don't exist on the record.

Why you need one

The classic: a selectable list

public with sharing class AccountSelectionController {

    // The wrapper — usually an inner class
    public class AccountWrapper {
        @AuraEnabled public Account record      { get; set; }
        @AuraEnabled public Boolean isSelected  { get; set; }
        @AuraEnabled public Integer contactCount{ get; set; }
        @AuraEnabled public String  healthLabel { get; set; }

        public AccountWrapper(Account a, Integer contacts) {
            this.record       = a;
            this.isSelected   = false;
            this.contactCount = contacts;
            this.healthLabel  = contacts > 5 ? 'Healthy' : 'At Risk';
        }
    }

    @AuraEnabled(cacheable=true)
    public static List<AccountWrapper> getAccounts() {
        List<AccountWrapper> wrappers = new List<AccountWrapper>();
        for (Account a : [SELECT Id, Name, Industry, AnnualRevenue,
                                 (SELECT Id FROM Contacts)
                          FROM Account
                          WHERE AnnualRevenue != null
                          WITH USER_MODE
                          ORDER BY AnnualRevenue DESC
                          LIMIT 200]) {
            wrappers.add(new AccountWrapper(a, a.Contacts.size()));
        }
        return wrappers;
    }
}
🔖
Rules for LWC-facing wrappers Every field you want in JavaScript must be @AuraEnabled and public. The class itself must be public (or global in a package). Inner classes are fine and keep things tidy. Use { get; set; } properties or plain public fields — both serialise.

Wrapper + Comparable for custom sorting

public class OpportunityScore implements Comparable {
    public Opportunity opp;
    public Decimal score;

    public OpportunityScore(Opportunity o, Decimal s) { opp = o; score = s; }

    // Required by Comparable: -1 (before), 0 (same), 1 (after)
    public Integer compareTo(Object other) {
        OpportunityScore o = (OpportunityScore) other;
        if (score == o.score)  return 0;
        return score > o.score ? -1 : 1;        // descending
    }
}

List<OpportunityScore> scores = buildScores();
scores.sort();                                   // uses compareTo automatically
🎯
Use cases for wrappers ① A datatable with checkboxes ("select accounts to merge"). ② Combining data from two objects into one row (Account + its latest Case). ③ Adding calculated values (age, health score, RAG status) without creating formula fields. ④ Shaping a JSON response for an external API. ⑤ Sorting by something SOQL can't order by.

Advanced concepts

Dynamic Apex & Schema describe

Write code that adapts to metadata at runtime instead of hard-coding object and field names.

// ---------- Global describe: every object in the org ----------
Map<String, Schema.SObjectType> globalDescribe = Schema.getGlobalDescribe();
Schema.SObjectType accType = globalDescribe.get('Account');

// ---------- Object describe ----------
Schema.DescribeSObjectResult d = accType.getDescribe();
System.debug(d.getLabel());          // Account
System.debug(d.getKeyPrefix());      // 001
System.debug(d.isCreateable());      // CRUD check
System.debug(d.isAccessible());

// ---------- Field describe ----------
Map<String, Schema.SObjectField> fieldMap = d.fields.getMap();
for (String apiName : fieldMap.keySet()) {
    Schema.DescribeFieldResult f = fieldMap.get(apiName).getDescribe();
    System.debug(f.getLabel() + ' | ' + f.getType() + ' | len=' + f.getLength()
                 + ' | updateable=' + f.isUpdateable() + ' | accessible=' + f.isAccessible());
}

// ---------- Picklist values ----------
for (Schema.PicklistEntry pe : Account.Industry.getDescribe().getPicklistValues()) {
    System.debug(pe.getLabel() + ' = ' + pe.getValue() + ' active=' + pe.isActive());
}

// ---------- Record types ----------
Map<String, Schema.RecordTypeInfo> rts = accType.getDescribe().getRecordTypeInfosByDeveloperName();
Id b2bRtId = rts.get('B2B').getRecordTypeId();

// ---------- Generic, object-agnostic code ----------
public static List<sObject> getRecent(String objectName, Integer howMany) {
    Schema.SObjectType t = Schema.getGlobalDescribe().get(objectName);
    if (t == null) throw new IllegalArgumentException('Unknown object: ' + objectName);

    String soql = 'SELECT Id, Name FROM ' + String.escapeSingleQuotes(objectName) +
                  ' ORDER BY CreatedDate DESC LIMIT :howMany';
    return Database.query(soql);
}

// ---------- Dynamic instantiation ----------
sObject rec = accType.newSObject();
rec.put('Name', 'Dynamic Account');
rec.put('Industry', 'Retail');
insert rec;
String name = (String) rec.get('Name');

// ---------- Dynamic class loading (plug-in pattern) ----------
Type handlerType = Type.forName('MyNamespace', 'DiscountStrategyPremium');
DiscountStrategy strategy = (DiscountStrategy) handlerType.newInstance();
🐌
Performance Schema.getGlobalDescribe() is expensive in orgs with thousands of objects — it can consume real CPU time. Prefer Account.SObjectType.getDescribe() when you know the object, and cache describes in a static variable for the transaction.

JSON

// ---------- Serialize ----------
Account a = [SELECT Id, Name, Industry FROM Account LIMIT 1];
String json       = JSON.serialize(a);
String prettyJson = JSON.serializePretty(a);
String noNulls    = JSON.serialize(a, true);           // suppress nulls

// ---------- Deserialize (typed) ----------
Account back = (Account) JSON.deserialize(json, Account.class);
List<Account> list = (List<Account>) JSON.deserialize(jsonArray, List<Account>.class);

// ---------- Deserialize (untyped) — for unknown/awkward shapes ----------
Map<String, Object> parsed = (Map<String, Object>) JSON.deserializeUntyped(responseBody);
List<Object> records = (List<Object>) parsed.get('records');
for (Object o : records) {
    Map<String, Object> rec = (Map<String, Object>) o;
    System.debug(rec.get('id') + ' → ' + rec.get('status'));
}

// ---------- Strict deserialize: throws on unknown attributes ----------
MyDto dto = (MyDto) JSON.deserializeStrict(body, MyDto.class);

// ---------- Handling reserved words / different names ----------
public class OrderDto {
    public String orderNumber;
    public Decimal total;
    // JSON key "class" is a reserved word — deserializeUntyped, or rename in a wrapper
}

// ---------- Streaming generator: full control of output ----------
JSONGenerator gen = JSON.createGenerator(true);
gen.writeStartObject();
gen.writeStringField('accountName', a.Name);
gen.writeNumberField('revenue', 150000);
gen.writeFieldName('contacts');
gen.writeStartArray();
for (Contact c : contacts) {
    gen.writeStartObject();
    gen.writeStringField('name', c.LastName);
    gen.writeEndObject();
}
gen.writeEndArray();
gen.writeEndObject();
String payload = gen.getAsString();

Custom exceptions

// Any class ending in "Exception" and extending Exception
public class InvoiceException extends Exception {}

public class ValidationException extends Exception {
    public List<String> failedFields = new List<String>();
}

// Throwing
if (invoice.Amount__c <= 0) {
    throw new InvoiceException('Amount must be positive for ' + invoice.Name);
}

// Chaining the cause
try {
    doWork();
} catch (DmlException e) {
    throw new InvoiceException('Could not save invoice', e);   // preserves the stack
}

// Catching in the right order — specific first
try {
    riskyOperation();
} catch (DmlException e) {
    System.debug(e.getDmlMessage(0) + ' on record ' + e.getDmlId(0)
                 + ' field ' + e.getDmlFieldNames(0));
} catch (QueryException e) {
    System.debug('Bad query: ' + e.getMessage());
} catch (CalloutException e) {
    System.debug('Integration down: ' + e.getMessage());
} catch (Exception e) {
    System.debug(e.getTypeName() + ': ' + e.getMessage()
                 + '\nLine ' + e.getLineNumber() + '\n' + e.getStackTraceString());
    throw e;                                   // rethrow if you can't handle it
} finally {
    cleanup();                                 // always runs
}
🚫
You cannot catch these LimitException (governor limits) is uncatchable — you cannot try/catch your way out of "Too many SOQL queries". Neither can you catch assertion failures. Design within limits instead; check Limits.getQueries() proactively.

Custom iterator

public class EvenNumberIterator implements Iterator<Integer>, Iterable<Integer> {
    private Integer current = 0, max;
    public EvenNumberIterator(Integer max) { this.max = max; }

    public Boolean hasNext() { return current + 2 <= max; }
    public Integer next()    { current += 2; return current; }
    public Iterator<Integer> iterator() { return this; }
}

for (Integer i : new EvenNumberIterator(10)) System.debug(i);   // 2 4 6 8 10

Static vs instance — and initialisation order

public class Counter {
    public static Integer transactionCount = 0;     // ONE per transaction
    public Integer instanceCount = 0;               // one per object

    static  { transactionCount = 100; }             // static initialiser — runs once
    { instanceCount = 5; }                          // instance initialiser — runs per new

    public Counter() { instanceCount++; }           // constructor runs last
}
  • Static variables live for the whole transaction and are shared by every instance — that's why they work as recursion guards and caches.
  • Statics are not shared between transactions, users or async jobs. A @future call starts with fresh statics.
  • Order: static initialiser → instance initialiser → constructor.

Platform Cache — a real cross-transaction cache

// Org cache: shared by all users. Session cache: per user session.
Cache.OrgPartition part = Cache.Org.getPartition('local.Config');

String value = (String) part.get('exchangeRate');
if (value == null) {
    value = fetchFromExternalService();
    part.put('exchangeRate', value, 3600);           // TTL in seconds (max 48h org / 8h session)
}
part.remove('exchangeRate');
Boolean cached = part.contains('exchangeRate');

Design patterns that matter in Apex

Selector / Service / Domain

Separation of concerns (the "Enterprise Patterns"/fflib approach):

  • Selector — all SOQL for an object
  • Domain — behaviour of records of one object (trigger logic)
  • Service — cross-object business processes
  • Unit of Work — batches DML and manages relationships

Singleton

public class Config {
  private static Config inst;
  private Config() { load(); }
  public static Config get() {
    if (inst == null) inst = new Config();
    return inst;
  }
}

One expensive setup per transaction — ideal for configuration and describe caching.

Strategy

An interface plus interchangeable implementations selected at runtime (often via Custom Metadata + Type.forName). Perfect for "different discount rules per country".

Factory

A class that decides which concrete implementation to build, keeping new out of your business logic and making mocking trivial.

Apex best practices

The layered architecture to aim for

✅ Always

  • Bulkify — every method takes and returns collections
  • One trigger per object, logic in a handler
  • Query with WITH USER_MODE and DML with AccessLevel.USER_MODE where the user's access should apply
  • Use Database.method(list, false) when partial success is acceptable, and log the failures
  • Declare classes with sharing or inherited sharing
  • Use constants and Custom Metadata instead of magic numbers and hard-coded Ids
  • Handle exceptions where you can act on them; log the rest to a custom object
  • Name things for what they do: OpportunityDiscountService.applyTierCap()
  • Write meaningful assertions with messages: Assert.areEqual(exp, act, 'why')
  • Keep methods short and single-purpose

❌ Never

  • SOQL, SOSL, DML or callouts inside a loop
  • @isTest(SeeAllData=true) unless you have no choice
  • Hard-coded record Ids, profile Ids or usernames
  • Empty catch blocks that swallow errors
  • List<Account> a = [SELECT …]; a[0] without a size check
  • Business logic in the trigger body
  • Assuming Trigger.new.size() == 1
  • without sharing "to make it work"
  • Duplicating logic between a flow and a trigger on one object
  • Chasing 75% coverage with assertion-free tests

Interview questions

1 What is a wrapper class and when did you last need one?Easy

A custom Apex class that bundles an sObject with data that isn't a field on it — a selection checkbox, a computed score, values from a second object. It exists because you can't invent fields at runtime and shouldn't pollute the schema with UI-only state.

Typical answer: "a datatable where users tick rows to merge, with a calculated health label per row. The wrapper had @AuraEnabled public Account record, isSelected and healthLabel, returned from a cacheable=true Apex method." Every field exposed to LWC must be public and @AuraEnabled.

2 How do you sort a list by two fields, descending then ascending?Medium

Implement Comparable on a wrapper and handle both keys in compareTo:

public Integer compareTo(Object other) {
    OppWrapper o = (OppWrapper) other;
    if (amount != o.amount) return amount > o.amount ? -1 : 1;   // desc
    return closeDate < o.closeDate ? -1 : (closeDate == o.closeDate ? 0 : 1);  // asc
}

Then call list.sort(). Prefer ORDER BY in SOQL when the fields are queryable — Comparable is for computed values SOQL can't order by.

3 Why can't you catch a LimitException?Medium

Because the platform must be able to terminate a runaway transaction unconditionally — if you could catch "Too many SOQL queries" you could keep consuming shared resources. It's uncatchable by design, as are assertion failures in tests.

The correct approach is prevention: check Limits.getQueries() / getCpuTime() before an expensive block and hand off to a Queueable when you're near the ceiling.

4 Explain static variables and give a legitimate use.Medium

A static exists once per transaction, shared across all instances of the class. It is not shared across transactions, users or async jobs — a @future call starts with fresh statics.

Legitimate uses: a recursion guard in a trigger, and caching an expensive Schema.describe or configuration lookup for the duration of the transaction. Initialisation order is: static initialiser → instance initialiser → constructor.

5 When is Dynamic Apex worth the complexity, and what does it cost?Hard

Worth it for genuinely generic components: a Field-Set-driven table, an object-agnostic audit framework, or a strategy pattern where Type.forName() instantiates a handler named in Custom Metadata.

Costs: Schema.getGlobalDescribe() is expensive in large orgs and counts against the 100 describe limit — cache it in a static; dynamic SOQL loses compile-time safety and opens injection risk unless you bind; and the code is harder to read and debug. If you know the object, use Account.SObjectType.getDescribe() instead of the global describe.

6 Compare with sharing, without sharing and inherited sharing.Medium

with sharing enforces the running user's record access (not FLS or CRUD). without sharing runs in system context — a deliberate elevation, e.g. a service that must aggregate across all records. inherited sharing adopts the caller's mode and defaults to with sharing when entered directly, which makes it the safest choice for reusable service classes.

The trap: a class with no keyword inherits from its caller, and runs without sharing when it is itself the entry point. Omitting the keyword is a bug, not a style preference. Triggers always run in system context regardless.

7 How would you design a rule engine where discount caps vary by country and change often?Hard

Strategy pattern driven by Custom Metadata. Define an interface DiscountStrategy with Decimal cap(Opportunity o). Create one implementing class per rule variant. Add a Discount_Rule__mdt record per country holding the Apex class name, then resolve it at runtime:

Discount_Rule__mdt cfg = Discount_Rule__mdt.getInstance(countryCode);
DiscountStrategy s = (DiscountStrategy) Type.forName(cfg.Apex_Class__c).newInstance();
Decimal cap = s.cap(opp);

Admins change thresholds without a deploy, new countries need only a metadata record, and each strategy is unit testable in isolation.

8 What's the difference between JSON.deserialize, deserializeUntyped and deserializeStrict?Medium

deserialize(json, MyType.class) maps into a typed class and ignores unknown keys. deserializeStrict does the same but throws if the JSON contains a field your class doesn't declare — useful to detect an upstream API change. deserializeUntyped returns Map<String, Object> / List<Object> and needs casting as you walk it — the right choice for unpredictable payloads, or when a JSON key collides with an Apex reserved word such as class or currency.

Quick check

1. You need a datatable with checkboxes plus a calculated "risk" label per row. What do you build?
Selection state and derived values are UI concerns — a wrapper keeps them out of your schema.
2. Which of these can you not catch in Apex?
Governor limit exceptions are uncatchable by design — the platform must be able to terminate a runaway transaction.
3. Your code must work for any object name passed in at runtime. Which feature?
Schema describe plus dynamic SOQL lets one class serve any object. Add String.escapeSingleQuotes or bind maps to stay injection-safe.
