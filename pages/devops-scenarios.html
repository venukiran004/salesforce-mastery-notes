Deployment & DevOps — 100 Scenarios

Deployment mechanics and test levels, scratch orgs and packaging, CI authentication, sandbox strategy, the config that is data, rollback, and the metrics that tell you whether the pipeline works.

📚
How to use this Answer out loud in ninety seconds, then open the answer. Concepts on Deployment & DevOps, its Advanced section, and Branching Strategy.

Deployment mechanics (1–20)

1 A production deployment takes three hours.Medium

Full-org deployment with all tests. Two changes fix it: delta deployments (manifest generated from the diff since the last release tag) and validate-then-quick-deploy.

Run the tests in a validation-only deployment ahead of the window, then promote that validated build without re-running them — minutes instead of hours.

2 How long is a validated deployment valid for?Easy

A limited window (commonly 10 days) during which you can quick-deploy it without re-running tests — provided nothing else changed in the target org.

That window is what makes a short production release possible, so validate early in the day.

3 Quick deploy is unavailable after validation.Medium

Something changed in the target org since you validated, or the window expired, or the validation did not run the required test level.

Re-validate. The eligibility rules are strict precisely because the point is that the tests have already passed.

4 Which test level for a normal release?Easy

RunLocalTests — everything except managed-package tests. That is the sensible production default.

RunAllTestsInOrg only before a major package upgrade, when you need the package's tests to pass too.

5 A hotfix needs to deploy in ten minutes.Medium

RunSpecifiedTests naming the tests that cover the changed classes — fast, but the deployment is rejected if coverage of those classes is insufficient.

Which is an argument for having meaningful per-class coverage before you need a hotfix.

6 The deployment fails on code coverage.Medium

You need 75% org-wide and every trigger covered — and with RunSpecifiedTests, sufficient coverage of the specific classes being deployed.

The fix is a real test, not a test that merely executes lines. Set a per-class floor in CI so this is caught at PR time instead.

7 A field deletion is in your deployment.Hard

Destructive changes go in a separate destructiveChanges.xml, applied pre- or post-deployment — never automatically, and never without explicit review.

They take the data with them and nothing rolls back transactionally. Keep a per-release list of irreversible changes.

8 Can you roll back a deployment?Hard

Not transactionally. "Roll back" means deploying the previous tagged state and manually reversing what cannot be redeployed: deletions, data changes, picklist values, irreversible settings.

A tag per release makes the first half trivial; the documented irreversible list makes the second half a judgement rather than a discovery.

9 A component is not deployable at all.Medium

Check the Metadata Coverage Report before promising automation — not everything is supported, and the gaps become documented manual steps in the runbook.

Discovering a coverage gap during the release is how a two-hour window becomes an evening.

10 The deployment succeeded but the feature does not work.Medium

Missing data: custom setting rows, Custom Metadata records, queue members, picklist assignments per record type, or package configuration.

Write an idempotent post-deployment Apex script that seeds what is required and can be re-run safely.

11 Scheduled jobs break after every release.Medium

Deployments can leave schedules pointing at changed logic, or block changes to classes referenced by active jobs.

Build an idempotent scheduler setup method that aborts and recreates every schedule, run it post-deployment, and verify CronTrigger afterwards.

12 A change set is missing dependencies.Easy

Change sets do not resolve dependencies for you — you add each component by hand and discover omissions on deployment.

That is the core argument for source-driven deployment, where the manifest is generated from the diff.

13 Should you still use change sets?Medium

They are a legitimate intermediate state for a declarative-only team, with git providing history and review.

But they do not scale: no delta generation, no automation, manual dependency management, and no rollback reference. Treat them as a step on the way, not a destination.

14 A deployment overwrites an admin's production fix.Hard

Config drift: production had changes that were not in your branch, and a full deployment steamrolled them.

Add nightly drift detection (retrieve production, diff against main, fail loudly), capture the change into a config/* branch, and give admins a sanctioned fast path. See drift.

15 Delta or full deployment?Medium

Delta for speed and a scoped blast radius; full deployments get slower as the org grows and overwrite undocumented production changes.

The catch is that delta hides drift rather than steamrolling it — so pair it with scheduled drift detection.

16 How do you generate a delta manifest?Medium

From the git diff between the last release tag and HEAD, with a tool that also produces the destructive manifest (sfdx-git-delta is the common community plugin).

Hand-maintaining package.xml guarantees omissions and merge conflicts.

17 A deployment fails with an unrelated test failure.Medium

A pre-existing broken test, or a test that depends on org data that changed. Either way it is blocking you now.

Fix or delete it deliberately — never leave a red test, because the next real failure will be invisible among the noise.

18 You need to deploy to five orgs.Medium

One pipeline, parameterised per target, with the same artefact deployed to each — plus per-org configuration data seeded by script.

Deploying from different branches to different orgs is how they diverge permanently.

19 What belongs in a release runbook?Medium

Pre-checks, the validation step, the deploy command, post-deployment scripts (schedules, config data), verification steps, the rollback position, and the irreversible-change list.

Written before the release, not reconstructed during it.

20 How do you verify a deployment actually worked?Medium

A post-deployment smoke suite: auth, key endpoints, a read, a write with cleanup, and limit health — plus verification that page assignments and schedules are correct.

"The deployment reported success" is not verification. See Newman in CI.

Scratch orgs & environments (21–40)

21 Your scratch org does not look like production.Medium

The definition file declares edition, features and settings, and yours does not match. Derive it from an org shape rather than guessing.

Then an org snapshot turns a 20-minute setup into a 2-minute spin-up, which transforms developer onboarding.

22 A developer needs data to work with.Easy

Seed it: sf data tree import with a plan file, kept in the repo so every scratch org gets the same baseline.

A scratch org with no data is useless for realistic testing, and hand-creating records wastes an hour per developer.

23 What is source tracking actually doing?Medium

The org remembers what changed locally and remotely, so retrieve/deploy work without a manifest — and conflicts are reported rather than silently overwritten.

deploy preview and retrieve preview are the commands worth habituating.

24 Which sandbox type for UAT?Medium

Partial Copy with a good sandbox template is usually the right balance — realistic data shape, 5-day refresh.

Full Copy for performance testing and data-migration rehearsal, where real volume matters and the 29-day refresh is acceptable.

25 You have one Full sandbox and three competing needs.Medium

Sequence them against the refresh cycle and be explicit with the business about the trade-off — performance testing and migration rehearsal need volume; UAT mostly needs shape.

If the programme genuinely needs more, another Full sandbox is cheaper than a failed go-live.

26 After a refresh, customers received test emails.Hard

Deliverability was left at All Email with real data present. The fix is a scripted post-refresh checklist run before anyone logs in.

Set deliverability to System Email Only first, mask PII, repoint named credentials, deactivate scheduled jobs and integration users, disable outbound messages, then reseed config data.

27 A developer sandbox cannot hold the migration test data.Easy

Developer sandboxes are metadata-only with small data storage. Use them for transformation logic; use a Full sandbox for the timed rehearsal.

Testing a 2-million-record load in a Developer sandbox tells you nothing except that storage limits exist.

28 How do you keep sandboxes from diverging?Medium

Deploy to them from the pipeline rather than by hand, refresh on a schedule, and run the same config-data seeding script in each.

A sandbox nobody deploys to becomes a snapshot of whenever it was last touched, and then nothing tested there means anything.

29 Scratch org or developer sandbox?Medium

Scratch orgs for source-driven work: disposable, defined in version control, fast to recreate, ideal per feature branch.

Developer sandboxes when you need a persistent environment or the org's existing configuration as a starting point.

30 A scratch org expired mid-feature.Easy

They have a maximum duration. Recreate it from the definition file and re-seed — which is only painless if the setup is fully scripted.

If recreating is painful, that is a signal the setup is not in version control.

31 You need a sandbox with production-like volume.Medium

Full Copy, or Partial Copy plus a generated data load to reach realistic volumes on the objects that matter.

Query selectivity and lock contention only reproduce at volume, which is why performance testing in a Developer sandbox is misleading.

32 Environment Hub — is it worth it?Medium

Once you have more than a handful of connected orgs, yes — central visibility and sandbox creation.

For two sandboxes it is overhead. The decision is about the number of environments you are tracking, not sophistication.

33 How do you onboard a developer in under an hour?Medium

Clone, create a scratch org from the definition (or snapshot), deploy, assign a permission set, import seed data, run a post-setup Apex script.

All scripted, in the repo. If onboarding needs a human walkthrough, the environment setup is not reproducible.

34 Two developers' scratch orgs behave differently.Medium

Different definition files, different seed data, or one of them changed settings by hand.

The definition and the seed data belong in version control precisely so this cannot happen.

35 Should production access be restricted?Medium

Yes — remove human metadata-edit rights and deploy as a service account, once the sanctioned fast path is genuinely fast.

Locking the door before building the corridor just moves the problem somewhere you cannot see it.

36 How do you handle an urgent admin change in production?Medium

Give them a hotfix branch and a twenty-minute pipeline. People bypass process when process is slow.

Then capture anything that did happen directly into a config/* branch so git matches production again.

37 What should a post-refresh script cover?Medium

Deliverability first, then PII masking, endpoint repointing, deactivating schedules and integration users, disabling outbound messages, resetting the users you need, and reseeding config data.

Automate it as an Apex class. The one time someone forgets, real customers receive test emails.

38 A sandbox refresh lost your work.Easy

A refresh replaces the sandbox. Anything not in version control is gone.

That is the clearest argument for source control that exists, and it is usually learned the hard way.

39 How many environments do you actually need?Medium

At minimum: per-developer (scratch or dev sandbox), one integration, one UAT, production. More only if parallel release trains genuinely require it.

Your branch topology cannot exceed your org topology, so this decision constrains everything downstream.

40 A migration needs a dry run.Medium

Full sandbox, production-shaped data, timed, with row counts and checksums compared before and after — and the rollback rehearsed too.

Unit tests cannot cover this; the risk is volume, duration and data shape.

Packaging (41–56)

41 Unlocked, managed or unmanaged?Medium

Unlocked for modularising your own org — versioned, upgradeable, no namespace required. Managed for ISV distribution with IP protection. Unmanaged has no upgrade path at all.

Get org-based source control working reliably before decomposing into packages.

42 A package build fails on a dependency cycle.Hard

The dependency graph must be acyclic. Break the cycle by extracting the shared pieces into a lower-level package both depend on.

Most of the work of decomposing an org is breaking cycles; the packaging mechanics are the easy part.

43 A subscriber edited your unlocked package's metadata.Medium

Unlocked packages permit it — both the feature and the risk, since their change is drift your next version may overwrite.

Document what is safe to change, and consider a managed package if components must be immutable.

44 Ancestry is wrong and subscribers cannot upgrade.Hard

Managed packages declare an ancestry so upgrades know their lineage; getting it wrong produces versions that cannot install over what subscribers already have.

A packaging-configuration problem worth getting right before the first release.

45 Your package's tests fail in a subscriber org.Hard

They depend on org-specific data or configuration. Package tests run in the subscriber's org on upgrade, where your assumptions about records, picklists and automation do not hold.

Build all data in the test, never use SeeAllData, and tolerate their automation firing on your inserts.

46 How do you version a package?Easy

Semantic versioning with a build number per promoted version, and a tag in git matching each released version.

The tag is how you reproduce what a subscriber is running, which you will need during a support case.

47 A package needs configuration data in the subscriber org.Medium

Custom Metadata records can ship with the package; most other configuration is data and cannot.

Provide a post-install script or setup page that seeds required rows idempotently, and a test that fails clearly when configuration is missing.

48 Should you package everything in the org?Medium

No. Decompose where boundaries are genuinely clean and ownership is clear — and leave the rest in an unpackaged directory.

A forced decomposition of tangled metadata produces packages that cannot be deployed independently, which is all cost and no benefit.

49 How do you test a package upgrade?Medium

Install the previous version in a sandbox with realistic data and automation, then upgrade — exercising the paths subscribers actually use.

For configuration-heavy packages, recalculate a golden set with known expected outputs afterwards.

50 A global method needs removing.Hard

In a managed package it is a permanent contract: deprecate it, ship the replacement alongside, and remove it only in a major version with a documented migration.

Default to public and expose global deliberately and rarely.

51 Two of your packages need to share internal code.Medium

@namespaceAccessible — visible to other packages in your namespace without exposing it to subscribers.

That is the right tool for the shared "common" package you extract when breaking cycles.

52 An installed package is consuming your CPU budget.Hard

Its triggers run in your transaction and CPU is shared, even though some limits are namespace-scoped.

Prove it from CUMULATIVE_LIMIT_USAGE, which attributes consumption per namespace, then slim your own logic or take the evidence to the vendor.

53 How do you evaluate a package before installing?Medium

Install in a sandbox and check what it adds to your objects (triggers, flows, validation rules, fields), how much CPU it adds, what data leaves your org, the upgrade path, and what uninstalling leaves behind.

Then plan the exit before you depend on it.

54 Uninstalling a package left data behind.Medium

Expected — uninstall does not always remove data, and sometimes leaves metadata.

Know what removal looks like before you commit, and keep the cleanup steps in your notes. "We'll just uninstall it" is rarely as clean as assumed.

55 Package licences expired silently.Medium

Per-user package licences need assigning and auditing, and they expire without fanfare.

Put a licence true-up in your monthly platform health review alongside Salesforce, permission set and feature licences.

56 When is package-based development premature?Medium

Before you have reliable source control, a working pipeline, meaningful test coverage and clean module boundaries.

Doing both migrations at once is how programmes stall for a year. Get org-based GitFlow boring first, then decompose.

CI/CD (57–78)

57 How should CI authenticate to an org?Easy

JWT bearer with a certificate on a Connected App and the key in CI secrets, or an auth URL stored as a single secret.

Never a password or an interactive login. And use a dedicated deployment user, not a named human's admin account.

58 Your CI certificate expires next month.Medium

Rotate with overlap: generate the new one, add it, switch, retire the old. Put every expiry in a shared calendar with an owner.

An expired CI certificate on release night is a predictable, self-inflicted outage.

59 What gates belong on a feature PR?Medium

Fast ones: lint, LWC Jest, Apex static analysis, and unit tests in a scratch org — an answer in a couple of minutes.

Feedback slower than ten minutes gets batched around, which defeats CI.

60 What gates belong on a PR into main?Medium

Everything: validation deploy against production, the real test level, drift check, up-to-date-with-main, two reviewers and no direct pushes.

The gate should match the blast radius of the target branch. A PR into main should be slow, thorough and boring.

61 Static analysis returns 300 findings.Medium

Set a severity threshold that fails the build, fix those, and baseline the rest so new code cannot add to the pile.

An unprioritised list of 300 gets ignored; a gate plus a non-regression baseline gets the codebase improving steadily.

62 Validation takes 40 minutes on every PR.Medium

Tier it: static analysis and Jest on every PR, delta validation for develop, full validation only for release branches.

And use validate-then-quick-deploy so the production window is minutes rather than hours.

63 How do you detect config drift?Hard

A scheduled job that retrieves production metadata, diffs it against main, and fails loudly on divergence.

It is the single highest-value piece of automation in a Salesforce pipeline, and its run history is the artefact an auditor actually wants.

64 What do you do when drift is detected?Medium

Retrieve the change into a config/* branch, PR it into main like any other change, then merge down to develop and every open release branch the same day.

Skip the merge-down and your next release reverts it again.

65 How do you deploy the config that is data?Hard

A scripted, version-controlled migration — export/import or a seeding job — run as part of the release, with references re-pointed by name because Ids differ per org.

CPQ, Field Service, territories, operating hours and scheduling policies all fall here. See CPQ.

66 Should the pipeline deploy to production automatically?Medium

Eventually, once the gates have earned trust — and with a manual approval step for the promotion in most enterprises.

Automate the tiers in order, production last. Automating production first is how a pipeline loses its mandate.

67 A pipeline secret leaked.Hard

Revoke the OAuth tokens from the Connected App first (fastest), rotate the certificate or secret, then update the pipeline's store.

Removing it from the repo is insufficient — git history retains it, so revocation is the action that actually closes it.

68 How do you test LWC in CI?Easy

Jest via sfdx-lwc-jest — no org required, so it runs in seconds on every PR.

Cover the three rendering states (data, error, empty) and the event contracts; that catches most real component defects.

69 How do you test flows in CI?Medium

Flow Tests for record-triggered flows, run alongside Apex tests.

In orgs where flows carry most of the logic, this is the application's test suite, and its absence is a bigger risk than low Apex coverage.

70 A post-deployment smoke test is failing.Medium

Good — that is it working. Check whether it is the deployment, missing config data, a page assignment, or a broken schedule.

A smoke suite that has never failed is probably not testing anything.

71 How do you keep CI runs fast as the org grows?Medium

Delta validation rather than full, specified tests where coverage allows, parallel jobs for independent checks, and a small smoke set.

Measure the pipeline duration as a metric — when it creeps past ten minutes for PRs, developers start working around it.

72 Tests fail intermittently in CI.Hard

Usual causes: dependence on real SOSL indexing, on today's date, on unsorted query order, on static state, or parallel test contention.

Fix them as high priority — a suite people distrust provides no protection, and flaky tests get disabled.

73 Should CI run against a scratch org or a sandbox?Medium

Scratch org for PR validation — clean, disposable, reproducible from the definition file.

A sandbox for anything needing realistic data or integration endpoints, and for the validation against production itself.

74 How do you handle a package dependency in CI?Medium

Install the dependency into the scratch org as part of setup, pinned to a version, before deploying your source.

Unpinned dependencies make builds non-reproducible, and "it worked yesterday" becomes unexplainable.

75 What should fail a build versus warn?Medium

Fail: test failures, validation failures, coverage below the per-class floor on changed classes, high-severity static findings.

Warn: style, lower-severity findings, documentation gaps. Everything failing means nothing is prioritised.

76 Nobody trusts the pipeline.Medium

Usually flaky tests, slow feedback, or failures with unreadable output.

Fix reliability before adding gates. A pipeline people bypass is worse than none, because it gives false assurance.

77 How do you introduce CI to a team with none?Hard

A read-only pipeline first: validate PRs, deploy nothing, plus nightly drift detection.

It builds trust and reveals the real change volume before you block anyone's work. Then automate deployment tier by tier, production last.

78 DevOps Center or a third-party tool?Medium

DevOps Center lowers the barrier for declarative teams with no git experience. Third-party tools offer more control, better delta handling and richer release management.

Either is better than manual change sets. Choose from your team's skills and your release complexity, not from feature lists.

Metrics & judgement (79–100)

79 Which metric best indicates pipeline health?Medium

Lead time — commit to production. It is the most honest single measure of whether the process works.

Then deployment frequency with change failure rate: rising frequency at flat failure rate means the gates are doing their job.

80 Mean time to restore is four hours.Medium

Too slow — people will bypass the process for anything urgent, which is worse than the four hours.

Target a hotfix path measured in tens of minutes: branch from main, validate, deploy, tag, forward-merge. See hotfixes.

81 Drift events are increasing month on month.Medium

The sanctioned path is too slow, or does not exist for the kind of change people need.

The fix is process speed, not more enforcement. Rising drift with tighter controls means people are routing around you.

82 How do you justify DevOps investment?Medium

In their terms, with your own numbers: deployment duration, failure rate, hotfix frequency, and hours spent diagnosing incidents.

"Best practice" loses the argument. "Three of our last five incidents were drift reverting an admin's fix" wins it.

83 A release failed and nobody knows what changed.Medium

No tags, no generated release notes, no ticket ids in commits.

Tag every release, put ticket ids in branch names and merge commits, and generate notes from them. That makes "what shipped" answerable in seconds.

84 How do you decide what goes in a release?Medium

At the branch level: cut a release branch and freeze its scope, so "what is in this release" is a commit range rather than an argument.

If you are routinely cherry-picking to assemble a release, the branch model is wrong.

85 Two teams need different release cadences.Hard

Two release branches live at once — and both must receive every hotfix and every merge to main, which is where discipline breaks.

Automate a staleness check that fails when a branch is missing commits from main. The structural answer is unlocked packages.

86 A deployment window is 30 minutes and you need 90.Medium

Validate ahead of the window and quick-deploy inside it, move post-deployment scripts to idempotent jobs that can run after, and defer non-essential steps.

Most 90-minute releases are 80 minutes of tests that could have run yesterday.

87 How do you handle a failed production deployment mid-way?Hard

Metadata deployments are largely transactional, so a failure usually leaves nothing applied — verify that, then diagnose from the error.

The dangerous cases are post-deployment scripts and data migrations that partially ran, which is why they must be idempotent.

88 You inherit a pipeline nobody documented.Medium

Trace it from the workflow files: what triggers it, which orgs it touches, which credentials it uses and when they expire.

Then document it and add the credential expiry dates to a calendar — that is usually the nearest time-bomb.

89 A release needs a database-style migration script.Medium

Write it as idempotent Apex or a scripted data operation, version it with the release, and rehearse it in a Full sandbox.

And record whether it is reversible — most data migrations are not.

90 How do you keep release notes honest?Easy

Generate them from the ticket ids in merge commits rather than writing them by hand.

Hand-written notes omit the things nobody wanted to mention, which are frequently the ones operations needs to know.

91 A stakeholder wants to deploy on Friday afternoon.Medium

State the risk plainly — reduced support coverage for a weekend — and let them decide. If they accept it, record the acceptance.

A fast, tested hotfix path makes Friday deployments far less frightening, which is the real answer.

92 How do you prove to an auditor that git matches production?Hard

The drift-detection job and its run history, plus main equals production as an enforced invariant, tagged releases, deployment by a service account, and Setup Audit Trail review.

And state the caveat honestly: config that is data needs its own migration and reconciliation. Saying that unprompted is what makes the answer credible.

93 The team wants to skip code review for small changes.Medium

Tier it rather than abolishing it: a field label needs no board, a shared automation or anything touching security does.

Publish the tiers so people can self-serve the small stuff — uniformly heavy governance gets bypassed, producing less control than none.

94 How much test coverage should the pipeline require?Medium

A per-class floor on changed classes — say 80% — rather than trusting the org-wide 75%, which hides exactly the regressions you care about.

And remember coverage is not verified behaviour. Review the assertions, not just the number.

95 You are asked to deploy without tests "just this once".Medium

Not to production — the platform requires a test level, and the point of the gate is the case where you are under pressure.

If the tests are blocking because they are broken, fix the tests. That is a shorter path than it sounds.

96 What is the first thing to automate in a manual process?Medium

Validation on pull requests — it catches problems before they reach an org and requires no deployment rights.

Then drift detection. Both build trust without blocking anyone, which is what earns you the mandate for more.

97 A manual step keeps being forgotten.Easy

Automate it or make the pipeline fail without it. A checklist item that is skipped twice will be skipped again.

Post-deployment scheduler setup and config-data seeding are the usual candidates.

98 How do you know the pipeline is good enough?Medium

A developer can go from commit to production in a known, short time; failures are caught before production; drift is detected; and a hotfix takes tens of minutes.

Tooling sophistication is not the measure. Those four outcomes are.

99 What is the most common Salesforce DevOps mistake?Hard

Treating all configuration as deployable metadata — then discovering that scheduling policies, CPQ rules, territories and custom setting rows are data that no deployment carries.

Closely followed by no drift detection, and hard-coded Ids that break after every sandbox refresh.

100 One habit that most improves releases?Hard

Validate early, quick-deploy late — and tag every release.

The first turns a long, risky window into a short one; the second gives you a rollback reference, an audit answer and a way to reproduce exactly what shipped. Neither is clever and both pay back immediately.
