Dynamic Forms, Actions & Related Lists

The old way — Page Layouts

  • Fields live in one monolithic layout
  • To show different fields to different people you clone the layout — or invent a record type
  • Layout assignment is only by record type × profile
  • Ends with 12 layouts nobody dares change
→

The modern way — Dynamic Forms

  • Fields placed individually in App Builder
  • Each field or section has its own visibility rule (record value, user field, device, permission)
  • Sections and tabs arranged freely
  • One page, many audiences — far less to maintain
FeatureWhat it gives you
Dynamic FormsField-level placement and conditional visibility, replacing the layout's field section
Dynamic ActionsButtons shown conditionally — "Escalate" only appears on open, high-priority cases
Dynamic Related ListsA related list filtered to specific criteria, with chosen columns and sort — several on one page, each showing a different slice
Component VisibilityAny component shown by record field, user field, custom permission, device form factor or a combination
Tabs & AccordionsReduce a wall of fields to a scannable page
Page Performance analysisBuilt into App Builder — flags slow components and too many on one page
⚡
Page performance rules of thumb Keep components per page modest — every one is a server call. Put heavy components (charts, related lists, custom LWCs doing Apex work) in tabs that aren't the default, so they load only when clicked. Use cacheable=true Apex or LDS wherever possible. Run the Page Analysis tool before go-live: users judge the whole platform by how fast the account page opens.

SLDS & design consistency

  • Salesforce Lightning Design System is the CSS framework and design language. Using it means your custom components look native and stay consistent through Salesforce's own redesigns.
  • Base components (lightning-card, lightning-datatable, lightning-input) already implement SLDS, accessibility and responsiveness — always try these before hand-rolling markup.
  • Utility classes handle spacing and layout: slds-var-m-around_medium, slds-grid, slds-col, slds-text-heading_small.
  • Styling Hooks (CSS custom properties) are the supported way to theme base components — never target SLDS internal class names, which change without notice.
  • Themes and branding at app level control colours and logo without any CSS.
/* Supported: styling hooks and your own scoped classes */
:host {
    --slds-c-card-color-background: var(--lwc-colorBackgroundAlt);
}
.risk-banner {
    border-left: 3px solid var(--lwc-colorTextError, #ea001e);
    padding: var(--lwc-spacingSmall, .75rem);
}

/* NOT supported: reaching into SLDS internals — breaks without warning
.slds-card__header .slds-media__body { ... }  */

Accessibility

♿
Not optional Accessibility is a legal requirement in many markets and a procurement question in most enterprise deals. Salesforce targets WCAG 2.1 AA; if your custom components break it, the org is non-compliant regardless of what the platform does.

Build it in

  • Use base components — they handle roles, focus and ARIA already
  • Every input needs a real label, not just a placeholder
  • Meaningful alt text; decorative images get alt=""
  • Keyboard operability: everything reachable and actionable by Tab and Enter
  • Visible focus indicators — never outline: none without a replacement
  • Colour contrast ≥ 4.5:1, and never colour alone to convey meaning
  • Announce dynamic changes with aria-live

Test it

  • Navigate a whole flow with the keyboard only
  • Run a screen reader (NVDA, VoiceOver) over the page
  • Automated checks: axe DevTools, Lighthouse
  • Zoom to 200% and confirm nothing is lost
  • Check in both light and dark backgrounds

Designing for mobile

  • Component Visibility by form factor — hide dense components on phones rather than shipping a cramped page.
  • Compact Layouts drive the mobile record header — pick the 4–5 fields that identify the record.
  • Mobile navigation menu is separate from desktop; curate it ruthlessly.
  • Quick Actions are the primary mobile interaction — global actions appear in the action bar.
  • Test on a real device: touch targets, thumb reach, and how a 40-field Dynamic Form actually feels.
  • LWCs are responsive by default with SLDS grid; verify at 375px width.

UX patterns that work

Reduce, then arrange

The best page redesign removes fields. Ask which are read weekly vs never. Move the rest to a collapsed section or a tab.

Guide, don't validate

Path with guidance-for-success, and screen flows for complex entry, beat a wall of validation-rule errors after the fact.

Progressive disclosure

Show the summary; reveal detail on demand. Tabs, accordions and Dynamic Forms visibility rules all serve this.

Make the next action obvious

Dynamic Actions surface exactly the buttons valid right now, instead of 14 buttons of which 12 are irrelevant.

Consistency over cleverness

Users learn one pattern. A bespoke component that behaves differently costs more in confusion than it gains in elegance.

Measure adoption

Lightning Usage App and login/report metrics show whether the redesign actually helped, rather than whether people said they liked it.

Interview questions

1 Page Layout vs Dynamic Forms — what changed?Easy

A page layout is monolithic: to show different fields to different users you clone the layout, and assignment is only by record type × profile — which is how orgs end up with a dozen near-identical layouts.

Dynamic Forms place fields individually in App Builder, each with its own visibility rule based on record values, user fields, custom permissions or device. One page serves many audiences, and you stop creating record types purely to hide fields. Page layouts still control related lists and buttons in some contexts, so both concepts persist.

2 A record page takes 8 seconds to load. What do you do?Hard

Run App Builder's Page Performance analysis first — it names the slow components. Then: reduce the number of components (each is a server call); move heavy ones (charts, custom LWCs doing Apex work, long related lists) into non-default tabs so they load lazily; ensure Apex is cacheable=true or replaced by LDS; check for a custom component doing SOQL in a loop or querying without limits; and confirm you're not rendering a 60-field Dynamic Form on a phone.

Also check the Lightning Usage App for EPT (Experienced Page Time) trends across users.

3 How do you show a button only to managers on high-value open deals?Medium

Dynamic Actions with a visibility filter combining record and user criteria: Amount > 100000 AND IsClosed = false AND a custom permission such as Approve_Large_Discount held by the manager's permission set.

Using a custom permission rather than a profile name is the detail interviewers look for — it survives profile restructuring and is testable in Apex with FeatureManagement.checkPermission().

4 Why shouldn't you style SLDS internal classes?Medium

Because they're implementation detail, not API. Salesforce changes the internal DOM and class names of base components between releases, so a rule targeting .slds-card__header .slds-media__body silently breaks — and with native Shadow DOM it may not apply at all.

The supported route is SLDS Styling Hooks — CSS custom properties like --slds-c-card-color-background — plus your own scoped classes inside your component. Those are contractual and survive upgrades.

5 What accessibility issues would you check in a custom LWC?Hard

Labels on every input (not placeholders), meaningful alt text, full keyboard operability with a visible focus indicator, logical tab order, colour contrast of at least 4.5:1, never using colour alone to convey state, correct heading hierarchy, and aria-live regions so dynamic updates are announced.

Then test properly: keyboard-only navigation through the whole flow, a screen reader pass, axe DevTools or Lighthouse, and 200% zoom. Best answer of all: use base components, which already handle most of this.

6 How do you support users with poor mobile coverage?Medium

Briefcase Builder defines which records are cached offline in the Salesforce mobile app, so field sales can view and edit key accounts with no signal. For technicians, the Field Service mobile app is fully offline-first.

Design accordingly: avoid logic requiring a server round trip, keep on-device work simple, and make server-side post-sync processing idempotent and order-tolerant, because records may arrive hours later and out of sequence.

7 The business asks for 60 fields on one page. How do you respond?Medium

Push back with data, not opinion. Ask which fields are actually read or edited — usually a report on field usage (or Salesforce Optimizer) shows many are never populated. Then apply progressive disclosure: the 8 fields that identify and drive the record at the top, the rest in collapsed sections or tabs, with Dynamic Forms visibility rules so each role sees only what's relevant to them.

Frame it as speed and adoption: fewer components load faster, and a scannable page is used, whereas a wall of fields gets ignored and the data quality problem persists.

Quick check

1. You need different fields visible to Sales vs Support on the same record type. Best approach?
Dynamic Forms removed the old reason for creating record types purely to vary which fields appear.
2. Which is the supported way to theme a base component?
Internal class names are implementation detail and change between releases; styling hooks are a supported contract.
3. What controls which records are available offline in the Salesforce mobile app?
Briefcase Builder defines the offline record set; Compact Layouts control the mobile record header fields.
