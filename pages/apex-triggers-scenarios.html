Triggers & Order of Execution — 100 Scenarios

Context variables, the save order and its re-entry cases, recursion, bulkification, partial success, frameworks and the special objects — as production situations.

📚
How to use this Answer out loud in ninety seconds, then open the answer. Concepts on Triggers & Order of Execution and its Advanced section.

Context variables (1–12)

1 You need the old value of a field in an after-update trigger.Easy

Trigger.oldMap.get(record.Id).Field__c. Trigger.old is a list in the same order as Trigger.new, but the map is safer because you are matching by Id rather than trusting index alignment.

Both are null on insert, and Trigger.new is null on delete — so a handler that does not check its context will throw.

2 Trigger.new is null and your code throws on delete.Easy

On delete there is no new version, so only Trigger.old and Trigger.oldMap are populated. On insert the reverse applies — no old, and Ids only exist in the after context.

A handler framework that dispatches to explicit beforeInsert/afterDelete methods removes this class of bug entirely, which is most of its value.

3 You try to set a field in an after-insert trigger and get an error.Easy

Trigger.new records are read-only in after contexts. Same-record field updates belong in before triggers, where you mutate the in-memory record and the platform saves it with no extra DML.

If you genuinely must update in after context, you need an explicit DML — which re-fires the triggers and is usually the wrong answer.

4 You need the record Id to create a child, but you are in before-insert.Easy

Ids do not exist until after the insert. Anything needing the parent Id — children, shares, related records — belongs in after insert.

That split is the simplest rule of thumb for choosing context: before for same-record values, after for anything involving the Id or related records.

5 How do you tell an insert from an update in a combined trigger?Easy

Trigger.isInsert / isUpdate / isDelete / isUndelete, combined with isBefore / isAfter.

Better: one trigger per object that immediately dispatches to a handler with explicit context methods, so the branching lives in one place and each method has a clear contract.

6 Trigger.size is 200 but you expected 10,000.Easy

The platform chunks DML into batches of 200, each its own trigger invocation — and a Data Loader job arrives as separate transactions entirely.

So your trigger must be correct per chunk and must not assume it sees the whole job. Any cross-batch aggregation needs to happen elsewhere (a batch job, or a reconciliation pass).

7 Trigger.isExecuting — when is it useful?Medium

It tells a shared class whether it was invoked from trigger context, which is occasionally useful for logging or for choosing a bulk-safe path.

It is not a recursion guard, and using it to branch business logic is usually a sign the class is doing too much — a service called from both a trigger and a UI should behave the same way.

8 You need to detect that a specific field changed.Easy

Compare new against old for each record: record.Status__c != Trigger.oldMap.get(record.Id).Status__c.

Do it per record in a loop, not once for the batch — a batch where one record changed and 199 did not is the normal case, and acting on all 200 is a common bug.

9 Your trigger fires on every update even when nothing relevant changed.Medium

Add an explicit change check and build a filtered collection of only the records that need work — then do nothing (and return early) when it is empty.

That is both a correctness fix and a performance fix: it stops cascading automation and keeps the transaction cheap when a bulk load touches unrelated fields.

10 Can you access a related record's fields from Trigger.new?Medium

Not reliably — Trigger.new contains only the fields of the record itself, not populated relationship fields.

Query for what you need: collect the parent Ids into a set, query once, and build a map. Attempting record.Account.Name in a trigger returns null and is a classic beginner bug.

11 You need to stop a delete from happening.Easy

addError() on the record in before delete, iterating Trigger.old.

Write the message for the user ("Cannot delete an invoice that has been posted"), and remember cascade deletes from a master-detail parent also run this trigger — which is where "why can't I delete the account" originates.

12 Should you ever have two triggers on one object?Easy

No — their execution order is not guaranteed, so behaviour becomes dependent on an implementation detail.

One trigger per object, delegating to a handler. If a managed package adds its own, you cannot control that ordering either, which is another reason to keep your own logic in one place and thin.

Order of execution (13–28)

13 Your trigger appears to run twice on one save.Hard

A workflow field update re-fires before and after triggers on that record once. Validation rules do not re-run by default, which is why the second pass behaves slightly differently.

Other causes: roll-up recalculation saving the parent, an after-save flow updating its own record, or assignment rules changing the owner. Guard by record Id rather than with a blunt boolean.

14 A validation rule rejects a value your trigger just set.Medium

Correct ordering: before-save flows, then before triggers, then validation rules. So a before trigger's value is validated — which is usually what you want.

If your logic is in an after trigger, it runs after validation and cannot influence it. Move defaulting earlier.

15 Logic keyed on OwnerId sees the wrong owner.Medium

Assignment rules run after your before triggers, so a before trigger sees the pre-assignment owner.

Put owner-dependent logic in an after trigger, or in a separate async step. This is a frequent cause of notifications going to the wrong person on case creation.

16 Updating a child causes the parent's triggers to fire.Medium

Roll-up summary recalculation saves the parent, which runs the parent's triggers. This is how cross-object trigger storms start.

It is also why implicit parent locking exists: child DML locks the master-detail parent, which is the root cause of most UNABLE_TO_LOCK_ROW errors.

17 Where do before-save flows sit relative to triggers?Easy

Before-save flows run before before-triggers. They are also substantially faster than an after-save flow for same-record field updates because there is no additional save.

Practical rule: same-record field defaults in a before-save flow, cross-object work in after-save or Apex.

18 When do platform events published in a trigger actually fire subscribers?Medium

With publish-after-commit (the usual choice), after the transaction commits — so subscribers run in a separate transaction with fresh limits and no access to your static state.

That makes events a clean way to do post-commit work and to escape mixed-DML restrictions. Publish-immediately fires even if you later roll back, which is only appropriate for telemetry.

19 A CDC subscriber sees a child change before its parent.Hard

Change events are not ordered across objects. Use the transaction key in the event header to group changes that happened together, and design consumers to tolerate out-of-order arrival or to query current state.

Also handle gap events — ignoring them silently loses changes. See CDC fine print.

20 Entitlement and escalation rules interfere with your trigger logic.Medium

They fire inside the same save, after triggers — so fields they set are not visible to your trigger, and fields you set can change their behaviour.

Sequence deliberately: if your logic must react to the escalation outcome, it belongs in a later step (an async job or an event subscriber).

21 Deleting a parent runs delete triggers you did not expect.Medium

Cascade delete on master-detail deletes children and runs their delete triggers. Archiving logic routinely forgets this and either double-processes or fails.

Make delete handlers tolerant and idempotent, and consider whether the relationship should restrict deletion instead.

22 Two record-triggered flows on an object run in an unexpected order.Medium

Within the same object and timing, order is unspecified unless you set the flow's trigger order explicitly.

Set it, document it, and ideally converge on one entry point per timing. Relying on observed order is relying on something that can change between releases.

23 Does a roll-up field update fire the parent's before trigger?Medium

The parent is saved, so yes — its triggers run. That is why a parent trigger that recalculates something from children can end up in a loop with the roll-up.

Guard by checking whether the fields you care about actually changed, and never react to fields the platform itself maintains unless you mean to.

24 Your logic must run after everything else in the save.Medium

There is no "last" hook. The closest are an after trigger (late in the save, but before roll-ups and some rules) or a post-commit mechanism — a platform event published after commit, or an async job.

If the requirement is genuinely "after the whole transaction settles", post-commit is the honest answer, and it means accepting a short delay.

25 Does Database.update with partial success still fire triggers?Easy

Yes — for the records that are processed. Failed records do not get saved, so their after-trigger logic does not run, but the successful ones proceed normally.

That is why partial-success DML plus addError interact subtly: in a partial-success context, an error on one record removes that record rather than the whole operation.

26 Why does a user see different behaviour than an integration?Medium

Different entry points mean different automation applies: assignment rules and auto-response run on UI-created cases but can be skipped by API depending on headers; validation rules differ if you scoped them; and the running user's sharing and FLS differ.

Log Request.getCurrent().getQuiddity() so "it behaves differently from the API" becomes provable.

27 Someone asks you to recite the order of execution. What matters?Medium

The sequence matters less than the consequences: before-save flows → before triggers → validation → save → after triggers → after-save flows → roll-ups → commit, with workflow field updates causing one re-entry.

What interviewers want is the practical conclusions: why same-record updates go in before context, why assignment rules surprise you, and why your trigger can run twice.

28 A field is empty in your after trigger but populated on the record afterwards.Hard

Something later in the save set it: a roll-up, a workflow field update, an escalation or entitlement rule, or an after-save flow.

Read the CODE_UNIT_STARTED/FINISHED tree in a debug log to see the real sequence. Reasoning from configuration is slower and frequently wrong, because orgs contain automation nobody documented.

Bulkification (29–44)

29 Your trigger throws "Too many SOQL queries: 101".Easy

A query inside a loop. Collect the Ids into a Set first, query once outside the loop, and build a Map for lookups.

The limit counts queries, not rows, so one query returning 10,000 rows is fine and 101 queries returning one row each is not.

30 "Too many DML statements: 151".Easy

DML inside a loop. Accumulate records into a list and issue one statement after the loop.

If you need to insert into several objects, build one list per object and issue one statement each — four statements, not four hundred.

31 Your code works for 200 records but the business loads 50,000.Medium

It arrives as 250 chunks of 200 in separate transactions, so per-transaction limits are fine — but anything accumulating in a static across chunks, or any cross-record aggregation, will be wrong.

Also watch for lock contention between chunks on shared parents, and for row limits if your trigger queries broadly per chunk.

32 A trigger calls a method that queries — and that method is called in a loop.Medium

The query is still in a loop; moving it into a method only hides it. This is the most common form of the bug in "clean-looking" code.

Change the method's signature to take a collection and return a map. Bulk-safe interfaces force bulk-safe callers.

33 You need to query related records for 200 parents.Easy

One query with WHERE ParentId IN :parentIds, then group into a Map<Id, List<Child__c>> in a single pass.

That map-building pattern is the backbone of bulk Apex — once you have it, most trigger logic becomes a loop over parents with a map lookup.

34 Nested loops over two collections blow CPU.Medium

Quadratic behaviour: 200 × 200 is 40,000 iterations, and it grows fast.

Replace the inner loop with a Map lookup keyed on whatever you were matching. Almost every nested loop in Apex can become a map build plus a single pass.

35 A trigger makes a callout and fails.Easy

You cannot call out from a trigger synchronously (and you cannot call out after DML in a transaction at all).

Publish a platform event or enqueue a Queueable (or @future(callout=true)) and do the callout there. That also gives you retry and error handling, which a trigger callout would not.

36 Your trigger sends an email per record.Medium

Email limits are per transaction and daily, and one send per record will hit both. Build a list of SingleEmailMessage and send once with Messaging.sendEmail(list).

Better still, question whether email is right at all — for high volume, platform events or custom notifications scale and do not share a daily cap with everything else.

37 You need to process only records whose status changed to Closed.Easy

Build a filtered collection in one pass: for each record, compare against Trigger.oldMap and add to a working list only on the transition.

Then return early if the list is empty. That single habit prevents a large amount of unnecessary work and cascading automation.

38 A heap error in a trigger processing 200 records.Medium

Something is loading too much: a query selecting every field, a large related collection per record, or accumulated strings.

Query only rendered/needed fields, avoid FIELDS(ALL), and do not hold parallel copies of collections. 6MB synchronous is not much when you select 80 fields across several objects.

39 How do you keep a trigger fast when the org has 12 other automations?Hard

Your trigger shares the transaction's CPU with every flow, validation rule, roll-up and managed package on that save — so being efficient is necessary but not sufficient.

Keep your handler thin, push heavy work async, and campaign to consolidate the other automations. Read CUMULATIVE_LIMIT_USAGE to see who is actually spending the budget.

40 Should a trigger handler query in every context?Medium

No — query lazily and only when the filtered working set is non-empty. A trigger that queries unconditionally costs a query on every save, including the 199 saves that needed nothing.

At scale that is the difference between a save that is fast and one that is not, and it compounds with every other automation on the object.

41 Your trigger needs data from a related object five levels up.Medium

SOQL allows five levels of parent traversal in the SELECT, so often one query suffices — but deep traversal costs work per row.

If you need it repeatedly, consider stamping the value closer with automation so the trigger can read it directly. Denormalisation is legitimate when it is a decision.

42 You must process 100,000 related records from a trigger.Hard

Not in the trigger. Row and DML limits make it impossible, and even if it fit, you would be holding a user's save open.

Enqueue a Queueable or Batch Apex from the trigger and process asynchronously, with a high-water mark so a failure resumes. See chunking strategies.

43 Your trigger logic is correct but slow because of a describe call.Medium

getGlobalDescribe() is expensive and should essentially never appear in a trigger path, let alone in a loop.

Cache describe results in a static map on first use, and prefer targeted describes (Account.SObjectType.getDescribe()) over indexing into a global one.

44 How do you write a bulk test that actually tests bulk?Medium

Insert 200 records in one DML, with variation — some meeting the criteria, some not, some with null fields, some referencing the same parent.

200 identical records passes trivially and proves little. The variation is what finds the index-alignment bugs and the "acted on all 200" bugs.

Recursion & guards (45–58)

45 Your static boolean guard skips records in a legitimate second batch.Hard

A transaction updating 400 records through two DML statements hits your trigger twice legitimately — and alreadyRan silently skips the second 200.

Guard by record Id: keep a static Set<Id> of processed records and filter against it, returning an empty working set when appropriate. That stays correct under both shapes.

46 You get "maximum trigger depth exceeded".Medium

Logic is re-triggering itself — typically an after trigger updating records that fire the same trigger again, or two triggers updating each other's objects.

Fix with an Id-based guard, or by moving same-record updates into before context so no second save occurs. Then verify with a debug log that the recursion is genuinely gone rather than merely deeper.

47 You need exactly two passes, not one and not infinite.Hard

A depth counter: increment on entry, decrement on exit, and refuse beyond your maximum. That expresses "up to N passes" rather than "once".

Make sure the decrement happens even on exception (or reset the counter at a known boundary), or one failure leaves the guard permanently closed for the transaction.

48 Two triggers on different objects update each other.Hard

A cross-object loop, which is harder to see because each trigger looks reasonable alone.

Break it with an Id-based guard shared between them (a single static registry), or by having one side publish an event instead of writing directly. And add a circuit-breaker counter you can alert on.

49 Static state persists in a way that surprises you across a transaction.Medium

Statics live for the whole transaction, so a guard set during the first DML affects the second — which is sometimes exactly what you want and sometimes the bug.

Be explicit about scope: Id-based sets for "do not reprocess this record", depth counters for "limit passes", and a reset hook for tests.

50 An async job re-enters your trigger and the guard does not help.Medium

Async work runs in a new transaction, so statics are fresh. A guard cannot span transactions.

Use a field on the record (a processed flag or timestamp) when the guarantee must survive the transaction boundary, and make the handler idempotent so a repeat is harmless.

51 A platform event subscriber loops with the publisher.Hard

The subscriber's write re-triggers the publishing logic, which publishes again — and because each hop is a separate transaction, no static guard sees it.

Break the cycle with a durable marker: a flag or source field on the record saying "this change came from the subscriber", checked by the publisher. And add a counter you can alert on, because this loop is invisible in a single debug log.

52 You need to disable a trigger for one data load.Easy

A bypass switch: a hierarchy custom setting or custom permission checked at the top of every handler, enabled for the load user only.

Build it before you need it. "We commented out the trigger in production" is not a plan, and deactivating a trigger is a metadata change requiring a deployment.

53 Who should be allowed to use the bypass?Medium

A named integration or migration user, and administrators during an incident — not a general permission.

Make its use visible: log when the bypass is active, and report on it. An undetectable bypass becomes a permanent exception that explains a year of data-quality problems.

54 Should the bypass be per-object or global?Medium

Per-object (ideally per-handler) so you can disable the minimum. A global switch disables validation you still wanted and makes the blast radius unnecessarily wide.

A custom setting with a checkbox per object, plus a global override for emergencies, covers both needs.

55 A flow and a trigger both react to the same change and conflict.Medium

Decide ownership per field and per behaviour, then remove the duplicate. Two automations maintaining the same field is a loop waiting to happen and a debugging nightmare.

If both must exist, make the ordering explicit (before-save flow then trigger) and document which owns what.

56 How do you detect a runaway automation loop in production?Hard

A counter: increment a static or a custom setting per execution and publish a platform event when it exceeds a threshold, so you get an alert rather than a user complaint.

Because async hops create new transactions, loops can run for hours and are invisible in any single debug log — which is why the counter has to be durable, not static.

57 Your guard breaks a test that runs two DML operations.Medium

That is the guard working as written — and a signal it is too blunt. The test is simulating a legitimate real-world shape.

Switch to an Id-based guard, and add a @TestVisible reset method so tests can clear state deliberately rather than working around it.

58 Is recursion always a bug?Medium

No. One extra pass caused by a roll-up or a field update is normal platform behaviour, and some designs legitimately need a second pass to settle derived values.

The bug is unbounded recursion, or logic that is incorrect when it runs twice. Idempotent handlers make recursion a performance consideration rather than a correctness one.

Errors & partial success (59–72)

59 Field-level or record-level addError?Easy

Field-level (record.Field__c.addError(...)) whenever one field is at fault — the message appears next to the input, which is a much better experience.

Record-level for cross-field rules where no single field is wrong. Either way, write the message for the user and say what to change.

60 One addError kills a 200-record integration load.Medium

In an all-or-none DML, any error fails the whole operation. In a partial-success DML (Database.insert(records, false)), addError removes only that record.

So the integration should use partial success and log the failures — and your trigger should error per record rather than throwing an exception, which fails everything regardless.

61 A trigger throws an unhandled exception in production.Medium

The user sees a stack trace with internal class names, and the save fails. Both are avoidable.

Catch, log via a platform event (so the log survives the rollback), and addError with a user-facing message. Unhandled exceptions also email the Apex exception recipient — make sure that is a monitored address.

62 Should a trigger catch exceptions from a service it calls?Medium

Catch to add context and decide the user-facing behaviour, then either addError or re-throw. Never swallow.

The question to answer explicitly: should this failure block the save? Data-integrity failures should; a failed nice-to-have enrichment should not, and should instead queue for retry.

63 You need to log errors but the transaction rolls back.Hard

A log row written with DML is rolled back with everything else — which is why so many orgs have an error log that is empty precisely when it matters.

Publish a platform event instead; event publication survives the rollback, and a subscriber writes the durable log. See production debugging.

64 How do you report which of 200 records failed and why?Medium

Iterate Database.SaveResult[] by index against the input list, and for each failure capture the status code, message and fields from getErrors().

Write them with the record Id and a correlation id. A count without causes is almost useless when the integration owner asks at 09:00.

65 A savepoint rollback leaves side effects behind.Hard

Rollback undoes database changes only — not static state, not sent emails, not callouts made, not platform events published immediately.

Savepoints also consume DML statement limits. Use them sparingly and never as a substitute for designing the operation to be idempotent.

66 Should the trigger validate, or should a validation rule?Medium

Validation rule when it is formula-expressible on the record and admins should be able to see and change it. Trigger when it needs related data, bulk context, or a message the rule cannot produce.

Pick one home per rule. Duplicated validation means three places to change and inconsistent behaviour between UI and API.

67 An integration needs failures to be data, not exceptions.Medium

Use partial-success DML, write failures to an error object or event with enough context to retry, and return a structured result to the caller rather than throwing.

"Fail the record, not the batch" is the general rule — one bad row should never cost you 199 good ones.

68 How do you make a trigger handler idempotent?Hard

Key side effects on something durable: a processed flag or timestamp on the record, or an existence check against the records you would create (with a unique key on them).

Then running twice changes nothing the second time. That property is what makes retries, async redelivery and recursion safe rather than dangerous.

69 A duplicate-value error on insert — is that a failure?Medium

Often it is the success signal in disguise: the unique constraint prevented a duplicate, meaning the work was already done.

In idempotent integration code, treat DUPLICATE_VALUE on your idempotency key as "already processed" and continue, rather than alerting.

70 You need to notify someone when a trigger fails, without emailing a departed developer.Easy

Set the Apex exception email recipients to a monitored distribution list, and build your own alerting off the error log (a report subscription with a conditional alert, or an integration to your alerting tool).

Single-person notification is a guaranteed future gap, and it is one of the most common findings when an org changes hands.

71 Errors in an after trigger confuse users.Medium

addError in after context still rolls the save back, but the message can be attributed oddly in the UI.

Validate in before context wherever possible, and reserve after-trigger errors for cases that genuinely cannot be known earlier (something requiring the record Id).

72 A managed package trigger errors on your save.Medium

You cannot modify it. Determine what it objects to from the error and the cumulative limits log, and adjust your data or sequencing.

If it is a limits problem, slim your own logic and move work async to free budget. If it is a validation problem, the vendor's configuration usually has a switch — and if not, that is a support case with evidence.

Frameworks & special objects (73–86)

73 What is the minimum viable trigger framework?Easy

One trigger per object with all contexts declared, delegating immediately to a handler class with explicit beforeInsert, afterUpdate and so on.

Add a bypass check and an Id-based recursion guard, and you have 90% of the value of any published framework with none of the onboarding cost.

74 When is a metadata-driven dispatch framework worth it?Hard

When admins or consultants genuinely need to reorder or disable logic without a deployment — a packaged product, or a large org with many teams writing handlers for one object.

The cost is real: dispatch via Type.forName makes stack traces less direct and behaviour depends on data. Log which handlers ran, or debugging becomes archaeology.

75 A framework gives you ordering. How do you decide the order?Medium

By dependency, documented: validation first (fail fast before doing work), then defaulting, then derived values, then cross-object side effects, then notifications.

Write the reason next to each registration. Ordering that exists only as numbers is ordering nobody can safely change.

76 Is the Domain/Selector/Service pattern worth it for a small org?Medium

Usually not in full. For two developers and a dozen classes, the layering costs more than it returns.

Adopt the selector first — centralising queries pays off immediately and independently. Add services when more than one entry point needs the same logic, and domain classes only if the object's behaviour genuinely justifies it.

77 A platform event trigger behaves unlike a normal trigger.Medium

It is after-insert only, runs as the Automated Process user in its own transaction with fresh limits, and has no access to the publisher's static state.

So: set your trace flag on that user to debug it, pass everything needed in the payload, and make it idempotent because delivery is at-least-once.

78 How do you retry a failed platform event subscriber?Hard

Throw EventBus.RetryableException to ask the bus to redeliver, up to a limited number of attempts — and count them via EventBus.TriggerContext.currentContext().retries so you can stop and dead-letter rather than looping.

Beyond the retry limit the event is discarded, so anything that must not be lost needs its own durable record.

79 A CDC trigger receives only some fields.Medium

CDC payloads contain the changed fields plus a header. If you need full state, query the record — but be aware it may have changed again since.

Use the transaction key to group related changes, and handle gap events explicitly or you will silently lose changes.

80 A trigger on Task cannot determine the parent type.Medium

WhatId and WhoId are polymorphic. Resolve the type at runtime with ((Id) task.WhatId).getSObjectType(), or use TYPEOF in the query.

Never assume the parent type from current usage — someone will relate a Task to a Case next quarter and your logic will throw or silently do the wrong thing.

81 A User trigger causes a mixed DML error.Medium

Setup objects (User, Group, PermissionSetAssignment) cannot be modified in the same transaction as non-setup objects.

Split the work: do the non-setup part asynchronously, or publish an event. In tests, wrap the setup-object work in System.runAs.

82 Triggers on FeedItem or ContentDocumentLink behave oddly.Hard

These objects have unusual sharing and delete semantics, and behave differently for different user types — particularly external and guest users.

Test with real user contexts rather than as an administrator, including a community user if relevant. Assumptions that hold for an admin frequently do not hold here.

83 You need trigger logic that only runs for one record type.Easy

Filter on RecordTypeId while building your working set — resolved by developer name at runtime, never hard-coded.

Schema.SObjectType.Account.getRecordTypeInfosByDeveloperName() gives you the Id without coupling your code to an org-specific value.

84 Logic must differ between UI and API saves.Medium

Request.getCurrent().getQuiddity() tells you the entry point, so you can branch — but ask whether you should.

Diverging behaviour by channel is a frequent source of "works in the UI, breaks for the integration" confusion. Prefer one behaviour, with explicit bypasses for named integration users where genuinely required.

85 How do you unit test a trigger handler without DML?Hard

Call the handler method directly with in-memory sObjects and injected dependencies (a stubbed selector), asserting the outcome on the collection.

That requires the handler to accept collections and dependencies rather than reading Trigger.new internally — which is a design property worth having anyway. See Stub API.

86 A trigger must not run during a package upgrade's test execution.Hard

Subscriber-org tests run on upgrade, and your trigger will fire against their data shapes.

Make handlers tolerant of unexpected data, avoid assumptions about configuration rows existing, and never use SeeAllData. Provide a bypass the subscriber can use if your automation conflicts with their load processes.

Judgement & migration (87–100)

87 You inherit an object with 14 automations.Hard

Document before changing: a debug log of one save gives the real execution tree, including the automations nobody remembered.

Then consolidate by risk — delete what is provably dead, migrate workflow rules and processes into flows, converge on one entry point per timing, move same-record updates to before-save. Incrementally, behind tests, so each step is attributable.

88 Trigger or record-triggered flow for new logic?Medium

Flow for field updates, related-record creation and notifications that admins should own and see. Trigger for bulk-sensitive logic, complex data shapes, reuse across entry points, and anything needing real error handling.

The deciding question is usually "who maintains this in two years?" — not which is technically capable.

89 A stakeholder wants logic in a flow so admins can change it; you want Apex.Medium

Split it: the flow owns orchestration and the admin-tunable decisions; an invocable Apex action owns the complex, bulk-sensitive computation.

Everyone gets what they need, and the flow stays small enough to read. That boundary is the most useful pattern in modern Salesforce automation.

90 Migrating a workflow rule to a flow changes behaviour.Medium

Expected in two ways: workflow field updates re-fire triggers (and a before-save flow does not), and timing in the save order differs.

So test the whole save path, not just the field value — particularly any trigger that was relying on the re-entry. Migrate one rule at a time.

91 Your consolidation breaks something three weeks later.Medium

That is why consolidation ships incrementally: each change separately deployable and attributable, with tests capturing the prior behaviour first.

If you cannot attribute it, you merged too much at once. Characterisation tests written before refactoring are what make this safe.

92 How do you prove a trigger is bulk-safe in review?Medium

Show the test: 200 records, with variation, asserting outcomes — plus the absence of SOQL and DML inside loops in the diff.

Static analysis catches the mechanical cases automatically; the review question is whether the test data exercises the bulk path meaningfully.

93 A trigger needs to call out and update records atomically.Hard

You cannot — callouts are not allowed from a trigger, and after DML you cannot call out in the same transaction at all. Atomicity across a remote system is not available regardless.

Design for eventual consistency: commit locally, publish an event, make the remote call idempotent with a correlation id, and reconcile. See consistency models.

94 Your trigger is correct but the save takes four seconds.Medium

Measure where it goes: CODE_UNIT_STARTED/FINISHED shows every trigger, flow and rule in the save, and CUMULATIVE_LIMIT_USAGE attributes CPU per namespace.

Frequently your trigger is a small slice and the cost is elsewhere. Fixing your own code when a flow or package owns the time is wasted effort.

95 You need to add logic to a managed package's object.Medium

You can write your own trigger on it (if the package permits), but ordering relative to the package's own trigger is not under your control.

So make your logic independent of theirs where possible, test against upgrades, and prefer reacting to the committed outcome (an event, an async job) over racing them in the same save.

96 Should every object have a trigger "just in case"?Easy

No. An empty or near-empty trigger still costs execution and still needs test coverage, and it invites logic to accumulate without design.

Add one when there is a reason. Scaffolding automation ahead of requirements is how orgs end up with fourteen automations nobody can explain.

97 A reviewer says your handler is too long.Easy

They are usually right. A handler method should read as a short sequence of named steps — filter the working set, load what you need, compute, write.

Extract each step into a method named for what it does. That also makes the bulk and failure tests easier to write, which is the real payoff.

98 How do you decide what belongs in before versus after?Easy

Before: same-record field values, validation, defaulting — no extra DML needed. After: anything requiring the record Id, related records, shares, or reacting to the saved state.

If you find yourself doing DML on Trigger.new records in after context, the logic probably belongs in before.

99 The business asks for "no automation on this object for the migration".Medium

Give them the bypass switch scoped to the migration user, then run a reconciliation pass afterwards to apply the derived values the automation would have set.

Bypassing without reconciling imports incomplete data permanently, and it surfaces months later as a data-quality mystery.

100 One habit that most reduces trigger defects?Hard

Building the filtered working set first, and returning early when it is empty. Almost every trigger bug — acting on all 200 records, cascading automation, unnecessary queries, recursion — is downstream of not doing this.

Pair it with an Id-based guard and a bypass switch, and the object becomes genuinely safe to operate on at volume.
