Test Classes — 100 Scenarios

Test data strategy, mocking, async and event testing, permissions, coverage that means something, and the failures that reach production with 90% coverage.

📚
How to use this Answer out loud in ninety seconds, then open the answer. Concepts on Test Classes and its Advanced section.

Test data (1–16)

1 A new required field breaks 80 test classes at once.Medium

That is actually the good outcome if your test data is centralised — one fix in the factory. If it is 80 separate fixes, the lesson is the factory.

Build a TestDataFactory (or builder classes) so required-field changes, picklist changes and new validation rules are absorbed in one place.

2 Tests are slow — 400 tests take 50 minutes.Medium

Usually DML volume. Use @TestSetup so data is created once per class and each method gets a rolled-back copy, and avoid inserting records for tests that only need in-memory objects.

For pure logic, fake Ids and never touch the database — those tests run in milliseconds.

3 How do you fake a record Id without inserting?Medium

Generate one from the object's key prefix plus a padded counter, which is enough for logic that only compares or maps by Id.

It lets you test mapping, grouping and decision logic with zero DML. Reserve real inserts for tests that genuinely exercise the database.

4 @TestSetup data is not visible in a test method.Medium

It is visible, but you must query for it — the method does not return anything, and Ids assigned there are not in scope.

Also note @TestSetup cannot be used with SeeAllData=true, and its records count against the class's limits.

5 A test passes alone and fails in the suite.Hard

Almost always static state or an assumption about data another test created. Each method is its own transaction, but statics set by code under test can persist within a method, and parallel execution adds contention.

Provide a @TestVisible reset for caches and guards, and make every test create exactly the data it needs.

6 Why is SeeAllData=true dangerous?Easy

The test depends on org data that will change, so it passes today and fails later for reasons unrelated to the code. In a managed package it is worse — subscriber orgs have different data entirely.

Use it only where genuinely unavoidable (some standard objects and settings cannot be created in a test), and document why.

7 You need Custom Metadata in a test but cannot insert it.Hard

Custom Metadata is visible without SeeAllData but not insertable. Design for injection: the class accepts configuration (a constructor parameter or a @TestVisible static) with the metadata lookup as the default.

That makes the logic unit-testable and removes the dependency on deployed rows.

8 You need a user with a specific profile for a test.Medium

Create one in the test, querying the profile by name — but beware: profile names vary by org and language, which breaks packaged tests.

Prefer a minimum-access profile plus the permission set under test, and handle the case where the profile query returns nothing.

9 A test needs 200 records with variation, not 200 identical ones.Medium

Build the variation deliberately: some meeting the criteria, some not, some with nulls, several sharing a parent, one at a boundary value.

200 identical records passes trivially and proves almost nothing. The variation is what finds index-alignment bugs and "acted on all 200" bugs.

10 Test data violates a validation rule added by another team.Medium

Your factory must produce valid records, so update it — that is the factory earning its keep.

If the rule makes valid data impossible to construct in a test, that is a signal the rule may be too strict for integration paths too.

11 A test fails because a record-triggered flow fires.Medium

Tests run your org's automation, so flows and triggers fire on your test inserts. That is realistic and usually desirable.

If the automation is irrelevant and expensive, use your bypass switch for the test context — but do not routinely disable automation, or your tests stop reflecting production.

12 You cannot create a record because of a required lookup chain.Easy

The factory should build the whole chain — account, then contact, then case — with sensible defaults and overrides for the fields the test cares about.

A builder pattern makes this readable: new CaseBuilder().withAccount(acct).withPriority('High').build().

13 Tests hit DML row limits creating data.Medium

Create the minimum needed to prove the behaviour. A bulk test needs 200 records, not 10,000 — the trigger behaves the same and the test runs in a fraction of the time.

If you genuinely need volume, that is a scenario test in a sandbox, not a unit test.

14 How do you test something that depends on today's date?Medium

Inject the clock: a @TestVisible static Date today the production code reads, which tests can set.

Hard-coded dates in tests break at year boundaries and fiscal period changes, and Date.today() in logic makes behaviour untestable at the edges.

15 A test depends on a queue or group existing.Medium

Queues and groups are setup objects — mixed DML restrictions apply, and creating them in a test needs System.runAs.

Alternatively query for one by developer name and skip gracefully if absent, which is safer for packaged tests.

16 Your factory has 40 methods and nobody knows which to use.Medium

Switch to builders: one entry point per object with fluent overrides, rather than a method per permutation.

It reads better in the test, it does not grow combinatorially, and a new required field is still one change.

Assertions & structure (17–32)

17 A test has no assertions but gives 100% coverage.Easy

It verifies nothing — it only proves the lines execute without throwing. Coverage without assertions is decoration.

The honest check: break a line deliberately and re-run. If the test still passes, it was never testing anything.

18 How many assertions should a test have?Easy

Enough to pin the behaviour the test is named for — usually a small number, all about one outcome.

One test per behaviour, named for the behaviour, beats one giant test asserting twenty things where the first failure hides the rest.

19 An assertion failure message says "Assertion Failed".Easy

Always pass a message: Assert.areEqual(expected, actual, 'Discount should be 10% for gold tier').

The person reading the failed build is often not you, and a message turns a five-minute investigation into a five-second one.

20 You need to assert that an exception was thrown.Easy

Try the operation, call Assert.fail() immediately after it, and catch the specific exception type — asserting on its message or type.

Without the fail(), a test that throws nothing passes silently, which is the most common form of a broken negative test.

21 Where do startTest and stopTest go?Easy

Around the code under test only — setup before, assertions after. They reset governor limits so your setup DML does not count against the code you are measuring, and they force async work to complete.

Putting setup inside them is the usual mistake, and it makes limit assertions meaningless.

22 A test asserts on implementation details and breaks on every refactor.Medium

It is testing how rather than what. Assert on observable outcomes — the record state, the returned value, the error raised — not on which private method ran or how many queries were used.

Tests that break on refactoring without finding bugs get deleted, which costs you the coverage entirely.

23 How do you name a test method?Easy

After the behaviour and the condition: discountIsTenPercentForGoldTier, insertFailsWhenAmountIsNull.

testMethod1 tells the next person nothing, and a failing build full of such names is impossible to triage quickly.

24 Which cases should every unit have?Medium

Happy path, bulk (200), a negative case that must fail, and a boundary (null, empty collection, maximum length).

For triggers add a recursion case. Those five shapes catch the overwhelming majority of real defects.

25 Should tests share a helper that asserts everything?Medium

Shared setup helpers are good; shared mega-assertions are not — they obscure which expectation failed and encourage asserting irrelevant things.

Keep assertions in the test, close to the behaviour being verified.

26 You need to test a private method.Medium

Usually test it through the public behaviour it supports. If it is genuinely complex and independent, that is a signal it belongs in its own class with a public interface.

@TestVisible exists for the pragmatic middle ground, but reaching for it often means the design wants splitting.

27 How do you test a method that returns void and only does DML?Easy

Query the records afterwards and assert their state. The side effect is the behaviour.

Assert the specific fields you expect to have changed, not just the record count — a count assertion passes even when every value is wrong.

28 A reviewer wants a test for a getter.Easy

Push back politely — a trivial accessor has no behaviour to verify, and testing it only inflates coverage.

Spend the effort on the branch logic and error paths. Coverage targets that force this produce worse test suites, not better.

29 How do you verify behaviour under 200 records specifically?Medium

Insert 200 in one DML and assert per-record outcomes — ideally that exactly the right subset was affected, by seeding records that should and should not qualify.

Asserting only an aggregate count hides the case where the right number of wrong records was updated.

30 A test asserts a limit was not exceeded. Is that useful?Medium

Occasionally — asserting SOQL count after stopTest catches a query creeping into a loop, which is a genuine regression guard.

Keep it to the few hot paths where it matters; asserting exact query counts everywhere makes every refactor a test rewrite.

31 Should a test ever have no DML at all?Easy

Yes, and the best ones often do — pure logic tested with in-memory objects runs in milliseconds and is completely deterministic.

A suite where every test inserts data is a slow suite, and slow suites get run less often, which defeats the purpose.

32 How do you structure a test class for readability?Easy

Arrange–Act–Assert, visually separated, with @TestSetup for shared data and one behaviour per method.

A test is also documentation of intended usage, so it should read as an example someone could copy.

Mocking (33–50)

33 A method makes a callout. How do you test it?Easy

Test.setMock(HttpCalloutMock.class, new MyMock()) before startTest, returning a canned HttpResponse.

Also test the failure paths — a 500, a timeout, a malformed body — because those are the cases that actually break in production.

34 Your code makes three different callouts in sequence.Medium

A mock that inspects the request endpoint (or counts invocations) and returns a different response for each.

A single canned response hides sequencing bugs — you want to prove the second call uses data from the first.

35 You need to test retry behaviour on a 429.Medium

A mock that returns 429 on the first call and 200 on the second, then assert the operation ultimately succeeded and that the attempt count is what you expect.

Testing the retry path is how you discover your backoff logic never actually retries.

36 How do you test a class without touching its dependencies?Hard

The Stub API: Test.createStub(MyDependency.class, new MockProvider(...)) returning canned answers per method.

Requirements: the class is public/global and not final, the methods are virtual or interface-defined, and the dependency is injectable. Designing for that is what makes a codebase unit-testable.

37 Test.createStub fails on your class.Medium

It is final, or the methods you want to stub are not virtual and not from an interface, or it is an inner class in an unsupported position.

Extract an interface — which is the better design anyway, because it documents the seam explicitly.

38 You need to simulate a DML failure.Hard

Make the data genuinely invalid (a required field missing, a validation rule tripped) so the platform produces a real failure, or stub the layer that performs the DML.

Stubbing is cleaner for unit tests of error handling; real invalid data is better for proving the end-to-end behaviour users will see.

39 How do you test code that calls a managed package?Hard

Wrap the package call in a thin adapter class of your own, then stub the adapter. You cannot stub the package's classes directly.

That wrapper also insulates you from their signature changes on upgrade, which is worth having regardless.

40 You need to test a SOSL-dependent path.Medium

Test.setFixedSearchResults() with the Ids you want returned — search indexing is asynchronous, so real SOSL in a test is non-deterministic.

Relying on actual indexing produces a build that fails intermittently.

41 Mocking makes your test pass while production breaks.Hard

Your mock does not reflect reality — it returns a shape the real service never produces, or always succeeds.

Base mock responses on captured real payloads, and supplement unit tests with an integration smoke test against a sandbox endpoint. See Newman in CI.

42 Should you mock your own database layer?Medium

For unit tests of business logic, yes — a stubbed selector makes them fast and deterministic.

But keep some tests that use real DML to verify the queries themselves work and that automation behaves. Mocked-only suites miss real integration problems.

43 How do you test an @AuraEnabled method?Easy

Call it directly as a static method, asserting the returned DTO and the thrown AuraHandledException for error cases.

Also test it under System.runAs with a restricted user, since these methods are callable endpoints and FLS enforcement is exactly what you want to verify.

44 You need to test a REST resource.Medium

Construct a RestRequest and RestResponse, assign them to RestContext, then call your handler method directly.

Test the error responses and status codes as carefully as the success path — an API's error contract is part of its contract.

45 Testing an invocable action for a flow.Easy

Call the @InvocableMethod with a List of requests — including a list of several, to prove it is bulk-safe and that results align positionally with inputs.

That alignment is where invocable actions most often go wrong, and a single-item test never finds it.

46 How do you test email sending without sending email?Easy

In a test context, emails are not actually delivered, and you can assert on Limits.getEmailInvocations() or capture the messages via your own wrapper.

Wrapping Messaging.sendEmail in your own class makes it stubbable, which is cleaner than asserting on limits.

47 A mock needs to assert what it was called with.Medium

Record the arguments in the mock (or the stub provider) and assert on them afterwards — that is how you verify the right payload was sent.

Verifying interactions matters for integration code, where the outgoing request is the behaviour under test.

48 Your stub provider is 200 lines of switch statement.Medium

Pass a map of method name to canned return value into a generic provider, so each test configures only what it needs.

A reusable provider plus per-test configuration keeps the mocking infrastructure small and the tests readable.

49 Should you mock platform events?Medium

No need — publish them and use Test.getEventBus().deliver() to force synchronous delivery, then assert the subscriber's effect.

That tests the real path including the trigger, which is better than mocking it away.

50 How much mocking is too much?Medium

When the test only verifies that your mocks were called in the order you configured — at that point it tests the test.

Keep a layer of tests that exercise real DML and real automation, so the suite proves the system works and not just that the wiring matches your assumptions.

Async, events & integration (51–66)

51 Async work does not complete in your test.Easy

Async jobs run at Test.stopTest(). Assert after it, not before.

If you assert inside the start/stop block, the job has not run and your test will fail for the wrong reason.

52 Queueable chaining fails in a test.Medium

Tests allow one chaining level. Assert the first job's work and that the next was enqueued; test later links separately.

Design chains so each link is independently testable — a chain you can only test end-to-end is one you cannot debug.

53 How do you test a batch job's finish()?Medium

Run the batch inside start/stop and assert the side effects of finish() afterwards, or call it directly with a constructed context for unit-level checks.

Its error reporting is the part most worth testing, since that is what tells you about partial failure.

54 Testing a scheduled job.Easy

System.schedule() inside the test and assert on CronTrigger; separately call the execute method to test the logic.

Keeping the schedulable trivial — it just starts a batch — makes this almost free.

55 How do you test CDC-driven logic?Hard

Test.enableChangeDataCapture() before the DML, then deliver the event bus, then assert the subscriber's effect.

Also test the gap-event path if your consumer must handle it — ignoring gap events silently loses changes.

56 You need to test a platform event retry.Hard

Make the handler throw EventBus.RetryableException under a test condition and assert your retry counting and dead-letter behaviour.

The retry limit is small, so what matters is proving you stop and record rather than loop forever.

57 A test asserts idempotency. How?Medium

Run the operation twice and assert the state after the second run is identical to after the first — same counts, same values.

That one test prevents most duplicate-side-effect incidents caused by retries and redelivery.

58 Your async test passes but production fails under load.Hard

Unit tests are single-threaded with clean data. Production has concurrency, lock contention, partial failures and real volumes.

Scenario-test in a sandbox: two simultaneous Bulk API loads against related data, and watch for lock errors and duplicates.

59 How do you test a Continuation?Hard

Test.setContinuationResponse() with a mocked response and invoke the callback method, asserting the result it produces.

It is fiddly, which is one reason to keep continuation logic thin and push the real work into a testable service.

60 Testing code that reads a Named Credential.Medium

The callout is mocked, so the credential is never used — which is good, because tests must never make real callouts.

Assert on the request endpoint and headers your code constructs, so a misconfigured callout: reference is still caught at the shape level.

61 How do you test an integration end to end?Medium

Not in Apex unit tests. Use a post-deployment smoke suite (Postman collection run by Newman, or a scripted call) against a sandbox, asserting the real contract.

Unit tests prove your logic; smoke tests prove the deployed system works. Both belong in CI at different stages.

62 You need to test behaviour when the remote system is down.Medium

A mock that throws CalloutException, and another that returns a 503 — then assert you retried appropriately, logged, and did not corrupt local state.

A timeout in particular should be treated as "unknown outcome", not failure, which is a behaviour worth asserting explicitly.

63 Testing an LWC that calls Apex.Medium

Jest with a registered Apex wire adapter mock, emitting three cases: data, error and empty — then assert the rendered DOM for each.

Those three cases catch most real component defects and run in milliseconds with no org involved.

64 How do you test a flow?Medium

Flow Tests for record-triggered flows — declarative, asserting the outcome for a given input record — and Apex tests for invocable actions.

Put both in CI. An org where flows carry significant logic and have no tests has an untested application.

65 You need to verify a trigger's bulk behaviour with related records.Medium

Insert 200 records across several parents, with some qualifying and some not, then assert per-parent outcomes.

Using one parent for all 200 hides both the grouping bugs and the lock contention you would see in production.

66 Your test suite has no failure-path coverage at all.Medium

Then the error handling has never run. Add, per integration: a failure response, a timeout, a malformed payload, and a partial-success DML.

Error paths are where production incidents live and where coverage is almost always thinnest.

Permissions & context (67–80)

67 Your code passes tests and fails for real users.Medium

Tests run in system mode, so they never exercise sharing or FLS.

Use System.runAs with a user built from a minimum-access profile plus only the permission set under test. Testing as an admin proves nothing about access.

68 System.runAs does not seem to enforce FLS.Hard

runAs changes the user context for sharing, but your Apex still has to enforce FLS — with WITH USER_MODE, as user, or stripInaccessible.

So the test proves enforcement only if the code attempts enforcement. That combination is exactly what you want to verify.

69 Mixed DML error when creating a test user.Easy

User is a setup object. Wrap its creation (and permission set assignment) in System.runAs, which gives you a separate context.

That is the standard idiom for test setup involving users, groups or permission set assignments.

70 You need to test a guest user context.Hard

You cannot fully simulate a guest user in Apex tests. Test with a minimum-access user for the code path, then verify the real guest behaviour manually in an incognito window.

Given guest exposure is the most common cause of Salesforce data leaks, the manual verification is not optional.

71 A test needs a user with a permission set licence.Medium

Assign it in the test within runAs, but be aware licence availability differs by org — which makes such tests fragile, especially in packages.

Where possible, test the logic independently of the licence and verify the licence requirement in a documented manual check.

72 How do you test that a restriction rule applies?Hard

Create data that should and should not be visible, then query under System.runAs as an affected user and assert the row count.

Restriction rules apply to Apex queries too, which is exactly why this test is worth having — and why an integration user may be narrowed unexpectedly.

73 Tests pass in one org and fail in another.Medium

Org-dependent assumptions: profile names, picklist values, record types, Custom Metadata rows, installed packages, or SeeAllData.

Make tests self-sufficient — create what they need, inject configuration, and query by developer name rather than label.

74 A packaged test fails in a subscriber org.Hard

It depends on something only your org has, or the subscriber's automation interferes with your inserts.

Build all data in the test, never use SeeAllData, tolerate their validation rules and triggers firing, and avoid assumptions about profiles and picklists.

75 How do you test logic that branches on a custom permission?Medium

Create a user with and without it (via a permission set assigned inside runAs) and assert both branches.

Testing only the permitted branch means the deny path — usually the security-relevant one — has never executed.

76 Your test asserts an admin can do something. Is that enough?Easy

No — admins can do nearly everything, so the test proves little. The valuable assertions are about restricted users: what they can and cannot see or do.

Every access-sensitive feature deserves at least one test as a least-privileged user.

77 You need to test timezone-sensitive behaviour.Hard

Create users in two timezones and assert under each with runAs, or inject the timezone so the logic is testable directly.

Timezone bugs are reliably invisible to a developer in the same zone as the test data, which is why they reach production so often.

78 How do you test that an integration user cannot overreach?Medium

Run the endpoint's logic under runAs as that user and assert it cannot read or write what it should not.

That converts a permission review into an automated regression test, which is far more durable than a checklist.

79 A test relies on the running user being the record owner.Medium

Set ownership explicitly in the test data rather than depending on who created it — the creating user is the owner by default, and that changes under runAs.

Implicit ownership assumptions are a common cause of tests that behave differently in a packaged context.

80 How do you keep permission tests from being brittle?Medium

Assert on capability rather than configuration: "this user cannot read the field" rather than "this user has profile X".

Then reorganising permission sets does not break the suite, while a genuine access regression still does.

Coverage, CI & judgement (81–100)

81 Org coverage is 78% and a deployment fails on coverage.Medium

You need 75% org-wide and every trigger covered. A deployment can also fail because the specific classes being deployed lack coverage when using RunSpecifiedTests.

Set a per-class floor in CI on changed classes rather than relying on the org number, which hides exactly the regressions you care about.

82 A class sits at 40% but the org average carries it.Medium

It passes until someone deletes the test that was inflating the average, and then an unrelated deployment fails.

Per-class gates on changed code catch this at the point of change, which is also when it is cheapest to fix.

83 Which test level for a hotfix deployment?Medium

RunSpecifiedTests naming the tests that cover the changed code — fast, but the deployment is rejected if coverage of the changed classes is insufficient.

For a normal release, RunLocalTests is the sensible default: everything except managed-package tests.

84 Validation takes 40 minutes and developers stop waiting.Medium

Tier the pipeline: static analysis and Jest on every PR (two minutes), delta validation for develop, full validation for release branches.

Then use validate-then-quick-deploy so production windows are minutes. Feedback slower than ten minutes gets batched around, which defeats CI.

85 How do you speed up a slow test suite?Medium

Reduce DML (in-memory tests, @TestSetup, fake Ids), remove redundant tests that cover the same branch, and stop creating 200 records where 5 prove the logic.

Measure first — the Tests tab shows per-method duration, and a handful of tests usually account for most of the time.

86 Parallel test execution causes lock errors.Hard

Tests are contending on shared records — often the same parent account or the same user.

Fix the contention (unique data per test) rather than disabling parallelism, because the contention usually mirrors a real production hotspot.

87 Should tests run on every commit or every PR?Easy

Fast checks on every commit, the full validation on PR into a protected branch. The gate should match the blast radius of the target.

A PR into main should be slow, thorough and boring; a feature push should answer in minutes.

88 How do you test a data migration?Hard

Rehearse it in a Full sandbox with production-shaped data, timed, with row counts and checksums compared before and after — and the rollback rehearsed too.

Unit tests cannot cover this; the risk is volume, duration and data shape, none of which a test org reproduces.

89 A bug reaches production. What is the first thing you write?Easy

A failing test that reproduces it. Then fix it and watch the test pass.

That guarantees the defect cannot return silently, and it grows the suite in exactly the places where it has proven weak.

90 How do you know whether your suite is actually good?Hard

Break things deliberately. Invert a condition, delete a line, change a constant — then run the tests. The proportion that fail tells you far more than any coverage number.

Ten minutes of this is the most informative test-quality exercise available.

91 A reviewer demands 90% coverage on a trivial class.Medium

Argue for verified behaviour over a percentage, and propose a per-class floor that applies to logic rather than accessors and DTOs.

Blanket targets produce assertion-free tests, which is worse than lower coverage with meaningful tests.

92 You inherit 2,000 tests, many meaningless.Hard

Do not delete in bulk — you lose the deployment coverage you depend on. Instead add meaningful tests alongside, and retire the worthless ones as you touch the code they cover.

Prioritise adding assertions to existing tests for critical paths; that is cheaper than rewriting and immediately valuable.

93 Tests fail intermittently in CI.Hard

Usual causes: dependence on real SOSL indexing, on today's date, on record order from an unsorted query, on static state, or on parallel contention.

Flaky tests get ignored and then disabled, so fix them as high priority — a suite people distrust provides no protection.

94 Should CI block a deployment on a single failing test?Easy

Yes. A tolerated failure becomes a permanent one, and then the next real failure is invisible among the noise.

If a test is genuinely wrong, fix or delete it deliberately — never leave it red.

95 How do you test declarative automation nobody wrote tests for?Medium

Flow Tests for record-triggered flows, and Apex tests that insert records and assert the automation's effect — treating the whole save as the unit under test.

In orgs where flows carry most of the logic, this is the application's test suite, and its absence is a bigger risk than low Apex coverage.

96 Who should write the tests?Easy

The person writing the code, as they go — tests written later by someone else encode the implementation rather than the intent.

Review the tests as carefully as the code; a PR with good code and decorative tests is not done.

97 A test documents behaviour everyone agrees is wrong.Medium

Change the test and the code together, in one reviewed change, with the reason in the commit message.

Silently changing behaviour without updating the test (or vice versa) is how a codebase loses the ability to explain itself.

98 You have one hour to improve a test suite. What do you do?Medium

Add assertions to the tests covering the most critical path, and add a bulk test and a failure test to the busiest trigger.

That is a bigger improvement than ten new tests on trivial classes, because it targets where production incidents actually originate.

99 How do you argue for test investment to a sceptical manager?Medium

In their terms: deployment failures, hotfix frequency, and time spent diagnosing production issues — with your own numbers from the last quarter.

"Tests are good practice" loses the argument. "Three of our last five incidents would have been caught by a bulk test" wins it.

100 One habit that most improves test quality?Hard

Writing the bulk test and the negative test first — 200 records with variation, and a record that must fail.

They catch most real defects, they shape the code toward being bulk-safe, and they are exactly the two that get skipped when coverage is the target.
