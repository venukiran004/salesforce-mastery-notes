Debugging & Troubleshooting

How to find out what actually happened — debug logs, the Developer Console, checkpoints, LWC debugging, and a lookup table for the errors you'll meet most often.

A method, not guesswork

The troubleshooting loop

Debug logs

  • Setup → Debug Logs → New, add a trace flag on the user who reproduces the issue (not yourself).
  • Choose a debug level — start with Apex = FINEST, Database = INFO, and leave the rest low.
  • Reproduce the problem.
  • Open the log and read it in this order: the exception at the bottom → CUMULATIVE_LIMIT_USAGE → the CODE_UNIT_STARTED entries showing what ran, in order.
Log categorySet it high when…
Apex CodeDebugging your own logic — FINEST shows every statement and variable assignment
DatabaseInvestigating SOQL/DML counts and rows returned
WorkflowA flow, workflow rule or approval isn't firing — this shows entry criteria evaluation
ValidationA save is blocked and you don't know by what
CalloutIntegration debugging — shows request and response
SystemRarely; very noisy
Visualforce / Apex ProfilingView state and performance analysis
✂️
Logs truncate at 20 MB And when they do, Salesforce drops the earliest entries — so a FINEST log of a bulk operation often loses exactly the part you needed. Narrow the log level, reproduce with one record, or use targeted System.debug statements with a distinctive prefix you can search for.
// Make your debug statements findable and useful
System.debug(LoggingLevel.ERROR, '### AccountService.calculate ENTRY ids=' + ids);

// Log limits at checkpoints — the fastest way to find what's expensive
System.debug(LoggingLevel.ERROR, '### after query: SOQL=' + Limits.getQueries()
    + ' rows=' + Limits.getQueryRows()
    + ' CPU=' + Limits.getCpuTime()
    + ' heap=' + Limits.getHeapSize());

// Dump a complex structure readably
System.debug(LoggingLevel.ERROR, '### wrapper: ' + JSON.serializePretty(wrapperList));

// LoggingLevel.ERROR survives lower log levels, so these still appear
// when Apex Code is set to ERROR — useful for production diagnostics.

Reading the log

MarkerMeaning
CODE_UNIT_STARTED / FINISHEDA trigger, flow, class or validation began/ended — the execution tree. Repeated entries for the same trigger = recursion
SOQL_EXECUTE_BEGIN / ENDEach query and its row count — spot the query in a loop here
DML_BEGIN / ENDEach DML and how many rows
FLOW_ELEMENT_BEGINFlow execution step by step, including decision outcomes
VALIDATION_RULE / VALIDATION_FAILExactly which rule blocked the save
CUMULATIVE_LIMIT_USAGEFinal consumption of every governor limit
LIMIT_USAGE_FOR_NSUsage broken down per namespace — how you prove a managed package consumed your queries
FATAL_ERRORThe exception, with the stack trace and line number

The tools

Developer Console

  • Execute Anonymous (Ctrl+E) — run Apex instantly
  • Query Editor — SOQL with inline editing of results
  • Checkpoints — heap dumps at a line, showing every variable's value
  • Execution Overview — Timeline, Executed Units and a Limits tab
  • Test tab with per-line code coverage highlighting

VS Code

  • Apex Replay Debugger — step through a downloaded debug log line by line with real variable values
  • Apex Interactive Debugger (paid) — true breakpoints in a sandbox
  • sf apex tail log --color — live streaming logs
  • Apex Log Analyzer extension for flame graphs

Browser DevTools (LWC)

  • Enable Debug Mode (Setup → Debug Mode) for unminified JS
  • Inspect the shadow root in Elements; breakpoints in Sources
  • Network tab → aura/webruntime calls show Apex payloads and errors
  • console.log(JSON.parse(JSON.stringify(data))) — wire results are Proxies and log unhelpfully raw

Org health

  • Salesforce Optimizer — a report on limits, unused fields, over-complex config
  • Security Health Check — settings scored against a baseline
  • Setup Audit Trail — who changed what config, last 6 months
  • Apex Jobs and Apex Exception Email for async failures
  • Event Monitoring (Shield) for full API/UI telemetry

Diagnosing in production

🏭
You can't attach a debugger to production So build observability in advance: a custom Error_Log__c object written from every catch block and Finalizer, with the class, method, record Id, stack trace and a correlation id. A report on today's errors and an email alert turn "a user says it's broken" into "here is the exact failure at 14:03".
  • Apex Exception Email — Setup → Apex Exception Email, add the developer distribution list. Unhandled exceptions in async code go here.
  • Setup Audit Trail — the first place to look when "it worked yesterday".
  • Apex Jobs — check Status and NumberOfErrors; a Batch job can complete with failures.
  • Debug logs on a specific user are allowed in production — just keep the level low and remove the trace flag afterwards.
  • Event Monitoring (Shield) for API usage, report exports and page performance.

Interview questions

1 A user reports "it doesn't work". What are your first three steps?Easy

① Reproduce it as that user — "Login As" is the single highest-yield step, because a large share of reports are permission or sharing issues, not bugs. ② Get the exact error text and the record Id and timestamp. ③ Set a trace flag on that user and reproduce with a debug log capturing it. Only then start reading code.

2 Where in a debug log do you look first, and why?Medium

Bottom first — FATAL_ERROR gives the exception, line number and stack trace. Then CUMULATIVE_LIMIT_USAGE to see whether you're near a governor limit, and LIMIT_USAGE_FOR_NS to attribute usage per namespace. Then scan the CODE_UNIT_STARTED entries to see what ran and in what order — repeated entries for the same trigger reveal recursion, and unexpected entries reveal automation you didn't know existed.

3 Your debug log is truncated and missing the part you need.Medium

Logs cap at 20 MB and drop the earliest entries. Reduce the noise: set only Apex Code to FINEST and everything else to NONE or ERROR; reproduce with a single record rather than a bulk operation; add targeted System.debug(LoggingLevel.ERROR, '### marker') statements you can search for; or use checkpoints in the Developer Console to capture a heap dump at one line instead of logging everything.

4 What is the Apex Replay Debugger and when would you use it?Hard

A VS Code feature that replays a downloaded debug log as if it were a live debugging session — you step line by line and inspect real variable values, with no need for a live connection. It needs the log captured at FINEST.

Use it for logic bugs where you need to see how a value evolved. The paid Apex Interactive Debugger gives true live breakpoints in a sandbox, and there's a free Apex Debugger for scratch orgs.

5 "It worked yesterday and nobody changed anything." How do you check?Medium

Setup Audit Trail — six months of configuration changes with user and timestamp; someone almost always did change something. Then: was there a release (check Release Updates that auto-activated)? Was a managed package upgraded? Did a scheduled job fail overnight (Apex Jobs)? Did data volume cross a selectivity threshold, turning a fine query into a non-selective one? And check deployment history in your pipeline.

6 An LWC shows a blank error with no message. How do you debug it?Hard

Enable Debug Mode for your user so the JS is unminified. Open DevTools → Network and inspect the Apex/aura response, which carries the real server-side message. Add a reduceErrors helper because Apex, wire and LDS errors all have different shapes (error.body.message, error.body.pageErrors, error.message).

The root cause is usually Apex throwing a raw exception — fix it at source by throwing AuraHandledException with a meaningful message.

7 How do you find out whether a managed package is consuming your governor limits?Hard

The LIMIT_USAGE_FOR_NS section of the debug log breaks consumption down per namespace, so you can see exactly how many queries and DML statements the package used versus your own code (the default namespace). The Developer Console's Execution Overview shows the same split.

If a package is the problem, options are: reduce your own footprint, move your logic async so it gets a fresh transaction, or raise it with the vendor with the log as evidence.

8 How do you make production failures diagnosable before they happen?Hard

Build observability in: a custom Error_Log__c object populated from every catch block, Finalizer and flow fault path, capturing class, method, record Id, stack trace, timestamp and a correlation id shared with integrated systems. Add a report and an email/Slack alert on today's errors.

Then: set Apex Exception Email recipients, redirect flow error emails away from "last modified by", monitor AsyncApexJob for failed batches, and log limit usage at checkpoints in expensive jobs. The goal is that the first person to know is you, not the customer.

Quick check

1. Which log section proves a managed package used your SOQL budget?
It breaks limit consumption down per namespace, separating your code from installed packages.
2. A user can't see a record. What's the fastest first check?
Most "it doesn't work" reports are access issues. The Sharing button lists every reason a user does or doesn't have access.
3. Your debug log is missing the beginning of the transaction. Why?
Reduce the log level on other categories, or reproduce with a single record instead of a bulk operation.
