APIs & Callouts — 100 Scenarios

Choosing an API, OAuth and Named Credentials, idempotency and retries, timeouts, bulk and composite, exposing endpoints safely, versioning and observability.

📚
How to use this Answer out loud in ninety seconds, then open the answer. Concepts on APIs & Callouts and its Advanced section.

Choosing an API (1–16)

1 A partner needs to load 2 million records nightly.Easy

Bulk API 2.0: they upload a CSV, Salesforce chunks and processes it asynchronously. Per-record REST calls would exhaust the daily API allocation and take hours.

Give them an External Id to upsert against so re-running the job is safe.

2 A partner wants to "submit an order" in one call.Medium

An Apex REST endpoint with a business contract — not raw sObject access. You then own validation, logic, logging and a stable interface that survives schema change.

Exposing /sobjects/Order couples them to your field names, and renaming a field breaks a contract you did not know you had.

3 Create an account and three contacts atomically from outside.Medium

Composite Graph (or sObject Tree) — one round trip, reference ids linking children to the parent, all-or-none per graph.

Four separate REST calls give you four round trips and no atomicity.

4 A client needs to read data shaped across several objects.Medium

The GraphQL API lets the client shape its own reads, or a purpose-built Apex REST endpoint if you want to control the contract.

GraphQL reduces your maintenance; a custom endpoint gives you a stable shape and a place to add logic.

5 You need to query a remote system without storing the data.Medium

Salesforce Connect external objects over OData — the data stays remote and is queried live.

Accept the limitations: reporting, sharing and SOQL behaviour differ, and the remote system's availability becomes your page's availability.

6 A custom client must respect layouts and FLS.Medium

The UI API — it returns layout metadata, picklist values and record data with FLS applied, so you do not re-implement them.

Building that yourself over the sObject API means duplicating platform behaviour you will get subtly wrong.

7 Fire-and-forget notification to several systems.Easy

Platform events — publish once, multiple subscribers consume independently.

Remember delivery to each subscriber consumes allocation, and delivery is at-least-once with no ordering guarantee. See Events.

8 SOAP or REST for a new integration?Easy

REST, unless the counterparty mandates SOAP (common with older enterprise middleware and some finance systems).

SOAP remains fully supported, and WSDL-generated Apex is occasionally the pragmatic choice — but it is more brittle to regenerate.

9 Outbound Messages — when are they still appropriate?Medium

Rarely. They are declarative, retry automatically and need no code, which is their appeal — but they are SOAP, tightly coupled to field sets, and awkward to version.

For new work, platform events or an async callout give you far better control and observability.

10 External Services versus hand-written Apex callouts.Medium

External Services generates invocable actions from an OpenAPI spec, which is excellent for admin-consumable integrations in Flow.

Hand-written Apex when you need control over retries, error classification, payload shaping or anything the schema registration cannot express.

11 You need a synchronous response inside a user's save.Hard

Possible but risky: you cannot call out after DML, the transaction has a 120-second cumulative callout budget, and the user is waiting.

Prefer validating synchronously with a fast call and doing the heavy work asynchronously. If latency is genuinely unavoidable, a Continuation avoids consuming a long-running request slot.

12 Middleware or direct point-to-point?Medium

Middleware once you have more than a couple of consumers of the same data, a system of record you expect to replace, or real transformation and orchestration needs.

For a single simple feed it is ceremony. See API-led layering.

13 A partner can only poll. How do you limit the damage?Medium

Give them a narrow, indexed, incremental query (changes since a timestamp they pass), cap the page size, and give them their own integration user so you can attribute and rate-limit them.

Then measure their consumption against your daily API allocation.

14 You need to push data out when a record changes.Medium

Change Data Capture if the consumer wants raw changes, or a platform event if you want to publish a business-meaningful fact with a shape you control.

Prefer the event: a fact ("OrderShipped") is a contract you can keep; a field-level change stream exposes your schema.

15 Connect REST API — what is it for?Easy

Chatter, feeds, files, communities and user profiles — functionality the sObject APIs do not expose cleanly.

If you are manipulating FeedItems or community content, this is the API that already knows the rules.

16 How do you choose between all of these quickly?Medium

Volume → Bulk. Multiple dependent writes → Composite Graph. A business operation → Apex REST. Client-shaped reads → GraphQL. Layout-aware client → UI API. Fire-and-forget → events. No storage → Salesforce Connect.

Default to a business contract over table access whenever a partner is involved.

Authentication (17–32)

17 Which OAuth flow for a CI pipeline?Easy

JWT bearer — a certificate on a Connected App and a key in CI secrets. No password, no refresh token to leak, no interactive step.

Client credentials is the simpler modern alternative, tied to a nominated integration user.

18 A vendor asks for the username-password flow.Medium

Decline. It stores a credential, bypasses MFA, and is being actively restricted on the platform.

Offer JWT bearer or client credentials. If they genuinely cannot, that is a vendor risk to escalate rather than a configuration to make.

19 A refresh token works for months then stops.Medium

Refresh token policy on the Connected App — it may expire after a period of inactivity, or it was revoked, or the user was deactivated or had their password reset.

Also check whether someone rotated the connected app's secret.

20 You get 401 on every call despite a valid token.Medium

Most commonly you are calling login.salesforce.com instead of the instance_url returned with the token.

Then check scopes, IP restrictions on the Connected App, and whether the token has actually expired.

21 How should an outbound callout authenticate?Easy

A Named Credential with an External Credential — the endpoint and auth live in configuration, token refresh is handled, and your Apex calls callout:My_Service/path with no secret in sight.

Rotation becomes a config change rather than a deployment.

22 Named Principal or Per-User Principal?Medium

Named Principal = one shared identity for the whole org, simple and appropriate for system-to-system. Per-User = each user authenticates individually, so the remote system sees who acted.

Choose per-user when the remote system's own authorisation or audit depends on the identity.

23 Who can use a Named Credential?Medium

Access to the external credential is granted through permission sets, so you control which users and integration accounts can use it.

That is a real improvement over the old model, and worth auditing — a credential available to everyone is a credential available to anyone.

24 Secrets are currently in a custom setting.Medium

Anyone who can read the setting can read the secret, and it is in your metadata and git history.

Move to a Named Credential / External Credential, then rotate the secret — because the old one must be assumed compromised.

25 Your integration certificate expires next month.Medium

Rotate it with overlap: generate the new one, add it to the remote side, switch, then retire the old.

Put every certificate expiry in a shared calendar with an owner. Expiry is the single most common cause of an integration outage, and it is entirely predictable.

26 An integration user should not be a human's admin account.Easy

Correct — it breaks the day they leave, and it makes every audit trail ambiguous.

Use a dedicated integration user with a least-privilege permission set, IP restrictions where egress is stable, and minimal OAuth scopes.

27 How do you scope OAuth scopes properly?Medium

Request the minimum: an API scope plus refresh_token/offline_access if needed. full is almost never justified.

Scopes are a security control a reviewer will look at, and "the documentation said full" is not a justification.

28 Credentials leaked. What is your order of action?Hard

Revoke the tokens from the Connected App first (fastest), then rotate the certificate or secret, then update the pipeline's stored secret.

Afterwards: move to JWT if you were not already, add IP restrictions, tighten scopes, and set refresh tokens to expire on inactivity rather than "until revoked".

29 An inbound caller must only see their own data.Hard

Authenticate as a user whose access is the restriction — a per-partner integration user — and write the Apex with sharing so record access does the filtering.

A WHERE clause on an elevated query means a bug there becomes a breach; sharing fails closed.

30 External Client Apps versus Connected Apps.Medium

External Client Apps are the newer, more granular framework — prefer them for new integrations.

Understand both, because every existing org has Connected Apps and you will be auditing and migrating them.

31 mTLS is required by the remote system.Hard

Supported via certificate configuration on the Named Credential — you upload or generate the client certificate and the remote side trusts it.

Plan the certificate lifecycle carefully: mTLS failures are opaque, and expiry takes the integration down with an unhelpful error.

32 How do you test authentication without real credentials?Medium

Mock the callout in Apex tests — the credential is never exercised, which is correct because tests must never make real calls.

Verify the real auth with a Postman request or a post-deployment smoke test against a sandbox. See Postman.

Idempotency, retries & timeouts (33–52)

33 A timeout occurred. Do you retry?Hard

Not blindly — a timeout means you do not know whether the remote system succeeded. Treating it as failure and retrying is how duplicate orders get created.

Query the remote system for your correlation id first, or make the operation idempotent so a retry is harmless.

34 How do you make an inbound endpoint idempotent?Medium

Require an idempotency key or external id on every request, upsert against a unique field, and return the same response for a repeated key rather than erroring.

The unique index is the real guarantee; a pre-check query does not hold under concurrency.

35 How do you make an outbound call idempotent?Medium

Send your own correlation id, and persist the fact that you sent it before the callout.

Then an unknown outcome can be resolved by querying rather than re-sending, and the remote system can deduplicate on the id.

36 What timeout should you set?Medium

Explicitly, always — the default is 10 seconds and the maximum is 120. Choose from the remote system's realistic p99, not optimism.

And budget the total: three sequential 40-second timeouts exhaust the transaction's cumulative callout allowance.

37 How should you classify HTTP responses?Medium

2xx success; 409 often "already processed" (treat as success for an idempotent write); 429 and 5xx transient (retry with backoff); other 4xx your bug (dead-letter, do not retry).

Treating everything non-200 identically is why integrations either retry forever or lose data.

38 How much retry is right?Medium

Exponential backoff with jitter, about three attempts, then dead-letter. Beyond that a failure is usually deterministic.

Jitter matters: synchronised retries from many records turn a brief outage into a longer one.

39 What is a dead-letter destination here?Medium

A custom object holding the payload, endpoint, error, attempt count and correlation id — inspectable, reportable and replayable.

A log line is not a dead-letter queue. If nobody can see what failed and re-run it, the failure is permanent.

40 The remote system is down and you keep calling it.Hard

Add a circuit breaker: after n consecutive failures, stop calling for a cooling period and fail fast.

Store the breaker state somewhere all transactions can see (a custom setting or a record), since statics do not span transactions.

41 A retry created a duplicate record.Medium

The operation was not idempotent. Add a unique external id and upsert, then treat the duplicate-value error as "already done".

Retry safety is a property you design in, not something you add after the first incident.

42 You cannot call out after DML.Easy

Correct — in one transaction, once you have done DML you cannot make a callout.

Publish a platform event or enqueue a Queueable so the callout happens in a fresh transaction after commit. That is also where retry belongs anyway.

43 A callout per record over 100,000 records.Hard

Batch Apex with AllowsCallouts and a very small scope, since callout limits are per execution.

Far better if the remote API supports a batch payload — one call per 200 records rather than 200 calls, which is also kinder to their rate limits.

44 How do you handle a 429 from the remote system?Medium

Respect Retry-After if present, back off, and reduce your concurrency — a 429 means you are the problem.

Build the rate limit into your design (a cap on parallel batch jobs) rather than discovering it through rejection.

45 Your integration silently stopped working.Hard

Alert on absence, not just errors: a feed that normally delivers 5,000 records and delivered zero should page someone.

Most monitoring only catches failures, and silence is the more dangerous failure mode.

46 How do you know an integration is healthy?Medium

Business-level reconciliation: orders in Salesforce yesterday versus orders in the remote system yesterday. Counts, not logs.

Plus a freshness metric — the age of the oldest unprocessed item, which is the earliest warning you will get.

47 A partial failure left systems inconsistent.Hard

There is no distributed transaction. You need a compensating action for every step with external side effects — and the compensation must itself be idempotent, because it will be retried.

Design the reversal at design time; afterwards it is a data-repair project.

48 How do you trace a request across systems?Medium

A correlation id generated at the edge, passed in a header, stored on the record, and logged at every hop.

Non-negotiable. Debugging a distributed flow without one is guesswork.

49 What should an integration log contain?Medium

Direction, endpoint, status, duration, attempt number, correlation id and the record Id — and not the sensitive payload.

Logging full payloads creates a second copy of your data with weaker controls.

50 A nightly job double-processed after a restart.Medium

No high-water mark and no idempotency. Persist "processed up to here" and make each operation safe to repeat.

Then a restart resumes rather than duplicating.

51 You need exactly-once delivery.Hard

You cannot have it across systems. What you can have is at-least-once delivery plus idempotent processing, which is operationally equivalent.

Anyone insisting on exactly-once is usually asking for idempotency without knowing the term.

52 How do you replay failed messages?Medium

Store enough in the dead-letter record to reconstruct the call, and provide a button or batch to re-submit selected rows.

Replay must be idempotent, because some of what you replay may have partially succeeded.

Volume & performance (53–68)

53 A screen needs a 30-second callout.Hard

Continuations — the request is parked server-side without holding a thread, and a callback resumes it, so it does not consume a concurrent long-running request slot.

Up to three can be chained. Without it, a handful of such users degrades interactive performance for the whole org.

54 Interactive users get errors while your integration runs.Hard

The concurrent long-running request limit — ten synchronous requests over five seconds per org, shared with real users.

Move integration work off the synchronous path. This limit's symptom appears nowhere near its cause.

55 Your daily API allocation is exhausted by mid-afternoon.Medium

Find the consumer from the API usage page or Event Monitoring — usually a polling integration.

Replace polling with events or CDC, batch with Composite, and alert at a percentage of the limit rather than discovering it at 100%.

56 A 60MB response blows your heap.Medium

Page the remote API, request only the fields you need, and accept gzip.

If the remote system cannot page, the transformation belongs in middleware — Apex heap is 6MB synchronous, 12MB async.

57 Compression — worth enabling?Easy

Yes, for large payloads: accept and send gzip. It is often the easiest latency win available and costs almost nothing to configure.

Verify the remote side honours it rather than assuming.

58 How many records per Composite call?Easy

Composite allows up to 25 subrequests; composite/sobjects handles up to 200 records of one object with an allOrNone flag.

For more than that, Bulk API. Looping single-record REST calls for volume is the mistake to avoid.

59 Bulk API parallel mode causes lock errors.Medium

Chunks are contending on shared parents. Switch to serial — slower and it finishes, versus faster and it fails.

Better still, sort the file by parent Id so children of the same parent land in the same chunk. That is the cheapest migration optimisation there is.

60 A load triggers all your automation per row.Medium

Triggers, flows, validation, roll-ups and sharing recalculation all run per record, which can multiply the load time by an order of magnitude.

Use a bypass switch for the load user, then run a reconciliation pass afterwards to apply what was skipped.

61 You need to extract 20 million rows.Hard

Bulk API with PK chunking, which splits the query by Id ranges so each chunk is selective.

A single unselective query over 20 million rows will time out before it returns anything.

62 An integration is slow and you cannot tell why.Medium

Log duration per hop with the correlation id. Usually it is remote latency, not your code — and you cannot fix what you have not attributed.

Also check whether you are making N calls where one batched call would do.

63 Should you cache remote data in Salesforce?Medium

Only with a defined freshness requirement and an invalidation strategy — otherwise you have created a second system of record that silently diverges.

Platform Cache for short-lived reference data; a record with a timestamp when users need to see how fresh it is.

64 How do you rate-limit an inbound partner?Medium

At the gateway, not in Apex — and give each consumer its own integration user so you can measure and cap them individually.

Inside the org, bound page sizes and reject oversized requests rather than trying to process them.

65 An unbounded request payload crashes the transaction.Medium

Cap the request size and the record count explicitly, and return a clear 400 when exceeded.

"The partner sent 50MB" should be a documented rejection, not a heap failure.

66 Sequential callouts are too slow.Medium

Reduce the number (batch the payload), or parallelise across separate async executions — Apex has no true concurrent HTTP within one transaction.

And remember the cumulative 120-second budget applies to the whole transaction.

67 How do you size a nightly integration window?Medium

Measure a representative run, add headroom for growth, and check it does not collide with other scheduled jobs for batch concurrency.

Then monitor the duration trend so you see the window closing months before it fails.

68 The integration works in sandbox and is slow in production.Medium

Real data volume, real query selectivity, real remote latency, real concurrency and real rate limits — sandbox mocks hide all of them.

Run a timed rehearsal in a Full sandbox, and a post-deployment smoke test against the real endpoints.

Exposing endpoints (69–84)

69 What does a good Apex REST endpoint look like?Medium

A versioned path, a typed request and response DTO, explicit validation, meaningful HTTP status codes, logging with a correlation id, and CRUD/FLS enforcement — because Apex does not do it for you.

And a documented contract the partner can build against.

70 How do you version an Apex REST endpoint?Medium

In the URL from day one (/orders/v1), supporting the old version while consumers migrate.

Adding versioning later means migrating every caller simultaneously, which is rarely possible.

71 A partner complains your API broke.Medium

Check what changed: a field rename, a validation rule, a required field, a picklist value — all of which are breaking changes if you exposed raw sObjects.

This is the argument for a business contract and DTOs: your schema can change without breaking anyone's integration.

72 Which status codes should you return?Easy

200/201 success, 400 for a malformed or invalid request, 401/403 for auth and permission, 404 for not found, 409 for a conflict or duplicate, 429 for rate limiting, 5xx only for your own faults.

Returning 200 with an error body makes every consumer write special-case handling.

73 Your endpoint returns the whole sObject.Medium

It leaks fields the partner should not see and couples them to your schema.

Return a DTO with exactly the fields in the contract — and enforce FLS, since serialising an sObject includes whatever happens to be populated.

74 How do you validate an inbound payload?Medium

Explicitly, before touching the database: required fields present, types and formats correct, enumerations allow-listed, collection sizes bounded.

Return a 400 listing every problem, not just the first — partners debugging one error at a time is a poor experience.

75 Should your endpoint accept a SOQL filter?Hard

Never. That is a generic query endpoint with your integration user's privileges, regardless of intent.

Accept typed parameters, allow-list sortable and filterable fields, and bound the rows.

76 How do you handle authentication errors clearly?Easy

401 for "not authenticated", 403 for "authenticated but not permitted" — and a message that does not reveal whether a record exists.

Distinguishing "no access" from "not found" in your messages can itself leak information.

77 An endpoint needs to be callable by a guest.Hard

Treat it as a fully public endpoint: rate limiting, CAPTCHA where appropriate, strict validation, bounded payloads, no without sharing, and no information disclosure in errors.

Review the guest profile's permissions field by field. See guest hardening.

78 How do you document an API for a partner?Easy

An OpenAPI spec plus a Postman collection with example requests, error cases and auth setup.

A working collection answers more partner questions than any prose document, and it doubles as your smoke test.

79 You need to deprecate an endpoint.Medium

Announce it, support both versions for a defined period, log usage of the old version so you know who is still calling, and chase them individually.

Turning it off on the announced date without usage data is how you break a partner you forgot about.

80 How do you test an endpoint end to end?Medium

Apex tests for the handler logic (constructing RestRequest/RestResponse), plus a Postman collection run by Newman against a sandbox after deployment.

Unit tests prove the logic; the smoke test proves the deployed system and the real auth.

81 A partner needs bulk upload to your endpoint.Medium

Accept a bounded collection (say 200 per request) with per-record results, so one bad record does not fail the batch — and point them at Bulk API for genuine volume.

Per-record results plus idempotency keys make retries straightforward.

82 Your API is used by a mobile app directly.Hard

Public clients cannot keep secrets, so use authorization code with PKCE rather than embedding credentials.

Also expect hostile input and version carefully — you cannot force app users to upgrade.

83 How do you monitor an exposed endpoint?Medium

Log every request with correlation id, status and duration, then report on volume, error rate and p95 latency by consumer.

Alert on error-rate spikes and on volume dropping to zero — the second catches a partner whose job has broken.

84 Security review of an endpoint you did not write.Hard

Check: running user and its privileges, explicit CRUD/FLS enforcement, sharing keyword, parameter validation and allow-listing, row and payload bounds, error messages for information disclosure, and whether secrets appear anywhere.

Then ask who can reach it — guest, partner, internal — because that determines priority.

Judgement (85–100)

85 The business asks for "real-time" integration.Hard

Decompose it: must the user see it before finishing their task (under ~2 seconds, synchronous), within seconds but nobody waiting (events), within minutes (events plus reconciliation), or overnight (batch, far cheaper)?

Often the real need is "I don't want to explain stale data", which a visible last-synced timestamp solves better.

86 Who owns each field in a two-way sync?Hard

Decide per field, not per object, and write it down — the ERP may own billing address while Salesforce owns preferences.

Most "bidirectional" requirements collapse into two one-way flows once you do this, which is dramatically safer.

87 A conflict rule was never agreed.Medium

Then the rule is "whichever job ran last", which nobody can defend. Agree explicitly: last-write-wins, source-of-truth-wins per field, or raise for human review.

Undecided conflict handling is a data-integrity incident with a future date.

88 Deletes are not propagating.Medium

Deletes are the hardest case and frequently unspecified. Decide whether a delete propagates, soft-deletes, or is ignored.

Also remember Salesforce deletes can be undone from the recycle bin, so a propagated hard delete elsewhere may be irreversible.

89 An integration has no documentation and its author left.Medium

Reverse-engineer from the logs and the Connected App usage, then document the contract, the schedule, the credentials and their expiry, and the failure handling.

Add monitoring and alerting first — an unmonitored integration you do not understand is the highest-risk thing in most orgs.

90 How do you plan an integration cutover?Hard

Run old and new in parallel where possible, compare outputs, then cut over with a tested rollback. Reconcile counts after the first full cycle.

A big-bang switch with no comparison period means your first evidence of a problem is a business complaint.

91 A vendor's API has no sandbox.Medium

Build a mock service you control, and agree a test account or a dry-run mode with the vendor.

Testing against production third-party systems is how test orders reach real customers — and it is a risk worth escalating in writing.

92 How do you decide synchronous versus asynchronous?Medium

Is a user waiting on the result, and is the result needed to proceed? If not, asynchronous — which gives you retry, isolation and no user-facing latency.

Synchronous integrations couple your availability to theirs, which is the cost people underestimate.

93 The remote system's availability is worse than yours.Medium

Then do not put it in a synchronous user path. Queue the work, degrade the feature gracefully, and show the user the operation is pending.

A circuit breaker prevents their outage from consuming your async capacity as well.

94 How do you cost an integration?Medium

API calls against your allocation, middleware licensing, storage if you persist the data, and the operational cost of monitoring and incidents.

The last is routinely ignored and is frequently the largest over several years.

95 A partner wants direct database access.Easy

There is none to give — no infrastructure or database access on a multitenant platform.

Offer the right API for their need, and a business contract rather than table access. Explaining this early avoids a design built on a false premise.

96 How do you keep an integration maintainable?Medium

A documented contract, DTOs decoupled from schema, Named Credentials for config, correlation ids, structured logging, a dead-letter path, a reconciliation job, and an owner.

Each is small. Together they are the difference between an integration you operate and one you fear.

97 What is the most common integration design mistake?Hard

Assuming success: no idempotency, no retry classification, no dead letter, no reconciliation — and treating a timeout as a failure.

Followed closely by exposing raw sObjects and calling it an API.

98 How do you handle an integration incident at 3am?Medium

With what you built beforehand: the correlation id, the integration log, the dead-letter queue, the runbook and the replay mechanism.

If none of those exist, the incident is an investigation rather than a recovery — which is the argument for building them on day one.

99 You inherit 20 undocumented integrations.Hard

Inventory first: which user, which Connected App, which API version, what schedule, what volume, who owns the other end.

Then prioritise by blast radius, add monitoring, and document as you go. API version retirement dates give you a forced deadline for the oldest.

100 One habit that most improves integrations?Hard

Designing for the second delivery: an idempotency key, classified retries, a dead letter, and a reconciliation job.

Every integration is retried eventually. Making the second attempt harmless converts most future incidents into non-events.
