Apex Triggers & Order of Execution

Context variables, the full save order, recursion control, a production-grade handler framework — and scenario questions with worked answers.

What a trigger is

Apex code that executes automatically before or after a DML operation on a specific object. It is the code equivalent of a record-triggered flow, but with full programmatic power.

trigger AccountTrigger on Account (
    before insert, before update, before delete,
    after  insert, after  update, after  delete, after undelete) {

    AccountTriggerHandler.run();          // one line — all logic lives in the handler
}

Order of execution

The exact sequence when a record is saved. Memorise this — it explains nearly every "why did my automation not work?" question.

1 · Load the recordThe original record is loaded from the database (or initialised for insert).
2 · Overwrite with new valuesNew field values from the request overwrite the old ones. No automation yet.
3 · System validationRequired fields, field data types, max length. (For UI saves only: layout-level rules run here too.)
4 · Record-triggered flows — before save"Fast Field Update" flows run before before-triggers.
5 · BEFORE triggersYour before insert/update/delete Apex.
6 · System validation againRe-runs the system checks plus custom validation on the values your trigger set.
7 · Duplicate rulesIf set to Block, the save stops here.
8 · Save to databaseRecord written — but not committed. Ids now exist.
9 · AFTER triggersYour after insert/update/delete/undelete Apex.
10 · Assignment rulesLead/Case owner assignment.
11 · Auto-response rulesLead/Case acknowledgement emails.
12 · Workflow rulesLegacy — field updates here cause the record to be saved again, re-firing before/after triggers once.
13 · Escalation rulesCase escalation.
14 · Record-triggered flows — after saveYour after-save flows. These run after workflow field updates.
15 · Entitlement rulesMilestones and entitlement processes.
16 · Roll-up summary fieldsParent records are recalculated — which fires the parent's triggers.
17 · Criteria-based sharingSharing rules evaluated.
18 · Grandparent roll-upsIf the parent is itself a detail record, the chain continues upward.
19 · CommitEverything is committed to the database. Only now do post-commit actions run.
20 · Post-commit logicEmails sent, @future/Queueable jobs enqueued, async paths, platform events published (Publish After Commit).
🔁
The three consequences that matter ① A workflow field update re-runs your triggers — the classic cause of "my trigger ran twice". ② A roll-up summary updating a parent fires the parent's triggers, cascading upward. ③ @future and emails only fire after commit, so they never see a rolled-back transaction.

Bulkification

A trigger receives up to 200 records per invocation. Data Loader sends 10,000 records as 50 chunks of 200 — and your governor limits reset per chunk, but not within one.

❌ Never

for (Account a : Trigger.new) {
  // SOQL in a loop → 101 error
  List<Contact> cs = [SELECT Id FROM Contact
                      WHERE AccountId = :a.Id];
  for (Contact c : cs) {
    c.Description = 'x';
    update c;        // DML in a loop
  }
}
→

✅ Always

Set<Id> accIds = Trigger.newMap.keySet();

List<Contact> toUpdate = new List<Contact>();
for (Contact c : [SELECT Id, AccountId FROM Contact
                  WHERE AccountId IN :accIds]) {
  c.Description = 'x';
  toUpdate.add(c);
}
if (!toUpdate.isEmpty()) update toUpdate;
✅
The bulkification checklist ① No SOQL/SOSL inside a loop. ② No DML inside a loop. ③ No @future/callout inside a loop. ④ Query with IN :setOfIds. ⑤ Collect into a List, DML once. ⑥ Guard with if (!list.isEmpty()). ⑦ Test with 200 records.

Recursion

Recursion happens when a trigger's own DML causes the same trigger to fire again — potentially hitting System.LimitException: Maximum trigger depth exceeded (16 levels) or silently doubling work.

How recursion happens — and how the static flag stops it

Solution 1 — static Boolean (simple)

public class TriggerControl {
    public static Boolean accountTriggerHasRun = false;
}

trigger AccountTrigger on Account (after update) {
    if (TriggerControl.accountTriggerHasRun) return;
    TriggerControl.accountTriggerHasRun = true;

    AccountTriggerHandler.handleAfterUpdate(Trigger.new, Trigger.oldMap);
}
⚠️
The flaw A blanket flag also blocks legitimate second runs. Load 400 records with Data Loader: chunk 1 (200 records) sets the flag, and chunk 2 is skipped entirely because statics persist across chunks in the same transaction. Data silently goes unprocessed.

Solution 2 — track processed record Ids (recommended)

public class TriggerControl {
    private static Set<Id> processedAccountIds = new Set<Id>();

    /** Returns only the records not yet processed in this transaction. */
    public static List<Account> filterUnprocessed(List<Account> records) {
        List<Account> fresh = new List<Account>();
        for (Account a : records) {
            if (!processedAccountIds.contains(a.Id)) {
                fresh.add(a);
                processedAccountIds.add(a.Id);
            }
        }
        return fresh;
    }
}

// In the handler
List<Account> toProcess = TriggerControl.filterUnprocessed(Trigger.new);
if (toProcess.isEmpty()) return;

Solution 3 — only act when something relevant changed

// Often the best fix: recursion is harmless if the second pass does nothing
List<Opportunity> changed = new List<Opportunity>();
for (Opportunity o : Trigger.new) {
    if (o.StageName != Trigger.oldMap.get(o.Id).StageName) changed.add(o);
}
if (changed.isEmpty()) return;    // second pass exits immediately

Static BooleanOne line, easyBreaks multi-chunk loads and legitimate re-entry
Set of processed IdsPrecise, chunk-safeSlightly more code; watch heap on huge volumes
Change detectionNo state at all; also improves performanceRequires disciplined field comparisons

Trigger handler framework

One trigger per object, and the trigger contains no logic. Otherwise you cannot control execution order between multiple triggers on the same object — Salesforce does not guarantee it.

/* ---------- 1. The base class ---------- */
public virtual class TriggerHandler {

    private static Map<String, Integer> loopCount = new Map<String, Integer>();
    private static Set<String> bypassed = new Set<String>();
    private String handlerName;

    public TriggerHandler() {
        this.handlerName = String.valueOf(this).substring(0, String.valueOf(this).indexOf(':'));
    }

    public void run() {
        if (!Trigger.isExecuting || isBypassed(handlerName)) return;
        if (!checkRecursion()) return;

        switch on Trigger.operationType {
            when BEFORE_INSERT  { beforeInsert();  }
            when BEFORE_UPDATE  { beforeUpdate();  }
            when BEFORE_DELETE  { beforeDelete();  }
            when AFTER_INSERT   { afterInsert();   }
            when AFTER_UPDATE   { afterUpdate();   }
            when AFTER_DELETE   { afterDelete();   }
            when AFTER_UNDELETE { afterUndelete(); }
        }
    }

    /* Virtual no-ops — subclasses override only what they need */
    protected virtual void beforeInsert()  {}
    protected virtual void beforeUpdate()  {}
    protected virtual void beforeDelete()  {}
    protected virtual void afterInsert()   {}
    protected virtual void afterUpdate()   {}
    protected virtual void afterDelete()   {}
    protected virtual void afterUndelete() {}

    /* Recursion guard with a configurable max depth */
    private Boolean checkRecursion() {
        String key = handlerName + '.' + Trigger.operationType;
        Integer count = loopCount.containsKey(key) ? loopCount.get(key) : 0;
        loopCount.put(key, count + 1);
        return count < 2;                       // allow one legitimate re-entry
    }

    /* Admin/test bypass */
    public static void bypass(String handler)   { bypassed.add(handler); }
    public static void clearBypass(String h)    { bypassed.remove(h); }
    public static Boolean isBypassed(String h)  {
        if (bypassed.contains(h)) return true;
        Trigger_Settings__c s = Trigger_Settings__c.getInstance();
        return s != null && s.Disable_All_Triggers__c == true;
    }
}

/* ---------- 2. The object handler ---------- */
public with sharing class AccountTriggerHandler extends TriggerHandler {

    private List<Account>      newList = (List<Account>) Trigger.new;
    private Map<Id, Account>   oldMap  = (Map<Id, Account>) Trigger.oldMap;

    protected override void beforeInsert() {
        AccountService.normaliseNames(newList);
        AccountService.setDefaultOwnerRegion(newList);
    }

    protected override void beforeUpdate() {
        AccountService.validateTierChange(newList, oldMap);
    }

    protected override void afterInsert() {
        AccountService.createDefaultContact(newList);
    }

    protected override void afterUpdate() {
        List<Account> tierChanged = new List<Account>();
        for (Account a : newList) {
            if (a.Tier__c != oldMap.get(a.Id).Tier__c) tierChanged.add(a);
        }
        if (!tierChanged.isEmpty()) AccountService.syncTierToContacts(tierChanged);
    }
}

/* ---------- 3. The trigger : one line ---------- */
trigger AccountTrigger on Account (
    before insert, before update, before delete,
    after insert, after update, after delete, after undelete) {
    new AccountTriggerHandler().run();
}

Why this design

  • Deterministic order
  • Logic is unit-testable without DML
  • Recursion handled centrally
  • Admin bypass built in

Layers

  • Trigger — routing only
  • Handler — orchestration per event
  • Service — reusable business logic
  • Selector — all SOQL lives here

Naming convention

  • AccountTrigger
  • AccountTriggerHandler

  • AccountTriggerHandlerTest

Trigger best practices

✅ Do

  • One trigger per object
  • No logic in the trigger body
  • Bulkify everything
  • Use collections and maps
  • Handle recursion deliberately
  • Use addError() for validation, not exceptions
  • Keep queries in a selector layer
  • Test with 200 records and negative cases
  • Respect FLS/sharing in handlers

❌ Don't

  • SOQL/DML/callouts in loops
  • Hard-code Ids
  • Use Trigger.new[0] — that ignores 199 records
  • Write business logic that duplicates a flow on the same object
  • Assume the trigger runs once
  • Make synchronous callouts from a trigger (use Queueable)
  • Swallow exceptions silently

Trigger practice questions (with answers)

1 Write a trigger that prevents deleting an Account which has open Opportunities.Medium 
trigger AccountTrigger on Account (before delete) {
    // Query children once, grouped by parent
    Map<Id, Integer> openCountByAccount = new Map<Id, Integer>();
    for (AggregateResult ar : [
            SELECT AccountId aid, COUNT(Id) cnt
            FROM Opportunity
            WHERE AccountId IN :Trigger.oldMap.keySet()
              AND IsClosed = false
            GROUP BY AccountId]) {
        openCountByAccount.put((Id) ar.get('aid'), (Integer) ar.get('cnt'));
    }

    for (Account a : Trigger.old) {
        if (openCountByAccount.containsKey(a.Id)) {
            a.addError('Cannot delete: ' + openCountByAccount.get(a.Id) + ' open opportunities exist.');
        }
    }
}

Key points: before delete (so you can block it), Trigger.old only, one aggregate query outside the loop, and addError() rather than throwing.

2 Update a custom field on Account with the count of its Contacts, on insert/update/delete/undelete of Contact.Medium 
trigger ContactTrigger on Contact (after insert, after update, after delete, after undelete) {

    Set<Id> accountIds = new Set<Id>();

    if (Trigger.isInsert || Trigger.isUndelete || Trigger.isUpdate) {
        for (Contact c : Trigger.new) if (c.AccountId != null) accountIds.add(c.AccountId);
    }
    if (Trigger.isDelete || Trigger.isUpdate) {
        // On update, the contact may have been REPARENTED — recount both accounts
        for (Contact c : Trigger.old) if (c.AccountId != null) accountIds.add(c.AccountId);
    }
    if (accountIds.isEmpty()) return;

    Map<Id, Account> toUpdate = new Map<Id, Account>();
    for (Id accId : accountIds) toUpdate.put(accId, new Account(Id = accId, Contact_Count__c = 0));

    for (AggregateResult ar : [SELECT AccountId aid, COUNT(Id) c
                               FROM Contact WHERE AccountId IN :accountIds GROUP BY AccountId]) {
        toUpdate.get((Id) ar.get('aid')).Contact_Count__c = (Integer) ar.get('c');
    }
    update toUpdate.values();
}

The trap: most candidates forget reparenting on update — you must recount the old account too. Also note seeding every account with 0 so a count that drops to zero is written.

3 Your trigger runs twice for a single save. Give three possible causes.Hard
  1. A workflow rule with a field update — step 12 of the order of execution re-saves the record and re-fires before/after triggers once.
  2. Your own trigger's DML — updating a related record whose trigger updates back (true recursion).
  3. A roll-up summary or a record-triggered flow updating the record after save.
  4. Also possible: an after update that updates the same record, or a process/flow doing an "Update the record that triggered the flow" on the after-save path.

How to diagnose: add System.debug(Trigger.operationType + ' depth ' + Limits.getDmlStatements()) at the top and read the debug log's CODE_UNIT_STARTED entries.

4 Why can't you modify Trigger.new in an after trigger, and what do you do instead?Easy

The record has already been written to the database, so the in-memory copy is read-only — modifying it would have no effect. Attempting it throws "Record is read-only".

Instead: either move the logic to a before trigger (free, no extra DML), or in the after trigger build new sObject instances and issue an explicit update:

List<Account> updates = new List<Account>();
for (Account a : Trigger.new) {
    updates.add(new Account(Id = a.Id, Status__c = 'Processed'));
}
update updates;   // but prefer a before trigger if it's the same record!
5 A trigger makes a callout and fails with "You have uncommitted work pending". Fix it.Medium

You cannot make a callout after a DML in the same transaction, because the platform will not hold an open database transaction while waiting on an external system.

// ✅ Move the callout to an async context that starts after commit
public class NotifyErpQueueable implements Queueable, Database.AllowsCallouts {
    private Set<Id> accountIds;
    public NotifyErpQueueable(Set<Id> ids) { this.accountIds = ids; }

    public void execute(QueueableContext ctx) {
        for (Account a : [SELECT Id, Name FROM Account WHERE Id IN :accountIds]) {
            HttpRequest req = new HttpRequest();
            req.setEndpoint('callout:ERP_Named_Cred/accounts');
            req.setMethod('POST');
            req.setHeader('Content-Type', 'application/json');
            req.setBody(JSON.serialize(a));
            new Http().send(req);
        }
    }
}

// In the after trigger
System.enqueueJob(new NotifyErpQueueable(Trigger.newMap.keySet()));

@future(callout=true) also works but Queueable is preferred: it takes sObject/complex parameters, can be chained, and returns a job Id you can monitor.

6 Prevent duplicate Contacts by email within the same Account, handling both existing records and duplicates inside the same batch.Hard 
trigger ContactTrigger on Contact (before insert, before update) {

    Map<String, Contact> seenInBatch = new Map<String, Contact>();
    Set<String> emails = new Set<String>();
    Set<Id> accountIds = new Set<Id>();

    for (Contact c : Trigger.new) {
        if (String.isBlank(c.Email) || c.AccountId == null) continue;
        String key = c.AccountId + '|' + c.Email.toLowerCase();

        // 1. Duplicate WITHIN this batch
        if (seenInBatch.containsKey(key)) {
            c.Email.addError('Duplicate email in this batch for the same Account.');
        } else {
            seenInBatch.put(key, c);
            emails.add(c.Email);
            accountIds.add(c.AccountId);
        }
    }
    if (seenInBatch.isEmpty()) return;

    // 2. Duplicate against records ALREADY in the database
    for (Contact existing : [SELECT Id, Email, AccountId FROM Contact
                             WHERE Email IN :emails AND AccountId IN :accountIds]) {
        String key = existing.AccountId + '|' + existing.Email.toLowerCase();
        Contact incoming = seenInBatch.get(key);
        if (incoming != null && incoming.Id != existing.Id) {
            incoming.Email.addError('A contact with this email already exists on the account.');
        }
    }
}

Why it's a hard question: candidates almost always check the database but forget duplicates inside the same 200-record batch, and forget to exclude the record itself on update.

7 What happens to a trigger when a record is updated by a roll-up summary recalculation?Hard

The parent's before update and after update triggers do fire. Trigger.old and Trigger.new differ only in the roll-up field. This cascades: if the parent is itself a detail of a grandparent, the grandparent's triggers fire too (step 18).

Practical implication: guard "did anything I care about change?" logic, or a simple roll-up will fire expensive automation across your whole hierarchy.

8 Trigger.new vs Trigger.newMap — when would you deliberately choose one?Easy
  • Trigger.new when you're iterating and possibly modifying records (before triggers).
  • Trigger.newMap.keySet() when you need the Ids for a query — cleaner than building a Set in a loop.
  • Trigger.oldMap.get(record.Id) to compare old vs new — this is the standard change-detection idiom.
  • Remember Trigger.newMap is not available in before insert (no Ids yet).
9 How do you let an admin disable a trigger during a data migration without deploying code?Medium 
// Hierarchy Custom Setting: Trigger_Settings__c
//   Disable_All_Triggers__c (checkbox)
//   Disable_Account_Trigger__c (checkbox)
// Set at Org level, or per-Profile/per-User for the migration user only.

public static Boolean isDisabled(String triggerName) {
    Trigger_Settings__c s = Trigger_Settings__c.getInstance();   // no SOQL consumed
    if (s == null) return false;
    if (s.Disable_All_Triggers__c) return true;
    return triggerName == 'Account' && s.Disable_Account_Trigger__c;
}

Setting it at the User level for the integration user is the safest pattern — normal users are unaffected. Pair it with a checklist so it's turned back on.

10 Trigger vs record-triggered Flow — how do you decide?Medium
Choose FlowChoose Trigger
Simple field updates and record creationComplex logic, loops with conditions, recursion
Admins must maintain itNeeds unit tests and code review
Same-record updates (before-save is very fast)Large data volumes / bulk processing

Interview questions

The ten scenarios above are coding exercises. These are the conceptual questions that come before them.

1 Before or after trigger — how do you decide?Easy

Before for validating or setting fields on the record being saved — you edit Trigger.new directly, so there's no extra DML and no recursion. After for anything needing the record's Id or touching other records: creating children, updating parents, sending email, enqueuing async work. In an after trigger Trigger.new is read-only; attempting to modify it throws "Record is read-only".

2 Which context variables are unavailable in which events?Medium

Trigger.new is absent in delete events; Trigger.old is absent in insert and undelete. The one people miss: Trigger.newMap is not available in before insert, because the records have no Ids yet. Trigger.oldMap exists only in update and delete — and Trigger.oldMap.get(record.Id) is the standard change-detection idiom.

3 Why one trigger per object?Easy

Because Salesforce gives no guarantee about the execution order of multiple triggers on the same object. With two triggers you get non-deterministic, unreproducible behaviour that changes between orgs. One trigger delegating to a handler gives you explicit ordering, one place to control recursion, testable logic that doesn't need DML, and a single switch to bypass during data loads.

4 Walk me through the order of execution.Hard

Load record → overwrite with new values → system validation → before-save flows → before triggers → system + custom validation again → duplicate rules → save to DB (not committed) → after triggers → assignment rules → auto-response rules → workflow rules → escalation rules → after-save flows → entitlements → roll-up summary → criteria-based sharing → grandparent roll-ups → commit → post-commit (email, @future, platform events).

The three consequences worth stating: a workflow field update re-fires your triggers once; a roll-up fires the parent's triggers and can cascade upward; and @future/email only happen after commit, so they never see a rolled-back transaction.

5 What is recursion, and why is a simple static Boolean a bad fix?Hard

Recursion is a trigger's own DML causing the same trigger to fire again — hitting "Maximum trigger depth exceeded" (16) or silently doubling work.

A blanket static Boolean hasRun also blocks legitimate re-entry. Load 400 records with Data Loader: chunk 1 sets the flag, and chunk 2 is skipped entirely because statics persist across chunks in the same transaction — 200 records silently unprocessed. Better: track a Set of processed record Ids, or best of all make the second pass a no-op by only acting when a relevant field actually changed.

6 addError() or throw an exception — which and why?Medium

addError() — it attaches the message to the specific record (or field, with record.Field.addError()), so in a bulk operation the valid records still save when the caller used allOrNone = false, and the UI shows the error in the right place.

Throwing an exception aborts the entire transaction and surfaces an ugly technical message. Reserve it for genuinely unrecoverable states, not business validation.

7 How do you let an admin disable your trigger during a migration?Medium

A hierarchy Custom Setting such as Trigger_Settings__c with Disable_All_Triggers__c and per-object checkboxes. Read it with Trigger_Settings__c.getInstance(), which is cached and consumes no SOQL.

The important refinement: set it at the User level for the migration user only, so normal users are unaffected — and pair it with a checklist item to turn it back on.

8 Trigger or record-triggered Flow — how do you choose in a real org?Medium

Flow for simple field updates and record creation, admin-maintainable logic, and same-record updates (before-save is very fast). Trigger for complex branching, large volumes, aggregate SOQL, callouts with retry, and anything needing real unit tests.

The answer that matters most: never both on the same object doing overlapping work. Pick one tool per concern, document the decision, and enforce it in code review — otherwise you get unpredictable ordering and double-processing that nobody can reproduce.
