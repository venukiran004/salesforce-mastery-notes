Flow Builder — 100 Scenarios

Entry conditions and re-entry, before versus after save, bulkification, fault handling, running context, Orchestrator, Apex boundaries, and the flows that become unmaintainable.

📚
How to use this Answer out loud in ninety seconds, then open the answer. Concepts on Flow Builder (Deep) and its Advanced section.

Entry conditions & timing (1–16)

1 Your flow creates a duplicate task every time the record is edited.Medium

The entry condition matches on every save while the condition remains true. You want "only when a record is updated to meet the condition" so it fires on the transition.

That single setting prevents most duplicate-task and repeated-email complaints.

2 You need to fire only when a specific field changes.Easy

Use ISCHANGED() in a formula entry condition, or the transition option with a condition on that field.

Checking only the current value means the flow runs when unrelated fields change, which cascades automation and wastes limits.

3 You need the prior value of a field.Easy

$Record__Prior in a record-triggered flow, or PRIORVALUE() in a formula.

It is null on create, so guard for that — a comparison against a null prior value is a common cause of flows firing on insert.

4 Before-save or after-save for setting a field on the same record?Easy

Before-save, always. It mutates the record in flight with no extra DML, is dramatically faster, and avoids a second save that re-triggers automation.

After-save for same-record updates is the single most common flow performance and recursion mistake.

5 Your before-save flow cannot do what you need.Medium

Before-save flows are deliberately restricted: no Apex actions, no creating or updating other records, no callouts — only field assignment on the triggering record (plus Get Records).

If you need related records, that is after-save. Splitting into one before-save for fields and one after-save for related work is a legitimate and common pattern.

6 Two flows on the same object run in an unexpected order.Medium

Within the same object and timing, order is unspecified unless you set the flow's trigger order (1–2000).

Set it, document it, and prefer converging on one flow per object per timing with a named owner.

7 Where does a record-triggered flow sit relative to triggers?Medium

Before-save flows run before before-triggers; after-save flows run after after-triggers and before roll-ups.

So a before-save flow can set a value an Apex trigger then reads — which is useful and occasionally surprising.

8 A flow needs to run only for one record type.Easy

Add it to the entry conditions using the record type's developer name via a formula, not a hard-coded Id.

Ids differ per org and per refreshed sandbox, so a hard-coded record type Id in a flow is a guaranteed post-refresh break.

9 Your flow must not run during a data migration.Medium

Add a bypass to the entry conditions — a custom permission check or a hierarchy custom setting the migration user has.

Then run a reconciliation afterwards to apply the derived values the flow would have set. Bypassing without reconciling imports incomplete data permanently.

10 A flow fires on records created by another flow.Medium

Expected — automation triggers automation. Whether it is a problem depends on whether the cascade is intended.

Guard the entry condition on something that distinguishes the origin (a source field), and keep one automation per object per timing so cascades are traceable.

11 The flow must run when a related record changes.Medium

Flows trigger on their own object only. Put the flow on the related object and have it update or act on the parent.

Be careful about volume: a flow on a high-volume child object acting on parents is a lock-contention risk at scale.

12 You need to react to a delete.Easy

A record-triggered flow configured for delete, which runs before the delete — so you can read the record but you are acting ahead of the deletion.

Cascade deletes from a master-detail parent also trigger it, which archiving logic frequently forgets.

13 A flow should run 24 hours after a status change.Easy

A scheduled path on the record-triggered flow, offset from a date field or from when the criteria were met.

It runs in a separate asynchronous transaction, so re-check the record state — it may have changed in the interim.

14 A scheduled path acts on stale data.Medium

By the time it runs, the record may have moved on. Always re-evaluate the condition inside the scheduled path rather than trusting the original entry.

That is the difference between "send the reminder if still open" and "send the reminder regardless".

15 You need a flow to run on a schedule, not on a record change.Easy

A schedule-triggered flow with a filter — it runs for each matching record on the schedule.

Watch volume: these iterate records and can hit element-execution limits. Above a few thousand records, Batch Apex is the right tool.

16 A flow needs to run immediately after commit, not during the save.Medium

An asynchronous path — it runs right after the transaction commits, with fresh limits, which is where callouts belong.

It is also the right place for work that must not block or fail the user's save.

Bulkification & limits (17–32)

17 Your flow hits a SOQL limit on a bulk load.Medium

A Get Records inside a loop. The engine bulkifies elements outside loops across all records in the transaction, but not inside one.

Restructure: get all the data you need once, then loop over an in-memory collection.

18 An Apex action inside a loop blows limits.Medium

Apex actions, subflows and callouts inside loops are not bulkified by the engine. Each iteration is a separate invocation.

Move the action outside the loop and pass it a collection — which requires the Apex to accept a List, as a well-written invocable action does.

19 You need to create one child per parent for 200 parents.Easy

Build a collection in the loop with Assignment, then one Create Records element after the loop.

That is the canonical flow bulk pattern, and it is exactly analogous to collecting and doing one DML in Apex.

20 A loop over 50,000 records fails.Medium

Flow has a limit on executed elements per transaction, and a loop multiplies elements by iterations.

That volume belongs in Batch Apex. Flow is not the tool for large-scale data processing.

21 How do you know whether your flow is bulk-safe?Medium

Test it with a 200-record load and read the debug log's cumulative limits. The flow debugger runs one record and will not reveal bulkification problems.

Also look for any Get, Create, Update, Delete, Apex or subflow element inside a loop.

22 A subflow inside a loop is slow.Medium

Each invocation is separate, so its elements and DML multiply by the iteration count.

Either move the subflow outside the loop and pass a collection, or inline the logic. Subflows are for reuse and clarity, not for use inside hot loops.

23 You need to filter a collection without querying again.Easy

Use a collection filter element (or a loop with a decision building a second collection) rather than a second Get Records.

In-memory filtering costs elements but no queries, which is usually the right trade in a bulk context.

24 A flow updates the same record twice in one run.Medium

Two Update elements on the same record means two DML operations and two save paths. Consolidate into one update after all the assignments.

In a before-save flow, you assign fields and the platform saves once — which is why it is so much cheaper.

25 Your flow is one of five automations on the object and the save is slow.Hard

They all share the transaction's CPU and limits, so being individually efficient is necessary but not sufficient.

Read CODE_UNIT_STARTED/FINISHED to see the real cost distribution, then campaign to consolidate — one entry point per object per timing.

26 A Get Records returns more rows than you expected.Easy

No filter, or a filter that is not selective. Flow will happily fetch a very large collection into memory.

Always filter, and set a limit where the logic allows — an unbounded Get is a future failure with a date on it.

27 You need only the first matching record.Easy

Set the Get Records element to store only the first record, with an explicit sort order — otherwise "first" is whatever the database returns.

Relying on an unsorted first record produces behaviour that changes as data changes.

28 A flow needs data from five levels up the hierarchy.Medium

Use cross-object references on the triggering record where possible ($Record.Account.Parent.Name), which costs no extra query.

Multiple sequential Get Records elements are the expensive alternative, and they add up quickly in a bulk context.

29 Your flow fails only for one user.Medium

In a screen flow (user context), a Get Records returning nothing is almost always sharing or FLS — not the flow.

Log in as them and check record access. In a record-triggered flow (system context) the cause is more likely data shape or a null they have that others do not.

30 How do you reduce element count in a complex flow?Medium

Use formulas instead of chains of decisions and assignments, filter collections in one element rather than looping, and move genuinely complex computation into an invocable Apex action.

A flow needing 200 elements has usually outgrown the tool for part of its job.

31 A flow hits the DML row limit.Medium

It is creating or updating too many records in one transaction — frequently a loop creating children per parent across a bulk load.

Reduce the work, or move it to an asynchronous path or Batch Apex. Flow shares the same 10,000 DML-row ceiling as Apex.

32 Is Flow slower than Apex for the same logic?Medium

Generally yes for bulk work — the engine's element execution has overhead Apex does not, and after-save flows add a save.

For modest volumes the difference is irrelevant and the maintainability wins. At scale, the gap matters and Apex becomes the right choice.

Fault handling (33–48)

33 A record-triggered flow fails and the user's save is rolled back.Medium

Without a fault path, an element failure throws and takes the transaction with it, showing the user an unhelpful technical message.

Add a fault path on every DML and Apex element: log the failure, and either continue or fail with a message that explains itself.

34 Where should a fault path write the error?Medium

To an error-log object (or a platform event), capturing $Flow.FaultMessage, the record Id, the flow name and the interview context.

Reportable, alertable, and available in production where debug logs are not. A fault path that only shows a screen loses the diagnostic entirely.

35 Flow errors email the person who built it, who has left.Easy

Default behaviour emails the flow owner. Change the error-email recipient setting to a monitored address, and build real alerting off your error log.

Single-person notification is a guaranteed future gap and a common finding when an org changes hands.

36 A screen flow shows a raw platform error to a customer.Easy

Fault path to a screen that explains what happened and what to do next, while the log record captures the technical detail.

In a customer-facing context that difference is reputational, not merely cosmetic.

37 Should every element have a fault path?Medium

Every element that can fail for reasons outside your control — DML, Apex actions, callouts, Get Records that may return nothing you did not expect.

Decisions and assignments do not need them. Blanket fault paths add clutter; targeted ones add reliability.

38 A fault path itself fails.Medium

Usually because it does DML that is also invalid, or writes a message longer than the field allows.

Keep fault paths minimal and defensive: truncate the message, use a simple object with few required fields, and prefer a platform event so the log survives a rollback.

39 How do you make a flow retry a failed callout?Hard

Flow has no native retry. Patterns: a fault path that creates a "to retry" record which a scheduled flow or batch picks up, or push the callout into Apex that handles retry properly.

For anything where delivery matters, the Apex route with a finalizer and a dead-letter path is the honest answer.

40 You need partial success — process the good records, log the bad.Hard

Flow DML is all-or-none for the collection, so one bad record fails the element.

Either validate and split the collection before the DML, or call an invocable Apex action that performs partial-success DML and returns the failures. The Apex route is cleaner for integration volumes.

41 How do you test fault paths?Medium

Force the failure: a Flow Test with data that violates a validation rule, or an Apex action configured to throw.

Untested fault paths routinely contain their own bugs, which only surface during the incident they were meant to handle.

42 Flow Tests — what are they good for?Medium

Declarative tests for record-triggered flows: given an input record, assert the outcome. They belong in CI alongside Apex tests.

In orgs where flows carry most of the logic, this is the application's test suite, and its absence is a bigger risk than low Apex coverage.

43 You cannot reproduce a flow failure.Medium

Check the error email or your log for the element that failed and the fault message, then reproduce with that record's data as that user.

Enable WORKFLOW=FINER in a debug log to see element-by-element execution — it shows exactly which branch was taken.

44 Errors appear only on bulk loads.Medium

A limit, or a null that exists in some records and not others. The flow debugger with one record will never show either.

Test at 200 records with variation, including nulls and records that should not qualify.

45 A flow silently does nothing.Medium

Check the entry conditions first (the transition option in particular), then whether the flow is active, then whether a Get Records returned nothing and a decision took the default path.

"Did nothing" is usually a condition evaluating differently than you think, not a failure.

46 How do you log a flow's progress for debugging?Easy

Create log records (or publish platform events) at key decision points during development, behind a custom-permission check so you can enable it for one user in production.

That gives you production tracing without logging for everyone.

47 Should a flow ever swallow an error?Medium

Only where the failure is genuinely tolerable — a nice-to-have enrichment — and even then it must be logged.

A fault path that routes to the end with no record of what happened turns a visible failure into an invisible one, which is worse.

48 How do you alert the business about flow failures?Medium

Surface the error log as a list view and a report with a conditional subscription, so failures are data the business can see and chase.

Nobody chases an email nobody reads, or a log nobody can access.

Running context & security (49–62)

49 A record-triggered flow sees records the user cannot.Medium

By default they run in system context without sharing. That is powerful and it is a security review item.

If the flow must respect the user, use an autolaunched flow with the user-context option, or do the sensitive work in Apex that enforces access.

50 A screen flow's Get Records returns nothing for some users.Easy

Screen flows run in the user's context, so sharing and FLS apply. The records exist but are not visible to them.

Check record access by logging in as the user — this is almost never a flow problem.

51 A flow exposed to guest users worries you. Why?Hard

A system-context flow reachable from a public page is the same risk class as without sharing Apex — and it is reviewed far less often.

Audit what it reads and writes, run it in user context where possible, validate every input, and treat it as a public endpoint. See guest hardening.

52 An autolaunched flow — which context should it use?Medium

Choose deliberately: system context with or without sharing, or user context — and write the choice and the reason in the flow description.

Undocumented context choices are how a flow becomes an unexamined elevation path.

53 Does a flow enforce field-level security?Medium

In user context, yes. In system context, no — it can read and write fields the user cannot see.

Which means a system-context flow returning data to a screen can leak fields. Decide what the flow should be permitted to surface.

54 An invoked Apex class behaves differently than expected in a flow.Hard

The Apex keeps its own sharing declaration. An inherited sharing class called from a system-context flow runs in system mode.

Declare with sharing and use USER_MODE explicitly if the Apex must respect the user.

55 A flow needs to do something the running user cannot.Medium

That is a legitimate use of system context — but scope it: do only the elevated operation that way, and keep the rest in user context.

Blanket elevation for convenience is the pattern that turns up in security reviews.

56 How do you check a permission inside a flow?Easy

$Permission for custom permissions, and $User fields for profile or role checks — with custom permissions strongly preferred, since they survive profile reorganisation.

Use the same custom permission for component visibility and for the server-side check, so they cannot diverge.

57 A screen flow must not be launchable by anyone.Medium

Control access through the flow's own access settings and through where you surface it — then check the permission inside the flow as well.

Hiding the launch point is presentation. The in-flow check is the control.

58 Flow input from a screen is used in a Get Records filter.Hard

In user context, sharing limits the damage. In system context it is a user-controlled query over data they may not be entitled to see.

Validate and constrain the input, and prefer user context for anything driven by user input.

59 Who should be able to edit a flow in production?Medium

Ideally nobody — flows are metadata and should arrive through the pipeline, because a flow edit is a behaviour change with no review trail.

In practice, give admins a fast sanctioned path instead, and detect production flow changes with drift detection. See drift.

60 Two developers changed the same flow on different branches.Hard

A text merge of flow XML produces a flow that deploys and behaves incorrectly — missing connectors, duplicated elements.

Treat flows as unmergeable: force a conflict via .gitattributes, one owner per flow per release, and split large flows into subflows so two people are not in the same file.

61 A flow version was activated in production by accident.Medium

Activate the correct version (versions are retained, so this is recoverable), then capture how it happened.

Prevention: remove flow-edit rights in production, deploy flows through the pipeline, and alert on flow definition changes via Setup Audit Trail.

62 How do you review a flow for security?Hard

Three questions: what context does it run in; what can invoke it (guest page? external user?); and what does it touch and return.

Those three cover the realistic risk. A system-context flow on a public page is the case to find first.

Flow, Apex & Orchestrator (63–80)

63 When has logic outgrown Flow?Medium

Signals: a loop inside a loop, a formula nobody can read, 200 elements, or a flow that needs a comment to explain it.

Move that piece into an invocable Apex action and keep the flow as orchestration — admins keep visibility, you get testability and performance.

64 How should an invocable action be written for Flow?Medium

Accept a List of typed requests, return a List of responses aligned positionally and in count, and do one query for all requests rather than per request.

Mismatched sizes or reordered results land values on the wrong records, silently.

65 Your Apex action works for one record and breaks in bulk.Medium

The flow bulkified the call but your Apex handles only the first request, or queries per request.

Build the output inside a loop over the input, with a single query up front. Test with a list of several requests.

66 A flow needs a callout.Easy

Use an asynchronous path, or an invocable Apex action marked for callouts, or an External Service / HTTP Callout action — never synchronously inside the save.

And handle the failure path, because a callout in automation will fail eventually.

67 What does a Pause element actually do?Hard

It commits everything so far and ends the transaction, resuming later in a new one with fresh limits.

That is the sanctioned way to do a callout after DML, or to wait for a time or an event — and it means anything after the pause sees a potentially changed world.

68 A five-stage approval with reassignment and reminders.Hard

Flow Orchestrator: stages, steps, assignment to users or queues, each step its own interview, with conditional routing.

Say what you give up versus an approval process: record locking and the built-in approval history, both of which you then implement deliberately.

69 Orchestrator or a screen flow with a wizard?Medium

A screen flow is one person, one sitting. Orchestrator is multi-person, multi-day, with work assigned and tracked across steps.

If the process spans people and time, a screen flow will become a series of records and reminders you build yourself — badly.

70 A flow calls a subflow that calls another subflow.Medium

Legitimate for reuse, but each level adds elements and makes debugging harder, and depth inside loops multiplies cost.

Keep the hierarchy shallow and the interfaces explicit — subflows with many input variables are usually doing too much.

71 You need to call a flow from Apex.Medium

Flow.Interview with a map of inputs, started from Apex. Useful for reusing an admin-maintained decision from code.

Be careful about limits and error handling: a flow failure inside your transaction behaves like any other failure, and you own the message.

72 Platform event-triggered flow — what is different?Medium

It runs as the Automated Process user in its own transaction after publication, with no access to the publisher's state.

So pass everything needed in the payload, make it idempotent (delivery is at-least-once), and set trace flags on that user to debug it.

73 Migrating a Process Builder process to Flow changes behaviour.Medium

Expected: timing in the save order differs, and a before-save flow does not re-fire triggers the way a workflow field update does.

Test the whole save path, not just the field value — particularly any trigger that was relying on the re-entry. Migrate one at a time.

74 Should new automation be Flow or Apex by default?Medium

Flow for field updates, related-record creation and notifications that admins should own and see. Apex for bulk-sensitive logic, complex data shapes, reuse across entry points and real error handling.

The deciding question is usually "who maintains this in two years?", not which is technically capable.

75 A flow and a trigger both react to the same change.Medium

Decide ownership per field and per behaviour, and remove the duplicate. Two automations maintaining the same field is a loop waiting to happen.

If both must exist, make the ordering explicit and document which owns what.

76 How do you reuse a decision across several flows?Medium

A subflow returning the outcome, or a formula field on the record, or an invocable Apex action — depending on whether the logic is flow-shaped or computation-heavy.

Duplicating a decision across five flows guarantees they drift apart.

77 Admins want to change thresholds without a deployment.Easy

Read the threshold from a Hierarchy Custom Setting or Custom Metadata rather than hard-coding it in the flow.

Flows are metadata, so a hard-coded value means a deployment for every tweak — which pushes people toward editing flows in production.

78 A flow needs to call out and then update records atomically.Hard

Not possible — you cannot call out after DML in a transaction, and atomicity across a remote system does not exist.

Use a Pause or asynchronous path, make the remote call idempotent with a correlation id, and reconcile. See consistency models.

79 You need to process 100,000 records from a flow.Medium

That is Batch Apex. A schedule-triggered flow iterating 100,000 records will hit element and DML limits.

Flow can start the batch via an invocable action, keeping the orchestration declarative and the heavy lifting in Apex.

80 How do you hand over a complex flow to an admin team?Medium

Descriptions on the flow and on every non-obvious element, named resources (not varTemp1), a documented entry condition, and a Flow Test that encodes the intended behaviour.

An undocumented 100-element flow is not a handover; it is a liability.

Judgement & maintenance (81–100)

81 Your org has 14 flows on Account.Hard

Document before changing: a debug log of one save shows the real execution tree, including flows nobody remembered.

Then consolidate by risk — delete the dead, merge by timing, set trigger order, move same-record updates to before-save — incrementally, behind Flow Tests.

82 A flow nobody understands is business-critical.Medium

Write Flow Tests capturing its current behaviour before touching it, which both documents it and protects you.

Then refactor in small steps — extracting subflows or an Apex action — with each step separately deployable.

83 How do you name flow resources?Easy

Descriptively and consistently: varSelectedAccountId, colOverdueCases, fmlDiscountPercent.

A convention that signals type and purpose makes a large flow readable. var1 and decision3 make it archaeology.

84 Flows are deployed but inactive in production.Medium

Flow activation state can differ by environment and is a common post-deployment gap — the metadata arrived, the behaviour did not.

Include activation verification in the release checklist, and ideally assert it in a post-deployment script.

85 How many flow versions should you keep?Easy

Keep enough to roll back (the previous working version, at least) and delete the rest periodically — dozens of obsolete versions make the list unusable.

Version history is also your rollback mechanism for a flow, which makes it worth curating.

86 A stakeholder wants logic in Flow so they can change it.Medium

Split it: the flow owns orchestration and the tunable decisions; an invocable Apex action owns complex, bulk-sensitive computation.

Everyone gets what they need, and the flow stays small enough to read.

87 Flow or validation rule for a data check?Medium

Validation rule when the check is formula-expressible on the record and admins should see it in one place. Before-save flow when it needs related data or a friendlier message.

Pick one home per rule — duplicated validation produces inconsistent behaviour between UI and API.

88 A flow is slow and you cannot tell which element.Medium

Enable WORKFLOW=FINER in a debug log for element-by-element execution with timings.

It is verbose, but it is the only way to see which decision branch was taken and where the time went.

89 Should flows be version-controlled?Easy

Yes — they are metadata and they are business logic. But treat the files as unmergeable and assign one owner per flow per release.

Version control also gives you the review conversation, which matters more for flows than for most metadata because the diff is hard to read.

90 How do you review a flow in a pull request?Hard

Not from the XML diff, which is unreadable. Review it in the builder in a sandbox, against a written description of the intended change.

Check entry conditions, context, fault paths, loops containing DML or Apex, and whether a Flow Test exists.

91 A flow works in the builder debugger but fails in production.Medium

The debugger runs one record, as you, often in a different context. Production has bulk, other users' sharing, real data shapes and other automation.

Test with a bulk load, as a non-admin user, in a sandbox with realistic data.

92 How do you stop flows proliferating?Medium

A convention: one record-triggered flow per object per timing, with subflows for logical grouping, and a design-authority check for anything touching a shared object.

Proliferation is a governance problem, and the cost lands on whoever debugs the save two years later.

93 An admin built a flow that breaks an integration.Medium

Flows run on API writes too, so a new validation-style flow or a required-field assignment can reject integration records.

Treat flow changes as changes: tiered review, and an integration regression smoke test after release.

94 You need to disable a flow quickly during an incident.Medium

Deactivating is a metadata change; faster is a bypass condition in the entry criteria checking a custom permission or hierarchy custom setting you can flip instantly.

Build that bypass before you need it — the same principle as a trigger kill switch.

95 A flow sends emails to the wrong people after a sandbox refresh.Easy

Real data came across and deliverability was not restricted. Set email deliverability to System Email Only before anyone logs in.

Include it in a scripted post-refresh checklist — it is the mistake that reaches real customers. See post-refresh.

96 How do you measure whether a flow is worth keeping?Medium

Does it still run (log its executions), does anyone rely on its output, and does its cost in the save justify it?

Orgs accumulate flows for processes that ended years ago, and nobody deletes them because nobody can prove they are unused.

97 A flow's logic duplicates an Apex trigger's.Medium

Remove one. Duplication means two places to change, two chances to diverge, and double the cost in every save.

Keep whichever better fits the maintenance population, and delete the other deliberately with a note of what was removed.

98 What makes a flow genuinely production-ready?Hard

Transition-based entry conditions, before-save for same-record fields, no DML or Apex inside loops, fault paths with durable logging, a documented running context, a bypass switch, named resources, a description, and a Flow Test.

That list takes an extra hour and prevents most flow incidents.

99 The business wants everything in Flow because "no code".Medium

"No code" is not "no engineering" — flows need bulk thinking, error handling, testing, version control and review exactly as code does.

The honest framing: Flow changes who can maintain the logic, not whether it needs to be engineered properly.

100 One habit that most improves flows?Hard

Using transition-based entry conditions and before-save for same-record updates, by default.

Those two choices prevent duplicate side effects, recursion, unnecessary saves and most of the performance complaints — before you have written a single element.
