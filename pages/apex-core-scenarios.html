Apex Core & SOQL — 100 Scenarios

Collections, SOQL behaviour at volume, DML and partial success, locking, security modes, numbers and dates — the situations that produce real defects rather than syntax questions.

📚
How to use this Answer out loud in ninety seconds, then open the answer. Concepts on Apex Core & SOQL/SOSL and its Advanced section.

Collections & data structures (1–12)

1 A Map<Account, String> lookup returns null for an Account you just put in.Hard

sObject equality uses all queried fields, so two Account instances with the same Id but different selected fields are not equal — and the hash differs.

Never key a map on an sObject. Key on Id or String, which is also cheaper and clearer. This is one of the most common silent bugs in Apex written by otherwise experienced developers.

2 Removing items from a list inside a for loop skips records.Medium

List.remove(index) shifts every subsequent element down, so your loop counter skips the next one.

Fix: iterate backwards, or build a new list of the items you want to keep. Building a new collection is usually clearer and avoids the class of bug entirely.

3 You need to sort a list of wrapper objects by two fields.Medium

Implement Comparable on the wrapper for its natural ordering, or pass a Comparator to sort() when you need more than one ordering of the same type.

Comparator is the better choice when different screens need different sorts — otherwise you end up with a compareTo containing a mode flag, which nobody can read.

4 Sorting a List<Account> gives an order you did not expect.Medium

List<SObject>.sort() sorts on the first field in the SELECT clause, which is rarely what you intended, and nulls sort first ascending.

Sort in SOQL with an explicit ORDER BY instead — it is also cheaper, because the database does it. Reserve Apex sorting for wrappers and computed values.

5 clone() on a list of records did not give you independent copies.Medium

clone() on a list copies the references, so both lists point at the same sObject instances — mutating one mutates the other.

Use deepClone() on each sObject (with the appropriate flags for Id, timestamps and autonumbers) when you need genuinely independent records.

6 You need to group child records by parent Id.Easy

A Map<Id, List<Child__c>> built in one pass over the query results — the single most useful pattern in bulk Apex.

Build it with the containsKey / put(new List...) idiom, or query with a parent-child subquery if you are starting from the parent side and need both in one query.

7 A set of 50,000 Ids causes a heap error.Medium

Collections count against heap (6MB synchronous, 12MB async), and Ids plus the records behind them add up fast.

Fix by not holding it all: use Database.getQueryLocator in Batch Apex so the platform streams the rows, query only the fields you need, and null out large collections once finished with them.

8 Map.get() returns null and you cannot tell whether the key was absent.Easy

A null return is ambiguous: the key may be missing, or present with a null value. Use containsKey() when the distinction matters.

In practice this bites with maps of configuration values where "not configured" and "configured as blank" mean different things.

9 You need the records in a list that are not in another list.Easy

Build a Set of Ids from the second list, then iterate the first checking !set.contains(id). Set membership is a hash lookup; a nested loop is quadratic and will blow CPU on a few thousand records.

Set.removeAll() and retainAll() also exist and are worth using for clarity.

10 A string built in a loop causes a heap failure.Medium

Each concatenation creates a new immutable string, so a loop over thousands of records creates thousands of intermediate strings.

Collect the pieces into a List<String> and use String.join() once. Same principle for building CSV or JSON — never accumulate with += in a loop.

11 You need a list of unique records preserving insertion order.Medium

A Set does not guarantee order you can rely on for business logic. Use a Map<Id, SObject> if you need dedupe plus lookup, or track a Set<Id> of seen keys while appending to a List to preserve order explicitly.

Do not depend on iteration order of sets or maps for anything the business sees — make the ordering explicit.

12 An untyped List<SObject> makes your code fragile.Medium

It compiles but you lose type safety and field access requires get('Field__c'), so typos become runtime errors.

Use it only where genuinely generic (a framework method handling any object), and cast to the concrete type as early as possible. Generic Apex is powerful and should be a deliberate boundary, not the default style.

SOQL at volume (13–30)

13 A query that ran in 200ms now takes 40 seconds. No code changed.Hard

Data growth pushed the filter past the selectivity threshold, so the optimiser abandoned the index for a table scan. The same SQL legitimately changes plan as the data changes.

Run the Query Plan tool against the production org: cost above roughly 1 means a scan. Then lead with an indexed selective filter, or request a custom index for the field you filter on constantly.

14 Which fields are indexed without you doing anything?Easy

Id, Name, OwnerId, CreatedDate, SystemModstamp, RecordTypeId, master-detail and lookup relationship fields, and anything marked External Id or Unique.

That last one is the free lever: marking a field External Id gives you an index and upsert-by-key in one move.

15 Your WHERE Status__c != 'Closed' filter is slow.Medium

Negative operators (!=, NOT) generally cannot use an index, and "not closed" is usually not selective anyway.

Rewrite as a positive IN list of the statuses you want, and add a selective filter (a date range, an owner, a record type) to lead the query.

16 LIKE '%urgent%' is slow and you cannot change the requirement.Medium

A leading wildcard cannot use an index. If the requirement is genuinely free-text search, use SOSL, which hits the search index rather than scanning.

If it is really "flag records containing a keyword", have automation set a checkbox or category field at save time and filter on that instead.

17 You need to page through 100,000 records in a UI.Hard

OFFSET is capped at 2,000 and degrades badly, so it is not the answer.

Use keyset pagination: WHERE Id > :lastSeenId ORDER BY Id LIMIT 200, carrying the last Id forward. It stays fast at any depth because it is always an indexed range scan.

18 A query returns 50,001 rows and throws.Easy

You hit the total query rows limit (50,000 per transaction, and it does not increase in async context — a common misconception).

Use Batch Apex with a QueryLocator, which streams rows outside that limit, or narrow the query. Moving to async buys CPU, heap and query count, not rows.

19 Aggregate query hits a limit on a large object.Medium

Aggregate queries still process the underlying rows, so an unselective aggregate over millions of records is expensive and the grouped result set is itself capped.

Add a selective filter (a period, a segment), pre-aggregate with a scheduled batch into a summary object, or do the aggregation in CRM Analytics where it belongs.

20 You need data from a grandparent and a grandchild in one query.Medium

SOQL allows five levels up (child to parent) in the SELECT, and one level down (parent to child subquery) — so a grandchild subquery is not possible in a single query.

Query twice and join in Apex with a map, which is usually cheaper than contorting one query. That relationship limit is a genuine shape constraint on your query design.

21 A relationship query returns parents with empty child lists.Easy

That is correct behaviour — a parent-child subquery returns the parent regardless, with an empty (or null) child collection.

Always null-check the subquery result before iterating; assuming children exist is a reliable source of null pointer exceptions in production where test data always had children.

22 You need "Accounts with no Opportunities".Medium

An anti-join: WHERE Id NOT IN (SELECT AccountId FROM Opportunity). Be aware these are limited in number per query and are rarely selective, so they get slow at volume.

At scale, a maintained roll-up count field on Account (filterable and indexable) outperforms the anti-join substantially — and it also makes the requirement reportable.

23 A Task.WhatId could point at several objects.Medium

Polymorphic field. Use TYPEOF WhatId WHEN Account THEN Name WHEN Opportunity THEN StageName ELSE Id END to select different fields per type in one query.

In Apex, ((Id) task.WhatId).getSObjectType() tells you the type at runtime. Never assume the parent type from context — it will be a Case one day.

24 FIELDS(ALL) seems convenient. When is it a bad idea?Medium

In any bulk path. It selects every field, inflating heap and query cost, and it is row-bounded so it cannot be used freely in Batch Apex.

Use it for exploration and for genuinely dynamic UI needs; name your fields explicitly in production code paths. Querying only what you render is also the cheapest performance habit available.

25 How do you check whether an index is being used?Medium

The Query Plan tool in the Developer Console — it shows the cost and which index (if any) each plan option uses.

Also read SOQL_EXECUTE_BEGIN/END in a debug log, which gives rows returned and elapsed time. Three rows returned in 4,000ms is a selectivity problem, not a code problem.

26 When would you ask Salesforce for a skinny table?Hard

When a heavy, repeated read pattern on a large object needs fields from both the base and custom field sets, and indexing alone has not fixed it — typically reports and list views on tens of millions of rows.

Caveats: Support creates them, they are limited in field count, they contain no joins, and they do not automatically include fields you add later. They are a tuning step, not an architecture.

27 Your query filters on a formula field and is slow.Medium

Cross-object or non-deterministic formulas cannot be indexed, and they are evaluated per row.

Materialise the value: have automation write it to a plain indexable field and backfill, then filter on that. Deterministic single-object formulas can be indexed, so sometimes flattening the formula is enough.

28 You need the most recent child record for each of 5,000 parents.Hard

SOQL has no per-group limit, so you cannot ask for "latest per parent" directly. Options: query children ordered by parent and date and take the first per parent in Apex; or maintain a "latest child" lookup on the parent via automation.

At volume the maintained lookup wins decisively — it turns an expensive query into an indexed field, and it is reportable.

29 Should you use SOQL or SOSL?Easy

SOQL when you know the object and are filtering on field values. SOSL when you are doing text search, especially across multiple objects — it hits the search index rather than scanning.

SOSL also has its own limits (queries per transaction, rows returned) and does not return everything a scan would, since indexing is eventually consistent.

30 A newly created record is not found by a SOSL search in the same transaction.Medium

Search indexing is asynchronous, so a just-inserted record may not be searchable yet.

Do not build logic that depends on it. In tests, Test.setFixedSearchResults() gives deterministic SOSL results — relying on real indexing in a test produces an intermittently failing build.

DML, partial success & transactions (31–45)

31 One bad record in a batch of 200 fails the whole insert.Easy

Default DML is all-or-none. Use Database.insert(records, false) to allow partial success, then inspect each SaveResult and log the failures with their status codes and fields.

Choose deliberately: all-or-none for anything that must be atomic (financial postings), partial for integration and bulk loads where the good 199 should succeed.

32 You need to know which records failed and why.Medium

Iterate the results by index — results[i] corresponds to records[i] — and for each failure read getErrors() for the status code, message and affected fields.

Write those to an error log object or platform event with the record Id. A count of failures without causes is almost useless at 3am.

33 UNABLE_TO_LOCK_ROW appears intermittently in an integration.Hard

Lock contention, almost always on a shared parent: inserting or updating a detail record locks its master-detail parent, and roll-up recalculation holds it longer.

Fixes: sort your DML by parent Id so concurrent transactions lock in the same order, reduce batch size, switch Bulk API from parallel to serial, and look for ownership or lookup skew in the data shape. See skew.

34 Two processes deadlock updating related records.Hard

They acquired locks in a different order. Deadlock is an ordering problem, not a volume problem.

Make lock order deterministic: always ORDER BY Id when using FOR UPDATE, and sort collections by parent Id before DML. Then reduce how long locks are held by doing less inside the transaction.

35 You need to prevent two users overwriting each other's changes.Medium

SELECT ... FOR UPDATE takes a row lock for the rest of the transaction, so the second transaction waits.

Use it for genuine read-modify-write sequences (incrementing a counter, allocating from a pool), lock in a deterministic order, and keep the locked window short. For UI edits, optimistic concurrency via a version field is often the better user experience.

36 A savepoint rollback did not undo everything.Hard

Rollback undoes database changes only. It does not reset static variables, un-send emails, un-publish platform events published immediately, or recall callouts already made.

Savepoints also count against DML statement limits. Use them sparingly, and never rely on rollback to undo side effects outside the database.

37 You get a mixed DML error inserting a User and an Account together.Medium

Setup objects (User, Group, PermissionSetAssignment, Territory) cannot be modified in the same transaction as non-setup objects.

Split them: do one in an async context (@future, Queueable) or use System.runAs in tests. A platform event subscriber is also a legitimate way to get a separate transaction.

38 Upsert sometimes creates duplicates.Medium

Upsert matches on Id or an External Id field. If the external id is blank on some rows, or not marked unique, upsert inserts instead of matching.

Make the field unique (the database constraint is the real guarantee), ensure every incoming row carries it, and handle the duplicate-value error as "already processed" rather than a failure.

39 A trigger throws and the user sees a stack trace.Easy

An unhandled exception surfaces internal class names, which is unhelpful and leaks implementation detail.

Use addError() with a message written for the user — on the field where possible so it appears next to the input. For Aura/LWC entry points, throw AuraHandledException with a user-facing message and log the detail separately.

40 Should you ever catch and swallow an exception in a trigger?Medium

No. A bare catch (Exception e) {} turns a data-integrity failure into a silent one, which is strictly worse — the save succeeds with wrong data and nobody learns.

Catch to add context and re-throw, or catch to log and addError. If a failure is genuinely tolerable, that is a business decision and the record should record that it was skipped.

41 You hit 151 DML statements.Easy

DML inside a loop. The limit counts statements, not rows, so one update of 10,000 records is one statement.

Collect into a list in the loop and perform one DML after it. If the DML must vary by type, build several lists and issue one statement each.

42 You need to delete 5 million records.Hard

Batch Apex or Bulk API, in chunks, and decide between delete (goes to the recycle bin, still consumes storage, recoverable) and hard delete (irreversible, frees storage immediately).

Verify the selection with a count first, run it in a controlled window, and expect sharing and roll-up recalculation load. For anything irreversible, prove the data is right before you start.

43 Deleting a parent deleted children you wanted to keep.Medium

Master-detail relationships cascade delete, and the children's delete triggers fire too — which archiving logic frequently forgets.

If children must survive the parent, the relationship must be a lookup (with the delete-constraint option set appropriately). Test archive and delete paths with real automation active.

44 An undelete restores a record but automation did not run as expected.Medium

after undelete is its own trigger context, and many handlers never implement it — so roll-ups and derived fields can be stale on restored records.

Implement undelete explicitly where it matters, or run a reconciliation after restores. This also applies to restoring from the recycle bin through the UI.

45 Your DML in a test does not seem to affect the database.Easy

Test data is rolled back at the end of each test method and is invisible to the rest of the org, by design.

If you cannot see any data, check whether you are relying on org data without SeeAllData (you cannot) or on Custom Metadata you tried to insert (you cannot). See test data.

Security in Apex (46–58)

46 Your class is with sharing but exposes fields the user cannot see.Medium

with sharing governs record visibility only. It never enforces field-level security or object permissions.

Add WITH USER_MODE to queries, as user to DML, or run results through Security.stripInaccessible. This distinction is the most common finding in a Salesforce security review.

47 When do you use stripInaccessible instead of USER_MODE?Medium

USER_MODE enforces at the database level, which is cleaner for queries and DML you control. stripInaccessible is for collections that arrived from elsewhere — a deserialised payload, a method parameter — where you need to remove inaccessible fields before using or returning them.

It also tells you what was removed, which is useful for logging and for deciding whether to fail rather than silently proceed.

48 An inner class behaves as if it were without sharing.Hard

Inner classes do not inherit the outer class's sharing declaration — they default to the caller's mode, which from some entry points is system mode.

Declare sharing explicitly on inner classes that do data access. This is a genuinely obscure rule that produces real exposure.

49 What should a reusable utility class declare?Medium

inherited sharing — it takes the mode of its caller, which is correct for a library and is the only safe-by-default option when it might be entered from a Visualforce page or REST endpoint.

An unannotated class runs in system mode from those entry points, which is how libraries accidentally become elevation paths.

50 Dynamic SOQL built from user input — what must you do?Hard

Bind variables wherever possible; String.escapeSingleQuotes() on any fragment you must concatenate; and allow-list field and object names against a known set rather than accepting them from the client.

Then add WITH USER_MODE, because dynamic queries bypass nothing automatically. Accepting a filter expression from a client is a data-exfiltration surface, not a feature.

51 An @AuraEnabled method takes an object name as a parameter.Hard

That is a generic read endpoint for anyone who can load the component, including guests on a public page.

Allow-list the permitted object names, enforce CRUD and FLS explicitly, bound the row count, and never return fields the caller did not ask for. Better still, write a purpose-specific method instead of a generic one.

52 Do you need to check CRUD if the user cannot see the button?Easy

Yes. Hiding a button is presentation; the Apex method remains callable. Client-side checks are UX, server-side checks are security.

Enforce it in the method itself, every time — and put the question "who can cause this to run, and in whose context?" in your PR checklist.

53 How do you test that FLS is enforced?Medium

System.runAs with a user built from a minimum-access profile plus only the permission set under test, then assert that restricted fields are absent or that the expected exception is thrown.

Testing as an admin proves nothing — tests run in system mode by default, which is why access bugs reach production with full coverage.

54 A query in user mode throws where system mode did not.Medium

That is it working: the user lacks access to an object or field in the query, so the query is rejected rather than silently returning data they should not see.

Decide the behaviour deliberately — catch and degrade the feature, or let it fail. Silently stripping may be worse than failing if the caller then makes a decision on incomplete data.

55 A flow calls your Apex and sees more than the user should.Medium

Record-triggered flows run in system context without sharing by default, and your inherited sharing class then runs in system mode too.

If the Apex must respect the user, declare with sharing and use USER_MODE explicitly rather than relying on the caller's context. See running context.

56 You need to grant access programmatically from Apex.Medium

Insert share rows (Object__Share) with a custom RowCause created in Setup, so the grant survives ownership changes and is identifiable later.

The class needs elevated context, so keep it small and reviewed, use partial-success DML, and build the corresponding revoke path — nothing cleans up stale shares for you.

57 Should an integration endpoint run without sharing for performance?Hard

No — and the premise is usually wrong anyway; sharing enforcement is not typically the bottleneck.

Prefer authenticating as a user whose access is the restriction and writing the class with sharing, so record access does the filtering. A WHERE clause on an elevated query means a bug in that clause becomes a breach, whereas sharing fails closed.

58 How do you audit an existing codebase for security gaps?Hard

Grep for without sharing, every @AuraEnabled and @RestResource, and every dynamic SOQL construction. Cross-reference against which components are on guest-accessible pages.

Then run the Salesforce Code Analyzer for the mechanical findings, and prioritise by reachability — anonymous or external first. Fix the pattern, not just the instance, and add the check to CI.

Numbers, dates & strings (59–72)

59 A currency total is a penny out.Medium

Rounding and scale. Intermediate results carry more precision than you display, so rounding once at the end differs from rounding per line.

Use Decimal with explicit setScale(2, RoundingMode.HALF_UP) at the stage finance agreed, and write the convention in a test with expected figures to the penny.

60 Why must you never use Double for money?Easy

Binary floating point cannot represent 0.1 exactly, so sums drift — and the drift appears after thousands of operations, in production, in a finance report.

Decimal is exact for decimal arithmetic. The rule is absolute: money, quantities and anything reconciled is Decimal.

61 A date comparison is off by one day for some users.Hard

Timezone. Datetime is stored in UTC and rendered in the user's timezone; Date has no timezone at all. Converting between them at a day boundary shifts the result.

Be explicit: decide whose timezone the business rule means, use Datetime.newInstance / dateGmt() deliberately, and test with users in two zones.

62 You need "three business days from now".Medium

Use BusinessHours methods with holidays attached — date arithmetic cannot know your holidays, and the business will notice on a bank holiday.

Missing holidays is also the standard cause of "the SLA says we breached but we were closed". Same mechanism underlies entitlement milestones.

63 A date field shows differently in a report and in Apex.Medium

Locale and timezone: locale controls the format, the user's timezone controls which calendar day a Datetime falls in.

Three separate user settings are involved — language (labels), locale (formats), timezone (datetime display). Most "wrong date" bugs are a confusion between locale and timezone.

64 You need to parse a date from an external system.Medium

Use Date.valueOf() / Datetime.valueOfGmt() with a known format, or parse the components explicitly — never Date.parse(), which is locale-dependent and will behave differently for different running users.

Agree the wire format with the other system (ISO 8601 with an explicit offset) rather than inferring it.

65 Integer division gives 0 where you expected 0.5.Easy

Integer arithmetic truncates. Cast one operand to Decimal or Double before dividing.

This appears most often in percentage calculations, where the result then displays as 0% and somebody assumes the data is missing.

66 You need to compare two strings ignoring case and whitespace.Easy

String.equalsIgnoreCase() after trim(), or normalise both sides through a single helper so the rule is in one place.

For matching keys, normalise at write time into a dedicated field (lowercased, trimmed, punctuation removed) so you can index and unique-constrain it rather than normalising on every read.

67 A long text field truncates when you write to it.Easy

You exceeded the field length. Apex does not truncate silently on all paths — it can throw STRING_TOO_LONG.

Use .left(n) (or abbreviate()) deliberately when writing logs and stack traces, so the behaviour is intentional rather than an exception in an error handler — which is a particularly annoying failure.

68 JSON deserialisation fails on a field name that is an Apex keyword.Medium

You cannot name a property currency or date. Use JSON.deserializeUntyped and read the map, or define the class with a different property name and map it manually.

For a stable contract, write an explicit DTO class and a mapping method rather than relying on name matching — it also gives you a place to validate.

69 JSON.serialize on a query result includes fields you did not want.Medium

It serialises everything populated on the sObject, including attributes and related records — which can leak fields and inflate payloads.

Serialise an explicit DTO instead. That also decouples your API contract from your schema, so renaming a field does not break a consumer.

70 A null in an expression makes the whole result null.Easy

Standard null propagation. Guard with explicit defaults, or use the safe navigation operator (?.) to avoid null pointer exceptions when traversing relationships.

In SOQL results, parent relationships can be null (no parent) and subqueries can be empty — both need checking before use.

71 An enum value from an integration does not match your Apex enum.Medium

valueOf on an unknown value throws. Map through a known lookup with an explicit "unknown" branch instead, and log the unrecognised value.

External systems add enum values without telling you, so an integration that throws on an unknown status is an integration that breaks on their next release.

72 How do you make heavy string/collection code cheaper on CPU?Hard

Measure first with the cumulative limits section of a debug log, then: avoid nested loops (use maps for lookups), avoid concatenation in loops (String.join), avoid repeated getGlobalDescribe(), avoid deserialising the same payload twice, and avoid re-sorting inside a loop.

CPU time counts computation, not waiting — so optimise the loops, not the queries, when CPU is the limit you are hitting. See what counts as CPU.

Classes, interfaces & structure (73–86)

73 Where should logic live if a trigger, an LWC and REST all need it?Medium

A service class owning the transaction boundary, with all three as thin adapters. One implementation, one place to test, and a new entry point costs nothing.

That is the highest-value structure in a growing codebase, and it is worth adopting long before a full enterprise-pattern layering. See patterns.

74 Why centralise SOQL in a selector class?Medium

Consistent field lists and security enforcement in one place, no duplicated queries drifting apart, and a single place to fix a selectivity problem.

It is also the pattern that makes services unit-testable: inject a stubbed selector and the test never touches the database. Adopt the selector first if you adopt nothing else.

75 An interface would let you swap implementations. When is that over-engineering?Medium

When there is exactly one implementation and no test seam needed. An interface with one implementor adds indirection for nothing.

It earns its place when there are genuinely multiple strategies, when you need a test double (the Stub API requires a seam), or when a package boundary requires loose coupling.

76 You need to instantiate a class named in configuration.Medium

Type.forName(className).newInstance(), cast to your interface — with a null check and a clear exception when the class does not exist.

That is the basis of metadata-driven dispatch, which lets admins reorder or disable logic without a deployment. The trade-off is genuinely harder debugging, so log which implementation ran.

77 A static variable keeps state between two DML statements unexpectedly.Medium

Statics live for the whole transaction, not per DML — so a second batch of records in the same transaction sees state from the first.

That is useful for caching and for recursion guards keyed by record Id, and harmful for a blunt alreadyRan boolean. Know which you are writing. See recursion control.

78 Static state leaks between test methods.Medium

Each test method is its own transaction, so statics reset — but within a method, code under test may have already set them.

Provide a reset hook (@TestVisible static void reset()) for caches and guards, and call it in setup. Tests that pass alone and fail in a suite are almost always static state or test data assumptions.

79 How do you cache expensive describe calls?Medium

A static map populated on first use. Describe results are cached per transaction by the platform, but building them is not free and getGlobalDescribe() in particular is expensive.

Prefer targeted describes (Account.SObjectType.getDescribe()) over a global describe you index into, and never call either inside a loop.

80 When would you use Platform Cache?Medium

For expensive, re-derivable, shared data: describe results, Custom Metadata lookups, aggregate results, external reference data with a known TTL.

Every read must handle a miss and recompute, because entries can be evicted at any time — and an unallocated partition silently does nothing. Never cache anything you cannot recompute, and never cache user-specific data in the org cache.

81 A wrapper class needs to go to an LWC.Easy

Mark the class and its properties @AuraEnabled — properties as well as the class, which is the step people miss.

Keep it a purpose-built DTO rather than exposing sObjects directly: smaller payloads, a stable contract, and no accidental field leakage.

82 How do you make a class testable without touching the database?Hard

Inject its dependencies — a selector interface for queries, a service for side effects — so a test can pass stubs via the Stub API.

Requirements for stubbing: the class is public/global and not final, the methods are virtual or interface-defined, and the dependency is injectable. Designing for that is what makes a codebase unit-testable rather than integration-testable. See Stub API.

83 A custom exception should carry the record Id that failed.Easy

Define a custom exception extending Exception and add properties for context (record Id, operation, correlation id). Apex custom exceptions can hold state like any class.

That context is what makes a production error log useful — a message without the record Id tells you something broke, not what to fix.

84 Should a method return null or throw when nothing is found?Medium

Be consistent and document it. Returning an empty collection is almost always better than null for list returns — callers can iterate without a null check.

For single-record lookups, throw when absence is a genuine error (a required configuration row), return null or an Optional-style wrapper when absence is normal. The failure mode to avoid is a method that sometimes does each.

85 Why does the API version a class was saved against matter?Medium

Each class keeps the semantics of its saved API version forever, which is the stability guarantee that stops platform upgrades breaking your code.

The cost is slowly accumulating debt — old classes miss newer behaviour and can block features. Bump versions deliberately with regression tests, not silently while editing something else.

86 You are writing Apex that will ship in a managed package.Hard

Treat global as a permanent contract you can never break — default to public and expose global deliberately. Use @namespaceAccessible for cross-package internal reuse.

Also: your tests run in subscriber orgs on upgrade, so they must not depend on org-specific data, and SeeAllData becomes actively dangerous. See packaging.

Debugging & judgement (87–100)

87 A null pointer exception in production with no debug log.Hard

You need instrumentation you built in advance: a structured error log published as a platform event so it survives the rollback, carrying class, method, record Id, correlation id and the quiddity.

A log row written with plain DML disappears when the failing transaction rolls back — which is the single most common logging mistake. See production debugging.

88 A bug only happens from the mobile app.Medium

Request.getCurrent().getQuiddity() tells you the invocation context — AURA, REST, BATCH_APEX, SYNCHRONOUS and so on — so "it only fails from X" becomes a provable statement rather than a theory.

Log it on every error. Behaviour differing by entry point usually means a context assumption (sharing mode, available fields, timezone of the running user).

89 Your code works with 1 record and fails with 200.Easy

Something is per-record that should be per-transaction: a SOQL or DML inside the loop, or logic assuming Trigger.new[0].

Write the bulk test first — 200 records is the standard shape — and it will catch this class of defect before review does.

90 CPU time limit exceeded, but the queries look fine.Hard

CPU counts computation, not waiting. Query time, callout time and commit time do not count — so the cause is loops, collections, JSON, or formula evaluation during your DML.

Read CUMULATIVE_LIMIT_USAGE in the debug log, which also attributes consumption per namespace — frequently revealing that a managed package is spending your budget.

91 An intermittent failure you cannot reproduce.Hard

Intermittent usually means concurrency, data shape, or ordering: lock contention, a record that is null only in old data, an async job arriving out of order, or a limit approached under load.

Instrument rather than guess — log limit snapshots and correlation ids, then look for the pattern across occurrences (same user? same hour? same record type?). "Unreproducible" is often "not yet reproduced as the right user with the right data".

92 A query returns different results for different users and you expected it not to.Medium

The class is with sharing (or inherited sharing from a user-context caller), so record access differs per user — which is usually correct.

If the result must be consistent regardless of the caller, that is deliberate elevation: a small, reviewed without sharing class, with the reason documented.

93 You need to prove a managed package is causing your CPU problem.Medium

CUMULATIVE_LIMIT_USAGE and LIMIT_USAGE_FOR_NS in a debug log break consumption down by namespace.

That log naming their namespace is the artefact that gets a vendor support case taken seriously. Also isolate by disabling your own logic and re-measuring, so your evidence is clean.

94 Should you optimise before measuring?Easy

No. The slow thing is rarely the thing you suspect, and on this platform the distinction between CPU and waiting changes the fix entirely.

Measure with the cumulative limits section and the Query Plan tool, change one thing, re-measure. Optimising by intuition usually produces more complex code with the same performance.

95 A query is selective but the transaction is still slow.Medium

Look at what the save triggers: validation rules, roll-up recalculation, other triggers, flows, sharing recalculation, and managed package logic — all inside your transaction.

The CODE_UNIT_STARTED/FINISHED tree in a debug log shows the real execution order and usually reveals automation you did not know existed.

96 You inherit 400 lines in one method.Medium

Add tests around the current behaviour first — you cannot refactor safely without them, and the tests also document what it actually does versus what the name claims.

Then extract in small, separately-deployable steps. A big-bang rewrite of untested logic is how a refactor becomes an incident nobody can attribute.

97 A reviewer asks you to remove a LIMIT because "we need all the records".Medium

Push back. An unbounded query works until the data grows, then fails — usually in production with no code change to blame.

If all records genuinely must be processed, that is Batch Apex with a QueryLocator, not a bigger list in one transaction. Bound every collection with a limit you chose.

98 When is it right to write Apex instead of a flow?Medium

Bulk performance, complex data shapes, reuse across entry points, real error handling, and anything that must be unit-tested as part of a service.

Flow wins on visibility and admin maintainability. The honest signal that logic has outgrown Flow: a loop inside a loop, a formula nobody can read, or a 200-element canvas nobody dares touch. See Flow ⇄ Apex.

99 What makes Apex code reviewable?Medium

Small methods with names that say what they do, one DML and one query per logical operation, no magic numbers or hard-coded Ids, explicit security mode, and tests that assert behaviour rather than just executing lines.

Plus the Salesforce-specific checklist: bulkified, sharing keyword deliberate, FLS enforced, no SOQL/DML in loops, destructive changes called out. See what to review.

100 One habit that most improves Apex quality?Hard

Writing the bulk test and the failure test first. 200 records, plus a record that must fail — those two cases catch the overwhelming majority of real defects, and they are exactly the two that get skipped when coverage is the only target.

Everything else (patterns, selectors, layering) is valuable but optional. Those two tests are not.
