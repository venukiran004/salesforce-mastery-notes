Apex Core & SOQL / SOSL

The language itself: types, collections and OOP — then the two query languages and every way to write data back, in the depth your notes asked for.

📖
What Apex is A strongly-typed, object-oriented, case-insensitive language with Java-like syntax that runs on Salesforce servers. It's compiled to bytecode, stored as metadata, multitenant-aware (governor limits), and has SOQL/DML built directly into the language rather than bolted on as a library.

Set<Id> accountIds = new Set<Id>();

accountIds.removeAll(otherSet);               // difference

Set<Id>  keys   = accById.keySet();

Map<Id, List<Contact>> contactsByAccount = new Map<Id, List<Contact>>();

Classes & OOP

public with sharing class OpportunityService {

    // ---- static: one per transaction, shared by all instances ----
    private static Integer callCount = 0;
    public  static final Decimal MAX_DISCOUNT = 0.30;

    // ---- instance members ----
    private final Id accountId;
    private List<Opportunity> opportunities;

    // ---- constructors (overloaded) ----
    public OpportunityService(Id accountId) {
        this.accountId = accountId;
        this.opportunities = new List<Opportunity>();
    }
    public OpportunityService(Id accountId, List<Opportunity> opps) {
        this(accountId);                 // constructor chaining
        this.opportunities = opps;
    }

    // ---- properties (getter/setter shorthand) ----
    public Integer count {
        get { return opportunities == null ? 0 : opportunities.size(); }
    }
    public String stage { get; set; }                  // auto-property
    public Boolean isClosed { get; private set; }      // read-only outside

    // ---- methods ----
    public void load() {
        this.opportunities = [
            SELECT Id, Name, Amount, StageName
            FROM Opportunity WHERE AccountId = :accountId
        ];
        callCount++;
    }

    // static factory
    public static OpportunityService forAccount(Id accId) {
        OpportunityService svc = new OpportunityService(accId);
        svc.load();
        return svc;
    }
}

Inheritance, abstract classes and interfaces

// ---------- INTERFACE : a contract, no implementation ----------
public interface Payable {
    Decimal calculatePay();
    void approve(Id approverId);
}

// ---------- ABSTRACT : partial implementation, cannot be instantiated ----------
public abstract class Employee implements Payable {
    protected String name;
    protected Decimal baseSalary;

    public Employee(String name, Decimal baseSalary) {
        this.name = name;
        this.baseSalary = baseSalary;
    }

    // concrete method — inherited as-is
    public String getName() { return name; }

    // abstract — every subclass MUST implement
    public abstract Decimal calculatePay();

    // virtual — subclasses MAY override
    public virtual void approve(Id approverId) {
        System.debug('Approved by ' + approverId);
    }
}

// ---------- CONCRETE SUBCLASSES ----------
public class SalariedEmployee extends Employee {
    public SalariedEmployee(String n, Decimal s) { super(n, s); }
    public override Decimal calculatePay() { return baseSalary / 12; }
}

public class ContractEmployee extends Employee {
    private Decimal hourlyRate, hours;
    public ContractEmployee(String n, Decimal rate, Decimal hrs) {
        super(n, 0);
        this.hourlyRate = rate; this.hours = hrs;
    }
    public override Decimal calculatePay() { return hourlyRate * hours; }
    public override void approve(Id approverId) {
        super.approve(approverId);                   // call the parent
        System.debug('Contractor approval logged');
    }
}

// ---------- POLYMORPHISM in action ----------
List<Payable> staff = new List<Payable>{
    new SalariedEmployee('Asha', 900000),
    new ContractEmployee('Ravi', 1200, 160)
};
Decimal total = 0;
for (Payable p : staff) total += p.calculatePay();   // correct method chosen at runtime

Apex specifics people miss Apex classes and methods are final by default — you must mark them virtual or abstract to allow overriding, and use the override keyword explicitly. Inner classes can be one level deep only, and static variables aren't allowed in inner classes.

SOQL — in detail

Salesforce Object Query Language. Like SQL but with one crucial difference: you query one object and traverse relationships — there is no arbitrary JOIN, no SELECT *.

// ---------- BASIC ----------
List<Account> accs = [
    SELECT Id, Name, Industry, AnnualRevenue
    FROM Account
    WHERE Industry = 'Technology'
      AND AnnualRevenue > 1000000
    ORDER BY AnnualRevenue DESC NULLS LAST
    LIMIT 50
    OFFSET 10
];

// Single record — throws QueryException if 0 or 2+ rows returned
Account one = [SELECT Id, Name FROM Account WHERE Id = :accId];

// Count without pulling records (doesn't count toward heap)
Integer total = [SELECT COUNT() FROM Contact WHERE AccountId = :accId];

Bind variables

Id       accId  = '001xx';
Set<Id>  accIds = new Set<Id>{ '001xx', '001yy' };
String   name   = 'Acme';
Date     cutoff = Date.today().addDays(-30);

List<Opportunity> opps = [
    SELECT Id FROM Opportunity
    WHERE AccountId IN :accIds              // Set / List / Map keySet all work
      AND Name LIKE :('%' + name + '%')
      AND CloseDate >= :cutoff
];
🛡️
Bind variables prevent SOQL injection Never concatenate user input into a query string. If you must build dynamic SOQL, use String.escapeSingleQuotes() or, better, Database.queryWithBinds().

Relationship queries — the two directions

Child → Parent vs Parent → Child
// CHILD → PARENT (up to 5 levels of dots)
List<Contact> cons = [
    SELECT Id, LastName,
           Account.Name,
           Account.Owner.Email,
           Account.Parent.Name
    FROM Contact
    WHERE Account.Industry = 'Banking'
];
System.debug(cons[0].Account.Owner.Email);

// PARENT → CHILD (subquery; only 1 level deep, max 20 child relationships)
List<Account> accs = [
    SELECT Id, Name,
           (SELECT Id, LastName, Email FROM Contacts WHERE Email != null ORDER BY LastName),
           (SELECT Id, Amount FROM Opportunities WHERE IsClosed = false),
           (SELECT Id, Subject FROM Invoices__r)          // custom object → __r
    FROM Account
    WHERE Id IN :accountIds
];
for (Account a : accs) {
    for (Contact c : a.Contacts) {              // no extra query — already loaded
        System.debug(a.Name + ' → ' + c.LastName);
    }
}

// Filtering a parent by children — semi-join / anti-join
List<Account> withOpps = [
    SELECT Id FROM Account
    WHERE Id IN (SELECT AccountId FROM Opportunity WHERE StageName = 'Closed Won')
];
List<Account> withoutCases = [
    SELECT Id FROM Account
    WHERE Id NOT IN (SELECT AccountId FROM Case WHERE IsClosed = false)
];

// GROUP BY ROLLUP adds subtotal rows

📏
Aggregate limits AggregateResult rows count toward the 50,000 query rows limit. GROUP BY is capped at 2,000 result rows. You cannot use aggregate functions with ORDER BY on an unaggregated field.

SOQL for loops — the heap saver

// ❌ Loads everything into heap at once — risks "Apex heap size too large"
List<Account> all = [SELECT Id, Name FROM Account];
for (Account a : all) { /* ... */ }

// ✅ Streams in chunks of 200 automatically
for (Account a : [SELECT Id, Name FROM Account]) { /* ... */ }

// ✅✅ Best for DML — processes 200 records per iteration
for (List<Account> batch : [SELECT Id, Name FROM Account WHERE Industry = 'Retail']) {
    for (Account a : batch) a.Description = 'Reviewed';
    update batch;                       // one DML per 200
}

Query selectivity & indexes

Non-selective queries on large objects throw System.QueryException: Non-selective query against large object type (in triggers) or simply run slowly.

Indexed by default

  • Id, Name, OwnerId, CreatedDate, SystemModstamp, RecordTypeId
  • Master-detail & lookup fields
  • Fields marked Unique or External ID

Kills selectivity

  • Leading wildcard: LIKE '%acme'
  • != and NOT IN
  • field = null (unless the index includes nulls)
  • Formula fields (unless deterministic)
  • OR across different fields where one is unindexed
🔢
Selectivity thresholds A filter is selective if it returns under 30% of the first million records and under 15% beyond that (roughly 333,000 rows max). Ask Salesforce Support for a custom index or skinny table on very large objects.

Security & locking clauses

// Enforce FLS + CRUD + sharing for the running user
List<Account> a1 = [SELECT Id, Name FROM Account WITH USER_MODE];

// Legacy: FLS/CRUD only
List<Account> a2 = [SELECT Id, Name FROM Account WITH SECURITY_ENFORCED];

// Row locking to prevent concurrent updates (releases at transaction end)
Account locked = [SELECT Id, Name FROM Account WHERE Id = :accId FOR UPDATE];

// Search scope
List<Account> mine = [SELECT Id FROM Account USING SCOPE mine];   // mine | everything | team | delegated

SOSL — in detail

Salesforce Object Search Language searches text indexes across multiple objects at once. Think of it as the platform's search box in query form.

// Basic shape — always returns List<List<sObject>>
List<List<sObject>> results = [
    FIND 'Acme*'
    IN ALL FIELDS
    RETURNING Account(Id, Name, Industry WHERE Industry = 'Technology' ORDER BY Name LIMIT 10),
              Contact(Id, LastName, Email),
              Lead(Id, Company),
              Opportunity(Id, Name)
    LIMIT 200
];

List<Account>     accounts = (List<Account>)     results[0];
List<Contact>     contacts = (List<Contact>)     results[1];
List<Lead>        leads    = (List<Lead>)        results[2];
List<Opportunity> opps     = (List<Opportunity>) results[3];

// Dynamic SOSL
String term = String.escapeSingleQuotes(userInput);
List<List<sObject>> r = Search.query(
    'FIND \'' + term + '\' IN NAME FIELDS RETURNING Account(Id, Name)'
);
Search groupSearches
IN ALL FIELDSEvery searchable text field (default)
IN NAME FIELDSName / Subject-type fields only — fastest
IN EMAIL FIELDSEmail fields
IN PHONE FIELDSPhone fields
IN SIDEBAR FIELDSFields in the classic sidebar search

Wildcards & operators

  • * — multiple characters ('Acm*'). Cannot be the first character.
  • ? — single character ('Jo?n' → John, Joan).
  • AND, OR, AND NOT, and quotes for exact phrases: FIND '"Acme Corp"'.
  • Escape reserved characters: ? & | ! { } [ ] ( ) ^ ~ * : \ " ' + -

Use case A support console has one search box. The agent types "acme" and must see matching Accounts, Contacts, Cases and Knowledge articles. That's SOSL. But "all open cases for account X created this month" is SOQL.

DML — writing data

Account a = new Account(Name = 'Acme India', Industry = 'Technology');

insert a;                  // a.Id is populated after this line
a.Industry = 'Banking';
update a;
delete a;                  // goes to Recycle Bin (15 days)
undelete a;                // restore from Recycle Bin

// upsert — insert or update based on Id or an External ID field
upsert accountList;                                  // by Id
upsert accountList Legacy_Id__c;                     // by external id field

// merge — only Account, Contact, Lead, Case (max 3 records total: 1 master + 2)
merge masterAccount duplicateAccount;

// ALWAYS bulk: pass a list, never DML inside a loop
List<Contact> toInsert = new List<Contact>();
for (Integer i = 0; i < 200; i++) toInsert.add(new Contact(LastName = 'Test ' + i));
insert toInsert;          // 1 DML statement, not 200
💥
All-or-nothing A DML statement is atomic: if one record in the list fails, the entire statement rolls back and a DmlException is thrown. When you need partial success, use the Database methods below.

Savepoints & rollback

Savepoint sp = Database.setSavepoint();
try {
    insert parentRecords;
    insert childRecords;                 // if this fails…
    doRiskyThing();
} catch (Exception e) {
    Database.rollback(sp);               // …undo the parents too
    // Note: Id values set during the rolled-back DML are NOT reset — clear them manually
    throw new AppException('Batch failed: ' + e.getMessage(), e);
}
📌
Savepoint limits Each setSavepoint() counts toward the DML statement limit (150). Don't create them in a loop. A rollback restores data but does not reset the Id fields on your in-memory sObjects.

Interview questions

1 Why must you use Decimal rather than Double for currency?Easy

Double is a 64-bit binary floating point type, so values like 0.1 can't be represented exactly and errors accumulate — you end up a cent out after enough arithmetic. Decimal has arbitrary precision and lets you control rounding explicitly with setScale(2, RoundingMode.HALF_UP). All Salesforce Currency fields map to Decimal, so matching the type also avoids silent conversions.

2 if (myBoolean) throws a NullPointerException. Explain.Easy

Every Apex type is nullable, including Boolean and Integer. An undeclared-value Boolean is null, not false, and evaluating null in a condition throws. Defend with if (myBoolean == true), initialise at declaration, or use the safe-navigation operator ?. when reaching through objects: opp.Account?.BillingCity.

3 List vs Set vs Map — give a real reason to pick each.Easy

List — ordered and allows duplicates; it's the only one you can pass to DML (insert myList). Set — uniqueness plus O(1) contains(); use it to collect Ids for a WHERE Id IN :ids filter and for membership tests inside loops (a List's contains() is O(n) and will cause CPU timeouts). Map — O(1) key lookup; the foundation of bulkification, because you query parents once into a Map and then get() inside the loop instead of querying.

4 Write a query returning Accounts with their Contacts and the Account owner's email.Medium 
SELECT Id, Name, Owner.Email,                  // child → parent: dot notation, up to 5 levels
       (SELECT Id, LastName FROM Contacts)     // parent → child: subquery, only 1 level deep
FROM Account
WHERE Id IN :accountIds
WITH USER_MODE

Naming rule people get wrong: standard child relationships use the plural name (Contacts), custom ones use __r (Invoices__r), and a custom parent field Account__c is traversed as Account__r.Name.

5 When would you use SOSL over SOQL?Easy

When you need a free-text search across multiple unrelated objects — a global search box returning Accounts, Contacts, Cases and Leads in one call. SOSL hits the tokenised search index, so it handles stemming and near-matches that LIKE can't, and it costs 1 of your 20 SOSL limits instead of 4 of your 100 SOQL queries.

Stay with SOQL when you know the object and the criteria, or need relationships, aggregates or GROUP BY. Remember the search index updates asynchronously, and in tests you must call Test.setFixedSearchResults().

6 What makes a query "non-selective" and why does it matter?Hard

A filter is selective if it uses an indexed field and returns under roughly 30% of the first million rows (15% beyond that, capped near 333,000). Indexed by default: Id, Name, OwnerId, CreatedDate, SystemModstamp, RecordTypeId, lookup and master-detail fields, and anything marked Unique or External ID.

Selectivity is destroyed by leading wildcards (LIKE '%acme'), !=, NOT IN, field = null, non-deterministic formula fields, and OR across unindexed fields. On a large object inside a trigger this throws "Non-selective query against large object type". Fix by filtering on indexed fields, or request a custom index or skinny table from Support.

7 DML statement or Database method — how do you choose?Medium

insert list; is all-or-nothing: one bad record throws a DmlException and the whole statement rolls back. Right when the records form one logical unit.

Database.insert(list, false) allows partial success and returns SaveResult[] so you can log failures and continue — right for bulk loads and integrations. Database methods also take DMLOptions for assignment rules, duplicate-rule overrides and email headers, which the plain statement can only do via setOptions().

8 Explain the difference between abstract, virtual and an interface.Medium

Apex classes and methods are final by default. virtual permits a subclass to override a method that already has an implementation; abstract declares a method with no body that every subclass must implement, and makes the class non-instantiable. An interface is a pure contract — no bodies, no variables, no constructor — and a class can implement many while extending only one class. Use an interface for "can do" capability and mocking; an abstract class for "is a" hierarchies that share code.

9 How do you prevent SOQL injection in dynamic queries?Hard

Prefer bind variables — WHERE Name = :userInput can't be injected at all. For genuinely dynamic queries use Database.queryWithBinds(soql, bindMap, AccessLevel.USER_MODE). If you must concatenate, wrap every user value in String.escapeSingleQuotes().

The subtlety interviewers look for: escaping protects values, not identifiers. A dynamic object or field name must be validated against a whitelist or resolved through Schema.getGlobalDescribe(), because no amount of quote-escaping makes an injected FROM clause safe.

Quick check

1. Which collection would you use to check membership of 10,000 Ids inside a loop?
List.contains() scans the whole list every call (O(n)); a Set hashes. On 10,000 items inside a loop that's the difference between milliseconds and a CPU timeout.
2. You need Accounts, Contacts and Cases matching the text "acme" in one call. What do you use?
SOSL is the only way to search multiple unrelated objects in one statement — and it uses 1 of your 20 SOSL limits instead of 3 of your 100 SOQL limits.
3. A data load of 5,000 records must insert everything valid and log the rest. Which do you use?
The DML statement is all-or-nothing — one bad row rolls back all 5,000. allOrNone = false gives you per-record results.
