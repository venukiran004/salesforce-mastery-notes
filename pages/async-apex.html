Asynchronous Apex

Future methods, Queueable, Batch, Schedulable and Finalizers — what each is for, complete working examples, the higher limits you unlock, and how to choose between them.

Why asynchronous?

Synchronous code runs immediately and the user waits. Asynchronous code is queued and executed when platform resources are available — the user gets their response straight away.

Synchronous vs asynchronous execution

Better user experience

Long-running work doesn't block the save or the page.

Higher limits

SOQL 200 (vs 100), heap 12 MB (vs 6 MB), CPU 60 s (vs 10 s), 100 callouts.

Callouts after DML

The only clean way to integrate from a trigger.

1 · Future methods

The oldest and simplest form. Mark a static method @future and it runs later.

public class AccountGeocodeService {

    @future(callout=true)
    public static void geocodeAddresses(Set<Id> accountIds) {
        List<Account> accounts = [
            SELECT Id, BillingStreet, BillingCity, BillingCountry
            FROM Account WHERE Id IN :accountIds
        ];

        List<Account> toUpdate = new List<Account>();
        for (Account a : accounts) {
            HttpRequest req = new HttpRequest();
            req.setEndpoint('callout:Geocode_API/geocode?address=' +
                            EncodingUtil.urlEncode(a.BillingCity + ' ' + a.BillingCountry, 'UTF-8'));
            req.setMethod('GET');
            req.setTimeout(20000);

            HttpResponse res = new Http().send(req);
            if (res.getStatusCode() == 200) {
                Map<String, Object> body = (Map<String, Object>) JSON.deserializeUntyped(res.getBody());
                a.Latitude__c  = (Decimal) body.get('lat');
                a.Longitude__c = (Decimal) body.get('lng');
                toUpdate.add(a);
            }
        }
        if (!toUpdate.isEmpty()) update toUpdate;
    }
}

// Called from an after-insert trigger
AccountGeocodeService.geocodeAddresses(Trigger.newMap.keySet());
🚧
Future method restrictions ① Must be static void. ② Parameters must be primitives or collections of primitives — no sObjects (their state could be stale by the time it runs). ③ Cannot be called from another future or from Batch. ④ Cannot be chained. ⑤ No job Id, so monitoring is awkward. ⑥ Limit: 50 future calls per transaction. For all these reasons, prefer Queueable in new code.

The workaround for passing records is to serialise them: MyClass.doWork(JSON.serialize(records)), then deserialise inside — but that's exactly what Queueable makes unnecessary.

2 · Queueable Apex

The modern replacement for @future: a class, not a method, so it can hold state and be chained.

public class InvoiceSyncQueueable implements Queueable, Database.AllowsCallouts {

    private List<Invoice__c> invoices;      // complex types ARE allowed
    private Integer attempt;

    public InvoiceSyncQueueable(List<Invoice__c> invoices) {
        this(invoices, 1);
    }
    public InvoiceSyncQueueable(List<Invoice__c> invoices, Integer attempt) {
        this.invoices = invoices;
        this.attempt  = attempt;
    }

    public void execute(QueueableContext context) {
        List<Invoice__c> failed = new List<Invoice__c>();

        for (Invoice__c inv : invoices) {
            HttpRequest req = new HttpRequest();
            req.setEndpoint('callout:ERP/api/invoices');
            req.setMethod('POST');
            req.setHeader('Content-Type', 'application/json');
            req.setBody(JSON.serialize(new Map<String, Object>{
                'externalId' => inv.Id,
                'amount'     => inv.Amount__c
            }));

            try {
                HttpResponse res = new Http().send(req);
                inv.Sync_Status__c = (res.getStatusCode() == 201) ? 'Synced' : 'Failed';
                if (res.getStatusCode() >= 500) failed.add(inv);       // retryable
            } catch (CalloutException e) {
                inv.Sync_Status__c = 'Failed';
                failed.add(inv);
            }
        }
        update invoices;

        // CHAINING — enqueue the next job (max 1 child from a Queueable in production)
        if (!failed.isEmpty() && attempt < 3 && !Test.isRunningTest()) {
            System.enqueueJob(new InvoiceSyncQueueable(failed, attempt + 1));
        }
    }
}

// Enqueue it — returns a job Id you can monitor
Id jobId = System.enqueueJob(new InvoiceSyncQueueable(invoiceList));
System.debug([SELECT Status, NumberOfErrors FROM AsyncApexJob WHERE Id = :jobId]);

// Delayed execution (API 61+): run in 5 minutes
// System.enqueueJob(new InvoiceSyncQueueable(list), 5);

Transaction Finalizers — reliable post-processing

public class SyncFinalizer implements Finalizer {
    private Id recordId;
    public SyncFinalizer(Id recordId) { this.recordId = recordId; }

    public void execute(FinalizerContext ctx) {
        // Runs even if the Queueable threw an UNHANDLED exception
        if (ctx.getResult() == ParentJobResult.SUCCESS) {
            update new Invoice__c(Id = recordId, Sync_Status__c = 'Complete');
        } else {
            insert new Error_Log__c(
                Message__c = ctx.getException()?.getMessage(),
                Job_Id__c  = String.valueOf(ctx.getAsyncApexJobId())
            );
            // You may enqueue ONE retry job from a finalizer
        }
    }
}

// Attach it inside execute()
public void execute(QueueableContext ctx) {
    System.attachFinalizer(new SyncFinalizer(this.recordId));
    doRiskyWork();
}
🛟
Why finalizers matter Before them, an unhandled exception in a Queueable left you with no way to record the failure — the transaction rolled back including your error log. A Finalizer runs in its own transaction afterwards, so the log survives.

Chaining limits

  • From a Queueable you may enqueue one child job (5 in Developer/Trial orgs).
  • Chain depth is unlimited in production, but each link is a separate transaction with fresh limits.
  • You cannot chain in a test — guard with if (!Test.isRunningTest()).
  • Maximum 50 jobs added to the queue from a single synchronous transaction.

3 · Batch Apex

For volumes that could never fit in one transaction. Salesforce splits your records into chunks (default 200) and runs execute() once per chunk, each with its own governor limits.

Batch Apex lifecycle
public class OpportunityCleanupBatch
       implements Database.Batchable<sObject>, Database.Stateful, Database.AllowsCallouts {

    // Database.Stateful → these survive across chunks
    private Integer recordsProcessed = 0;
    private Integer recordsFailed    = 0;
    private List<String> errorMessages = new List<String>();

    private Date cutoff;
    public OpportunityCleanupBatch(Date cutoff) { this.cutoff = cutoff; }

    /* ---------- 1. START: define the scope ---------- */
    public Database.QueryLocator start(Database.BatchableContext bc) {
        return Database.getQueryLocator([
            SELECT Id, Name, StageName, CloseDate, OwnerId
            FROM Opportunity
            WHERE IsClosed = false AND CloseDate < :cutoff
        ]);
    }

    /* ---------- 2. EXECUTE: process each chunk ---------- */
    public void execute(Database.BatchableContext bc, List<Opportunity> scope) {
        List<Opportunity> toUpdate = new List<Opportunity>();
        for (Opportunity o : scope) {
            o.StageName        = 'Closed Lost';
            o.Loss_Reason__c   = 'Expired — auto-closed';
            toUpdate.add(o);
        }

        Database.SaveResult[] results = Database.update(toUpdate, false);
        for (Integer i = 0; i < results.size(); i++) {
            if (results[i].isSuccess()) {
                recordsProcessed++;
            } else {
                recordsFailed++;
                if (errorMessages.size() < 100) {          // guard the heap
                    errorMessages.add(toUpdate[i].Name + ': ' + results[i].getErrors()[0].getMessage());
                }
            }
        }
    }

    /* ---------- 3. FINISH: wrap up ---------- */
    public void finish(Database.BatchableContext bc) {
        AsyncApexJob job = [
            SELECT Id, Status, NumberOfErrors, JobItemsProcessed, TotalJobItems, CreatedBy.Email
            FROM AsyncApexJob WHERE Id = :bc.getJobId()
        ];

        Messaging.SingleEmailMessage mail = new Messaging.SingleEmailMessage();
        mail.setToAddresses(new String[]{ job.CreatedBy.Email });
        mail.setSubject('Opportunity Cleanup — ' + job.Status);
        mail.setPlainTextBody(
            'Chunks: '    + job.JobItemsProcessed + '/' + job.TotalJobItems +
            '\nUpdated: ' + recordsProcessed +
            '\nFailed: '  + recordsFailed +
            '\n\n' + String.join(errorMessages, '\n'));
        Messaging.sendEmail(new Messaging.SingleEmailMessage[]{ mail });

        // Chain the next batch
        Database.executeBatch(new OpportunityArchiveBatch(), 200);
    }
}

/* ---------- Running it ---------- */
Id batchId = Database.executeBatch(new OpportunityCleanupBatch(Date.today()), 200);
// Smaller scope size when each record does heavy work or a callout:
// Database.executeBatch(new MyBatch(), 20);

QueryLocator vs Iterable

Database.QueryLocatorIterable<sObject>
Max records50 million50,000 (normal query limit)
SourceA SOQL queryAny custom logic — a callout result, a CSV, a computed list
Governor costDoesn't count toward query rowsCounts normally
Use when99% of casesData isn't a SOQL query

Batch rules & limits

  • 5 concurrent batch jobs; up to 100 held in the flex queue.
  • Scope size: 1–2,000 (default 200). Smaller scope = more chunks = more total limits available, but more overhead.
  • Each chunk gets fresh limits, but callouts are capped at 100 per chunk.
  • Only one Database.executeBatch can be called from finish() (chaining).
  • A batch class can't be called from another batch's execute() — only from finish().
  • Database.Stateful preserves instance variables only; statics always reset.
  • Test methods can process only one chunk — use ≤ 200 test records.

4 · Scheduled Apex

public class NightlyCleanupScheduler implements Schedulable {
    public void execute(SchedulableContext sc) {
        // Schedulers usually just launch a batch
        Database.executeBatch(new OpportunityCleanupBatch(Date.today()), 200);
    }
}

/* ---------- Scheduling from anonymous Apex ---------- */
// Cron:  Seconds Minutes Hours Day_of_month Month Day_of_week Optional_year
String cron = '0 0 2 * * ?';                       // every day at 02:00
Id jobId = System.schedule('Nightly Cleanup', cron, new NightlyCleanupScheduler());

/* ---------- Cron cookbook ---------- */
// '0 0 2 * * ?'        every day 02:00
// '0 30 6 ? * MON-FRI' weekdays 06:30
// '0 0 * * * ?'        every hour on the hour
// '0 0 0 1 * ?'        first day of every month at midnight
// '0 0 12 ? * SUN'     every Sunday at noon
// '0 0 8 ? * MON#1'    first Monday of the month at 08:00
// '0 0 22 L * ?'       last day of the month at 22:00

/* ---------- Managing jobs ---------- */
for (CronTrigger ct : [SELECT Id, CronJobDetail.Name, CronExpression, State,
                              NextFireTime, PreviousFireTime, TimesTriggered
                       FROM CronTrigger]) {
    System.debug(ct.CronJobDetail.Name + ' next: ' + ct.NextFireTime);
}
System.abortJob(jobId);
⏰
Scheduled Apex gotchas ① Max 100 scheduled jobs per org. ② You cannot modify a class that is currently scheduled — abort the job, deploy, reschedule (a real CI/CD pain point). ③ The minimum interval via the UI is hourly; use multiple cron expressions for every-15-minutes. ④ Scheduled jobs run in system context as the scheduling user. ⑤ Callouts are not allowed directly in execute() — delegate to a Queueable/Batch.

Every-15-minutes pattern

// Schedule the same class four times with different offsets
System.schedule('Sync 00', '0 0  * * * ?', new SyncScheduler());
System.schedule('Sync 15', '0 15 * * * ?', new SyncScheduler());
System.schedule('Sync 30', '0 30 * * * ?', new SyncScheduler());
System.schedule('Sync 45', '0 45 * * * ?', new SyncScheduler());

Testing async Apex

@isTest
private class OpportunityCleanupBatchTest {

    @testSetup
    static void setup() {
        Account a = new Account(Name = 'Test Co');
        insert a;
        List<Opportunity> opps = new List<Opportunity>();
        for (Integer i = 0; i < 200; i++) {       // one chunk max in tests
            opps.add(new Opportunity(
                Name = 'Old Deal ' + i, AccountId = a.Id,
                StageName = 'Prospecting', CloseDate = Date.today().addDays(-30)));
        }
        insert opps;
    }

    @isTest
    static void batchClosesExpiredOpportunities() {
        Test.startTest();
        Database.executeBatch(new OpportunityCleanupBatch(Date.today()), 200);
        Test.stopTest();                 // ← forces the async job to run synchronously

        Assert.areEqual(200,
            [SELECT COUNT() FROM Opportunity WHERE StageName = 'Closed Lost'],
            'All expired opportunities should be closed');
    }

    @isTest
    static void queueableRunsAndUpdatesStatus() {
        Test.startTest();
        System.enqueueJob(new InvoiceSyncQueueable(invoices));
        Test.stopTest();
        // assert results
    }

    @isTest
    static void schedulerEnqueuesBatch() {
        Test.startTest();
        String jobId = System.schedule('Test Cleanup', '0 0 0 15 3 ? 2099',
                                       new NightlyCleanupScheduler());
        Test.stopTest();
        CronTrigger ct = [SELECT CronExpression, TimesTriggered FROM CronTrigger WHERE Id = :jobId];
        Assert.areEqual('0 0 0 15 3 ? 2099', ct.CronExpression);
        Assert.areEqual(0, ct.TimesTriggered, 'Should not have fired yet');
    }
}
🔑
The one rule of async testing Async work queued between Test.startTest() and Test.stopTest() executes synchronously at stopTest(). Assert after that line. Chained jobs do not run — that's why chaining is guarded with Test.isRunningTest().

Interview questions

1 Why does async Apex exist when you could just write synchronous code?Easy

Three reasons. User experience — long work doesn't block the save. Higher limits — SOQL 100→200, heap 6→12 MB, CPU 10 s→60 s. Callouts after DML — async runs after commit, which is the only clean way to integrate from a trigger. Batch adds a fourth: fresh limits per chunk, letting you process up to 50 million records.

2 Why is Queueable preferred over @future?Easy

@future takes primitives only (no sObjects), returns no job Id so monitoring is awkward, can't be chained, and can't be called from another future or from Batch.

Queueable is a class, so it holds any type as a member including sObjects and wrapper objects; System.enqueueJob() returns a job Id you can query in AsyncApexJob; it supports chaining and Finalizers for reliable error handling. The only reason to still write @future is legacy consistency.

3 Explain the Batch Apex lifecycle and where state lives.Medium

start() returns a Database.QueryLocator (up to 50 M records) or an Iterable; execute() runs once per chunk (default 200, range 1–2,000), each chunk in its own transaction with fresh governor limits; finish() runs once at the end for summary emails or chaining the next job.

Instance variables reset between chunks unless the class implements Database.Stateful. Statics always reset. A failed chunk rolls back only itself — the rest continue, which is why you inspect NumberOfErrors rather than assuming "Completed" means success.

4 QueryLocator vs Iterable in start() — when would you use Iterable?Hard

QueryLocator handles up to 50 million records and its rows don't count against the 50,000 query-row limit — use it in 99% of cases. Iterable is for when the data isn't a SOQL query: rows parsed from a CSV in a static resource, results assembled from a callout, or a computed list. The catch is that an Iterable is subject to the normal 50,000-row limit, so it can't scale the same way.

5 What are the chaining rules, and how do you build a retry?Hard

From a Queueable you may enqueue one child job (5 in Developer/Trial orgs); depth is unlimited in production and each link is a fresh transaction. From Batch you may call Database.executeBatch once, and only from finish(). A synchronous transaction may enqueue up to 50 jobs.

A retry passes an attempt counter into the constructor, re-enqueues on a retryable status (408, 429, 5xx) while attempt < MAX, and logs a permanent failure otherwise. Guard the chain with !Test.isRunningTest() because chained jobs don't execute in tests.

6 What problem do Transaction Finalizers solve?Hard

If a Queueable throws an unhandled exception, its transaction rolls back — including the Error_Log__c record you inserted to record the failure. You were left blind.

A class implementing Finalizer, attached with System.attachFinalizer(), runs in its own transaction after the job completes, whatever the outcome. FinalizerContext gives you the parent job result and exception, and you may enqueue one retry job from it. This is the standard pattern for reliable async error handling.

7 You can't deploy because a class is scheduled. What now?Medium

Salesforce won't let you modify a class that a scheduled job holds. The sequence is: query CronTrigger to find the job, System.abortJob(jobId), deploy, then reschedule — and this must be scripted, because it bites every CI/CD pipeline. Some teams avoid it entirely by keeping the Schedulable class as a one-line shim that delegates to a Batch class, so the scheduled class itself almost never changes.

8 How do you test async code, and what won't run?Medium

Queue the work between Test.startTest() and Test.stopTest() — it executes synchronously at stopTest(), so all assertions go after that line.

What won't run: chained jobs (hence the Test.isRunningTest() guard), and batch tests process only one chunk, so keep test data at 200 records or fewer. For a scheduled job, use System.schedule with a far-future cron and assert on the CronTrigger record rather than trying to make it fire.

Quick check

1. You must pass a List<Account> to an async job. Which do you choose?
Future methods only accept primitives. Queueable takes any type as a class member, which is one of the main reasons it replaced @future.
2. You need to update 4 million records nightly. Design?
Batch handles up to 50 M via QueryLocator with fresh limits per chunk; Schedulable provides the nightly trigger.
3. Your Queueable throws an unhandled exception and you lose the error log you inserted. Fix?
An unhandled exception rolls back the job's transaction, taking your log with it. Finalizers run afterwards in a separate transaction, so the log commits.
