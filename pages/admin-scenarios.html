Admin — 100 Scenarios

Schema design, formulas and roll-ups, record types, validation, duplicates, queues, approvals and capture channels — as decisions you have to defend, not features to list.

📚
How to use this Answer out loud in under ninety seconds, then open the answer. The concepts are on Admin Essentials and its Advanced section.

Objects, fields & relationships (1–10)

1 The business needs a child record that can be moved to a different parent later.Easy

Master-detail relationships can allow reparenting, but it is off by default and master-detail brings cascade delete plus inherited sharing you may not want. If reparenting is routine, a lookup is usually the honest choice.

The cost of choosing lookup: no roll-up summary fields, so aggregation needs a flow, a trigger or a declarative roll-up tool. Make that trade explicitly rather than discovering it after the data model is live.

2 You need a many-to-many relationship between Projects and Employees.Easy

A junction object with two master-detail relationships. The first master-detail you create is the primary — it controls the record's ownership, sharing and the default layout, and it is what appears in the record name on list views.

Put extra context on the junction itself (role, allocation percentage, start and end dates) — that is usually why the relationship exists rather than a simple link.

3 A master-detail child needs its own sharing, independent of the parent.Medium

Not possible. Master-detail children have no share object; access is inherited from the master, full stop.

If independent sharing is a real requirement, it must be a lookup relationship with its own OWD and sharing rules — and you then lose roll-up summaries and cascade delete, which you may need to rebuild. Decide before building, because converting the relationship type later is a data migration.

4 Someone wants a picklist with 400 values.Medium

That is a lookup to a custom object, not a picklist. 400 values is unusable in a UI, impossible to maintain, and it will be wrong within a month.

A lookup gives you searchability, an owner, active/inactive flags, effective dates and reportability. Reserve picklists for small, stable, genuinely enumerated sets — and use a global value set when the same list appears on several objects.

5 A field needs to hold a value that must be unique across the org.Easy

Mark it Unique — and consider External Id as well if an outside system owns the value, because that gives you upsert-by-key plus a free index.

Decide case sensitivity deliberately: a case-insensitive unique text field treats "ABC123" and "abc123" as the same value, which is usually what you want for human-entered references and occasionally not.

6 You need to change a Text field to a Picklist on 2 million records.Hard

Possible but risky: values that do not match a picklist entry behave unpredictably, and anything filtering or integrating on the field may break. At that volume the conversion is also slow.

Safer pattern: create the new picklist field alongside, migrate values in controlled batches with a mapping you can verify, repoint reports, automation and integrations, then retire the old field after a bake period. Never convert in place on a large object without a rehearsal in a Full sandbox.

7 A field was deleted by mistake. What are your options?Medium

Deleted fields sit in a recycle-bin-like state for a limited period and can be undeleted with their data — act fast rather than rebuilding.

If it has been erased, the field comes back empty and you restore values from a backup or an export. This is exactly why destructive changes get explicit review in a release and why "deploy the previous tag" does not undo a deletion. See releases.

8 A new required field breaks an existing integration.Medium

Making a field required at the field level enforces it on every write path — API included — so an integration that does not send it now fails.

If the requirement is really about the UI, make it required on the page layout or via a validation rule scoped to exclude the integration user instead. Then fix the integration properly rather than leaving a permanent exception.

9 The business wants to track history on 30 fields of one object.Medium

Standard Field History Tracking is capped at around 20 fields per object with limited retention — so 30 does not fit, and the retention probably does not meet whatever the real requirement is.

Ask what the history is for. Audit and regulatory needs point to Field Audit Trail (Shield) with long retention. Operational "what changed recently" is often better served by a purpose-built custom object written by automation, which you then control and report on.

10 You are asked to add 40 fields nobody can explain the use of.Medium

Each field is permanent cognitive load, migration cost, layout clutter and a future "what is this?" ticket. Ask for the decision each field supports, and who will look at it.

Offer the alternatives: a report instead of a stored value, a formula instead of a duplicate, or one structured field instead of five flags. Then run a field-usage review periodically and delete the ones at 0% population — deliberately, with a note of what was removed.

Formulas & roll-ups (11–20)

11 A formula field won't save — "compiled size too large".Medium

Formulas compile to a byte size far beyond the characters you typed, and nested IFs plus repeated cross-object references explode it.

Fixes in order: replace nested IF chains with CASE; factor repeated sub-expressions into a helper formula field and reference that; shorten long cross-object paths by storing the value closer. If it still will not fit, the logic belongs in automation writing to a plain field.

12 A report filtered on a cross-object formula field times out at volume.Hard

A formula spanning objects generally cannot be indexed, so filtering on it forces a scan — and it is re-evaluated on every row returned.

Fix by materialising the value: have automation write it to a plain, indexable field on the record (and backfill), then filter on that. Single-object deterministic formulas can be indexed, so sometimes flattening the formula is enough. See selectivity.

13 Arithmetic in a formula returns blank instead of a number.Easy

A null in any operand makes the whole expression null unless you handle it. The field's "treat blank fields as zeroes" versus "as blanks" setting silently changes every result.

Be explicit: wrap operands in BLANKVALUE() or NULLVALUE() so the intent is visible in the formula rather than hidden in a radio button somebody will change later.

14 You need a roll-up but the relationship is a lookup.Medium

Roll-up summary fields require master-detail. Options: a record-triggered flow (easy, low volume, you own bulkification and recursion), an Apex trigger (complex criteria, high volume, fully controllable), or a declarative roll-up tool (admin-maintained, but it consumes the same governor limits your own code would).

First though — ask whether the number needs to be stored at all. If someone just needs to look at it, a report costs nothing to write and nothing to maintain.

15 A roll-up summary on a parent with 50,000 children causes lock errors.Hard

That is account data skew: child DML locks the master-detail parent while the roll-up recalculates, so concurrent operations on children of the same parent contend.

Mitigations: split the mega-parent if the business allows, sort DML by parent Id so transactions lock in a consistent order, reduce batch sizes, and move from parallel to serial loading. See skew.

16 A roll-up and a trigger both maintain the same field. Values flicker.Medium

They are fighting, and the roll-up generally wins because it recalculates on the platform's schedule within the save.

Pick one mechanism per field: if the aggregation is expressible as a roll-up summary, use it and delete the trigger logic; if it is not, use the trigger and do not create a roll-up on that field. Never both.

17 You need a roll-up that only counts children meeting a condition.Easy

Roll-up summary fields support filter criteria, so simple conditions are declarative and free.

The limits appear with conditions that reference the parent, cross-object values, or anything dynamic — those need automation. A common workaround is a formula checkbox on the child that encodes the condition, then roll up on that.

18 A formula needs the number of working days between two dates.Medium

Date arithmetic cannot know your holidays. A formula can approximate weekdays, but it will be wrong on public holidays and the business will notice at the worst moment.

Use Business Hours with holidays attached, driven from automation (Apex BusinessHours methods or an invocable action). Missing holidays is the standard cause of "the SLA says we breached but we were closed".

19 A currency formula is a penny out on some records.Hard

Rounding and scale. Intermediate results carry more precision than the displayed value, so rounding at the end differs from rounding at each step — and the field's decimal places only affect display.

Decide the rounding convention with finance and encode it explicitly (ROUND() at the defined stage). In Apex, never use Double for money; use Decimal with setScale(2, RoundingMode.HALF_UP).

20 Should a KPI live in a formula field, a roll-up, or a report?Medium

Formula if it is derived per record and must always be current. Roll-up or automation if it aggregates children and must be filterable, sortable or usable in automation. Report if someone only needs to look at it.

The question that settles it: "will anything other than a human eye consume this value?" If not, do not store it — stored values need maintaining, backfilling and testing forever.

Record types, layouts & Dynamic Forms (21–30)

21 A user says a picklist value exists but they cannot select it.Easy

Picklist values are assigned per record type. Check the record type's available values before you check the field — that is the answer the overwhelming majority of the time.

If it is a dependent picklist, there is a second dimension: the controlling field's value must also be available for that record type, and the dependency matrix must include the combination.

22 You have 10 record types and 15 profiles. Maintenance is unmanageable.Hard

That is a 150-cell matrix of layout assignments plus picklist value assignments per record type — and it grows multiplicatively.

Migrate to Dynamic Forms: one layout with conditional field visibility replaces most layout-driven record types. Keep record types only where they genuinely drive different processes (sales process, support process, different picklist domains), not different field arrangements.

23 Someone proposes a record type to hide sensitive fields from a team.Easy

Record types are not security. They shape the UI; the data remains accessible via API, reports and SOQL.

Field-level security is the control, applied through profiles and permission sets. Demonstrating the hole takes one REST call, which is a useful thing to do once with the stakeholder watching.

24 A field is on the layout but users cannot see it.Easy

Field-level security on their profile or permission sets overrides the layout — FLS wins.

Walk it in order: FLS, then the layout assigned to their profile/record type combination, then component visibility or Dynamic Forms conditions, then whether the field is on a section they have collapsed. Login as the user rather than reasoning about it.

25 Dynamic Forms has 25 conditional sections and the page is slow.Medium

Conditional visibility is still rendering work, and 25 sections is both slow and impossible to reason about.

Simplify the information architecture rather than tuning: what does this user need on load, and what belongs on a second tab, a related list, or a guided flow? Measure with EPT and component instrumentation first so you fix the real cost. See page performance.

26 The business wants a different page layout per country for 20 countries.Medium

Twenty layouts is twenty things to maintain in step. Use one layout with Dynamic Forms conditions on a country field, and drive labels through translation rather than separate layouts.

Push back on whether the differences are real: usually three or four genuine variants hide behind twenty requests, and the rest is local preference that does not justify permanent maintenance cost.

27 A quick action appears for everyone but should only appear for approvers.Easy

Dynamic Actions — set visibility criteria on the action, based on a custom permission the approvers hold (not a profile name, which breaks when profiles change).

And enforce it server side too: the action's underlying flow or Apex must check the permission itself, because hiding a button is presentation, not authorisation.

28 Users complain the record page has 40 fields and they use six.Medium

Design from the task, not the schema. The six fields go in a prominent top section or the highlights panel; the rest move to collapsed sections, tabs or a details subtab.

Also set the compact layout deliberately — its first four fields are the highlights panel and the mobile card, and most orgs never choose them on purpose.

29 You need a related list showing only the three primary contacts, sorted.Easy

Dynamic Related Lists — filter by criteria, choose the columns, set the sort and the row limit. No code, and it replaces the "all 400 contacts" default that nobody can use.

If the filter needs data not on the child record, a formula checkbox on the child encoding the condition gives the related list something to filter on.

30 Changing a record type's business process breaks existing records.Hard

Records hold a stage or status value that may no longer exist in the new process, so they end up in an invalid state that automation and reports treat inconsistently.

Plan it as a data migration: map old values to new, update records in controlled batches, verify there are no orphans, and only then retire the old values. Also check validation rules, automation and reports that reference the removed values.

Validation & data quality (31–40)

31 A new validation rule breaks the nightly integration load.Medium

Validation rules fire on every write path, including the API — so a rule written for the UI now rejects integration records that were previously fine.

Options: scope the rule to exclude the integration user or profile ($User.Id / a custom permission bypass), fix the integration to supply the data, or move the check to a report and remediation process. Choose deliberately — a permanent bypass is a decision, not an accident.

32 A validation rule is written as "error if valid" and blocks everything.Easy

The logic is inverted: a validation rule blocks the save when its formula evaluates to TRUE — "error if true".

Write the condition as the bad state, test it with a record that should pass and one that should fail, and put the intent in the error message so the next admin reads the purpose rather than reverse-engineering the formula.

33 A validation rule must only apply to records created from now on.Medium

Scope it by date or by a flag: AND(ISNEW(), condition) for creation only, or compare CreatedDate against a cutover date so historical records are exempt.

Without that, the rule blocks edits to legacy records that were valid when created — which surfaces as "I can't save a record I didn't change" and erodes trust in your rules generally.

34 Users complain an error message is unhelpful.Easy

Fix the message, it is the cheapest usability win available. Say what is wrong, what to change and why — "Close Date cannot be in the past for an open Opportunity" rather than "Invalid data".

Also attach the error to the field rather than the record where possible, so the message appears next to the input the user must fix.

35 A validation rule needs to check a value on the parent record.Medium

Cross-object formulas can walk up the relationship, so this is usually declarative. The catch is that the parent value is read at save time — so a later change to the parent does not retroactively invalidate the child.

If the rule must hold continuously, you need automation on the parent too, or a periodic data-quality report. State which guarantee the business actually needs.

36 A validation rule must not fire during a data migration.Medium

Add a bypass condition keyed on a custom permission held by the migration user, or a hierarchy custom setting switchable per user — not a hard-coded username, which breaks and cannot be audited.

Then run a reconciliation report after the load to find records that would have failed, and remediate them. Bypassing without reconciling imports the bad data permanently.

37 Required on the layout versus required on the field — which do you choose?Easy

Layout-required enforces in the UI only. Field-required (universally required) enforces on every write path including the API, and it also prevents the field being blank in existing data operations.

Use field-level for genuine data integrity that must never be violated anywhere; layout or validation for process requirements that integrations legitimately bypass. Getting this backwards is the usual cause of a broken integration.

38 60% of Accounts have no industry populated. How do you fix data quality?Medium

Measure, then prevent, then remediate, then keep measuring. A dashboard of completeness by field and by owner makes it visible; validation or required fields prevent new gaps; a backfill (enrichment data or an owner campaign) fixes history.

Making a field required without a backfill plan means users cannot save legacy records — which is how data-quality initiatives get abandoned in week two.

39 You need to prevent closing an Opportunity without a signed contract file.Medium

A validation rule cannot see related files directly. Pattern: automation sets a checkbox or counter field when a qualifying file or record exists, and the validation rule checks that field.

Make sure the automation handles deletion too — otherwise the flag stays true after the file is removed, and the control is theatre.

40 Validation rules, before-save flows and triggers all validate the same thing.Medium

Pick one home per rule and document it. Duplicated validation means three places to change, three error messages, and inconsistent behaviour between UI and API paths.

Rough division: validation rules for declarative, formula-expressible record checks; before-save flows or triggers where the check needs related data, bulk context or a friendlier message; Apex where it must be unit-tested as part of a service.

Duplicate & matching rules (41–50)

41 A duplicate rule blocks a 2am migration and the job fails.Medium

Duplicate rules apply to API writes unless configured otherwise, and a blocking rule will reject rows mid-load.

For a planned migration: deactivate the rule for the load window, or set it to Allow-with-alert, or bypass it in Apex with Database.DMLOptions.DuplicateRuleHeader.allowSave. Then run a duplicate report afterwards and merge deliberately — do not leave the rule off.

42 Duplicates still get created despite a duplicate rule.Medium

Check the matching rule's fuzziness and which fields it compares — exact-match on Email misses "j.smith@x.com" versus "jsmith@x.com". Then check whether the duplicate rule is active, whether it covers the entry path (UI, API, import), and whether it is set to alert rather than block.

Also remember matching rules need to be activated and can take time to index after creation.

43 A merge loses data the business needed.Hard

Merging keeps the master's field values unless you choose otherwise, reparents most child records, and deletes the losers — and related records with restrictive relationships or custom automation may not survive the way you expect.

Before any bulk merge: export both sides, test the merge on a sample in a sandbox with real automation active, and check what happens to tasks, files, campaign members and custom children. Merge is effectively irreversible.

44 How do you dedupe 200,000 existing Accounts?Hard

Not with duplicate rules — those prevent new duplicates, they do not clean history. You need a dedicated process: extract, match externally or with a dedupe tool, review the proposed merges (a human sampling step is non-negotiable), then merge in batches with a verified rollback position.

Decide the survivorship rules up front — which record wins, which field values survive, what happens to children — and record them. "The newest wins" is a decision; "whatever the tool did" is not.

45 Matching rules work for Leads but not for Person Accounts.Medium

Person Accounts behave as a hybrid of Account and Contact, and duplicate/matching support differs — cross-object Lead-to-Contact matching also has its own rules.

Verify what your edition and configuration actually support rather than assuming symmetry, and test each entry path (UI, API, web-to-lead, import) separately. Person Accounts are also an irreversible enablement, so this is worth knowing before you turn them on.

46 Sales wants to see potential duplicates without being blocked.Easy

Set the duplicate rule to Allow with alert, and add the Potential Duplicates component to the record page so matches are visible in context.

That is usually the right posture for a sales team: blocking creates workarounds (slightly misspelled names), while a visible alert plus a merge path gets the behaviour you wanted.

47 An integration creates duplicates every night.Medium

The integration is inserting rather than upserting on a stable key. Fix the integration, not the duplicates: add an External Id holding the source system's identifier and upsert against it.

The unique index on that field is the real guarantee — a repeated delivery then fails on the duplicate rather than creating a second record. See idempotency.

48 Two users create the same Account within seconds of each other.Hard

Duplicate rules compare against committed data, so a genuine race can slip through — and no amount of rule tuning closes that window.

If uniqueness genuinely matters, enforce it with a Unique field (a normalised key — lowercased name plus postcode, maintained by automation). A database constraint is the only thing that holds under concurrency.

49 Marketing and Sales disagree on what counts as a duplicate.Medium

That is the actual problem — matching rules just encode somebody's answer. A father and son at the same address, or two branches of one company, are duplicates to one team and distinct to the other.

Get the definition agreed in writing, test the rule against a labelled sample where you know the right answer, and revisit it periodically. The same conversation applies to Data Cloud identity resolution at much larger scale. See identity resolution.

50 How do you prevent duplicates from Web-to-Lead?Medium

Duplicate rules cover the Web-to-Lead path, so start there with alerting plus assignment to a review queue rather than blocking — a blocked web submission is a lost enquiry.

Better still, match on email and update the existing Lead or Contact (automation on creation), so repeat enquiries enrich the record rather than fragmenting it. Losing the enquiry is worse than holding a duplicate for an hour.

Custom Settings, Metadata & Labels (51–60)

51 You need a threshold an admin can change in production without a deployment.Easy

A Hierarchy Custom Setting — editable in production, with org, profile and user-level overrides at runtime.

If the value should instead ship with the release and be version-controlled, that is a Custom Metadata Type. The distinction is exactly "who owns changing this, and does it need a release?"

52 You need a kill switch to disable a trigger during an incident.Medium

Hierarchy Custom Setting, checked at the top of every handler, switchable per user — so you can disable automation for the migration user without affecting anyone else, and without a deployment at 2am.

"We commented out the trigger in production" is not a plan. Build the switch before you need it. See bypass design.

53 Custom Metadata rows are missing in production after deployment.Medium

The type deploys as metadata; whether the records come along depends on how they were packaged and deployed, and they are frequently forgotten.

Make the dependency explicit: include the rows in your deployment artefact, and write a test that fails when a required row is absent. A silent missing configuration row is far worse than a failed deployment.

54 Why prefer Custom Metadata over a Custom Setting for business rules?Medium

Custom Metadata is queryable without consuming SOQL limits, supports relationships and picklists, is deployable with the release, and can be packaged. That makes it the right home for mapping tables and rule configuration a consultant maintains.

Custom Settings win only where runtime per-user/per-profile values or production-editable switches are the point.

55 A test fails because it cannot insert Custom Metadata.Hard

You cannot insert Custom Metadata in a test — it is visible without SeeAllData but not insertable.

Design for it: have the class accept injected configuration (a constructor parameter or a settable static) so tests supply their own values, with the Custom Metadata lookup as the default. That makes the logic unit-testable rather than dependent on deployed rows. See test data.

56 UI text needs translating into five languages.Easy

Custom Labels for text in code, components, flows and validation messages; Translation Workbench for metadata labels, picklist values and help text.

Hard-coded strings are the thing that makes a localisation project expensive later, so use labels from the start even in a single-language org — it costs nothing extra at build time.

57 Custom labels cause merge conflicts on every pull request.Medium

All labels live in one file, so everyone edits it. Treat it as append-only with alphabetical ordering, and configure a union merge driver in .gitattributes so both sides' additions are kept.

Same approach for translation files. See the metadata that won't merge.

58 Where should an API endpoint URL live?Easy

In a Named Credential, not a custom setting — it holds the endpoint and the authentication, handles token refresh, keeps secrets out of code and metadata, and lets you rotate credentials as a config change.

Your Apex then calls callout:My_Service/path with no URL and no token in sight. See Named Credentials.

59 An admin edited a Custom Metadata row in production. Is that a problem?Medium

It is config drift — the deployed value and the production value now differ, and your next deployment may overwrite theirs.

Either bring it into the drift-detection loop and treat production edits as changes to capture, or move genuinely admin-owned values into Custom Settings where production editing is the intended behaviour. Ambiguity about who owns a value is what causes the incident. See drift.

60 You need environment-specific values (sandbox versus production).Medium

Named Credentials for endpoints, plus Custom Metadata or Custom Settings for the rest — seeded per environment by your post-deployment script rather than branched in code.

Never branch on org Id or sandbox name in Apex. That couples your logic to a specific environment, breaks on refresh, and makes the code untestable.

Queues, groups & ownership (61–70)

61 Queue, public group or role — which do you use for what?Easy

Queue when records need to be owned by a pool and worked from a list (cases, leads). Public group for sharing and permission grouping — groups cannot own records. Role for hierarchy-based access roll-up and reporting.

A frequent mistake is using a role hierarchy to express a work pool; the queue is what gives you ownership, a list view and assignment.

62 A queue owns 800,000 Cases and ownership changes cause lock errors.Hard

Ownership skew. When one owner holds a very large share of an object (commonly cited threshold around 10,000+), every ownership or role change involving them triggers massive sharing recalculation and record locking.

Mitigations: route to several queues rather than one, keep the skewed owner out of the role hierarchy (or at the top with no peers), and archive closed cases so the pool stays bounded. See sharing mechanics.

63 A user left and owns 40,000 records. You need to deactivate them.Medium

Reassign ownership first — you cannot deactivate cleanly while they are the owner of active records and the sharing recalculation on reassignment is substantial.

Do it in a controlled window, in batches, and also check what else they own: scheduled jobs, dashboard running user, integration credentials, queue memberships, Named Credential principal. Freeze them immediately for access, then reassign, then deactivate. See offboarding.

64 Cases assigned to a queue are not visible to the team.Medium

Queue membership grants access to records owned by the queue — so check the queue's members (users, roles, public groups) and whether the people complaining are actually in it.

Then check the queue's supported objects, the list view's filter and sharing, and whether the records were actually assigned to the queue or to a user. Login as the user rather than reasoning from configuration.

65 Records need to be owned by a team, not an individual.Medium

Use a queue for genuine shared ownership and working-from-a-list. If individuals must still own records but the team needs access, use Account/Opportunity/Case teams or sharing rules to a public group.

Avoid a single "shared" user account as the owner — it creates ownership skew, destroys accountability and breaks the audit trail.

66 You need a round-robin assignment across six agents.Medium

Assignment rules do not round-robin natively. The usual patterns: Omni-Channel routing with capacity-based models (the right answer for service at any scale), or a counter held in a custom setting or custom object incremented by automation.

If you hand-roll it, handle concurrency — two simultaneous records reading the same counter will both pick the same agent unless you lock or use a single-threaded path.

67 Ownership changes trigger hours of sharing recalculation.Hard

Expected at volume: changing an owner, a role hierarchy or a sharing rule recalculates share rows asynchronously, and it can take hours on a large org while locking groups.

Plan bulk ownership or hierarchy changes in controlled windows, never at 08:00 Monday. For a large reorganisation, ask Salesforce to enable deferred sharing maintenance so you suspend recalculation and resume once.

68 A public group's membership is locked and you cannot edit it.Medium

Group membership tables are locked while sharing recalculation runs — so a large change elsewhere is blocking you.

Wait for recalculation to finish (check the setup monitoring pages), and in future batch group and role changes rather than making them piecemeal during business hours.

69 How do you give one user access to one record, permanently?Easy

Manual share is the easy answer, but it is removed when ownership changes — which makes "permanently" false.

For durable programmatic grants use Apex managed sharing with a custom RowCause, which survives owner changes and is identifiable and reportable later. And remember you cannot share above the OWD. See Apex managed sharing.

70 A "Default" lookup record is referenced by 300,000 children and inserts are slow.Hard

Lookup skew. Concurrent inserts contend over the same parent row, producing DML lock errors that look like a code problem.

Fix the data shape: spread the values across multiple parents, or replace the lookup with a picklist or text field if the relationship was only ever there for reporting convenience.

Assignment, escalation & approvals (71–80)

71 A record is stuck in "Pending" approval forever.Medium

Usually a missing or unconfigured recall path, an approver who is inactive, or a delegated approver chain that leads nowhere.

Check the approval history on the record, then the process's approver assignment (dynamic approver fields pointing at a blank or deactivated user are the classic cause). Configure recall actions explicitly — they are the most commonly skipped part of an approval process.

72 Automation fails because a submitted record is locked.Medium

Approval submission locks the record by default, so automation attempting to update it fails.

Options: configure the process to leave records unlocked for the relevant step, grant the Modify All on locked records permission to the automation's running user, or sequence your automation to run before submission or after approval. Pick one and document why.

73 Approvers hard-coded by name have all left the company.Easy

Use a dynamic approver — route via the submitter's manager field or a custom user-lookup on the record — rather than naming individuals.

Where a named group is genuinely required, use a queue or a public group so membership is maintained in one place. Named individuals in process definitions are guaranteed future breakage.

74 The business needs a five-stage conditional sign-off with reminders and reassignment.Hard

That has outgrown approval processes, which are for linear, record-locking approvals. Flow Orchestrator is the fit: stages, steps, assignment to users or queues, each step its own interview, with conditional routing.

Say what you give up: record locking and the built-in approval history, both of which you then implement deliberately. See Orchestrator.

75 Submission silently fails and users do not know why.Medium

Entry criteria block submission without explanation. That is the designed behaviour and it is a poor user experience.

Add a validation rule expressing the same condition with a clear message, so the user learns what to fix. Keep the entry criteria as the guard, and the validation as the explanation.

76 Two approvers must both approve, and either can reject.Medium

A single step with parallel approvers set to require unanimous approval gives you exactly that — all must approve, any rejection stops it.

If you need "any one of three" instead, the same step configured for first-response. Spell out which behaviour the business means, because "both need to approve" and "two of these people" are different configurations.

77 Delegated approvers mean the manager never personally approved anything.Medium

Delegation covers absence but breaks the assumption that a specific person approved — which may matter to your auditors.

Decide the policy deliberately: allow delegation and record who actually approved (the approval history does), or disable it and accept approvals stalling during leave. The wrong answer is leaving it on by default and discovering the gap during an audit.

78 Case escalation rules fire at the wrong times.Medium

Almost always Business Hours: the wrong business hours applied, holidays missing, or a timezone mismatch between the business hours record and the case.

Then check the escalation rule's criteria order (first matching rule entry wins) and whether the clock is being stopped while waiting on the customer. See entitlements and the SLA clock.

79 Assignment rules put records with the wrong owner.Medium

Rule entries are evaluated in order and the first match wins — so a broad entry near the top swallows records intended for a specific entry below it.

Reorder from most specific to most general, and remember assignment runs after your before triggers, so logic keyed on OwnerId in a before trigger sees the pre-assignment value.

80 An approval must notify an external system when granted.Medium

Final approval actions can trigger a flow, which publishes a platform event or enqueues async work to make the callout — you cannot call out directly in the approval transaction.

Make the downstream handling idempotent and retryable, and log the correlation id, because an approval notification that silently fails is a business process that silently stops.

Lead & Case capture (81–90)

81 Web-to-Lead stops working after a form redesign.Easy

The generated form posts specific field ids plus your org id — a redesign that changed input names breaks the mapping silently, and Web-to-Lead fails quietly rather than erroring.

Regenerate the form, verify the hidden org id and return URL, and set up the lead creation notification so a drop in volume is visible. Also monitor volume as a metric — silent capture failure can run for weeks.

82 Web-to-Lead is being spammed with junk submissions.Medium

It is a public endpoint, so treat it like one: CAPTCHA on the form, honeypot fields, server-side validation before posting, and rate limiting at your web layer.

Inside Salesforce, route suspicious submissions to a review queue via assignment rules rather than into the sales pipeline, and keep the daily Web-to-Lead limit in mind — spam consumes it and legitimate leads get dropped.

83 Email-to-Case creates cases but loses attachments.Medium

Check the attachment size limits and whether you are using standard or On-Demand Email-to-Case, which differ. Large attachments can be dropped or truncated.

Also verify the email service's settings for how it handles unrecognised senders and bounced routing. Testing with a 20MB attachment before go-live is cheaper than discovering it from a customer.

84 Customer replies create new cases instead of threading.Medium

Thread identification is failing — either the thread token is missing from outbound templates, or you are relying on a mechanism the reply strips.

Ensure outbound emails include the threading token (or use the modern reference-header-based threading), and test with the real mail clients your customers use. Reply chains that fork into new cases wreck both metrics and customer experience.

85 You hit the daily Email-to-Case limit.Medium

Limits here scale with licences and are org-wide. First check what is consuming them — auto-replies looping, spam, or a mailbox forwarding everything including notifications.

Then reduce load at source: filter before forwarding, suppress auto-reply loops, and consider messaging channels for high-volume interactions rather than email. Alert on approaching the limit rather than discovering it at 100%.

86 Leads need to go to different teams by country and product.Easy

Assignment rules with entries ordered most-specific first, assigning to queues rather than individuals so membership is maintainable.

Keep the last entry as a catch-all to a triage queue — without it, non-matching leads stay with the default owner and nobody notices them. A silent default owner is where leads go to die.

87 Lead conversion loses custom field data.Medium

Custom lead fields need explicit field mapping to Account, Contact and Opportunity fields, and the types must be compatible.

Audit the mapping whenever either side changes, and test conversion with a fully populated lead. Lost data at conversion is usually discovered months later when someone asks why the information is missing.

88 Should duplicate leads block conversion?Medium

Usually alert rather than block, with the matched Account and Contact offered so the user converts into the existing records instead of creating new ones.

Blocking conversion tends to produce workarounds (slightly altered names), which is worse than a visible duplicate with a merge path.

89 A case needs to be created from a form on a public website, with files.Hard

Web-to-Case does not handle files well. The robust pattern is an Experience Cloud page or a custom endpoint (Apex REST) that creates the case and attaches files, behind proper validation and rate limiting.

Treat it as a public endpoint: guest user permissions reviewed field by field, no without sharing in the path, size limits enforced, and spam controls. See guest hardening.

90 Capture volumes dropped 40% and nobody noticed for three weeks.Medium

The real failure is monitoring, not the channel. Capture paths fail silently — Web-to-Lead stops posting, an email service bounces, a limit is exhausted.

Alert on absence, not just on errors: a feed that normally delivers 500 leads a day and delivered zero should page someone. That one dashboard prevents more lost revenue than any amount of rule tuning.

Automation order & admin judgement (91–100)

91 Your flow runs twice on one save.Hard

Something is re-saving the record: a workflow field update (which re-fires triggers and flows once), a roll-up recalculation, or an after-save flow updating its own record.

Fixes: use the "only when a record is updated to meet the condition" entry option so you fire on the transition, move same-record field updates into a before-save flow, and converge on one automation per object per timing. See re-entry.

92 Two flows on one object run in an order you did not expect.Medium

Within the same object and timing, order is not guaranteed unless you set the flow's trigger order value explicitly.

Set it, document it, and ideally reduce to one entry point per timing with a named owner. Relying on observed order is relying on an implementation detail.

93 A validation rule fires before your before-trigger can fix the data.Medium

Check the actual order: before-save flows, then before triggers, then validation rules. So a before trigger can correct data ahead of validation — if your logic is in an after trigger, it runs too late.

Move the defaulting into a before-save flow or before trigger. And remember workflow field updates re-fire triggers but do not re-run validation by default.

94 Your org has workflow rules, processes, flows and triggers on Account.Hard

Document before changing. A debug log of one Account save gives you the real execution tree, including the automations nobody remembered.

Then consolidate by risk: delete what is provably dead, migrate workflow rules and processes into flows, converge on one entry point per timing, and move same-record updates to before-save. Do it incrementally behind tests so each step is attributable. See automation order.

95 A stakeholder wants a change in production "right now".Medium

Offer the sanctioned fast path rather than a yes or a no: a hotfix branch, a quick validation, a deploy within the hour. People go around process when process is slow.

If the change is genuinely trivial and reversible (a label, a report), say so and do it through the normal route. If it is a validation rule or automation, the twenty-minute path is still faster than the incident.

96 You are asked to grant Modify All Data to solve an access problem.Medium

Almost never the right answer — it is the lazy fix that fails the first audit and grants far more than the requirement.

Diagnose the actual gap: object permissions, FLS, OWD, role hierarchy, sharing rules, or a restriction rule. Then grant the minimum through a permission set. If elevation is genuinely needed for a specific operation, that is without sharing Apex scoped to that operation, reviewed.

97 An admin made 30 changes in production last month, undocumented.Hard

Capture before you correct. Setup Audit Trail tells you what changed; retrieve those changes into a config/* branch and PR them so git matches production again, then merge down so the next release does not revert them.

Then address the cause rather than the person: 30 changes means the sanctioned path is too slow or does not exist. Build it, then restrict production edit rights. See drift.

98 You need to test an admin change safely but have no sandbox.Easy

Spin up a Developer Edition org or a scratch org for anything structural. For a change you must make in production, limit blast radius: scope it to one profile or permission set first, verify, then widen.

And never test an irreversible setting (multi-currency, state/country picklists, person accounts) anywhere you care about.

99 A declarative change caused a production incident. What is the process fix?Medium

Treat declarative changes with the same review as code, tiered by risk: a field label needs no board, but a validation rule, an automation, anything touching a shared object, integrations or security does.

Publish the tiers so people can self-serve the small stuff — governance that is uniformly heavy gets bypassed, which produces less control than none. See operating model.

100 What is the most under-rated admin habit?Hard

Writing down why. The description field on every field, rule, flow and permission set; the business reason in the error message; the decision and the rejected alternative in a comment.

Six months later nobody remembers, and undocumented configuration is the reason orgs accumulate automation nobody dares delete. It costs thirty seconds per change and it is the difference between an org you can evolve and one you can only add to.
