Deployment & DevOps

Getting your work from a sandbox into production safely — change sets, the Metadata API, the SF CLI, scratch orgs, packages, Git branching and a working CI/CD pipeline.

Two development models

Org-based vs source-driven development

Change sets

The click-based way to move metadata between connected orgs (orgs sharing the same production org).

  • Source org → Setup → Outbound Change Set → New.
  • Add components, then click View/Add Dependencies — the step everyone forgets, and the cause of most failed deployments.
  • Upload to the target org (must be a Deployment Connection with "Allow Inbound Changes" enabled there).
  • Target org → Inbound Change Sets → Validate first, then Deploy.
  • Choose the test level: Default, Run Local Tests, Run All Tests, or Run Specified Tests.

✅ Good for

  • Small admin changes
  • Teams with no developer tooling
  • Emergency fixes when the pipeline is down

❌ Painful because

  • Can't be edited after upload — you rebuild from scratch
  • No version control, no diff, no rollback
  • Manual and slow for large releases
  • Doesn't support all metadata types (e.g. some picklist value changes)
  • Doesn't delete components — you must delete manually in the target
  • Only between connected orgs — no deploying to a scratch org or a fresh org

Salesforce CLI (sf)

# ---------- Install & auth ----------
npm install -g @salesforce/cli
sf --version
sf org login web --alias devhub --set-default-dev-hub
sf org login web --alias uat --instance-url https://test.salesforce.com
sf org list
sf org display --target-org uat

# ---------- Project ----------
sf project generate --name my-sf-app
cd my-sf-app

# ---------- Retrieve metadata from an org into source ----------
sf project retrieve start --metadata ApexClass:AccountService --target-org uat
sf project retrieve start --metadata "ApexClass,LightningComponentBundle" --target-org uat
sf project retrieve start --manifest manifest/package.xml --target-org uat

# ---------- Deploy source to an org ----------
sf project deploy start --source-dir force-app --target-org uat
sf project deploy start --manifest manifest/package.xml --target-org uat \
    --test-level RunLocalTests --wait 60

# VALIDATE ONLY (no changes committed) — always do this first for production
sf project deploy validate --source-dir force-app --target-org prod \
    --test-level RunLocalTests --wait 90
# Then deploy the validated result in minutes instead of hours (valid for 10 days)
sf project deploy quick --job-id 0Af5j00000XXXXX --target-org prod

# ---------- Deletions ----------
sf project delete source --metadata ApexClass:OldClass --target-org uat

# ---------- Tests ----------
sf apex run test --target-org uat --test-level RunLocalTests --code-coverage --result-format human --wait 20
sf apex run test --tests AccountServiceTest --target-org uat --result-format json

# ---------- Data ----------
sf data query --query "SELECT Id, Name FROM Account LIMIT 5" --target-org uat
sf data query --query "SELECT Id FROM Contact" --bulk --target-org uat
sf data export tree --query "SELECT Id, Name, (SELECT LastName FROM Contacts) FROM Account" \
    --output-dir ./data --plan
sf data import tree --plan ./data/Account-Contact-plan.json --target-org scratch
sf data create record --sobject Account --values "Name='Acme' Industry='Technology'"

# ---------- Apex & logs ----------
sf apex run --file scripts/apex/hello.apex --target-org uat
sf apex tail log --target-org uat --color
sf apex get log --number 1 --target-org uat

# ---------- Scratch orgs ----------
sf org create scratch --definition-file config/project-scratch-def.json \
    --alias scratch1 --duration-days 7 --set-default
sf project deploy start --target-org scratch1
sf org open --target-org scratch1
sf org delete scratch --target-org scratch1 --no-prompt

# ---------- Packaging ----------
sf package create --name "Core Sales" --package-type Unlocked --path force-app
sf package version create --package "Core Sales" --installation-key-bypass --wait 20 --code-coverage
sf package version promote --package "Core Sales@1.0.0-1"
sf package install --package 04t5j000000XXXX --target-org uat --wait 20

# ---------- Useful extras ----------
sf org assign permset --name Sales_Rep_Bundle --target-org scratch1
sf apex generate class --name AccountService --output-dir force-app/main/default/classes
sf lightning generate component --name accountList --type lwc \
    --output-dir force-app/main/default/lwc
🔤
sfdx vs sf The old sfdx force:... commands still work but are deprecated. Modern syntax is sf <topic> <command>, e.g. sfdx force:source:deploy → sf project deploy start. Learn the new form.

Metadata API & package.xml

Underneath every deployment tool sits the Metadata API. The manifest that drives it is package.xml.

<?xml version="1.0" encoding="UTF-8"?>
<Package xmlns="http://soap.sforce.com/2006/04/metadata">

    <!-- Specific components -->
    <types>
        <members>AccountService</members>
        <members>AccountServiceTest</members>
        <name>ApexClass</name>
    </types>

    <!-- Wildcard: everything of this type -->
    <types>
        <members>*</members>
        <name>ApexTrigger</name>
    </types>

    <!-- Custom object with specific fields -->
    <types>
        <members>Invoice__c</members>
        <members>Invoice__c.Amount__c</members>
        <name>CustomObject</name>
    </types>
    <types>
        <members>Invoice__c.Amount__c</members>
        <name>CustomField</name>
    </types>

    <types>
        <members>accountList</members>
        <name>LightningComponentBundle</name>
    </types>

    <version>62.0</version>
</Package>

Destructive changes

<!-- destructiveChangesPost.xml — deletes AFTER the deployment -->
<?xml version="1.0" encoding="UTF-8"?>
<Package xmlns="http://soap.sforce.com/2006/04/metadata">
    <types>
        <members>ObsoleteClass</members>
        <name>ApexClass</name>
    </types>
    <version>62.0</version>
</Package>
sf project deploy start --manifest package.xml \
    --post-destructive-changes destructiveChangesPost.xml --target-org uat

Scratch orgs are disposable, source-driven orgs created from a definition file. Typical loop: create scratch org → push source → import seed data → develop → run tests → delete. They expire after 1–30 days, which forces your project to be fully reproducible from Git.

Git branching for Salesforce

Feature-branch workflow mapped to orgs
# Typical developer loop
git checkout develop && git pull
git checkout -b feature/W-1234-discount-approval

sf org create scratch -f config/project-scratch-def.json -a w1234 -d 7
sf project deploy start -o w1234
sf data import tree --plan data/seed-plan.json -o w1234
# ... develop ...
sf apex run test -o w1234 --test-level RunLocalTests --code-coverage

git add . && git commit -m "feat: cap discount by account tier (W-1234)"
git push -u origin feature/W-1234-discount-approval
# open a pull request → review → merge to develop
🔀
The Salesforce-specific Git problems ① Profiles and permission sets merge terribly — keep them minimal and prefer permission sets. ② Flows are XML — practically unmergeable, so only one person edits a flow at a time. ③ Layouts conflict constantly. ④ Never commit .sfdx/, auth files or package-lock churn — use a proper .gitignore.

A working CI/CD pipeline

name: Salesforce CI

on:
  pull_request:
    branches: [develop, main]
  push:
    branches: [develop, main]

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }

      - name: Install Salesforce CLI
        run: npm install -g @salesforce/cli

      - name: Authenticate (JWT — no passwords in CI)
        run: |
          echo "${{ secrets.SF_JWT_KEY }}" > server.key
          sf org login jwt \
            --client-id ${{ secrets.SF_CONSUMER_KEY }} \
            --jwt-key-file server.key \
            --username ${{ secrets.SF_USERNAME }} \
            --instance-url https://test.salesforce.com \
            --alias target

      - name: Static analysis
        run: |
          npm install -g @salesforce/sfdx-scanner
          sf scanner run --target force-app --format table --severity-threshold 2

      - name: Lint LWC and run Jest
        run: |
          npm ci
          npm run lint
          npm run test:unit -- --coverage

      # Deploy only what changed, using a delta package
      - name: Validate deployment
        run: |
          sf project deploy validate \
            --source-dir force-app \
            --target-org target \
            --test-level RunLocalTests \
            --wait 90 \
            --json | tee validate.json

      - name: Deploy (only on push to a protected branch)
        if: github.event_name == 'push'
        run: |
          JOB_ID=$(jq -r '.result.id' validate.json)
          sf project deploy quick --job-id $JOB_ID --target-org target --wait 60

Validate on PR

Every pull request runs a check-only deployment plus all local tests. Broken code never reaches a shared branch.

Quick Deploy

A successful validation stays valid for 10 days. deploy quick then takes minutes instead of re-running every test.

Delta deployments

Tools like sfdx-git-delta generate a package.xml of only the changed components — far faster on large orgs.

Quality gates worth adding

  • sfdx-scanner (PMD + ESLint) — fails the build on SOQL-in-loop, missing sharing declarations, hard-coded Ids.
  • Jest for LWC, Apex tests with a coverage threshold above the 75% minimum.
  • Prettier with the Apex plugin for consistent formatting.
  • Branch protection: require a review and a green build before merge.
  • Conventional commits so you can auto-generate release notes.

Deployment failures — the usual suspects

ErrorCause & fix
Test coverage below 75%Org-wide coverage after the deploy is too low. Add real tests — not SeeAllData shortcuts
Dependent class is invalidA referenced class isn't in the deployment. Add dependencies
Cannot deploy inactive flowActivate it in the source org, or set the flow's status appropriately
Missing field in a layout/profileInclude the field and the object in the same deployment
Cannot modify managed objectYou're trying to change a managed package component
Picklist value in useDeactivate rather than delete, and update dependent records first
Scheduled job holds the classAbort the scheduled job, deploy, then reschedule

🚀
Production release checklist ① Validate in a Full sandbox first. ② Run deploy validate against production the day before. ③ Have a rollback plan (previous package version, or a reverse change set). ④ Deploy in a low-traffic window. ⑤ Post-deploy: run the manual steps (activate flows, assign permission sets, populate custom settings, reschedule jobs). ⑥ Smoke-test the critical path. ⑦ Watch error logs for an hour.

Interview questions

1 Org development model vs package development model.Easy

Org model: the org is the source of truth, changes move by change set or Metadata API, sandbox → sandbox → production. Familiar to admins, minimal setup, but no real version control, no diff and no rollback.

Package (source-driven) model: Git is the source of truth, developers work in scratch orgs, and CI/CD deploys from the repo. Reviewable, versioned, automated and reproducible — at the cost of a steeper learning curve.

2 Why do change sets frustrate teams?Easy

They can't be edited after upload — you rebuild from scratch. There's no version control, diff or rollback. They only work between connected orgs, so you can't deploy to a scratch org or a fresh org. They don't delete components, so removals must be done manually in every environment. And forgetting View/Add Dependencies is the single biggest cause of failed deployments.

3 A production deployment takes 3 hours of tests but you have a 15-minute window. Solution?Medium

Validate then Quick Deploy. Run sf project deploy validate --test-level RunLocalTests against production the day before — it runs everything but commits nothing. A successful validation stays usable for 10 days, so during the window you run sf project deploy quick --job-id <id>, which skips re-running the tests and completes in minutes. NoTestRun is not permitted in production.

4 Which metadata types cause the worst Git conflicts, and how do you manage them?Hard

Profiles (huge generated XML touching every object and field), page layouts, and flows (effectively unmergeable XML).

Mitigations: keep profiles minimal and grant everything through permission sets; agree that only one person edits a given flow at a time and treat it as a locked file; use delta deployments (sfdx-git-delta) so you only deploy what changed; and never wildcard Profiles in package.xml.

5 How do you delete metadata as part of a deployment?Medium

A destructiveChanges.xml manifest listing the components to remove, paired with an empty package.xml, deployed via --pre-destructive-changes or --post-destructive-changes.

Why it matters: deleting manually in Setup leaves each org in a different state and isn't recorded anywhere. A destructive manifest keeps the removal in source control and in the pipeline, so every environment converges. Change sets can't do this at all.

6 What's a scratch org and why would you use one over a developer sandbox?Medium

A disposable, source-driven org created from a JSON definition file (edition, features, settings), living 1–30 days.

The real benefit is discipline: because it's thrown away and recreated, everything needed to build your app — metadata, permission sets, seed data — must be in Git. There's no "it works in my sandbox because someone configured something there three years ago". Each developer gets an isolated org per feature branch, so work never collides.

7 Design a CI/CD pipeline for a Salesforce team.Hard

Branching: feature/* → develop (deploys to UAT) → main (deploys to production).

On pull request: authenticate with JWT (never passwords in CI), run sfdx-scanner (PMD/ESLint), npm run lint and Jest for LWC, then deploy validate --test-level RunLocalTests. Branch protection requires a green build and a review.

On merge: deploy quick using the validated job id. Add delta packages for speed, JUnit reporting for visibility, and a documented post-deploy checklist (activate flows, assign permission sets, populate custom settings, reschedule jobs).

8 Your deployment fails: "Dependent class is invalid and needs recompilation". What now?Medium

Something the deployed code references isn't present or is itself broken — usually a class, field or object you forgot to include. Read the full error: it names the dependent component and the underlying compile error, which is often a missing field rather than a missing class.

Common cousins: a field referenced by a layout or profile that isn't in the same deployment; a picklist value still in use; an inactive flow; or a scheduled job holding the class, which requires System.abortJob before deploying and rescheduling afterwards.

9 Tests pass in UAT and fail in production. Why?Hard

Usually one of: data dependency (SeeAllData or an assumption a record exists); different automation — a validation rule, required field or active trigger present only in production so the test's data won't insert; governor limits, because production stacks more automation on the same object; or hard-coded Ids for record types, profiles or Pricebooks that differ between orgs.

The fix is the same in every case: self-contained test data from a factory, no hard-coded Ids, and always validate against a Full sandbox before production.

1. You need a 3-hour production deployment to finish in a 15-minute window. How?

2. Which metadata type causes the worst Git merge conflicts?
Prefer permission sets over profiles, and have only one person edit a given flow at a time.
