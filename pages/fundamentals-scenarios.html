Fundamentals — 100 Scenarios

Platform architecture, multitenancy, org strategy, licences, releases and record Ids — as situations you have to react to, not definitions to recite.

📚
How to use this Read the scenario, answer out loud in under ninety seconds, then open the answer. The concepts behind these are on Salesforce Fundamentals — if an answer surprises you, go back to that page rather than memorising this one.

Platform & multitenancy (1–10)

1 A developer says "let me add a database index to speed this up". What do you tell them?Easy

You cannot — there is no infrastructure access on a multitenant platform. Your data lives in shared structures with a tenant discriminator, so indexes are managed by Salesforce.

What you can do: mark a field External Id or Unique (which gives you an index for free), request a custom or two-column index from Support for a field you filter on constantly, or restructure the query to lead with an already-indexed selective field. See selectivity.

2 The same SOQL query is fast in your sandbox and times out in production. No code changed.Medium

The query optimiser keeps statistics per tenant and decides based on your data distribution. A filter that returned 2% of rows in the sandbox returns 40% in production, crosses the selectivity threshold, and the optimiser abandons the index for a scan.

Diagnose with the Query Plan tool against production, not the sandbox. Cost above roughly 1 means a table scan.

3 A stakeholder asks why Salesforce "arbitrarily" limits them to 100 SOQL queries.Easy

It is not arbitrary — it is the mechanism that stops one tenant consuming shared compute and degrading everyone else on the instance. That is also why limits are enforced per transaction and are not negotiable or purchasable.

The useful reframe for the stakeholder: the limit is a design constraint like a memory budget. Hitting it means the design needs to change shape (bulk patterns, asynchronous processing), not that the platform needs persuading.

4 Someone proposes storing 400 million rows of IoT telemetry on a custom object.Hard

Push back on the storage model, not the requirement. Standard objects at that volume cost real storage money, slow reports, and complicate sharing recalculation.

Options, in order: keep it in the source system and query live via Salesforce Connect external objects; land it in a Big Object if you need it on-platform (and design the composite index first, because it cannot be changed later); or put it in Data Cloud with zero-copy access to the warehouse. Only aggregate, decision-relevant data belongs in a standard object. See Data Management.

5 Your org is on the Winter release but a client's org is still on the previous one. How?Easy

Releases roll out by instance over several weeks, so two orgs can legitimately be on different versions for a short window. Sandboxes are upgraded ahead of production, which is what gives you a free preview window.

Check status.salesforce.com for each instance's release date. You cannot defer a release — but you can pin an API version so your integrations behave consistently across the change.

6 An Apex class written in 2019 still behaves per its old API version. Is that a bug?Medium

No — it is the stability guarantee. Each class is saved against an API version and keeps that version's semantics forever, which is why a platform upgrade does not break your code.

The cost is slow debt accumulation: classes on long-retired API versions miss newer behaviour and can block features. Bump API versions deliberately as a maintenance task with regression tests, not silently whenever you happen to edit a class.

7 A new admin adds a custom field and asks when the database migration will run.Easy

There isn't one. The platform is metadata-driven: your object and field definitions are rows in a metadata dictionary interpreted at runtime, not columns in a physical table.

That is why schema changes are instant and reversible, why there is no build step, and why "deploying" means moving metadata rather than running DDL.

8 A transaction takes 40 seconds of wall clock but never hits the CPU limit. Explain.Hard

CPU time counts your computation — loops, collections, JSON, formula evaluation. It does not count time waiting for SOQL to return, waiting for a callout, or database commit time.

So a transaction dominated by waiting can run long without approaching the 10-second limit, while a compute-heavy transaction can fail at 11 seconds of wall clock. Read the cumulative limits section of the debug log rather than timing with a stopwatch. See Limits.

9 A managed package is installed and your previously-fine trigger starts failing on CPU.Hard

The package's triggers run inside your transaction on the same save, and CPU time is shared even though some other limits are namespace-scoped. Your trigger did not get slower; the budget got smaller.

Prove it from the cumulative limits section of a debug log, which attributes consumption per namespace. Then either slim your own logic, move work asynchronous, or take the evidence to the vendor — a log naming their namespace is what gets a support case taken seriously.

10 Why can't you get a full database backup with a single SQL dump?Medium

No infrastructure or database access on a multitenant platform — your data is interleaved with other tenants' in shared structures.

Your options are API-based: the Weekly Export (CSV, no relationships preserved — not a backup), Bulk API extraction with PK chunking, or a third-party backup product. And metadata backup is a separate concern, which is what version control is for. Test the restore, or you have a hypothesis rather than a backup.

Org strategy & environments (11–20)

11 Two business units argue constantly over releases. One proposes splitting into two orgs.Hard

Ask the diagnostic question first: do they share customers, processes or reporting? If yes, splitting destroys the single customer view — the hardest thing to retrofit — and you will still have the same disagreement, now across two orgs plus an integration to build.

Release conflict is usually a governance and branching problem wearing an architecture costume. Fix it with parallel release branches, clear ownership of conflict-prone metadata, and decomposition into unlocked packages. Separate orgs are defensible when there is genuinely no shared customer or process, or when regulators force it.

12 You have one Full sandbox refreshed every 29 days and need UAT, performance testing and a data-migration rehearsal.Medium

You cannot have all three simultaneously on one Full sandbox, so sequence them against the refresh cycle and be explicit about the trade-off with the business: performance testing and migration rehearsal need real data volume, UAT mostly needs realistic shape.

Practical split: Full sandbox for the migration rehearsal and performance work close to go-live; a Partial Copy with a good sandbox template for ongoing UAT; Developer Pro for integration testing. If the programme genuinely needs more, buying another Full sandbox is cheaper than a failed go-live.

13 After a sandbox refresh, customers receive test emails. What went wrong and what is the fix?Medium

Email deliverability was left at "All Email" and real contact data came across with the refresh.

The fix is a scripted post-refresh checklist run before anyone logs in: set deliverability to System Email Only first, mask or scramble PII, repoint named credentials at test endpoints, deactivate scheduled jobs and integration users, disable outbound messages, then reseed config data. Automate it as an Apex class — a manual checklist gets skipped exactly once. See DevOps.

14 A developer asks for a Developer sandbox to test a 2-million-record migration.Easy

Wrong environment. Developer sandboxes carry metadata only and have small data storage — the load will fail on storage long before it tells you anything useful about performance.

Migration rehearsals need a Full sandbox (real volume and shape) or at minimum a Partial Copy for logic validation. Use the Developer sandbox for the transformation logic, the Full sandbox for the timed rehearsal.

15 Finance asks you to enable multi-currency "just to see what it does".Medium

Refuse in a sandbox-only form. Multi-currency is irreversible once enabled, and Advanced Currency Management on top of it changes roll-up and reporting behaviour again.

Test it in a throwaway Developer org or a sandbox you are willing to abandon, never in production or in a sandbox you depend on. Keep an explicit list of irreversible settings — multi-currency, custom fiscal years, state/country picklists, person accounts, enhanced domains — and require a design-authority decision for each. See Governance.

16 A regulator requires EU customer data to stay in the EU. Your org is hosted in the US.Hard

This is a data-residency constraint that can override architectural preference. Options: a Hyperforce org in the required region, or a separate org for the regulated population with integration back to the rest.

Work the problem with legal rather than guessing — "data residency" sometimes means storage location, sometimes processing location, sometimes only specific field categories. The answer changes the architecture substantially, so get the requirement precisely before designing.

17 Your scratch org "doesn't look like production" and features are missing.Medium

The scratch org definition file declares edition, features and settings, and yours does not match production. Derive it instead of guessing: use an org shape from production, which produces a definition reflecting real edition and features.

Then consider an org snapshot so a 20-minute setup becomes a 2-minute spin-up — it transforms developer onboarding.

18 A consultancy proposes a separate org per country for 12 countries.Hard

Challenge it hard. Twelve orgs means twelve of everything — releases, configuration, integrations, support — and no cross-country customer view or reporting without building it.

Ask: do countries share customers or processes? Are the differences really data residency and regulation, or just local preference? Most "country differences" are handled inside one org with record types, translation, multi-currency and territory-based sharing. Reserve separate orgs for genuine regulatory isolation, and expect to justify each one.

19 You inherit an org and nobody knows what is in it. First week?Medium

Inventory before touching anything. Run Optimizer and Health Check, review Setup Audit Trail for recent change patterns, list installed packages, count automations per object, and check limit headroom (storage, API, async, scheduled jobs).

Then baseline it into version control — retrieve production into main, accept that it is ugly, and tag it. You cannot manage drift without a starting point, and making the baseline beautiful first is how this exercise burns three months. See Branching Strategy.

20 Someone wants to develop directly in production because "it's faster".Easy

It is faster right up to the first mistake, and there is no rollback on this platform — a deployment cannot be reversed transactionally.

The honest response is to make the sanctioned path genuinely fast rather than lecturing: a hotfix branch with a twenty-minute pipeline. People bypass process when process is slow. Then remove metadata-edit rights in production, once the corridor exists.

Metadata vs data (21–30)

21 A change set deployment succeeds but the feature doesn't work in UAT.Medium

Almost always missing data that the feature depends on: custom setting rows, Custom Metadata records, queue members, picklist value assignments per record type, or package configuration.

Metadata deployed, configuration data did not. Build an idempotent post-deployment Apex script that seeds required rows and can be re-run safely, and include it in the release runbook.

22 Your CPQ price rules work in UAT and are missing in production after go-live.Hard

CPQ configuration — price rules, conditions, actions, lookup queries, discount schedules, product options — is data, not metadata. Deployments do not carry it.

You need a scripted, version-controlled migration in dependency order (products → options → rules → conditions/actions → lookups), re-pointing references because record Ids differ per org. Keep a set of golden quotes with known expected totals and recalculate them after every migration. See CPQ.

23 Is a report metadata or data?Easy

A report definition is metadata and deploys. Its folder and the folder's sharing are the fiddly part, and custom report types are metadata too.

The results are obviously data. The practical implication: a report can deploy successfully and be invisible to users because nobody deployed or configured the folder access.

24 A developer hard-codes a record type Id in Apex and it breaks after a sandbox refresh.Easy

Record Ids differ per org and per refreshed sandbox. Never hard-code any Id — record types, scheduling policies, queues, price books, Custom Metadata rows.

Resolve by developer name at runtime (Schema.SObjectType.Account.getRecordTypeInfosByDeveloperName()), or store the name in Custom Metadata and look it up. This single habit prevents a whole category of post-deployment incidents.

25 Should Custom Metadata hold your business rules or your environment switches?Medium

Both work, but know what you are choosing. Custom Metadata is deployable metadata, so it travels with your release and is queryable without consuming SOQL limits — ideal for business rules a consultant maintains and for environment-level feature flags that should ship with the code.

If an admin must change the value in production without a deployment, that is a Hierarchy Custom Setting instead — which is also what you want for an incident kill switch.

26 Profiles cause a merge conflict on every pull request. What do you do?Medium

Stop versioning them. A profile is one enormous XML file covering every object, field and tab, so two unrelated features both rewrite it — and people learn to resolve those diffs carelessly, including the ones that matter.

Move permissions into permission sets and permission set groups, strip profiles to the minimum (login hours, IP ranges, defaults, layout and record type assignments), and .forceignore them — then manage them deliberately per org and document that. See the metadata that won't merge.

27 Two developers edited the same flow on different branches. Git merged it cleanly.Hard

That is the dangerous outcome. A flow is one XML blob with generated element coordinates — a line-by-line merge produces a flow that deploys and behaves incorrectly: missing connectors, duplicated elements, orphaned decisions.

Mark flow files unmergeable in .gitattributes so a conflict is forced, assign one owner per flow per release, and split large flows into subflows so two people are not in the same file. If both must change it, they do it sequentially.

28 An admin fixed a validation rule in production on Friday. Your release on Monday reverts it.Hard

Classic config drift: main no longer matches production, and a full deployment overwrites the undocumented change silently.

Close the loop: nightly drift detection diffing production metadata against main and failing loudly; retrieve the change into a config/* branch and PR it into main; merge down to develop and open release branches the same day. Then give admins a sanctioned fast path so this stops being necessary. See drift.

29 Which is riskier to deploy: a new field, or a deleted field?Easy

The deletion, by a wide margin. Adding a field is additive and reversible. Deleting one is a destructive change that takes the data with it, and nothing on this platform rolls back transactionally.

So destructive changes live in a separate manifest, applied deliberately, with explicit review — and your per-release documentation should list what is not reversible, which is what turns a rollback decision into a judgement rather than a guess.

30 Your repo claims to describe the org. How do you prove it to an auditor?Hard

With a mechanism and its run history, not an assertion: a scheduled job that retrieves production metadata, diffs it against main, and fails on divergence.

Supporting controls: main equals production as an enforced invariant with tagged releases, deployments by a service account, human metadata-edit rights removed in production, Setup Audit Trail reviewed weekly, ticket ids in merge commits. And the honest caveat — config that is data (CPQ, Field Service, metadata rows) needs its own versioned migration and reconciliation.

Licences (31–40)

31 You designed an internal app on Platform licences. In UAT, users cannot see Opportunities.Hard

Platform licences cannot access standard CRM objects like Opportunity and Case. That is the trade for being much cheaper, and discovering it after design is a painful week.

Options: redesign to use custom objects only (legitimate if the CRM data was convenience rather than requirement), upgrade that population to full Salesforce licences, or split the app. The lesson is to verify object availability per licence before design, not after — it is the single most expensive licence mistake on the platform.

32 A user has the right profile but a feature still doesn't appear.Medium

Check for a missing permission set licence. Modern features (CRM Analytics, Field Service, Sales Console) are sold as permission set licences that must be assigned to the user in addition to the permission set itself.

Also check legacy feature licences — checkboxes on the user record like Marketing User or Knowledge User. The three-layer model (user licence, permission set licence, feature licence) is where most "it's not showing up" tickets live.

33 100,000 customers need portal access. Which licence family?Medium

At that volume, high-volume Customer Community. The critical consequence: high-volume licences have no role hierarchy, so access comes from Sharing Sets matching the user's Contact/Account to the record, and internal visibility of records they own requires a Share Group.

If they need roles, reports and sharing rules, that is Customer Community Plus at a higher price. Designing on the assumption roles exist and then discovering the licence lacks them is a redesign. See Experience Cloud.

34 Member-based or login-based community licences for 5,000 occasional users?Medium

Model it rather than guessing. Login-based licences are a monthly pool of logins and suit genuinely occasional use; member-based suits frequent users. The crossover is usually around two or three logins per member per month.

Then measure in a pilot before buying at scale — estimates of community login behaviour in business cases are consistently wrong, in both directions.

35 Partners need to work Leads and Opportunities. Which licence?Easy

Partner Community — it is the external licence family that includes CRM objects like Leads and Opportunities, plus partner roles under the account (up to three) and Super User access for partner managers.

Customer Community cannot do this. If there is a distributor/reseller tier, add External Account Hierarchy so a parent account can see its children's records.

36 An integration user is consuming a full Salesforce licence. Can you avoid that?Medium

Often yes — Salesforce offers integration-oriented licences with API access but no UI, which are cheaper for a service account that only makes API calls.

Whatever you use, make it a dedicated integration user with a least-privilege permission set, not a named human's admin account — which breaks the day they leave and makes every audit trail ambiguous.

37 You deactivate a departing user and a nightly batch stops two weeks later.Hard

They owned the scheduled Apex job, which runs as its submitter. Deactivating them killed it, and nothing alerted you.

Offboarding checklist: freeze first, revoke OAuth tokens, reassign record ownership, then check scheduled jobs, dashboard running users, integration credentials, queue and group memberships, and whether they are a Named Principal on a Named Credential. See Identity.

38 Licence counts look fine but a managed package feature stops working for some users.Medium

Package licences are assigned per user and are separate from your Salesforce licences — and they expire, often silently. Check the package's licence assignment page.

Build a periodic licence true-up into your platform health review: Salesforce licences, permission set licences, feature licences and package licences, with utilisation. It is also where you find the money nobody is using.

39 Can you reduce licence count mid-contract because usage is lower than expected?Easy

Generally not mid-term — reductions happen at renewal, which is a commercial conversation rather than a technical one.

What you can do technically is measure utilisation properly (active users, last login, feature usage) and bring evidence to the renewal. Start that measurement months ahead, because "we think about 200 are unused" does not survive a negotiation.

40 A guest user needs to create records on a public site. What licence does that consume?Medium

Guest access does not consume a per-user licence, but it is bounded by the site's limits and it is a security question before a licensing one.

Guest users cannot own records, so creations are reassigned to a default owner you must configure. Review the guest profile's object and field permissions, use guest sharing rules only, audit any @AuraEnabled method reachable from the page, and rate-limit creation — a guest-writable object with no validation is a spam target.

Releases & upgrades (41–50)

41 A critical update has an enforcement date in two releases. How do you handle it?Medium

Treat it as a backlog item with a deadline, not an email. Critical updates are the changes that actually break things, and the enforcement date is not negotiable.

Process: assign an owner, test it enabled in a sandbox well ahead of the date, fix what breaks, then enable in production before enforcement. Reacting at the deadline is how a critical update becomes an incident.

42 Your sandbox is on the new release and production is not. What should you be doing?Easy

Using the free testing window. Run your regression suite, exercise the areas the release notes touch for your stack, and verify integrations against the new API version if you plan to bump it.

Find out which preview window your sandbox falls into ahead of time — teams discover this too late and lose the window entirely, then meet the release in production.

43 How do you triage 400 pages of release notes?Medium

Filter to your own stack: the objects, APIs and features you actually use, plus anything marked as a critical update or security change. An hour per release with a named owner catches nearly everything that matters.

Keep a standing list of "features we depend on" to filter against, and record decisions (adopt now / evaluate / ignore) so the next release does not re-litigate the same items.

44 A new release changes behaviour your integration relied on. Who is at fault?Medium

Usually the integration, for not pinning an API version — behaviour is guaranteed within a version, which is precisely why versions exist.

Fix forward: pin the version explicitly in the endpoint path, keep an inventory of which integration uses which version, and track Salesforce's retirement schedule. A version retirement notice should be a planned project, never a surprise.

45 You want to upgrade a managed package. What do you do first?Medium

Install it in a sandbox and regression-test — a package upgrade can change calculation behaviour, add triggers and fields to your objects, and consume more of your CPU budget.

For packages with configuration (CPQ, Field Service), recalculate a golden set with known expected results afterwards. And schedule the upgrade as a change with a rollback position, because uninstalling is not a clean reverse.

46 Can you roll back a release in production?Hard

Not transactionally — there is no rollback primitive. "Roll back" means deploying the previous known-good state and manually reversing what cannot be redeployed: destructive changes, data changes, picklist values, irreversible settings.

So the practical controls are a tag per release (making the first half trivial) and a documented per-release list of irreversible changes. Forward-fix is usually the better answer, which is why a fast hotfix path matters more than a rollback plan.

47 A deployment to production takes three hours. Reduce it.Hard

Two changes. Delta deployments: generate the manifest from the diff between the last release tag and HEAD rather than deploying the whole repo. Validate then quick deploy: run the tests in a validation-only deployment ahead of the window, then promote that validated build without re-running them.

Minutes rather than hours. The trade-off is that delta deployments leave untouched metadata alone, so they hide drift — pair them with scheduled drift detection. See delta deployments.

48 Your scheduled jobs break after every deployment.Medium

Deployments can leave schedules intact but pointing at changed logic, or block changes to classes referenced by active jobs.

Build an idempotent scheduler setup method you can re-run post-deployment to abort and recreate every schedule, and include it in the release runbook. Also query CronTrigger after each release to verify NextFireTime and state.

49 A feature you built is being deprecated by Salesforce. How do you find out early?Easy

Release notes and the retirement announcements, read every release by a named owner — plus the Metadata Coverage Report and API version retirement schedule for anything you automate against.

The structural answer is to keep an inventory of platform features you depend on, so a retirement notice can be matched against it in minutes rather than discovered by a broken integration.

50 Should you adopt a new feature in the release it ships in?Medium

Usually not for anything load-bearing. New features often ship with gaps — missing metadata support (so you cannot deploy them), missing API coverage, or beta status with no SLA.

Check the Metadata Coverage Report and the GA status before building on it. Adopt early for low-risk improvements, deliberately late for anything in a critical path.

Record Ids & keys (51–60)

51 An external system merged two of your records into one. The Ids looked different to you.Hard

You sent 15-character Ids, which are case-sensitive, to a system that uppercases or compares case-insensitively — so two genuinely different Ids collapsed into one.

Always exchange 18-character Ids externally; the suffix is a case-safe checksum. Use CASESAFEID() in formulas and reports, and make 18 characters a rule on every interface. Excel does this too, which is why exported Id lists cause the same bug.

52 In Apex, a 15-character and 18-character Id compare as unequal. Why?Medium

You are comparing them as String. Cast both to Id and they are equal — the Id type normalises.

This is a common integration bug: a map keyed on String Ids misses lookups when one side is 15 characters and the other 18. Key maps on Id, not String.

53 You receive an Id and don't know what object it belongs to.Easy

The first three characters are the key prefix (001 Account, 003 Contact, 006 Opportunity, 500 Case, 00Q Lead, 005 User). In Apex, ((Id) idString).getSObjectType() resolves it at runtime.

That runtime resolution is the right approach for generic utilities and for polymorphic fields like Task.WhatId, where you cannot assume the parent type.

54 An integration needs to upsert records without storing Salesforce Ids.Medium

Use an External Id field — unique, indexed, holding the remote system's key — and upsert against it. The remote system keeps using its own identifier and never needs to know your Ids.

This is also your idempotency guarantee: the unique index means a duplicate delivery fails on the duplicate rather than creating a second record. Run the same upsert twice as a test and confirm it updates rather than duplicates.

55 Is a record Id reused after you delete the record?Easy

No — Ids are not recycled. A deleted record's Id continues to identify that (now deleted) record, which is why it can be restored from the recycle bin with the same Id.

Practical consequence: a stale Id in an external system resolves to nothing rather than to a different record. That is a safer failure than reuse would be, and it is why Ids are reasonable long-term references.

56 A URL with a record Id works for you and 404s for a colleague.Medium

Record access, not the Id — they lack sharing or object permissions, so the record is not visible to them and the page behaves as if it does not exist.

Diagnose by logging in as them, then walk the sharing chain: object permissions, FLS, OWD, role hierarchy, sharing rules, manual and Apex shares, implicit parent sharing, restriction rules. See Security.

57 Your My Domain changes and every bookmarked URL breaks.Hard

Enhanced domains change the hostname in every URL: bookmarks, SSO configuration (Entity Id and ACS URL), integration endpoints, email templates with hard-coded links, and embedded content.

Treat it as a project with a communication plan and an inventory of everything referencing the old host — not a setting. Test SSO and every integration in a sandbox first, because an Entity Id mismatch breaks login entirely.

58 Should you expose Salesforce Ids in a customer-facing URL?Medium

Prefer not to. Ids leak which object and roughly when a record was created, they are enumerable in spirit, and they couple your public surface to internal identifiers.

Use a separate opaque reference (a random token on the record, indexed and unique) for public URLs. And regardless, never rely on Id obscurity for access control — enforce sharing and FLS server side.

59 A data load fails on self-referential lookups (Account parent, Contact reports-to).Medium

You cannot populate a reference to a record that does not exist yet. Load in two passes: first create all records without the self-reference, then update them with the relationship using External Ids to resolve the targets.

Same principle for any dependency order: parents before children, and anything circular needs a second pass. See Data Management.

60 Why does sorting a list of sObjects in Apex give an unexpected order?Hard

List<SObject>.sort() sorts on the first field in the SELECT clause by default, which is rarely what you intended. Nulls also sort first ascending, so Apex and a report can disagree about "the top record".

Fix: sort in SOQL with an explicit ORDER BY, or implement Comparable on a wrapper class, or pass a Comparator to sort() when you need more than one ordering.

MVC, request lifecycle & architecture (61–70)

61 A user says "the page is slow". Where do you start?Medium

The Lightning Usage App, to see EPT by page, browser and user — it frequently reveals one browser or one user population rather than a platform problem.

Then component-level instrumentation on the page to attribute the time, and the browser network tab for Apex call count and payload size. Five components each fetching their own data is five round trips, and consolidation is usually the biggest single win. See performance.

62 Where does a validation rule fire relative to a before trigger?Medium

After before-save flows and before triggers, and before after triggers. So a before trigger can set a field that then fails validation — which is correct and occasionally surprising.

The ordering matters most for the re-entry cases: a workflow field update re-fires before and after triggers but does not re-run validation rules by default. See order of execution.

63 Is a flow part of the Model, the View or the Controller?Easy

Mostly Controller — it orchestrates logic. A screen flow spans Controller and View; the Model is your objects and fields.

The useful version of this question is not taxonomy but where logic should live: declarative automation for orchestration and simple field work, Apex for bulk performance, complex data shapes and reuse. See Flow ⇄ Apex.

64 Two record-triggered flows on the same object run in an unpredictable order.Medium

Within one category and timing, order is not guaranteed unless you set the flow's trigger order explicitly (1–2000).

Better still, converge on one entry point per object per timing with a named owner. Multiple automations on one object competing for order is how a save becomes unpredictable — see automation order.

65 Where should business logic live if it must be callable from a trigger, an LWC and a REST endpoint?Medium

A service class that owns the transaction boundary, with all three entry points calling it. The trigger handler, the @AuraEnabled method and the @RestResource become thin adapters.

That is the single highest-value piece of structure in a growing codebase: one implementation, one place to test, and new entry points cost nothing. See enterprise patterns.

66 A roll-up summary and a trigger both update the same parent field. What happens?Hard

They fight, and the roll-up generally wins because it recalculates on the platform's own schedule within the save. You will see values that flicker or revert.

Pick one mechanism per field. If the aggregation is expressible as a roll-up summary, use it and delete the trigger logic; if not, use the trigger and do not create a roll-up on that field. Never both.

67 Why does updating a child record fire the parent's triggers?Medium

Roll-up summary recalculation saves the parent, which runs the parent's triggers. This is how cross-object trigger storms usually start.

It also explains implicit parent locking: inserting or updating a detail record locks its master-detail parent, which is the root cause of most UNABLE_TO_LOCK_ROW errors. Sort DML by parent Id so concurrent transactions lock in the same order.

68 A platform event subscriber cannot see static variables set by the publisher.Medium

Correct and by design. Subscribers run in a separate transaction, as the Automated Process user, with fresh limits and no access to the publisher's static state.

Pass everything the subscriber needs in the event payload — ids plus the few fields it requires, a correlation id and a published timestamp. That separation is also a legitimate way to escape mixed-DML restrictions.

69 How does the platform decide which page layout a user sees?Easy

The combination of their profile (or permission-set assignment) and the record's record type. That matrix is why record types multiply maintenance so quickly.

Dynamic Forms largely removes the need for layout-driven record types — conditional field visibility on one layout instead of cloning layouts per variant. Do that before adding your eighth record type.

70 Is hiding a field with component visibility a security control?Easy

No. Component visibility and Dynamic Forms conditions are presentation — the data is still accessible via API, reports and SOQL.

Field-level security is the control. Conflating the two is one of the most common findings in a security review, and it is trivially demonstrable with a single REST call.

Limits in practice (71–80)

71 A Data Loader job of 10,000 records fires your trigger 50 times. Is that a bug?Medium

No — it arrives as 50 chunks of 200 in separate transactions, each with its own limits. That is normal and desirable.

What is a bug is a static alreadyRan boolean guard, which also blocks the legitimate second batch of 200 inside a single transaction. Guard by record Id instead. See recursion control.

72 "Just make it a batch job" — when does that not fix the limit problem?Hard

When the limit is row count. Async doubles CPU (10s → 60s), heap (6MB → 12MB) and query count (100 → 200), but total query rows (50,000) and DML rows (10,000) are unchanged.

So async fixes heavy computation over moderate data. It does not fix a design that tries to load 200,000 rows into one transaction — that needs chunking with a query locator.

73 Interactive users start getting errors at the same time your nightly integration runs.Hard

The concurrent long-running requests limit — ten synchronous requests over five seconds per org, shared between your background work and real users. Your integration is consuming the slots.

This is the nastiest limit on the platform because the symptom appears nowhere near the cause. Fix: move integration work asynchronous, off the synchronous path, and keep long-running synchronous calls out of integration patterns entirely.

74 Your API-based integration fails every day at 4pm.Medium

Daily API request limit exhaustion — it is org-wide and scales with licences, and a polling integration consumes a surprising share.

Check /limits, then fix the cause: replace polling with platform events or CDC, batch requests via Composite, and alert at a percentage of the daily limit rather than discovering it at 100%.

75 You cannot schedule a new Apex job. Nothing is obviously wrong.Medium

You have hit the org-wide limit on scheduled Apex jobs. Teams reach it by scheduling per-region or per-entity jobs.

Fix the pattern: one scheduled job that iterates over the regions, rather than one job per region. Also audit CronTrigger for abandoned schedules left behind by old projects.

76 A batch job fails at 95% complete after four hours.Hard

Design it so that cannot waste the whole run. Persist a high-water mark ("processed up to here") so a re-run resumes rather than restarting, and check remaining limits mid-loop so the job re-enqueues the remainder instead of dying.

Also use allOrNone = false with an error log so one bad record costs you that record, not the batch. And attach a Finalizer to Queueables so an uncatchable failure is at least recorded.

77 Email notifications silently stop sending. No exceptions anywhere.Medium

The daily single-email or mass-email limit, which is org-wide and fails quietly rather than throwing in your code path.

Monitor it, and reconsider whether email is the right channel for high-volume notification — platform events, custom notifications or an external messaging service scale better and do not share a daily cap with everything else.

78 Ten subscribers listen to one platform event. Your event allocation disappears.Hard

Both publishing and delivery to each subscriber consume allocation, so ten subscribers multiply consumption roughly tenfold.

Fix by consolidating subscribers (one subscriber that fans out internally), keeping payloads thin, and reviewing whether every subscriber genuinely needs every event. See allocations.

79 How do you find out you are approaching a limit before breaching it?Medium

Instrument it. Capture Limits.getCpuTime(), query and DML counts and heap at key points, compare against Limits.getLimitX(), and warn at around 60% — publishing a platform event so the warning is visible in production where debug logs are not.

At org level, monitor storage, daily API calls, async executions and scheduled job counts on a schedule with alerting. These are the limits that fail silently. See instrumenting limits.

80 An unbounded SOQL query has worked for three years. Is it fine?Easy

It is an incident with a date on it. An unbounded query works until the data crosses the row limit or the selectivity threshold, and then fails — usually at the worst possible time, with no code change to blame.

Bound every collection with a LIMIT you chose deliberately, and handle the case where there is more data than you fetched.

Product fit & the wider platform (81–90)

81 The business wants appointment booking. Salesforce Scheduler or Field Service?Medium

Scheduler if the customer comes to you — branch meetings, advisers, consultations — where travel is irrelevant and there are no parts. Field Service if you send people to places to do work, where drive time is the dominant cost and you need assets, inventory and an offline mobile app.

The test: if nobody drives anywhere and nothing gets fitted, Field Service is expensive machinery you will not use. See the comparison.

82 Standard quoting is not enough. When is CPQ justified?Medium

When you need configurable bundles with options and rules, discount schedules, subscription pricing, amendments mid-term and renewals. Standard Products, Price Books and Schedules cover simple catalogue selling and stop abruptly after that.

Be clear about the cost: CPQ configuration is largely data, so it brings its own migration and regression problem. See CPQ.

83 A stakeholder asks for "a dashboard like Tableau" inside Salesforce.Medium

Clarify what they actually need. Standard reports and dashboards for operational, live, single-object-plus-children data — free and buildable by anyone. CRM Analytics for blended Salesforce data, trending and large datasets embedded in CRM. Tableau for enterprise BI across many non-Salesforce sources.

The decision point: "do I need to join data Salesforce reporting cannot join, or trend beyond what snapshots hold?" If not, a report is cheaper to build and far cheaper to maintain. See choosing a tool.

84 Marketing wants email. Account Engagement or Marketing Cloud Engagement?Medium

Account Engagement (Pardot) for B2B: prospect nurture, scoring and grading, tight CRM integration, modest volumes. Marketing Cloud Engagement for B2C scale, cross-channel journeys, and complex data-driven personalisation.

The B2C platform's Contact Key decision is effectively permanent, so if that is the direction, settle it with the CRM team on day one. See Marketing.

85 Does an AppExchange package need its own review before you install it?Medium

Yes, regardless of its security review status. Install in a sandbox and check: what triggers, flows, validation rules and fields it adds to your objects; how much CPU it adds to your transactions; what data leaves your org and to where; the upgrade path; and what uninstalling actually leaves behind.

Also plan the exit before you depend on it. See ISV discipline.

86 When is Data Cloud the right answer rather than more custom objects?Hard

When you need a unified profile across systems with identity resolution, very large volumes, calculated insights across the lake, or activation of segments to other channels — and particularly when the data already lives in a warehouse, where zero copy avoids ingesting it twice.

It is not a cheaper custom object. It meters on consumption, and identity resolution is a business decision with real over-merge and under-merge consequences. See Data Cloud.

87 A stakeholder asks for an AI agent on day one of a new implementation.Hard

Sequence it honestly: AI amplifies whatever data and process you already have. On a new implementation there is no transcript history, no clean knowledge base and no measured baseline, so there is nothing to ground against and nothing to prove improvement against.

Deliver the core process first, instrument it, clean the knowledge content, then add agents against a measured baseline. Saying that costs you a little enthusiasm and saves a failed pilot. See Agentforce.

88 Do you build it, buy it from AppExchange, or integrate an existing system?Medium

Decide on three axes: is this a differentiating capability (build) or a commodity (buy); does a system of record already exist elsewhere (integrate, do not duplicate); and what is the total cost of ownership including upgrades, limits consumption and the exit.

The common failure is building a commodity because it felt easy in a demo, then maintaining it for eight years.

89 Experience Cloud or a custom front end against the APIs?Medium

Experience Cloud when you want speed, built-in identity, sharing and CMS, and your UX needs are within its templates — LWR for public and performance-sensitive sites. A custom front end when the UX is genuinely bespoke or must live inside an existing app, using headless identity and the APIs.

Be honest about the cost of custom: you now own authentication, authorisation surfaces, accessibility and every security review finding yourself.

90 The business asks for "real-time" integration. What do you ask back?Hard

Decompose it into a number. "Real-time" usually means one of: the user must see it before finishing the task (under ~2 seconds — synchronous request-reply), within seconds but nobody is waiting (platform events), within minutes (events plus reconciliation), or overnight is fine (batch, and far cheaper to run).

Very often the real requirement is "I don't want to explain stale data", which a visible last synced timestamp solves better than any architecture. See latency budgeting.

Judgement calls (91–100)

91 A requirement would need 14 automations on Account. What do you say?Hard

Not "no" — "not like that". Document the existing execution tree first (a debug log of one Account save shows what actually runs, including the automations nobody remembered), then consolidate toward one entry point per object per timing with explicit ordering.

Deliver the requirement inside that structure, incrementally and behind tests, so each consolidation is attributable if something regresses. And add a bypass switch while you are in there.

92 A stakeholder insists on a field that duplicates data already on the parent.Medium

Ask the diagnostic question: does the value need to be filterable, sortable or usable in automation on this object, or does someone just need to see it? If the latter, a cross-object formula field or the related record's layout solves it with no duplication and no sync problem.

If it genuinely must be stored (selectivity at volume, point-in-time snapshot), say so explicitly and own the sync mechanism — denormalisation is a legitimate choice when it is a decision rather than an accident.

93 You are asked to estimate a piece of work you have never done on the platform.Medium

Separate the known from the unknown and price the unknown as a spike. Give a range with the assumptions stated, name the specific thing you need to prove (does this metadata deploy? does this API support this volume? does this licence include this object?), and timebox a proof of concept.

An estimate with explicit assumptions is defensible when it moves. A single confident number is not.

94 A developer wants to use a brand-new beta feature in a critical path.Medium

Check three things before opinions: GA status and SLA, Metadata Coverage (can you even deploy it?), and whether there is a supported fallback.

Beta features in a critical path mean you own the risk with no support commitment. Use them where failure is recoverable, and keep the critical path on GA functionality — or carry the feature behind a flag you can switch off.

95 The business wants a change live tomorrow and your release is in two weeks.Medium

That is what a hotfix path is for: branch from main (never develop, which holds unreleased work), fix with a test, validate against production, deploy, tag — then forward-merge main into develop and every open release branch the same day.

If you do not have that path, build it, because the alternative is someone changing production directly and you never seeing it. See hotfixes.

96 You discover a security hole in production during a release.Hard

Contain first: if a user or integration is the vector, freeze the user and revoke tokens — freeze is instant and reversible, unlike deactivation. Restrict the surface (profile permission, guest access, site) rather than attempting an elegant fix under pressure.

Then assess exposure with Event Monitoring and Setup Audit Trail, fix forward through the hotfix path with a test, and write up what made it reachable. Containment before diagnosis, diagnosis before elegance.

97 Your predecessor built everything with without sharing. Where do you start?Hard

Inventory and triage, not a rewrite. Find every without sharing class and classify: genuinely needs elevation (document why), should be with sharing, or should be inherited sharing because it is a library called from multiple contexts.

Prioritise anything reachable from an @AuraEnabled method on a guest-accessible page or a REST endpoint — that is an exfiltration path, not a code-style issue. Remember inner classes do not inherit the outer declaration. See sharing keywords.

98 A report shows different numbers from a CRM Analytics dashboard on the same data.Hard

Nearly always a join in the data prep: an inner join silently dropping rows with no match, or a one-to-many join multiplying rows so every subsequent sum is inflated.

Check row counts after every join node in the recipe and reconcile the dataset total against the Salesforce report before anyone builds on it. The second candidate is a security predicate filtering rows for the viewing user. See CRM Analytics.

99 You are the only Salesforce person and everything is urgent. How do you choose?Medium

Rank by irreversibility and blast radius, not by who asked loudest: security exposure first, then data integrity (silent corruption is worse than visible downtime), then blocked revenue-generating work, then everything else.

Then spend some of the remaining time on the things that reduce future urgency — drift detection, error logging, a bypass switch, a fast hotfix path. Pure reaction never ends on its own.

100 What single habit prevents the most production incidents on this platform?Hard

Making every change reversible, observable and bounded. Concretely: no hard-coded Ids; bypass switches on every automation; structured error logging via platform events so records survive a rollback; bounded queries and collections; and a tag per release so "deploy the last known good state" is one command.

None of it is clever. All of it is the difference between a bad afternoon and a bad quarter — and it costs about a day each to put in place.
