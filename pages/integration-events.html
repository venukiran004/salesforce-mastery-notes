Platform Events, CDC & Salesforce Connect

Event-driven integration — publishing and subscribing instead of polling — plus how to read external data live without ever copying it into Salesforce.

Request-reply vs event-driven

Tight coupling vs loose coupling

Platform Events

A Platform Event is a custom-defined message — like a custom object, but the "records" are immutable messages on an event bus rather than rows in a table.

Defining one

  • Setup → Platform Events → New Platform Event. API name gets the suffix __e, e.g. Order_Shipped__e.
  • Choose the publish behaviour: Publish After Commit (only if the transaction succeeds — the safe default) or Publish Immediately (fires even if the transaction later rolls back — use for logging).
  • Add custom fields — Text, Number, Date/Time, Checkbox, Picklist. No lookups (store the Id as Text).
  • Deploy. The event is now publishable and subscribable everywhere.
Publishers and subscribers

Publishing

// ---------- From Apex ----------
List<Order_Shipped__e> events = new List<Order_Shipped__e>();
for (Order o : shippedOrders) {
    events.add(new Order_Shipped__e(
        Order_Number__c = o.OrderNumber,
        Account_Id__c   = o.AccountId,
        Ship_Date__c    = System.now(),
        Carrier__c      = o.Carrier__c,
        Tracking__c     = o.Tracking_Number__c
    ));
}

List<Database.SaveResult> results = EventBus.publish(events);

for (Integer i = 0; i < results.size(); i++) {
    Database.SaveResult sr = results[i];
    if (!sr.isSuccess()) {
        for (Database.Error err : sr.getErrors()) {
            System.debug('Publish failed: ' + err.getStatusCode() + ' ' + err.getMessage());
        }
    }
}
🧾
Two things about publishing ① EventBus.publish() counts as a DML statement against your 150 limit. ② With Publish After Commit, SaveResult.isSuccess() only tells you the event was queued; the actual publish happens at commit. The returned "Id" is a temporary placeholder, not a record Id.
// ---------- Subscribing with an Apex trigger ----------
trigger OrderShippedTrigger on Order_Shipped__e (after insert) {

    List<Task> tasks = new List<Task>();
    List<Order> toUpdate = new List<Order>();

    for (Order_Shipped__e evt : Trigger.new) {
        tasks.add(new Task(
            Subject = 'Order shipped: ' + evt.Order_Number__c,
            WhatId  = evt.Account_Id__c,
            ActivityDate = Date.today()));
    }
    insert tasks;

    // If something goes wrong you can ask the bus to retry this batch
    // EventBus.TriggerContext.currentContext().setResumeCheckpoint(lastReplayId);
}
Platform Event trigger rules
Only after insert exists — events are immutable and never stored as records
Runs asynchronously as the Automated Process user (set the "Platform Event user" in Setup to change this)
Batch size up to 2,000 events per trigger execution — much bigger than the usual 200
No Trigger.old, no Trigger.oldMap; ReplayId and EventUuid are available
An unhandled exception retries the batch, up to 10 times, then discards it
Standard governor limits apply per execution — bulkify as usual
 
// ---------- Subscribing in an LWC with empApi ----------
import { LightningElement } from 'lwc';
import { subscribe, unsubscribe, onError, setDebugFlag } from 'lightning/empApi';

export default class OrderMonitor extends LightningElement {
    subscription = {};
    channel = '/event/Order_Shipped__e';

    connectedCallback() {
        // -1 = only new events · -2 = replay everything retained (last 72 h)
        subscribe(this.channel, -1, (response) => {
            const payload = response.data.payload;
            this.orders = [...this.orders, {
                id      : response.data.event.replayId,
                number  : payload.Order_Number__c,
                carrier : payload.Carrier__c
            }];
        }).then(sub => { this.subscription = sub; });

        onError(error => console.error('EMP error', JSON.stringify(error)));
    }

    disconnectedCallback() {
        unsubscribe(this.subscription, () => {});
    }
}

Retention, replay and delivery guarantees

ConceptDetail
Retention72 hours (High Volume events). Miss the window and the event is gone forever
ReplayIdAn increasing (but not contiguous) id per channel. Store the last one you processed to resume after downtime
-1Subscribe to new events only (from now on)
-2Replay everything still retained, then continue live
Delivery guaranteeAt least once — so your subscriber must be idempotent. Use EventUuid to detect duplicates
OrderingGuaranteed within a channel by ReplayId, but not across channels
AllocationsDaily publish and delivery limits by edition (e.g. 100k published/day in Enterprise, plus per-client delivery caps)
🎯
Use cases ① Order fulfilment — Salesforce publishes Order_Placed__e; the ERP, the warehouse and the billing system each subscribe independently. Adding a fourth consumer requires no change in Salesforce.
② Decoupling heavy work — a trigger publishes an event instead of doing the work; the subscriber trigger runs in its own transaction with fresh limits.
③ Real-time UI — an LWC dashboard updates the moment another user's action publishes an event.
④ Guaranteed logging — publish immediately so the log survives even if the transaction rolls back.

Change Data Capture (CDC)

CDC publishes a change event automatically whenever a record is created, updated, deleted or undeleted — with no code and no configuration beyond ticking the object.

Platform Events vs Change Data Capture
  • Setup → Change Data Capture — move objects into "Selected Entities". Base allocation is 5 standard/custom objects free; more requires an add-on licence.
  • Channel: /data/AccountChangeEvent for standard objects, /data/Invoice__ChangeEvent for custom.
  • Custom channels let you group several objects onto one stream, which keeps related changes ordered.
  • Subscribe with an Apex trigger, a CometD/Pub-Sub client, or empApi in an LWC.
// A CDC event payload
{
  "ChangeEventHeader": {
    "entityName"      : "Account",
    "recordIds"       : ["0015j00000ABCDE"],
    "changeType"      : "UPDATE",           // CREATE | UPDATE | DELETE | UNDELETE | GAP_*
    "changeOrigin"    : "com/salesforce/api/rest/62.0",
    "transactionKey"  : "000f6a1c-...",
    "sequenceNumber"  : 1,
    "commitTimestamp" : 1754969600000,
    "commitUser"      : "0055j000000XXXX",
    "commitNumber"    : 10584327,
    "changedFields"   : ["Industry", "AnnualRevenue", "LastModifiedDate"]
  },
  "Industry": "Banking",
  "AnnualRevenue": 5000000
}
trigger AccountChangeTrigger on AccountChangeEvent (after insert) {

    Set<Id> changedIds = new Set<Id>();

    for (AccountChangeEvent evt : Trigger.new) {
        EventBus.ChangeEventHeader h = evt.ChangeEventHeader;

        // Ignore our own writes to avoid loops
        if (h.getCommitUser() == INTEGRATION_USER_ID) continue;

        if (h.getChangeType() == 'UPDATE'
            && h.getChangedFields() != null
            && new Set<String>(h.getChangedFields()).contains('Industry')) {
            changedIds.addAll(h.getRecordIds());
        }
    }
    if (!changedIds.isEmpty()) {
        System.enqueueJob(new SyncToDataLakeQueueable(changedIds));
    }
}
CDC detailNote
Retention72 hours, same as Platform Events
Only changed fieldsThe payload includes changed fields plus the header — not the whole record
Bulk changesOne event can carry multiple recordIds when a bulk operation changed many rows identically
GAP eventsGAP_CREATE, GAP_UPDATE… mean Salesforce couldn't generate a full event (e.g. a very large transaction). Re-query the record
SecuritySubscribers need "View All Data" or the specific CDC permission — CDC is not filtered by sharing
Doesn't fire forSome system/derived updates such as certain roll-up recalculations and archived data
Loop dangerIf your subscriber writes back to the same object, filter by commitUser or a flag field
🎯
Use case A data warehouse must mirror Salesforce in near real time. Nightly batch extracts are too slow and full extracts are wasteful. Enable CDC on Account, Contact and Opportunity, and a Kafka/Pub-Sub consumer streams only the deltas into Snowflake within seconds.

CometD vs Pub/Sub API The classic Streaming API uses CometD (long polling over HTTP with Bayeux). The newer Pub/Sub API uses gRPC with Avro — a single API for publishing and subscribing to Platform Events and CDC, with better throughput, flow control and language support. Use Pub/Sub API for any new external subscriber.

Salesforce Connect & external objects

Instead of copying external data into Salesforce, Salesforce Connect reads it live on every request. The data stays in the source system; Salesforce just renders it.

// Skeleton of a custom Apex adapter
global class ErpDataSourceConnection extends DataSource.Connection {

    override global List<DataSource.Table> sync() {
        List<DataSource.Column> columns = new List<DataSource.Column>();
        columns.add(DataSource.Column.text('ExternalId', 255));
        columns.add(DataSource.Column.url('DisplayUrl'));
        columns.add(DataSource.Column.number('Amount', 16, 2));
        return new List<DataSource.Table>{ DataSource.Table.get('Invoice', 'ExternalId', columns) };
    }

    override global DataSource.TableResult query(DataSource.QueryContext ctx) {
        // Translate the SOQL context into a REST call, map the response back
        return DataSource.TableResult.get(ctx, fetchRowsFromErp(ctx));
    }
}

Relationship types for external data

  • External Lookup — a standard/custom/external object points to a parent external object, matching on the parent's External Id.
  • Indirect Lookup — an external object points to a parent Salesforce object, matching on a custom External Id field on the parent.
  • Lookup — an external object can also use a standard lookup to a Salesforce record when the external data holds the actual 18-char Id.
🎯
Use case Twelve million historical invoices live in SAP. Copying them into Salesforce would cost a fortune in storage and be stale within a day. With Salesforce Connect, an Invoice__x external object appears as a related list on the Account, agents click through to live invoice data, and nothing is ever copied.
⚖️
When NOT to use Salesforce Connect If you need triggers, flows, full reporting, offline mobile access or fast list views over the data — copy it in instead (Bulk API or CDC-based replication). Connect trades functionality and reliability for zero storage and zero staleness. Also note the per-hour callout allocations on external object queries.

Interview questions

1 Platform Events vs Change Data Capture — the core distinction.Easy

Platform Events: you define the payload and decide when to publish. It's a business event — "Order Shipped" — and it can be published from Apex, Flow, the API or an external system.

CDC: Salesforce defines it and publishes automatically on every create/update/delete/undelete, carrying the changed fields plus a header. It's a data event — "this row changed" — ideal for replicating to a data lake. Both retain 72 hours and deliver at least once.

2 What does "at least once delivery" mean for how you write a subscriber?Hard

It means the same event can be delivered twice — after a retry, a reconnect or a replay. That is documented behaviour, not a bug.

So your subscriber must be idempotent: de-duplicate on EventUuid, or design the action so repeating it is harmless (upsert rather than insert; set a status rather than increment a counter). Ordering is guaranteed within a channel by ReplayId, but not across channels.

3 Publish After Commit vs Publish Immediately — when would you choose each?Medium

Publish After Commit (the safe default): the event only fires if the transaction succeeds. Use it whenever the event asserts something happened — you don't want downstream systems reacting to an order that got rolled back.

Publish Immediately: fires even if the transaction later rolls back. Use it for logging and diagnostics, where you specifically want the record of the attempt to survive the failure.

4 What's special about a Platform Event trigger?Medium

Only after insert exists — events are immutable messages, never stored records, so there is no Trigger.old. It runs asynchronously as the Automated Process user (configurable in Setup). The batch size is up to 2,000 events, far larger than the usual 200. An unhandled exception causes the batch to be retried up to 10 times and then discarded, and you can control resumption with EventBus.TriggerContext.currentContext().setResumeCheckpoint().

5 Your subscriber was down for four days. What happens?Hard

Events are retained for 72 hours — anything older is gone permanently. On reconnect, replaying from your stored ReplayId recovers only what's still in the window; if that ReplayId has aged out you'll get an error and must fall back to -1 (new events only).

This is why event-driven integration needs a reconciliation path: a scheduled job comparing SystemModstamp since the last successful sync, so a long outage can be repaired without the event stream.

6 How do you stop a CDC subscriber from creating an infinite loop?Hard

If the subscriber writes back to the same object, that write generates another change event. Break the cycle by inspecting the header: skip events where ChangeEventHeader.getCommitUser() equals your integration user, or check getChangedFields() and only act when a field you care about actually changed. A flag field (Sync_In_Progress__c) works too but adds storage and its own edge cases. Also watch for GAP events (GAP_UPDATE etc.), which mean Salesforce couldn't produce a full event — re-query the record rather than trusting the payload.

7 Compare the Streaming API family. Which would you pick today?Medium

PushTopic (/topic/) and Generic Events (/u/) are legacy — PushTopic is limited by what its SOQL can express. Platform Events (/event/) and CDC (/data/) are current.

For a new external subscriber, use the Pub/Sub API — gRPC with Avro, one API for both publishing and subscribing, better throughput, flow control and language support than CometD long-polling. Inside the browser, lightning/empApi remains the answer.

8 When is Salesforce Connect the wrong choice?Medium

When you need triggers, flows, full reporting, offline mobile access, or fast list views over the data — external objects support none of those. Also when the source system is slow or unreliable, because every page view depends on it, and when query volume would breach the per-hour callout allocations.

In those cases replicate the data instead: Bulk API for the initial load, CDC or a delta job to keep it current. Connect trades functionality and availability for zero storage and zero staleness.

9 External Lookup vs Indirect Lookup.Hard

External Lookup: the child (standard, custom or external) points to a parent external object, matching on the external object's External Id field.

Indirect Lookup: an external object points to a parent Salesforce object, matching on a custom field on the parent that is marked External Id and Unique. Use it when the external data holds your legacy key rather than an 18-character Salesforce Id — e.g. SAP invoices carrying CUSTNO, matched to Account.Legacy_Id__c.

Quick check

1. Your platform event subscriber processed the same event twice. Is that a bug in Salesforce?
At-least-once delivery is the documented contract. Design the subscriber so re-processing is harmless.
2. You must mirror every Account change into Snowflake within seconds, with no Apex to maintain.
CDC exists exactly for delta replication and requires no code in Salesforce. Connect goes the other direction — reading external data into Salesforce.
3. Which is true of external objects?
External objects hold no data in Salesforce, so triggers, workflow and standard master-detail don't apply.
