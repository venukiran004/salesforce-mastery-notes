Agentforce — A to Z

Salesforce's agentic AI platform: what an agent actually is, how the reasoning engine picks what to do, how you build topics and actions, and how to test, secure, deploy and observe one in production.

🔄
Read the concepts, verify the specifics Agentforce is the fastest-moving area of the platform — names, packaging, limits and licensing change with every release. This module teaches the architecture and the build method, which have been stable: topics, actions, instructions, grounding, the Trust Layer, testing and escalation. Always confirm current feature availability, limits and pricing against official Salesforce documentation before committing to a design.

What Agentforce actually is

An agent is software that is given a goal, decides for itself which steps to take, executes them using tools you provide, and observes the results before deciding what to do next. That last part — the loop — is what separates it from a chatbot or a prompt.

🧠
Topic classification is the part people underestimate Before anything runs, the engine must decide which topic the user's message belongs to. That decision is made from your topic's classification description — so two topics with vague, overlapping descriptions is the single most common cause of an agent "doing the wrong thing". Write descriptions that are specific and mutually exclusive.

The agent flavours

Service agent

Customer-facing on web chat, messaging or a help centre. Answers from Knowledge, checks order status, raises and updates cases, and escalates to a human when it should.

Success metric: deflection rate and CSAT, not conversation count.

Sales agents

SDR-style agents that engage and qualify inbound leads and book meetings, plus coaching agents that role-play pitches and summarise calls.

Watch: anything customer-facing and autonomous needs tight guardrails and clear disclosure.

Employee / internal agents

HR, IT and ops assistants inside Slack or the Salesforce UI — policy questions, provisioning requests, record lookups. Lower risk because the audience is internal.

Usually the right first project.

Custom agents

Built from scratch in Agent Builder for a process specific to your business, with your own topics and actions.

Everything in this module applies most directly here.

Topics — designing the agent's job list

A topic is a bounded job. Getting topic design right matters more than prompt wording.

FieldPurposeHow to write it well
Label / nameHuman identificationA verb phrase: "Check Order Status"
Classification descriptionUsed by the engine to route the request hereDescribe the user intents that belong here, and explicitly what does not. This is the highest-leverage field on the whole agent
ScopeThe boundary of what this topic handlesOne sentence stating what's in and out
InstructionsRules the engine follows once inside the topicShort, imperative, one rule per line; name the action to use for each situation
ActionsThe tools available within this topicOnly the ones this job needs — fewer actions means better selection accuracy
 
# A topic that behaves — note the specificity and the negative cases

Name: Check Order Status

Classification description:
  Use this topic when the customer asks where their order is, whether it has
  shipped, when it will arrive, or for a tracking number. Also use it for
  "has my order been dispatched" and delivery-date questions.
  Do NOT use this topic for returns, refunds, cancellations, or changing a
  delivery address — those belong to Manage Order Changes.

Scope:
  Read-only lookups of existing orders belonging to the authenticated customer.

Instructions:
  - Always confirm the order number before looking anything up.
  - If the customer does not know the order number, use the Find Recent Orders
    action with their contact record; never ask them to guess.
  - Use Get Order Status to retrieve the current status and tracking link.
  - If the order shows as delayed beyond the promised date, apologise once,
    state the new estimate, and offer to escalate to a human agent.
  - Never speculate about a delivery date that the system has not returned.
  - If no order is found, say so plainly and offer to escalate. Do not guess.
✂️
Fewer, sharper topics beat many vague ones Every additional topic makes classification harder. Start with the three or four jobs that cover most of the volume, get them reliable, then add. If two topics keep getting confused, either merge them or rewrite both classification descriptions to state explicitly what they exclude.

Actions — the developer's job

Actions are the only way an agent affects the world. The model chooses which to call and supplies the inputs; everything else is your code.

Action typeUse forNotes
FlowMost business logic — admin-maintainable, no code review neededAutolaunched flow with input/output variables. The usual first choice
ApexComplex logic, aggregates, callouts with retry, anything Flow can't express@InvocableMethod. Must be bulk-safe and well described
Prompt templateGenerating text — a summary, a drafted reply, an explanationGrounded via merge fields; see Prompt Builder

Writing an action the model can actually use

public with sharing class GetOrderStatus {

    /**
     * The label and description are READ BY THE MODEL to decide when to call
     * this action. They are prompt engineering, not documentation — be precise.
     */
    @InvocableMethod(
        label='Get Order Status'
        description='Returns the current status, carrier and tracking URL for a single order, '
                  + 'given its order number. Use when a customer asks where their order is or '
                  + 'whether it has shipped. Returns notFound=true if the order number does not '
                  + 'exist or does not belong to the requesting contact.'
        category='Order Management')
    public static List<Result> run(List<Request> requests) {

        // Bulk-safe: the platform may pass several at once
        Set<String> numbers = new Set<String>();
        for (Request r : requests) numbers.add(r.orderNumber);

        Map<String, Order> byNumber = new Map<String, Order>();
        for (Order o : [SELECT OrderNumber, Status, Carrier__c, Tracking_URL__c,
                               EffectiveDate, Account.Name
                        FROM Order
                        WHERE OrderNumber IN :numbers
                        WITH USER_MODE]) {          // respects the agent user's access
            byNumber.put(o.OrderNumber, o);
        }

        List<Result> out = new List<Result>();
        for (Request r : requests) {                 // same size, same order — required
            Result res = new Result();
            Order o = byNumber.get(r.orderNumber);
            if (o == null) {
                res.notFound = true;
                res.summary  = 'No order found with that number.';
            } else {
                res.notFound    = false;
                res.status      = o.Status;
                res.carrier     = o.Carrier__c;
                res.trackingUrl = o.Tracking_URL__c;
                res.summary     = 'Order ' + o.OrderNumber + ' is ' + o.Status + '.';
            }
            out.add(res);
        }
        return out;
    }

    public class Request {
        @InvocableVariable(required=true
            label='Order Number'
            description='The customer-facing order number, e.g. ORD-10024.')
        public String orderNumber;
    }

    public class Result {
        @InvocableVariable(label='Not Found'
            description='True when no matching order exists. The agent should say so and offer to escalate.')
        public Boolean notFound;
        @InvocableVariable(label='Status') public String status;
        @InvocableVariable(label='Carrier') public String carrier;
        @InvocableVariable(label='Tracking URL') public String trackingUrl;
        @InvocableVariable(label='Summary'
            description='A one-sentence summary the agent can relay directly to the customer.')
        public String summary;
    }
}

✅ What makes an action agent-ready

  • Description written for the model — say when to use it and what it returns, including failure cases
  • Every input and output has a clear @InvocableVariable description
  • Narrow scope — one action, one job. Don't build a "do everything" action with a mode flag
  • Returns a structured failure (notFound) rather than throwing, so the agent can respond gracefully
  • Includes a human-readable summary the agent can relay
  • WITH USER_MODE / with sharing so the agent user's access applies
  • Bulk-safe, and returns a list the same size and order as the input

❌ What breaks agents

  • Description like "Handles orders" — the model can't tell when to use it
  • Throwing an exception on a normal miss; the agent surfaces a raw error
  • Actions with 15 optional parameters — the model fills them wrongly
  • Side effects the description doesn't mention (an action named "get" that also writes)
  • Long free-text outputs that blow the context window
  • Running without sharing so the agent can read anything
  • Non-idempotent write actions with no confirmation step
⚠️
The description IS the interface With a normal API, a developer reads docs and writes the call. Here a language model reads your label and description and decides. A vague description isn't a documentation problem — it's a functional bug that makes the agent call the wrong tool. Review action descriptions as carefully as you review the code.

Grounding — where the agent's knowledge comes from

The model knows nothing about your business. Everything relevant must be supplied at runtime.

SourceGives the agentWatch out for
Conversation contextWhat's been said so far, plus who the user isContext windows are finite — long chats lose early detail
Record contextThe record the agent was launched from and its related dataOnly what the agent user can see
Knowledge articles (RAG)Policy and how-to answers retrieved by relevanceGarbage articles produce confident wrong answers. Curate first
Data Library / indexed filesPDFs, docs and web content chunked and indexed for retrievalChunking quality drives answer quality
Data CloudUnified profile — web behaviour, purchases, engagement across systemsSee Data Cloud
Action resultsLive data fetched mid-conversationThe most reliable grounding — real, current, scoped
🎯
Retrieval beats recall If an answer must be exact — a price, a policy clause, an order status — fetch it with an action rather than hoping retrieval surfaces the right article. Reserve RAG for open-ended "how do I…" questions where an approximate, cited answer is genuinely fine.

Building one, step by step

  • Pick a narrow, high-volume, low-risk job. "Answer order-status questions" beats "handle all support". You need a measurable baseline.
  • Turn on the prerequisites — Einstein/Agentforce settings, the Data Cloud or Knowledge grounding you'll use, and channel setup.
  • Create the agent user and a dedicated permission set with the minimum object, field and record access the job needs.
  • Build the actions first, as Flows or invocable Apex, and unit-test them independently of the agent. An agent is only as good as its tools.
  • Create the agent in Agent Builder: role, company context, and the tone/behaviour you expect.
  • Add topics, one per job, with sharp classification descriptions and explicit instructions naming the actions.
  • Attach grounding — Knowledge, Data Library, Data Cloud, record context.
  • Test in the conversation preview, watching the reasoning trace to see which topic and action it picked and why.
  • Build a test set in Testing Center — real utterances, including rude, ambiguous and out-of-scope ones.
  • Define escalation before go-live: when it hands to a human, and how context transfers.
  • Pilot on one channel with a small audience, review transcripts daily, and fix classification and descriptions.
  • Deploy and monitor — track containment, escalation, CSAT and action failure rates.

Testing an agent

🎲
Non-deterministic systems need a different test strategy The same question can produce different wording each time. You cannot assert on exact strings. You assert on behaviour: did it pick the right topic, call the right action with the right inputs, and stay inside policy?
LayerHow you test it
ActionsOrdinary Apex tests and Flow debug — deterministic, so test them properly here rather than through the agent
Topic classificationA test set of real utterances mapped to the expected topic. This is where most failures live
Action selectionAssert the expected action was invoked with the expected inputs
Response qualityHuman review, plus automated checks for policy phrases and forbidden content
AdversarialPrompt injection ("ignore your instructions"), out-of-scope requests, abuse, attempts to get it to promise refunds
RegressionRe-run the whole test set after any change to topics, descriptions or actions — small wording edits shift classification

Testing Center lets you run a batch of test utterances against the agent and review the results in bulk, which is far more reliable than ad-hoc chatting in the preview pane.

Security & guardrails

The blast radius is the agent user's permissions

Platform controls

  • Dedicated agent user, least privilege, never an admin
  • Trust Layer: PII masking, secure retrieval, toxicity detection, zero retention, audit
  • Grounding respects sharing and FLS automatically
  • Action-level control — an action only exists if you add it to a topic
  • Full audit trail of prompts, responses and actions taken

Design controls you must add

  • Read before write. Start with read-only actions; add writes deliberately
  • Confirmation before anything irreversible or financial
  • Caps in the action, not the prompt — never rely on "don't refund over £50" as an instruction; enforce it in Apex
  • Explicit escalation path and triggers
  • Disclosure that the user is talking to an AI
  • Rate limiting and abuse handling on public channels
🛑
Never enforce a business rule in natural language alone "Do not issue refunds above £50" in a topic instruction is a suggestion to a probabilistic system, and prompt injection can talk it out of it. Put the cap in the action's code, where it is deterministic and testable. Treat instructions as guidance for behaviour, never as a security boundary.

Observability & improvement

Watch

  • Containment / deflection rate
  • Escalation rate and reasons
  • Topic classification accuracy
  • Action failure rate
  • Latency per turn
  • CSAT after agent conversations

Read

  • Transcripts — daily at first
  • The reasoning trace: chosen topic, chosen action, inputs
  • Sessions ending without resolution
  • Repeated user rephrasing (a classification failure signal)

Improve

  • Sharpen classification descriptions
  • Split or merge confused topics
  • Fix or add actions
  • Improve the Knowledge articles behind bad answers
  • Re-run the regression set
📉
The metric that matters Not "how many conversations did the agent handle" — that rewards a chatty agent. Track successful containment (resolved without a human, and the customer didn't come back within 7 days) against CSAT. An agent with high containment and falling CSAT is deflecting people, not helping them.

When not to build an agent

🧭
The senior answer If the process is deterministic and well understood, a Flow or a screen is cheaper, faster, testable and auditable. Agents earn their cost where input is unstructured natural language and the path varies — that's the capability nothing else on the platform has. "We could use an agent" is not the same as "an agent is the right tool".

Good fit

  • High volume of varied, free-text questions
  • Answers exist in Knowledge or records
  • A human reviews anything consequential
  • A measurable baseline exists (handle time, deflection)
  • Failure is recoverable
vs

Poor fit

  • A fixed, known process → build a Flow
  • Regulated advice with no human in the loop
  • The underlying data is poor
  • Irreversible financial actions with no confirmation
  • Nobody owns monitoring it after launch

Interview questions

1 What makes an agent different from a chatbot or a prompt?Easy

A chatbot follows dialog trees an author wrote — it breaks on unexpected phrasing. Generative AI produces text when you call it, but decides nothing. An agent is given a goal, then chooses which actions to run, executes them, observes the results and re-plans until the request is handled.

The engineering consequence is the point worth making: you stop designing conversations and start designing capabilities, permissions and guardrails, because the system decides the path, not you.

2 Explain topics, actions and instructions.Easy

A topic is one job the agent can do, with a classification description the reasoning engine uses to route requests to it. Actions are the concrete things it can execute — Flows, Apex invocables, prompt templates, API calls — and are the only way it affects anything. Instructions are natural-language rules inside a topic saying when to use which action and what never to do.

Summary: the model decides which action; you decide what actions exist and what they can touch.

3 The agent keeps answering the wrong kind of question. Where do you look first?Hard

Topic classification descriptions. That text is what the engine uses to route the request, and overlapping or vague descriptions are the most common root cause by a wide margin.

Fix by rewriting each description to state the intents it covers and explicitly what it excludes, using the words real users use. Check the reasoning trace to confirm which topic was chosen. If two topics keep colliding, either merge them or make the boundary explicit in both. Then re-run the regression set — classification is sensitive to wording.

4 What's the developer's actual job on an Agentforce project?Medium

Building and securing the actions, and the grounding they return. Concretely: bulk-safe @InvocableMethod Apex and Flows with descriptions written for the model, precise @InvocableVariable descriptions, structured failure returns rather than exceptions, WITH USER_MODE enforcement, and business rules implemented in code rather than left to instructions.

Plus the engineering around it: unit tests for actions, the regression test set, and observability so you can see what the agent actually did.

5 How do you stop an agent doing something harmful?Hard

Layered. Permissions first — a dedicated agent user with least privilege, because its profile and sharing define the entire blast radius; grounding is filtered by the same access. Capability — an action only exists if you added it, so start read-only and add writes deliberately. Code-level limits — enforce caps and rules inside the action, never in an instruction, because a prompt-injected user can argue with natural language but not with Apex. Process — confirmation before irreversible steps, a defined escalation path, disclosure that it's an AI, full audit logging, and adversarial testing.

6 How do you test something non-deterministic?Hard

You don't assert exact strings. Test in layers: actions with ordinary deterministic Apex/Flow tests; classification with a set of real utterances mapped to expected topics; action selection by asserting the right action ran with the right inputs; response quality by human review plus checks for forbidden content; and adversarial cases — prompt injection, abuse, out-of-scope requests.

Then treat it as regression: re-run the whole set after any change to descriptions or actions, because small wording edits move classification.

7 Why is an action's description so important?Medium

Because a language model reads it to decide whether to call the action. With a normal API a developer reads docs; here the description is the interface. "Handles orders" gives the model nothing to discriminate on, so it calls the wrong tool or none.

A good description states what the action does, when to use it, what it returns, and what happens on failure — in the language users actually use. Review descriptions as carefully as code, and version them, because changing one changes behaviour.

8 A stakeholder wants an agent for a fixed 5-step approval process. Advise them.Medium

Push back. A deterministic, well-understood process should be a Flow or an approval process — cheaper, faster, fully testable, auditable and free of hallucination risk. Agents cost consumption credits and need ongoing monitoring.

Agents earn their keep where the input is unstructured natural language and the path varies. If there's a natural-language front door to that process — "how do I get this approved?" — an agent could route and explain, then hand off to the deterministic Flow to actually execute. That hybrid is usually the right answer.

9 How do you measure whether the agent is working?Hard

Not conversation volume — that rewards chattiness. Track successful containment: resolved without a human and the customer didn't return within a week. Pair it with CSAT, because containment alone can mean you're deflecting people rather than helping.

Also monitor escalation rate and reasons, topic classification accuracy, action failure rate and latency per turn. Establish the baseline before launch, or you can't prove impact.

10 Walk me through your first Agentforce project plan.Hard
  1. Pick one narrow, high-volume, low-risk job with a measurable baseline — internal IT/HR Q&A or order status, not "all of support".
  2. Audit the grounding data first. Poor Knowledge articles guarantee poor answers regardless of configuration.
  3. Create the agent user and least-privilege permission set.
  4. Build and unit-test the actions before touching the agent.
  5. Create the agent, then 2–3 sharp topics with explicit classification descriptions.
  6. Build a test set from real transcripts, including messy and adversarial input.
  7. Define escalation and disclosure before go-live.
  8. Pilot small, read transcripts daily, iterate on descriptions.
  9. Scale to more topics only once containment and CSAT hold.

Quick check

1. An agent must never refund more than £50. Where do you enforce it?
Natural-language instructions are guidance to a probabilistic system and can be argued away by prompt injection. Deterministic rules belong in code.
2. What determines everything an agent can read or change?
Actions and grounding both execute in the agent user's context, so its profile, permission sets and sharing define the entire blast radius.
3. Which field most directly decides whether a request reaches the right topic?
The reasoning engine routes on the classification description — vague or overlapping descriptions are the number one cause of an agent doing the wrong thing.
