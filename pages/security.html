Security & Sharing

Who can log in, which objects they see, which fields they see, and which records they see. Four independent layers — and record-level access is the one everybody finds hard.

The data security model

Salesforce security is layered and restrictive by default: access must be granted at every layer. A user who has "Read" on Account but no record access sees an empty list; a user with record access but no object permission sees nothing at all.

Four layers of access — all must pass
🧠
The mental model Layers 1–3 are restrictive (you need permission). Layer 4 is additive — OWD sets the floor, and everything else only ever opens up access. Nothing at record level can take access away (except Restriction Rules, the modern exception).

1 · Organisation-level security

Login restrictions

  • Login IP Ranges (Profile) — hard block outside the range
  • Trusted IP Ranges (Network Access) — inside = no verification code; outside = challenge, not block
  • Login Hours (Profile) — deny logins outside working hours

Authentication

  • MFA — mandatory for all Salesforce logins
  • SSO — SAML / OpenID Connect against your IdP
  • Session settings — timeout, lock to IP, high-assurance sessions

Auditing

  • Login History — who logged in, from where
  • Setup Audit Trail — last 6 months of config changes
  • Field History Tracking — up to 20 fields per object
  • Event Monitoring (Shield) — full API/UI telemetry

Shield

  • Platform Encryption — encrypt at rest
  • Event Monitoring
  • Field Audit Trail — up to 10 years of history

Permission architecture — the modern approach

Permission Set Groups & Muting

  • A Permission Set Group bundles permission sets for a job function (e.g. "Sales Manager").
  • A Muting Permission Set inside the group removes specific permissions the constituent sets grant — the only subtractive tool in the permissions model.
  • Groups are recalculated asynchronously after changes; the status shows as "Updating".

The dangerous permissions

PermissionEffectScope
View AllSee every record of one object, ignoring sharingPer object
Modify AllEdit/delete every record of one object, ignoring sharingPer object

Modify All DataEdit/delete everythingOrg-wide

🚨
Interview favourite "View All Data" bypasses OWD, role hierarchy and sharing rules — but it does not bypass Field-Level Security. Only Modify All Data plus FLS grants edit everything. Audit these permissions regularly.

3 · Field-Level Security

FLS is set per field per profile/permission set: Visible and Read-Only checkboxes.

  • FLS is enforced in the UI, reports, list views, search and the API — a hidden field simply isn't returned.
  • Apex ignores FLS by default. That's a security review failure. Enforce it explicitly:
// 1. Query-level enforcement (recommended, API 48+)
List<Account> accs = [SELECT Id, Name, AnnualRevenue FROM Account WITH USER_MODE];

// or the older form
List<Account> accs2 = [SELECT Id, Name FROM Account WITH SECURITY_ENFORCED];

// 2. DML in user mode (API 55+)
Database.insert(newAccounts, AccessLevel.USER_MODE);

// 3. Strip fields the user can't see (great for building JSON responses)
SObjectAccessDecision d = Security.stripInaccessible(AccessType.READABLE, accs);
List<Account> safe = (List<Account>) d.getRecords();

// 4. Manual describe check
if (Schema.sObjectType.Account.fields.AnnualRevenue.isAccessible()) { /* ... */ }
if (Schema.sObjectType.Account.isUpdateable()) { /* ... */ }
ApproachBehaviour on violationUse when
WITH USER_MODEThrows QueryExceptionDefault choice — also enforces sharing
WITH SECURITY_ENFORCEDThrows exceptionLegacy orgs (FLS/CRUD only, not sharing)
stripInaccessibleSilently removes fieldsReturning data to LWC/API without hard failure
Describe checksYou decideFine-grained conditional UI

4 · Record-level security

Everything below answers one question: which rows of an object can this user see? Start closed with OWD, then open access up.

Record access decision order

Org-Wide Defaults (Sharing Settings)

Setup → Sharing Settings. Set per object, and separately for internal and external users.

OWD valueMeaningTypical for
PrivateOnly the owner (and people above them in the hierarchy) can see itOpportunity, Case in competitive orgs
Public Read OnlyEveryone can view, only owner/hierarchy can editAccount, Contact
Public Read/WriteEveryone can view and editReference data
Public Read/Write/TransferPlus change ownerLead, Case only
Controlled by ParentInherits from the master recordMaster-Detail children, Contact under Account
Public Full AccessView/edit/transfer/deleteCampaign only
📉
Golden rule Set OWD to the most restrictive level any user should have, then open up. You cannot use sharing rules to restrict — if OWD is Public Read, no sharing rule can hide a record. Also: "Grant Access Using Hierarchies" can be unticked for custom objects only.

Role hierarchy

Access flows upward, never sideways
  • Role hierarchy grants upward access only. Peers see nothing of each other by default.
  • A role is not the job title — it exists purely for data visibility. Two VPs who must not see each other's data belong on separate branches.
  • Max 500 roles; keep the hierarchy under ~10 levels for performance.

Sharing rules

Owner-based

"Records owned by members of Role X are shared with Public Group Y at Read/Write."

Criteria-based

"Records where Country = 'India' are shared with Role Z." Field values drive it, not ownership.

  • Share to: Roles, Roles & Subordinates, Public Groups, Territories, Portal roles.
  • Access level: Read Only or Read/Write (never less than OWD).
  • Limits: 300 rules per object (50 criteria-based). Changing them triggers a sharing recalculation — do it in a maintenance window for large orgs, or use deferred sharing calculation.
  • Guest user sharing rules are a separate, restricted category (Read-only, no criteria-based on some objects).

Restriction & scoping rules (the modern additions)

Restriction Rule

Removes access that sharing granted — the only true subtractive record control. "Even though Reps can see all Cases, HR Cases are visible only to HR."

Applies to list views, reports, SOQL, API. Does not apply to users with View All Data.

Scoping Rule

Changes the default filter, not access. "Reps see only their region's records by default, but can still switch the filter." A UX convenience, not a security control.

⚠️
Triggers always run in system context A trigger itself ignores sharing. If your trigger calls a handler, declare that handler with sharing or inherited sharing when the logic should respect the user's access.

Apex Managed Sharing

Programmatically share a record by inserting into the object's share table: AccountShare for standard objects, MyObject__Share for custom ones.

public without sharing class ProjectSharingService {

    // Share a custom object record with a user at Read access
    public static void shareWithUser(Id projectId, Id userId) {
        Project__Share share = new Project__Share();
        share.ParentId       = projectId;              // the record
        share.UserOrGroupId  = userId;                 // who gets access
        share.AccessLevel    = 'Read';                 // Read | Edit | All
        share.RowCause       = Schema.Project__Share.RowCause.Manual;
        // Custom reason (Apex sharing reason) survives owner changes:
        // share.RowCause = Schema.Project__Share.RowCause.Team_Member__c;

        Database.SaveResult sr = Database.insert(share, false);
        if (!sr.isSuccess()) {
            System.debug('Share failed: ' + sr.getErrors()[0].getMessage());
        }
    }

    // Recalculate: delete Apex shares then rebuild
    public static void revoke(Id projectId, Id userId) {
        delete [SELECT Id FROM Project__Share
                WHERE ParentId = :projectId
                  AND UserOrGroupId = :userId
                  AND RowCause = 'Manual'];
    }
}
Share record fieldMeaning
ParentId (or AccountId for standard)The record being shared
UserOrGroupIdUser, public group, role group or queue receiving access
AccessLevelRead / Edit / All (All is reserved for the owner)
RowCauseWhy the share exists. Custom Apex Sharing Reasons survive owner changes; Manual shares don't
💡
Requirements Apex sharing only works when the object's OWD is more restrictive than Public Read/Write. Apex Sharing Reasons are available on custom objects only, and are defined in the object's setup page.

Debugging "why can't they see this record?"

  • Check the object permission — Profile/Permission Sets → does the user have Read on the object?
  • Check FLS — is the field visible for their profile?
  • Open the record → Sharing button — shows every reason a user has access.
  • Use "Login As" the user to reproduce it exactly.
  • Check OWD for the object, and whether "Grant Access Using Hierarchies" is on.
  • Look for Restriction Rules — the newest cause of unexplained invisibility.
  • Query the share table: SELECT UserOrGroupId, AccessLevel, RowCause FROM AccountShare WHERE AccountId = '001…'

Interview questions

1 Explain the Salesforce security model to a new admin in under two minutes.Easy

Four layers, all of which must pass. Org — can you log in (MFA, IP ranges, login hours)? Object — can you see this type of record (profiles and permission sets, CRUD)? Field — can you see this column (FLS)? Record — can you see this specific row (OWD, role hierarchy, sharing rules, manual/team/Apex sharing)?

The key nuance: layers 1–3 are restrictive — you need explicit permission. Layer 4 is additive — OWD sets the floor and everything else only opens access up. The single exception is a Restriction Rule.

2 Profile vs Permission Set — what's the modern best practice?Easy

Assign the "Minimum Access – Salesforce" profile to everyone and grant all capability through Permission Set Groups built per job function. A user has exactly one profile but many permission sets, so onboarding becomes "assign one group" rather than "clone and maintain another profile". Profiles are also being de-emphasised by Salesforce. Add a Muting Permission Set inside a group when you need to subtract a specific permission the constituent sets grant.

3 Does with sharing enforce field-level security?Hard

No — and this is the most common security-review failure. It enforces record-level sharing only: which rows the user can see. FLS and object CRUD need explicit handling: WITH USER_MODE on the query, AccessLevel.USER_MODE or insert as user on DML, Security.stripInaccessible() when returning data to an LWC, or describe checks like isAccessible(). Also remember triggers always run in system context.

4 OWD is Private on Opportunity. Give three ways to open access, and when each is right.Medium
  1. Role hierarchy — a manager should see their team's deals. Vertical access, zero maintenance.
  2. Sharing rule — owner-based ("records owned by the India role go to the India Support group") or criteria-based ("all records where Type = Partner"). This is lateral access between peers.
  3. Opportunity Teams / manual sharing — one-off collaboration on a specific deal.

Escalate to Apex managed sharing only when the rule can't be expressed declaratively, and to View All only when the user genuinely needs every record of that object.

5 A user's manual share disappeared after the record changed owner. Why, and how do you make it stick?Hard

Shares with RowCause = 'Manual' are deleted automatically on owner change — the platform assumes the new owner will decide who else needs access. To make a programmatic share survive, insert into the share object with a custom Apex Sharing Reason (defined on the custom object) rather than Manual: share.RowCause = Schema.Project__Share.RowCause.Team_Member__c;. Apex Sharing Reasons are available on custom objects only.

6 Distinguish View All, Modify All, View All Data and Modify All Data.Medium

View All / Modify All are per object and bypass sharing for that object only — the right tool for "support must see every Case". View All Data / Modify All Data are org-wide across every object and should be limited to a handful of admins.

Important detail: none of them bypass field-level security. A user with View All Data still can't see a field hidden by FLS. Audit these permissions regularly — they're the most common cause of accidental data exposure.

7 What is implicit sharing and why does it confuse people?Hard

Built-in, invisible, non-configurable sharing between an Account and its child Contacts, Cases and Opportunities. Access to a child grants Read on the parent Account; access to an Account grants access to children based on the Account's related-object settings. You can't switch it off and it appears in no sharing rule — so it's the usual answer to "why can this user see this record when nothing grants it?" Check the record's Sharing button, which lists every reason.

8 The business says "reps can see all Cases, but HR Cases must be hidden from them." How?Hard

This needs a Restriction Rule — the only feature that removes record access that sharing granted. Define it on Case with a criterion such as RecordType != 'HR' for the relevant user population; it applies to list views, reports, SOQL and the API.

Sharing rules and permission sets can't help because they're purely additive, and tightening OWD would break the "reps see all Cases" requirement. Note restriction rules don't apply to users with View All Data.

Quick check

1. OWD for Opportunity is Private. A sales manager must see their team's opportunities. Simplest solution?
Role hierarchy exists exactly for this. Sharing rules are for lateral access; Modify All Data is a sledgehammer.
2. Which can actually remove record access a user already had?
Sharing rules and permission sets are additive only. Restriction rules (and Muting Permission Sets, for permissions rather than records) are the subtractive tools.
3. Your Apex returns records the running user shouldn't see. The class is declared with sharing. What else could be wrong?
Use WITH USER_MODE on queries or stripInaccessible for field-level enforcement — with sharing only governs which rows are visible.
