Advanced Apex — 100 Scenarios

Patterns, dependency injection, dynamic Apex, caching, finalizers, sharing keywords, packaging and the design decisions that separate a codebase you can evolve from one you can only add to.

📚
How to use this Answer out loud in ninety seconds, then open the answer. Concepts on Advanced Apex and its Advanced section.

Patterns & structure (1–14)

1 Four developers keep writing the same query differently.Medium

Introduce a selector class per object: all SOQL for that object in one place, with consistent field lists and security mode. It is the single highest-return piece of structure available, and it pays off independently of any wider pattern.

It also makes services unit-testable — inject a stubbed selector and the test never touches the database.

2 Business logic lives in three trigger handlers and an LWC controller.Medium

Extract a service class owning the operation and the transaction boundary, then make the handlers and controllers thin adapters that call it.

One implementation, one place to test, and the next entry point (REST, a flow action) costs almost nothing. Duplicated logic across entry points is how behaviour quietly diverges by channel.

3 Is the full Domain/Selector/Service/UnitOfWork layering worth adopting?Hard

At four or more developers, or a codebase expected to live five years, yes. For two people and a dozen classes it costs more than it returns.

Adopt incrementally: selector first, then service when more than one entry point needs the same logic, then unit of work if DML is scattered. Domain classes last, and only where object behaviour genuinely justifies them.

4 DML happens in six places in one transaction and you hit statement limits.Medium

A unit of work: register records as you go, then commit once in dependency order (parents before children, resolving relationships).

It also makes rollback semantics clearer — one commit point rather than six partial states — and keeps statement counts predictable as the operation grows.

5 You need pluggable pricing logic a consultant can add without a deployment.Hard

An interface plus Custom Metadata naming the implementing class, instantiated with Type.forName(name).newInstance() and cast to the interface.

Guard it: null-check the type and throw a clear configuration exception, and log which implementation ran — dynamic dispatch makes stack traces less direct, so observability has to be deliberate.

6 Two packages need to call each other's logic without a compile dependency.Hard

Callable — a name-based entry point (call(String action, Map<String, Object> args)) that lets one package invoke another with no compile-time reference.

The cost is a loose contract: no type safety, so validate the action name and arguments explicitly and version the action names as carefully as you would a REST API.

7 An interface has exactly one implementation. Remove it?Medium

Usually yes — indirection with no variation is cost without benefit.

Keep it when you need a test seam (the Stub API requires one), when a package boundary demands loose coupling, or when a second implementation is genuinely imminent rather than hypothetical.

8 A 900-line class does five unrelated things.Medium

Write characterisation tests around the current behaviour first — you cannot refactor safely without them, and they document what it actually does versus what its name claims.

Then extract one responsibility at a time, each separately deployable. A big-bang split of untested logic turns a refactor into an incident nobody can attribute.

9 Where should validation live in a layered design?Medium

Record-level invariants belong with the object (domain or trigger handler) so they hold on every write path. Operation-level rules belong in the service, where the full context is available.

What you must avoid is the same rule in both places with slightly different conditions — that is how UI and API behaviour diverge.

10 A singleton cache causes stale data within a transaction.Medium

Statics live for the whole transaction, so a cache populated before a DML will not reflect the change afterwards.

Either invalidate on write (the cache owner also handles updates), or scope the cache to genuinely immutable data — describe results, Custom Metadata, reference lookups.

11 How do you keep a service class from becoming a god class?Medium

One service per business operation or closely related family, not one per object. "OrderSubmissionService" rather than "OrderService" that accumulates everything order-shaped.

When a service exceeds a few hundred lines or its name needs "and", split it. The name is the design signal.

12 You need the same logic in Apex and in a flow.Easy

Write it once as a service, and expose an invocable action wrapper that calls it — bulk-safe, with a typed request and response.

Never implement the rule twice. The invocable wrapper should contain no logic beyond mapping its inputs to the service call.

13 A reviewer says your class has too many dependencies.Medium

Count what it needs to be constructed: more than three or four collaborators usually means it is doing several jobs.

Split by responsibility, or introduce a facade for a cohesive group. Many dependencies also make it tedious to stub, which is itself a design smell worth listening to.

14 What is the minimum structure worth having in any org?Easy

One trigger per object delegating to a handler; a selector per object for queries; a service for anything more than one entry point needs; a bypass switch; and structured error logging via platform events.

That set costs a few days and prevents most of the problems that layering is usually introduced to solve later.

Dynamic Apex & describe (15–28)

15 getGlobalDescribe() is in a loop and CPU is exhausted.Medium

It is one of the most expensive calls in Apex and should essentially never appear in a bulk path, let alone a loop.

Cache in a static map on first use, and prefer targeted describes (Account.SObjectType.getDescribe(), Schema.SObjectType.Account.fields.Name) over indexing into a global describe.

16 You need to build a query from a field set.Medium

Iterate the field set members to build the SELECT clause — that is the supported way to let admins control which fields a component queries without a deployment.

Add WITH USER_MODE so FLS is enforced, and bound the row count. A field set the admin extends to 200 fields should not silently blow your heap.

17 Dynamic SOQL with a user-supplied filter — what are the rules?Hard

Bind variables wherever possible, String.escapeSingleQuotes() on any fragment you must concatenate, and allow-list field and object names against a known set.

Never accept a whole filter expression from a client — that is a generic data-read endpoint regardless of what you call it. And add WITH USER_MODE, because dynamic queries enforce nothing automatically.

18 You need to set a field whose API name is in configuration.Easy

record.put(fieldName, value) with a validity check first — getDescribe() on the object to confirm the field exists and is writeable.

Without the check, a typo in configuration becomes a runtime exception in production rather than a clear configuration error.

19 You receive an Id and must determine its object type.Easy

((Id) idString).getSObjectType() resolves it at runtime; the first three characters are the key prefix if you need to reason about it manually.

Use it for generic utilities and polymorphic fields like Task.WhatId — never assume the parent type from current usage.

20 A generic method must work for any sObject.Medium

Accept List<SObject> and use describe plus get()/put(). Keep the generic boundary small and cast to concrete types as soon as possible.

Generic Apex loses compile-time safety, so every field reference becomes a potential runtime error. It should be a deliberate boundary, not a default style.

21 You need to check whether a field exists before using it.Easy

Describe the object and check the field map — essential for code that must run in orgs where the field may not be deployed, such as a package.

Cache the result; describing on every call is wasteful, and in a package you may be doing it for many objects.

22 Picklist values must be read at runtime.Easy

getDescribe().getPicklistValues(), filtering on isActive(). For dependent picklists the validity matrix is also available via describe, though decoding it is fiddly.

Remember values are assigned per record type, so the full field-level list may include values the user cannot select.

23 Record type Ids are hard-coded in your codebase.Easy

Replace with Schema.SObjectType.Account.getRecordTypeInfosByDeveloperName().get('Partner').getRecordTypeId().

Ids differ in every org and every refreshed sandbox, so hard-coding guarantees a post-refresh break. The same applies to queues, price books and any configuration record.

24 You need to serialise an sObject for an external system.Medium

Define an explicit DTO class and map to it, rather than JSON.serialize on the sObject — which includes attributes and every populated field, leaking data and inflating payloads.

The DTO also decouples your API contract from your schema, so renaming a field does not break a consumer.

25 JSON from a partner has a field named currency.Medium

Reserved word, so you cannot name an Apex property that. Use JSON.deserializeUntyped and read the map, or define a DTO with a different property name and map manually.

A manual mapping method is usually better anyway — it gives you one place to validate and to handle their next schema change.

26 Deserialisation fails when the partner adds a new field.Medium

Strict typed deserialisation throws on unknown fields in some forms. Use a tolerant approach — untyped parsing, or a DTO that ignores extras — so their additive change does not break you.

Additive changes should never break a consumer; design for that on both sides of every integration.

27 An enum value arrives that your Apex enum does not have.Medium

valueOf throws. Map through an explicit lookup with an "unknown" branch, and log the unrecognised value so you learn about their change.

External systems add enum values without notice, so an integration that throws on unknown values breaks on their next release.

28 How do you test dynamic code paths?Medium

Drive the configuration from injectable values rather than deployed Custom Metadata rows (which you cannot insert in a test), and assert each branch — including the error branch where the configured class does not exist.

Dynamic code is exactly where tests matter most, because the compiler is no longer helping you.

Async patterns & reliability (29–44)

29 A Queueable hit a CPU limit and vanished with no trace.Hard

Attach a Finalizer. It runs after the job completes including after an uncatchable failure, in a fresh execution context with its own small limit allocation — so it can log the failure even though the parent exhausted everything.

Without one, limit breaches disappear silently. It is the most valuable async pattern added to the platform in years.

30 Your finalizer re-enqueues the job and it loops forever.Hard

You need a retry cap carried in the job's own state — an attempt counter passed to the constructor and checked before re-enqueuing.

Also shrink the scope on retry (halve the batch) so a deterministic failure eventually isolates itself rather than repeating identically.

31 Should the finalizer contain business logic?Easy

No — keep it tiny: log, alert, maybe re-enqueue. Its limit allocation is small and it runs in a failure context by definition.

Business logic there is logic that only runs when things went wrong, which is the worst possible place for it to live.

32 You need to process 5 million records nightly.Medium

Batch Apex with a QueryLocator so rows stream outside the 50,000-row transaction limit, scope tuned to the work per record (200 default; 1–10 if each row does a callout).

Add a high-water mark so a failure resumes rather than restarting, and report partial failure from finish() — a failed chunk does not stop the job.

33 Batch jobs sit in "Holding" and never run.Medium

The Flex Queue — you have more batch jobs than the concurrent limit allows, so they queue. You can reorder them; you cannot make them run sooner.

A growing Holding count is your early warning that the nightly window no longer fits. Stagger schedules and consolidate jobs.

34 Queueable chaining works in production but fails in tests.Medium

Tests allow only one level of chaining. Assert that the first job did its work and that the next was enqueued, then test subsequent links as separate units.

Designing chains so each link is independently testable is good practice anyway — a chain you can only test end-to-end is a chain you cannot debug.

35 You cannot schedule another Apex job.Medium

Org-wide limit on scheduled jobs reached — usually because someone scheduled one per region or per entity.

Replace with a single scheduled job that iterates, and audit CronTrigger for abandoned schedules from old projects.

36 A deployment leaves a scheduled job pointing at changed logic.Medium

Build an idempotent scheduler setup method that aborts and recreates all schedules, and run it as a documented post-deployment step.

Then verify CronTrigger.NextFireTime and state after each release. Silent schedule breakage is discovered a week later by the business.

37 Async work runs twice and creates duplicate records.Hard

Make it idempotent: a unique External Id on the records you create, insert with allOrNone = false, and treat DUPLICATE_VALUE as "already done".

The unique index is the real guard; a pre-check query is only an optimisation and does not hold under concurrency.

38 A static guard does not prevent re-processing in an async job.Medium

Async runs in a new transaction, so statics are fresh. A guard cannot span transactions.

Use a durable marker — a processed flag or timestamp on the record — when the guarantee must survive the transaction boundary.

39 You need a callout per record for 100,000 records.Hard

Batch Apex implementing Database.AllowsCallouts with a very small scope, since callout limits are per execution rather than per job.

Better if the remote system supports it: send a batch payload instead of per-record calls, or push the whole file to middleware and let it call you back.

40 How do you coordinate "do A, then B, then C" asynchronously?Medium

A Queueable chain, each link doing one stage and enqueuing the next, with small state held in instance fields rather than statics.

Persist progress durably if the sequence matters across failures — an in-flight chain that dies between links leaves no record unless you wrote one.

41 Monitoring shows nothing when async jobs fail.Medium

Query AsyncApexJob on a schedule for Failed and Aborted statuses and alert — the Apex Jobs UI is fine for humans and useless for automation.

NumberOfErrors gives you a count, never a cause, so your own error log (written per chunk) is what makes the failure actionable.

42 `@future` or Queueable for new code?Easy

Queueable, almost always: it takes complex types, returns a job Id you can monitor, supports chaining, and supports finalizers.

@future remains only for simple fire-and-forget work in existing code, and for the rare case where you specifically want its restrictions.

43 Async consumed your daily allocation and everything stopped.Hard

Async executions per 24 hours are org-wide and licence-scaled, and a retry loop can consume them quickly.

Cap retries, back off exponentially, dead-letter what never succeeds, and alert on the allocation rather than discovering it when all async work halts.

44 A long-running synchronous process is breaking the UI for other users.Hard

The concurrent long-running request limit — ten synchronous requests over five seconds per org, shared with interactive users.

Move the work async or use Continuations for long callouts. This limit is uniquely nasty because the symptom appears nowhere near the cause.

Caching & performance (45–56)

45 When should you reach for Platform Cache?Medium

Expensive, re-derivable, shared data: describe results, Custom Metadata lookups, aggregate results, external reference data with a known TTL.

Never for anything you cannot recompute, anything requiring consistency, or anything user-specific in the org cache.

46 Your cache reads return null intermittently.Medium

That is expected — entries can be evicted at any time under memory pressure. Every read must handle a miss and recompute.

Also check the partition is actually allocated capacity: an unallocated partition silently does nothing, which looks exactly like constant eviction.

47 Org cache or session cache?Easy

Org cache for data shared by all users (reference data, describes). Session cache for per-user state within a session.

Putting user-specific data in the org cache is a data-leak bug, not just a design smell.

48 A cached value is stale after someone edits the source.Medium

Invalidate on write: whatever updates the source also removes the cache key, ideally through a single owner class.

If invalidation is not feasible (the source changes outside your code), use a short TTL and accept bounded staleness — and document what "bounded" means.

49 CPU limit exceeded but queries look efficient.Hard

CPU counts computation, not waiting — query time, callout time and commit time are excluded. So the cost is loops, collections, JSON, or formula evaluation during your DML.

Read CUMULATIVE_LIMIT_USAGE, which attributes consumption per namespace and frequently reveals a managed package spending your budget.

50 Heap exceeded processing a large result set.Medium

Stop holding it all: Database.getQueryLocator in Batch Apex streams rows, and selecting fewer fields reduces per-row cost substantially.

Also null out large collections when finished and avoid keeping parallel copies (a list plus a map of the same records doubles the cost).

51 A nested loop over two 500-item collections is slow.Easy

250,000 iterations. Replace the inner loop with a Map lookup keyed on the matching value.

Almost every nested loop in Apex can become one map build plus a single pass, which is the difference between quadratic and linear.

52 JSON parsing dominates your CPU time.Medium

Parse once and pass the result around rather than re-deserialising the same payload in several methods — a surprisingly common pattern.

For very large payloads, parse untyped and extract only the fields you need, or push the parsing to middleware and accept a simpler shape in Salesforce.

53 How do you profile which part of your code is expensive?Medium

Limit snapshots at key points — capture Limits.getCpuTime() before and after each stage and log the deltas.

Combined with CODE_UNIT_STARTED/FINISHED in a debug log, that tells you where the time actually goes instead of where you assume it goes.

54 You want to warn before a limit is breached, not after.Medium

Compare consumed against Limits.getLimitX() and publish a platform event when you cross about 60%.

That converts a future incident into a ticket, and the event-based log is visible in production where debug logs are not.

55 A query is selective but the transaction is still slow.Medium

Look at what the save triggers: validation rules, roll-ups, other triggers, flows, sharing recalculation, package logic — all inside your transaction.

The execution tree in a debug log usually reveals automation nobody documented, and your code may be a small slice of the total.

56 Should you optimise before measuring?Easy

No. On this platform the CPU-versus-waiting distinction changes the fix entirely, and the slow thing is rarely the suspected one.

Measure, change one thing, re-measure. Optimising by intuition typically produces more complex code at the same speed.

Sharing keywords & security (57–70)

57 What should a reusable library class declare?Medium

inherited sharing — it adopts the caller's mode, which is correct for a library and is the only safe-by-default option when it might be entered from a Visualforce page or a REST endpoint.

An unannotated class runs in system mode from those entry points, which is how libraries accidentally become elevation paths.

58 An inner class is not respecting the outer class's sharing.Hard

Inner classes do not inherit the outer declaration — they default to the caller's mode.

Declare sharing explicitly on any inner class that does data access. It is an obscure rule that produces genuine exposure.

59 You need to elevate for one specific operation.Medium

A small, single-purpose without sharing class containing only that operation, with the justification in a comment and the inputs tightly validated.

Deliberate elevation is legitimate. Elevation for convenience across a large class is the finding.

60 Does with sharing enforce field-level security?Easy

No. It governs record visibility only — never FLS or object permissions.

Use WITH USER_MODE, as user DML, or Security.stripInaccessible. This is the most common misunderstanding in Salesforce security.

61 When is stripInaccessible the right tool?Medium

For collections arriving from elsewhere — a deserialised payload, a method parameter — where you must remove inaccessible fields before using or returning them.

It also reports what was removed, which lets you decide whether to proceed or fail rather than silently acting on incomplete data.

62 An @AuraEnabled method accepts an object name.Hard

That is a generic read endpoint for anyone who can load the component, including guests on a public page.

Allow-list permitted objects, enforce CRUD and FLS, bound the rows, and return a purpose-built DTO. Better still, write a specific method per use case.

63 How do you audit a codebase for security gaps?Hard

Grep for without sharing, every @AuraEnabled and @RestResource, and every dynamic SOQL construction — then cross-reference against which components are on guest-accessible pages.

Prioritise by reachability: anonymous and external first. Fix the pattern rather than the instance, and add the check to CI.

64 Should an integration endpoint elevate for performance?Hard

No, and the premise is usually wrong — sharing enforcement is rarely the bottleneck.

Authenticate as a user whose access is the restriction and write the class with sharing. A WHERE clause on an elevated query means a bug there becomes a breach; sharing fails closed.

65 A flow calls your class and sees too much.Medium

Record-triggered flows run in system context without sharing, and an inherited sharing class called from there runs in system mode too.

If the Apex must respect the user, declare with sharing and use USER_MODE explicitly rather than depending on the caller.

66 You must grant record access from code.Medium

Insert share rows with a custom RowCause created in Setup, so grants survive ownership changes and are identifiable later.

Build the revoke path and a reconciliation job in the same change — nothing cleans up stale shares, and they are a standard audit finding.

67 How do you test that security is enforced?Medium

System.runAs with a user from a minimum-access profile plus only the permission set under test, asserting that restricted data is absent or that the expected exception occurs.

Tests run in system mode by default, so testing as an admin proves nothing — which is why access bugs ship with full coverage.

68 A user-mode query throws where system mode succeeded.Medium

That is it working: the user lacks access to an object or field, so the query is rejected rather than returning data they should not see.

Decide deliberately whether to catch and degrade the feature or let it fail — silently stripping can be worse if a decision is then made on incomplete data.

69 Is hiding a button sufficient protection?Easy

No — the Apex method remains callable. Client-side checks are UX; server-side checks are security.

Put "who can cause this to run, and in whose context?" in your pull request template. It catches the category of bug that actually makes the news.

70 A secret needs to be used in a callout.Easy

A Named Credential with an External Credential — no secret in code, metadata or custom settings, token refresh handled, and rotation becomes a config change.

Secrets in custom settings are visible to anyone who can read the setting, and secrets in code are in your git history.

Packaging & distribution (71–82)

71 You marked a method global in a managed package and regret it.Hard

global in a managed package is a permanent contract — you cannot remove or change the signature without a major version and migrating every subscriber.

Deprecate it with @deprecated, add the replacement, and support both. Default to public and expose global only deliberately.

72 Two packages in your namespace need to share internal code.Medium

@namespaceAccessible — visible to other packages in your namespace without exposing it to subscribers.

That is the right tool for a shared "common" package, which is usually what you extract when breaking dependency cycles.

73 Package dependencies form a cycle and the build fails.Hard

The dependency graph must be acyclic. Break the cycle by extracting the shared pieces into a lower-level package both depend on.

Most of the work of decomposing an org into packages is breaking cycles — the packaging mechanics are the easy part.

74 Your package's tests fail in a subscriber org on upgrade.Hard

They depend on org-specific data or configuration. Package tests run in the subscriber's org, where your assumptions about records, picklist values and automation do not hold.

Build all test data in the test, never use SeeAllData, and tolerate the subscriber's own automation firing on your inserts.

75 Your package code hits limits in a subscriber org but not yours.Hard

Their org has other automation and other packages sharing the same transaction — and CPU time is shared even though some limits are namespace-scoped.

Be frugal, push heavy work async, and provide a bypass switch subscribers can use during data loads.

76 A subscriber edited your unlocked package's metadata.Medium

Unlocked packages allow it, which is both the feature and the risk — their change is now drift that your next version may overwrite.

Document what is safe to change, detect divergence if you can, and consider a managed package if the components must be immutable.

77 How do you version an API your package exposes?Medium

Treat global signatures and any @RestResource path as a contract: version in the path or the method name from day one, support the old form, and deprecate explicitly.

Adding versioning later means migrating every consumer simultaneously, which is rarely possible.

78 Unlocked, managed or unmanaged for internal modularisation?Medium

Unlocked — versioned, upgradeable, no namespace required, designed for your own org. Managed is for ISV distribution with IP protection; unmanaged has no upgrade path at all.

Get org-based source control working reliably first; decomposing into packages and introducing version control simultaneously stalls programmes.

79 You need to deprecate a class your subscribers use.Hard

Mark it @deprecated, ship the replacement alongside, communicate the timeline, and remove it only in a major version — with a migration path documented.

Subscribers upgrade on their own schedule, so "we removed it in the next release" is not an option for anything global.

80 How do you test a package upgrade safely?Medium

Install the previous version in a sandbox with realistic data and automation, then upgrade — exercising the paths subscribers actually use, and running their tests as well as yours.

For configuration-heavy packages, recalculate a golden set with known expected outputs. Upgrades change behaviour more often than release notes suggest.

81 Ancestry is wrong and subscribers cannot install your new version.Hard

Managed packages declare an ancestry so upgrades know their lineage; getting it wrong produces versions that cannot install over what subscribers already have.

Fix the ancestry declaration and rebuild. This is a packaging-configuration problem, not a code problem, and it is worth getting right before the first release.

82 Your package needs configuration data in the subscriber org.Medium

Custom Metadata records can ship with the package; most other configuration is data and cannot.

Provide a post-install script or a setup page that seeds required rows idempotently, and a test that fails clearly when configuration is missing.

Judgement & craft (83–100)

83 You are asked to add a feature to code you consider unsafe.Medium

Deliver the feature, and raise the specific risk with a concrete scenario and a cost to fix — in writing, briefly.

Vague objections get overruled; "an external user can read other accounts' data through this method, two days to fix" either gets fixed or gets consciously owned.

84 A pattern would be cleaner but the team does not know it.Medium

Weigh the cleverness against the maintenance population. Code is read far more than written, and a pattern nobody on the team recognises is a liability regardless of its elegance.

Introduce it where the benefit is clear, document why, and pair on it. Do not scatter it everywhere at once.

85 Build a custom framework or adopt an open-source one?Medium

Adopt if it is well-known in the ecosystem (new joiners already know it) and actively maintained. Build only if your needs are genuinely unusual.

Either way, keep it thin: a framework you cannot fully explain to a new developer in twenty minutes will be worked around.

86 How do you make a codebase easy to onboard into?Medium

Consistency over cleverness: one way to do each thing, names that describe behaviour, a documented entry point per object, and tests that show intended usage.

Plus a short written description of the layering decisions and the reasons. Undocumented conventions are learned by accident, inconsistently, over months.

87 You inherit code with no tests and must change it.Hard

Write characterisation tests capturing the current behaviour first — including the parts you think are wrong, which you note but do not change yet.

Then change behaviour deliberately, one test at a time. Refactoring and fixing simultaneously makes it impossible to attribute a regression.

88 A method name and its behaviour disagree.Easy

Fix the name, not the comment. A comment explaining that validate() also sends email is a comment that will be ignored.

If renaming is risky because of external callers, that is itself information about the coupling you have.

89 When is a comment worth writing?Easy

When it explains why — a non-obvious constraint, a rejected alternative, a platform quirk you worked around, a business rule with a source.

Comments restating what the code does rot and mislead. Comments recording decisions are the most valuable documentation in any Salesforce codebase.

90 How much abstraction is too much?Medium

When tracing a simple operation requires opening five files, or when adding a field means changing four layers.

Abstraction should absorb change, not multiply it. If the layers are not earning their keep by isolating something that actually varies, remove them.

91 A reviewer wants 100% coverage on a utility class.Medium

Coverage is not the goal; verified behaviour is. Push for tests that assert outcomes on the branches that matter, including error paths.

The honest check: break a line deliberately and see whether a test fails. If not, the coverage is decoration regardless of the percentage.

92 You need to prove a refactor changed nothing.Hard

Characterisation tests written before the change, run after — plus, for data-heavy logic, a comparison run on a realistic dataset in a sandbox with outputs diffed.

For pricing or calculation logic, a golden set with expected values to the penny is the only convincing evidence.

93 The org has no error logging. Where do you start?Medium

A platform-event-based log: class, method, message, stack, record Id, correlation id and quiddity — published so the record survives a rollback.

Then route Apex exception emails to a monitored address and add an alert on log volume. This is a one-day task that changes every future incident.

94 How do you decide between fixing forward and rolling back?Hard

There is no transactional rollback, so "roll back" means deploying the previous tag plus manually reversing what cannot be redeployed.

Fix forward when the fix is small and understood; roll back when the change is broad and the previous state is known-good. Keep a per-release list of irreversible changes so the decision is informed.

95 A dependency injection framework is proposed for a 20-class org.Medium

Overkill. Constructor injection by hand gives you the test seams without a framework, and twenty classes do not need a container.

Revisit if the codebase grows substantially or if you need runtime-configurable implementations — which Type.forName plus Custom Metadata already handles.

96 Static analysis flags 300 issues. What now?Medium

Set a severity threshold that fails the build, fix those, and baseline the rest so new code cannot add to the pile.

A list of 300 unprioritised findings gets ignored entirely. A gate on severity plus a non-regression baseline gets the codebase improving steadily.

97 Your clever solution is three times faster and much harder to read.Medium

Ask whether the speed matters — measured, against a limit you are actually approaching. If not, take the readable version.

If it does matter, keep the clever version but isolate it behind a clear interface, comment the why, and test it thoroughly.

98 How do you keep technical debt from accumulating invisibly?Medium

Measure it on one page — automations per object, API version spread, assertion-free tests, permission sprawl, limit headroom — and reserve a fixed slice of every sprint for the worst item.

Debt that competes with features for priority always loses; debt with a reserved allocation gets fixed. See measuring debt.

99 What makes Apex genuinely production-ready?Hard

Bulk-safe, idempotent, observable (structured logging with correlation ids), bounded (no unbounded queries or collections), bypassable (a switch you can flip during an incident), and tested on the failure paths as well as the happy one.

None of that is clever. All of it is the difference between a bad afternoon and a bad quarter.

100 One habit worth more than any pattern?Hard

Writing down why — the decision, the rejected alternative, the constraint that forced it — in the code and in the commit.

Patterns are rediscoverable from the code. Reasons are not, and their absence is why teams cannot safely change anything they did not personally write.
