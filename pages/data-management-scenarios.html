Data Management — 100 Scenarios

Migration that works, skew and selectivity, Bulk API, large data volumes, Big Objects, archiving, backup you have actually tested, and privacy obligations with teeth.

📚
How to use this Answer out loud in ninety seconds, then open the answer. Concepts on Data Management and its Advanced section.

Migration (1–20)

1 What is the first step of any migration?Easy

Profile the source data: volumes, quality, duplicates, mandatory gaps, and the keys available for matching.

Designing the load before you know the data is how timelines slip — the surprises are almost always in the data, not the tooling.

2 What load order do you use?Easy

Parents before children, and anything self-referential (Account parent, Contact reports-to) needs a second pass to populate the reference.

You cannot point at a record that does not exist yet, so plan the passes explicitly.

3 How do you make a load re-runnable?Medium

Upsert on an External Id holding the source system's key, marked unique.

Then a repeat run updates rather than duplicating, which means a failed load can simply be re-run — the single most valuable property of a migration.

4 A load of 2 million records is extremely slow.Hard

Automation running per row: triggers, flows, validation rules, workflow, roll-ups and sharing recalculation.

Use a bypass switch for the load user, then run a reconciliation pass afterwards to apply the derived values that were skipped.

5 The load fails with UNABLE_TO_LOCK_ROW.Hard

Chunks contending on shared parents. Sort the file by parent Id so children of the same parent land in the same chunk — the cheapest migration optimisation there is.

Then switch Bulk API from parallel to serial if needed: slower and it finishes, versus faster and it fails.

6 Should you disable validation rules for the load?Medium

Bypass them for the load user via a custom permission condition — and then run a data-quality report to find records that would have failed.

Bypassing without reconciling imports the bad data permanently, which is a worse outcome than a slow load.

7 How do you handle record ownership on load?Medium

Set the real owner during the load where possible — assigning everything to one integration user creates ownership skew, and reassigning later triggers a huge sharing recalculation.

If you must load as one user, plan the reassignment as a separate controlled exercise.

8 You need to preserve created dates and owners.Medium

Audit field creation must be enabled (by Salesforce) and then CreatedDate, CreatedById and LastModifiedDate can be set on insert.

Request it early — it is a prerequisite, not something you can add mid-migration.

9 How do you rehearse a migration?Medium

A Full sandbox with production-shaped data, timed end to end, with row counts and checksums compared before and after — and the rollback rehearsed too.

Unit tests cannot cover this: the risk is volume, duration and data shape.

10 How do you verify a migration succeeded?Medium

Counts per object, checksums on key numeric fields, spot-checks on relationship integrity, and a reconciliation report against the source.

"The load reported success" is not verification — partial failures and silently dropped rows are the normal failure mode.

11 Some rows failed and you do not know which.Easy

Bulk API returns per-record results with error messages — keep the success and error files, do not discard them.

A load without retained result files cannot be reconciled, which means you cannot prove what happened.

12 How much historical data should you migrate?Medium

As little as the business genuinely needs. Full history is usually unnecessary, expensive and slows everything down.

Keep the rest in a read-only archive or the legacy system. This single decision saves more migration time than any technical optimisation.

13 Duplicates exist in the source.Medium

Deduplicate before loading, with the survivorship rules agreed and documented — which record wins, which field values survive, what happens to children.

Cleaning after the load means merging in Salesforce, which is irreversible and far more work.

14 A picklist value in the source does not exist in Salesforce.Easy

Map it explicitly, with an exception path for unmapped values — logged and reviewed rather than silently defaulted or dropped.

Unmapped values are guaranteed; the only question is whether you find out during the load or six months later.

15 The migration window is four hours and the load takes six.Hard

Reduce the work (less history, fewer objects in the critical path), disable automation for the load, sort by parent Id, and parallelise where contention allows.

Or split the cutover: load static data in advance and only the delta during the window.

16 How do you handle attachments and files?Medium

Separately and last, as ContentVersion records linked to their parents — and they consume file storage rather than data storage.

Files are usually the slowest part of a migration and the part most often underestimated.

17 A cutover needs a rollback position.Hard

For a load into an empty org, deleting what you loaded (by a batch marker field) is feasible. Into a live org it is far harder.

So stamp every migrated record with a batch identifier, and rehearse the reversal — "we will just delete them" needs to be proven, not assumed.

18 Which tool for the load?Easy

Data Loader or the CLI for anything substantial; Import Wizard only for small, simple, one-off loads.

For millions of rows, Bulk API 2.0 — and for extraction at that scale, PK chunking.

19 How do you keep the mapping maintainable?Medium

In version control, as a documented mapping file per object with transformations stated — not in someone's spreadsheet.

Migrations always run more than once, and an undocumented mapping cannot be reproduced or reviewed.

20 What makes a migration go wrong most often?Hard

Data quality discovered late, and automation nobody thought to disable.

Both are found by profiling the source early and rehearsing in a Full sandbox — which is why those two steps are non-negotiable.

Skew & selectivity (21–40)

21 What are the three skews?Medium

Ownership skew (one user or queue owning a very large share, commonly cited around 10,000+), account data skew (one parent with very many children), lookup skew (thousands of children pointing at one lookup parent).

The first two cause sharing recalculation pain; the third causes DML lock contention.

22 An integration user owns 2 million records.Hard

Ownership skew. Every role or ownership change involving them triggers a massive recalculation, and record locking becomes routine.

Spread ownership, and keep the skewed owner out of the role hierarchy — or at the top with no peers.

23 A "House Account" has 80,000 contacts.Hard

Account data skew: implicit sharing recalculation on that parent, plus lock contention on any child DML.

Split the mega-account. Dumping-ground accounts are a data-model decision that becomes a performance problem.

24 Inserts are slow and contend on one record.Medium

Lookup skew — a "Default" or "Unknown" lookup parent referenced by thousands of children.

Spread the values, or replace the lookup with a picklist or text field if the relationship existed only for reporting convenience.

25 Which fields are indexed for free?Easy

Id, Name, OwnerId, CreatedDate, SystemModstamp, RecordTypeId, master-detail and lookup fields, and anything marked External Id or Unique.

That last one is the free lever: marking a field External Id gives you an index and upsert-by-key.

26 What is the selectivity threshold?Hard

A filter is index-eligible only when it returns a small enough fraction of the object — roughly under 30% of the first million rows and under ~15% beyond, capped at around a million rows, with tighter thresholds for custom indexes.

The key consequence: the same query changes plan as data grows.

27 A query was fast last year and times out now.Medium

Data growth pushed it past the threshold, so the optimiser abandoned the index for a scan.

Run the Query Plan tool against production and lead with a selective indexed filter, or request a custom index.

28 Which operators kill an index?Medium

!=, NOT, leading wildcards (LIKE '%x'), null checks on some field types, and comparisons against cross-object formula fields.

Rewrite as a positive IN list, and add a selective filter to lead the query.

29 When do you request a custom index?Medium

When you filter on a field constantly and it is not already indexed — requested from Support, with two-column indexes available for common composite filters.

Check first whether marking it External Id or Unique achieves the same thing for free.

30 A skinny table is proposed.Hard

A Support-created denormalised copy for heavy read patterns over tens of millions of rows — after indexing alone has not worked.

Caveats: limited field count, no joins, and it does not automatically include fields you add later. It is a tuning step, not an architecture.

31 Filtering on a formula field is slow.Medium

Cross-object and non-deterministic formulas cannot be indexed, and they are evaluated per row.

Materialise the value into a plain indexable field via automation and backfill, then filter on that.

32 How do you page through millions of records?Hard

Keyset pagination: WHERE Id > :lastId ORDER BY Id LIMIT n, carrying the last Id forward.

OFFSET is capped at 2,000 and degrades badly, so it is not an option at volume.

33 What is PK chunking for?Medium

Bulk extraction at scale — it splits the query by Id ranges so each chunk is selective.

Essential above a few million rows, where a single unselective query times out before returning anything.

34 Sharing recalculation is taking hours.Hard

Expected at volume after an OWD, hierarchy or ownership change — and it locks group membership while it runs.

Plan such changes in controlled windows, and for a large reorganisation ask Salesforce to enable deferred sharing maintenance.

35 A report on 40 million rows times out.Medium

Selectivity. Narrow the date range, filter on indexed fields, and avoid cross-object formula fields in filters.

If the requirement is genuinely analytical over that volume, it belongs in CRM Analytics or a warehouse rather than a report.

36 How do you find out whether an index is used?Easy

The Query Plan tool in the Developer Console: it shows cost and which index each plan option uses. Cost above roughly 1 means a scan.

Run it against production, because the statistics are per tenant.

37 Two batch jobs deadlock on related data.Hard

They lock the same parents in different orders — deadlock is an ordering problem.

Sort DML by parent Id so all transactions lock consistently, reduce scope, and consider serialising the jobs instead.

38 An anti-join is slow.Medium

NOT IN (SELECT ...) is rarely selective and is limited per query.

At volume, a maintained roll-up count field on the parent outperforms it substantially — and makes the requirement reportable too.

39 How do you design for 10× growth?Hard

Selective indexed queries, incremental processing, bounded collections, resumable jobs, and archiving so the working set stays bounded.

Then monitor the trend. Most volume incidents are visible six months ahead if someone is looking.

40 What four questions start an LDV design?Hard

How many rows and growing how fast; which queries must stay fast (and are their filters indexable); what the sharing shape is (skew, OWD, hierarchy depth); and what the retention rule is.

Those four determine indexes, skinny tables, archiving — and whether the data belongs in Salesforce at all.

Bulk operations (41–58)

41 Bulk API 1.0 or 2.0?Easy

2.0 for new work — you upload the data and Salesforce handles chunking, with a simpler job model.

1.0 remains where you need explicit batch control or a feature 2.0 lacks, but it is not the default.

42 Serial or parallel mode?Medium

Parallel is faster; serial avoids lock contention on shared parents.

Start parallel, switch to serial when you see UNABLE_TO_LOCK_ROW — and sort the file by parent Id first, which often lets you keep parallel.

43 Delete or hard delete?Medium

Normal delete goes to the recycle bin, still consumes storage and is recoverable. Hard delete skips it and frees storage immediately — and is irreversible.

Prove the selection is right before hard deleting, and keep the result files.

44 A bulk delete of 5 million records.Hard

Bulk API in chunks, in a controlled window, with a verified count first — and expect sharing and roll-up recalculation load.

Also check cascade deletes: a master-detail parent takes its children and runs their delete triggers.

45 The recycle bin is full.Medium

It is capacity-bounded and purges, so a mass delete is not reliably recoverable from it.

Which means "we can always restore from the bin" is not a backup strategy — and it is worth saying before someone relies on it.

46 How do you extract 20 million rows?Medium

Bulk API with PK chunking, so each chunk is a selective Id range.

A single unselective query over that volume times out before returning anything, regardless of the tool.

47 A bulk job is stuck in a queued state.Medium

Org-wide bulk processing capacity, or other jobs ahead of it. Check the job status and the batch states.

Staggering large jobs rather than submitting them simultaneously usually resolves it.

48 Upsert created duplicates.Medium

The External Id was blank on some rows, or the field is not marked unique, so upsert inserted rather than matched.

Make the field unique — the database constraint is the real guarantee — and ensure every incoming row carries it.

49 How do you load records with a lookup to an unloaded record?Medium

Load the referenced object first, or use the External Id reference syntax so the platform resolves the relationship by key.

That is also what makes the load re-runnable, since you are not depending on Salesforce Ids.

50 You need to update 50 million records.Hard

Chunk it across multiple runs with a persisted high-water mark, bypass automation, and spread it over a window — it is not a single operation.

And question whether every row needs updating: an incremental filter usually reduces it by an order of magnitude.

51 A load triggered 20 million roll-up recalculations.Hard

Each child write recalculates its parent. That is most of your load time and most of your lock contention.

Sort by parent Id to group the work, and consider whether the roll-up is needed during the load at all.

52 Should you use Apex for a bulk data operation?Medium

Batch Apex when the operation needs logic that must run in Salesforce. Bulk API when it is a straightforward load or extract.

Apex consumes your limits and is slower for raw movement; Bulk API is purpose-built for it.

53 How do you monitor a long bulk job?Easy

Poll the job status for state and record counts, and keep the result files for reconciliation.

Alert if it has not completed within the expected window — a stalled job discovered the next morning costs you the window.

54 A load consumed your daily API allocation.Medium

Per-record REST calls rather than Bulk API. Bulk consumes dramatically fewer API calls per record.

For a migration, per-record REST is essentially always the wrong choice.

55 Files need migrating at volume.Medium

ContentVersion records with the binary payload, loaded separately and usually last — and they consume file storage with their own size limits.

Budget considerably more time than for the equivalent record count; files are routinely the slowest phase.

56 A bulk operation partially failed.Easy

Normal and expected — read the per-record results, fix the failing rows, and re-run only those (safe because you are upserting on an External Id).

Discarding the error file is what makes a partial failure unrecoverable.

57 How do you test a bulk operation safely?Medium

A small subset first, verified, then a timed rehearsal at full volume in a Full sandbox.

And rehearse the reversal. "It worked on 100 rows" tells you the mapping is right, not that the operation is viable.

58 Bulk API is reporting row-level errors you do not understand.Medium

The status code names the cause — a validation rule, a required field, a duplicate rule, a lock, or a trigger exception.

Group the errors by code first; usually two or three causes account for nearly all rows.

Big Objects, archiving & storage (59–78)

59 What are Big Objects for?Medium

Append-oriented storage for very large volumes outside standard storage limits — history, telemetry, archived transactions.

Not a general-purpose object: no triggers, no sharing model, no roll-ups, and limited DML.

60 What is the critical Big Object design decision?Hard

The composite index — you can only query along it, in order, left to right, and it cannot be changed afterwards.

Get it wrong and the data is effectively unqueryable. Design the query patterns before the schema.

61 How do you query a Big Object at volume?Medium

Async SOQL, which writes results into another object rather than returning them. Synchronous SOQL works only for narrow, index-aligned queries.

Reporting is also not a standard source — surface it via CRM Analytics or a custom component.

62 Design an archiving process.Hard

A scheduled batch copies closed records older than n years into a Big Object or external store, verifies the copy, then hard-deletes the originals.

Verify in a separate job run with a reconciliation count — deleting in the same pass as copying is how data is lost.

63 The business wants to keep everything forever.Medium

That is itself a compliance position, and usually the wrong one — it costs storage, slows reports and extends breach exposure.

Agree a retention policy per object with legal, then implement it. "Keep everything" is a decision nobody has actually made.

64 Data storage is nearly full.Medium

Archive closed records, hard-delete what the recycle bin holds, and check for an object nobody expected to grow (log records, integration staging).

Put storage on a monthly health review — it fails silently and then loads start failing.

65 File storage is full but data storage is fine.Easy

They are separate allocations. File storage is usually consumed by email attachments and old documents.

Audit the largest files, and move archival content to external storage with links rather than buying capacity.

66 Should archived data live in Salesforce at all?Medium

Often not. If it is only needed occasionally for reference or audit, an external store or warehouse is cheaper and does not consume your limits.

Big Objects are the on-platform option when it must stay — which is a narrower requirement than people assume.

67 How do users access archived records?Medium

A custom component querying the Big Object along its index, or an external object via Salesforce Connect if the archive is outside.

Design that access path before archiving, or you will be asked for data you have made unreachable.

68 Can you update a Big Object record?Medium

Not in the usual sense — they are append-oriented, with insert and limited delete.

So the data model must treat each row as immutable. Trying to use one as a mutable table is a design mistake.

69 A nightly job writes a log record per transaction.Medium

That grows without bound and doubles your DML. Consider a Big Object, sampling, or a retention policy that purges aggressively.

Log objects are one of the commonest causes of unexpected storage consumption.

70 How do you reduce storage without deleting?Medium

Move files out to external storage, archive to a Big Object (which has its own allocation), and delete the recycle bin contents.

Also check whether field history and log objects are consuming more than the business data does.

71 Field history is consuming storage.Medium

Tracking many fields on a high-volume object generates a lot of rows, with limited retention anyway.

Track fewer fields, or move to Field Audit Trail if the requirement is genuinely long retention.

72 What is the risk of an unowned archive process?Medium

It stops running and nobody notices until storage fills — or it deletes something it should not and nobody checks the verification.

Alert on completion and on absence, and report the counts monthly.

73 Should you archive or move to a warehouse?Medium

Warehouse if the data's purpose is analysis — it is cheaper, more capable and does not consume platform limits.

Big Object if it must stay on-platform for operational lookup. Data Cloud zero-copy if it already lives in a warehouse.

74 How do you prove an archive is complete?Medium

Counts and checksums per period, compared between the source and the archive, retained as evidence.

Without that you cannot safely delete the originals, which makes the archive pointless.

75 An auditor asks for a record from 2019.Medium

You need to know where it is and how to retrieve it — which is a documented access path, not an improvisation.

Retention without a tested retrieval process is not compliance; it is storage.

76 Data skew appears after archiving.Medium

Plausible — archiving children can leave parents with uneven distributions, and bulk deletes trigger recalculation.

Re-check the shape after a large archive run, and schedule such runs in controlled windows.

77 How often should archiving run?Easy

Frequently enough that each run is small — monthly beats annually, because a year's backlog is a project rather than a job.

Small regular runs also keep the verification manageable.

78 What is the first archiving decision?Medium

The retention rule per object, agreed with the business and legal — because everything else follows from it.

Starting with the technology and working backwards produces an archive nobody can justify.

Backup, privacy & judgement (79–100)

79 Is the Weekly Export a backup?Easy

No. It is a CSV dump with no relationships preserved, no automation, and a restore measured in weeks of manual work.

Calling it a backup is the most common and most dangerous data-protection assumption in Salesforce orgs.

80 How do you know your backup works?Hard

Restore it. A backup you have never restored is a hypothesis.

Restore a subset into a sandbox quarterly, time it, and record the result. That number is what your RTO is actually based on.

81 What are RPO and RTO here?Medium

How much data you can afford to lose, and how long you can be down. They drive the tool choice.

Working backwards from a product rather than from those two numbers is how orgs end up with a backup that cannot meet the requirement.

82 A mass delete went wrong. What are your options?Hard

Recycle bin first — it is capacity-bounded and purges, so time matters. Restore in batches and verify counts.

If it was a hard delete or the bin has purged, you are into backup restore, which is where "we have never tested it" becomes expensive.

83 Metadata backup — do you need it?Easy

Yes, and that is what version control is for. A data backup with no metadata to restore into is not a recovery plan.

Which makes the baseline retrieval into main a data-protection activity, not just a DevOps one.

84 A customer invokes the right to be forgotten.Hard

Deletion must cascade further than people expect: the record, history, feeds, files, email logs, Big Objects, backups, sandboxes and downstream systems.

Build it as a documented, repeatable process with verification — and decide between deletion and anonymisation, which often preserves reporting integrity.

85 Sandboxes contain real customer data.Medium

Usually a policy breach and always a compliance exposure. Run Data Mask as part of the post-refresh checklist, before anyone logs in.

And set email deliverability to System Email Only first, which is the failure people notice loudest.

86 Legal asks you to encrypt all PII.Hard

Clarify the threat model: Shield Platform Encryption protects data at rest from infrastructure-level access — it does not hide data from a user with FLS.

If the requirement is "staff must not see it", that is field-level security. Shield also breaks filtering, sorting and some formulas.

87 An encrypted field can no longer be filtered.Medium

Expected — that is the main functional cost of Shield.

Keep a non-sensitive derived field for filtering (a hash, a bucketed value), or reconsider whether that field needs encryption.

88 Where does consent live?Medium

Nominate one system of record per channel and sync outward — Salesforce's Individual and consent objects, plus whatever the marketing platforms hold.

And record proof: timestamp, source, and the exact wording shown. See consent architecture.

89 How do you handle data residency?Hard

It can override architecture: a regional org (Hyperforce) or a separate org for the regulated population.

Get the requirement precisely from legal first — "residency" sometimes means storage, sometimes processing, sometimes only certain field categories.

90 Data quality is poor and nobody owns it.Medium

Measure, prevent, remediate, then keep measuring: a completeness dashboard by field and owner, validation to stop new gaps, and a backfill for history.

Making a field required without a backfill plan means users cannot save legacy records — which is how quality initiatives die in week two.

91 How do you dedupe 200,000 existing accounts?Hard

Not with duplicate rules — those prevent new duplicates. You need extraction, matching, a human review step, then merges in batches with a verified rollback position.

And survivorship rules agreed in advance: which record wins, which values survive, what happens to children.

92 A merge lost data the business needed.Hard

Merging keeps the master's values, reparents most children and deletes the losers — and some related records do not survive as expected.

Merge is effectively irreversible, so test it on a sample in a sandbox with real automation active first.

93 Who should own data management?Medium

A named owner with a monthly review: storage, quality metrics, archive runs, backup restore tests, and limit headroom.

Unowned data management is why orgs discover storage problems and untested backups simultaneously.

94 How do you justify data work to the business?Medium

In outcomes they feel: report performance, failed loads, duplicate customers in a mailing, the time to answer an audit request.

"Data hygiene" loses the argument; "we sent three letters to the same customer" wins it.

95 Should this data be in Salesforce at all?Hard

Only if a decision or process in Salesforce depends on it. Otherwise link to it, virtualise it, or report on it where it lives.

Every imported field is permanent cost: mapping, sync, storage, reconciliation and support. "No" is frequently the right answer.

96 A stakeholder wants all 15 years of history migrated.Medium

Ask what they will do with year 12. Usually the answer is "look at it occasionally", which is an archive rather than a migration.

Offer a read-only archive with a documented retrieval path, and migrate the operationally relevant window.

97 How do you handle a data incident?Hard

Contain (stop the job, restrict access), assess scope from your logs and reconciliation, preserve evidence, then repair in batches with verification.

Repairing before scoping makes the damage harder to quantify.

98 A load is scheduled for 2am and you are not there.Medium

It needs to be re-runnable, idempotent, monitored and alerted — and it needs a documented abort procedure for whoever is.

An unattended load with no alerting is a load whose failure you discover from the business.

99 What is the most common data-management mistake?Hard

Treating the Weekly Export as a backup, closely followed by migrating everything because deciding what to leave was harder than loading it.

Then ownership skew from loading everything as one user, and no retention policy at all.

100 One habit that most improves data work?Hard

Making every data operation re-runnable and verifiable: upsert on a unique External Id, retained result files, and a reconciliation count.

That one property turns a failed load from an incident into a retry, and it is what makes everything else — archiving, migration, integration — safe to operate.
