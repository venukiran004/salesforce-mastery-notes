Reports & Dashboards — 100 Scenarios

Report type design, formulas that are statistically honest, filters and cross filters, historical trending, dashboard running users, performance at volume, and sharing.

📚
How to use this Answer out loud in ninety seconds, then open the answer. Concepts on Reports & Dashboards and its Advanced section.

Report types (1–18)

1 You need "Accounts with no Opportunities".Easy

A report type using "with or without" (an outer join), or a cross filter on a standard type.

"A with B" is an inner join and will only ever show accounts that have opportunities — which is the most commonly missed report-type option.

2 A custom report type shows no records.Easy

Almost certainly an inner join where you wanted an outer one, or the type is in development status rather than deployed.

Check the A/B relationship setting first — it accounts for the large majority of these cases.

3 How many objects can a report type chain?Easy

Up to four, A→B→C→D — but each level narrows what you can do and makes the type slower and more confusing.

Before adding a fourth, check whether lookup "related fields" on an existing type already give you what you need.

4 Users cannot find the fields they need.Medium

The report type's field layout — you control which fields are available and how they are grouped in the picker.

A technically correct type with 400 ungrouped fields is unusable, and users will build the wrong report rather than hunt for the right field.

5 You need fields from a lookup's parent.Easy

The "related fields" sections on the existing report type frequently provide them without a deeper chain.

That avoids creating a new four-object type for what is really one extra column.

6 Should you create a new report type or reuse one?Medium

Reuse where the objects and join semantics match — each type is maintenance, and a proliferation of near-identical types confuses users.

Create a new one when the join (inner versus outer) or the object chain genuinely differs.

7 Do report types deploy?Easy

Yes — custom report types are metadata and deploy normally. Reports and dashboards are metadata too.

The fiddly part is folders and folder sharing, which is where "it deployed but nobody can see it" comes from.

8 A standard report type does not include a custom object.Easy

Standard types are fixed. For a custom object relationship you need a custom report type — and the object must allow reports in the first place.

Check the "Allow Reports" setting on the custom object; it is off by default in some cases.

9 How do you report across two unrelated objects?Hard

You generally cannot in a single report — report types require a relationship.

Options: add a lookup, use a joined report with separate blocks, or move the analysis to CRM Analytics where you can blend datasets.

10 A joined report is the proposed solution.Medium

Joined reports put several blocks side by side with a common grouping — useful for comparing related metrics from different report types.

They are limited in formatting and charting, so check the output is genuinely what the business wanted before building on them.

11 Users want a report on records they cannot see.Easy

Reports respect sharing and FLS, so the report cannot reveal more than the user's access.

If they legitimately need the data, that is a sharing change — not a reporting one. A dashboard with a running user is the other option.

12 A field is missing from the report but visible on the record.Medium

It is not in the report type's field layout, or it is a field type that cannot be reported on (some long text, encrypted fields in certain configurations).

Check the report type first, then FLS, then the field type.

13 You need to report on history.Medium

Field history report types exist for tracked fields, but they are a poor shape for trend analysis.

For trends use Historical Trending (built-in, limited) or Reporting Snapshots (you own the schema and the volume).

14 Should a report type include every field?Easy

No — curate it. Fewer, well-grouped, correctly-labelled fields produce better reports than an exhaustive list.

The field picker is a user interface, and it deserves the same design attention as a page layout.

15 A report type's name means nothing to users.Easy

Name it for the question it answers ("Cases with Milestones and SLA") rather than the object chain.

And put the join semantics in the description, since "with" versus "with or without" is invisible in the name.

16 Row-level formulas are not available.Easy

There is a small limit per report, and they are not supported in every report format or context.

If you need the value repeatedly across many reports, a formula field on the object is the better place for it.

17 A report needs data from a Big Object.Medium

Big Objects are not a standard reporting source. Surface them via CRM Analytics or a custom component instead.

Which is part of why the Big Object index design matters so much up front.

18 How do you decide report type versus CRM Analytics?Medium

Reports for operational, live, single-object-with-children analysis. CRM Analytics when you must blend sources, trend beyond snapshots, or handle multi-million-row datasets.

The honest test: "do I need to join data Salesforce reporting cannot join?" If not, a report is far cheaper to maintain.

Formulas & statistics (19–38)

19 A win rate is wrong when averaged by rep.Hard

You averaged an average. The mean of each rep's win rate weights a rep with 3 deals the same as one with 300.

Compute ratios from summed numerators and denominators at the level you display: SUM(Won)/SUM(Total).

20 Row-level or summary formula?Easy

Row-level for per-record arithmetic; summary for values that only make sense at group or grand-total level — ratios, percentages, margins.

Trying to compute a win rate per row and then summarise it is the commonest cause of wrong numbers.

21 You need "this region as a percentage of total".Medium

PARENTGROUPVAL — it gives you a value from a higher grouping, which is the standard contribution calculation.

Specify the grouping level explicitly; getting the level wrong produces plausible-looking but incorrect percentages.

22 You need period-over-period change.Medium

PREVGROUPVAL against the previous grouping — provided the groupings are ordered sensibly (by period ascending).

If the grouping order changes, the comparison silently becomes meaningless.

23 A summary formula divides by zero.Easy

Guard it: check the denominator with RowCount or the summed value before dividing.

An unguarded division produces an error or a blank where the business expects zero.

24 How do you count distinct values?Hard

Reports count rows, not distinct entities — so a report grouped by account counting opportunities does not give you distinct accounts.

Use a grouping (the group count is the distinct count), a unique-count feature where available, or move to CRM Analytics for genuine distinct aggregation.

25 A currency total is wrong in a multi-currency org.Hard

Conversion: reports convert to the user's or corporate currency, and with Advanced Currency Management the rate depends on the record's date.

Agree with finance which currency and which rate the report should use, and state it in the report description.

26 Two reports on the same data disagree.Hard

Different filters, different report types (inner versus outer join), different date fields, or different sharing for the running user.

Compare the filter sets and the join semantics first — those two account for nearly every discrepancy.

27 A bucket field is not grouping as expected.Easy

Values not explicitly bucketed fall into the "other" catch-all — including new picklist values added after you built it.

Review buckets when picklists change; they are not self-maintaining.

28 You need a calculation reused across many reports.Medium

A formula field on the object, so every report and list view shares the same definition.

Report-level formulas duplicated across fifteen reports will drift apart, and nobody will know which is authoritative.

29 A metric needs a definition everyone agrees on.Medium

Write it down — the numerator, the denominator, the date basis, the exclusions — and put it in the report description.

Undefined metrics produce meetings about the number rather than decisions from it.

30 Percentages do not sum to 100.Medium

Rounding, or records excluded by a filter that the denominator does not account for.

Decide whether the denominator is "all records" or "records in scope", and make it explicit in the label.

31 A conversion rate looks implausibly high.Medium

Check the date basis: counting conversions this month against leads created this month compares two different cohorts.

Cohort analysis needs the denominator fixed to the creation period, which reports handle poorly — a snapshot or CRM Analytics is usually required.

32 Averages are being skewed by outliers.Medium

Median is usually the honest statistic for durations and deal sizes, and reports offer limited support for it.

Show both, or bucket the distribution. An average handle time with one 40-day case in it tells nobody anything.

33 A report shows a total users cannot reconcile.Medium

Likely row duplication from a one-to-many join — each parent appears once per child, so parent-level sums are inflated.

Group by the parent and use a summary formula, or report from the parent object with a roll-up instead.

34 You need a running total.Medium

Reports have limited support; PREVGROUPVAL can accumulate across ordered groupings for simple cases.

For genuine windowing functions, CRM Analytics with SAQL is the right tool.

35 A formula references a field the user cannot see.Medium

FLS applies, so the formula may fail or the field may be unavailable for that user.

Which means a report that works for you can break for others — test as a restricted user.

36 How do you show a target versus actual?Medium

The target must be data: a quota record, a custom object, or a field — reports cannot invent it.

Then a summary formula computes attainment. Hard-coding a target in a formula guarantees it is wrong next quarter.

37 A report's numbers change between runs.Easy

Live data, relative date filters, or records moving in and out of scope. That is usually correct behaviour.

If the business needs a stable number, they need a snapshot — a point-in-time copy, not a live report.

38 The business asks for a statistically significant comparison.Hard

Reports do not do significance testing. Be honest about that rather than presenting a difference as meaningful.

Provide the counts alongside the rates so someone can judge, and escalate genuine statistical questions to a tool built for them.

Filters & data selection (39–56)

39 You need "Accounts without open cases".Easy

A cross filter: Accounts without Cases, with a sub-filter on status.

It is the declarative equivalent of a SOQL anti-join, and the answer to most "records missing something" requests.

40 Mixed AND/OR conditions behave unexpectedly.Medium

Without explicit filter logic, conditions AND together and the report quietly excludes rows.

Set the filter logic with parentheses. Silent exclusion is worse than an error because nobody notices the missing records.

41 A date filter should follow the fiscal year.Easy

Use relative fiscal periods (THIS FISCAL QUARTER) rather than hard-coded dates, so subscriptions and dashboards stay correct.

Hard-coded dates are the most common reason a scheduled report becomes wrong without anyone noticing.

42 You need to compare two fields on the same record.Easy

A field-to-field filter — "Close Date before Created Date", "Actual before Estimated".

Invaluable for data-quality reports, and frequently overlooked because people assume filters only compare to literals.

43 A report should show only the top 10.Easy

A row limit with an explicit sort on a tabular report — which is also what makes a tabular report usable in a dashboard.

Without the sort, "top 10" is whatever the database returned first.

44 Users need to change the filter themselves.Easy

Filter panel options on the report, or dashboard filters at dashboard level.

That beats cloning the report five times for five variations, which is how report folders reach three hundred items.

45 A cross filter is slow.Medium

It is effectively a subquery, and like an anti-join it is rarely selective at volume.

Narrow the main report's filters first, or maintain a roll-up count field on the parent and filter on that instead.

46 The report returns too many rows to display.Easy

Reports cap the rows shown in the UI, and a report that silently truncates is more dangerous than one that fails.

Filter it down, summarise rather than listing, or export via the API if the full set is genuinely needed.

47 How many bucket fields can a report have?Easy

A small limit per report, and they are not reusable across reports.

If the same bucketing appears in several reports, it belongs in a formula field on the object.

48 A filter on a picklist misses records.Medium

Inactive or renamed values, or values available only for certain record types.

Filter on a stable field where possible, and review filters when picklist values change.

49 You need "created in the last 7 days excluding weekends".Medium

Reports cannot do business-day arithmetic. You need a formula field on the object computing the business-day value, then filter on it.

Same principle as SLA calculations: Business Hours live in the data, not in the report.

50 A filter on a formula field is slow at volume.Medium

Cross-object formulas cannot be indexed and are evaluated per row.

Materialise the value into a plain indexable field via automation, backfill it, and filter on that.

51 You need to exclude test records.Easy

A flag field on the records, filtered out — not a name-based filter, which breaks the moment someone names a real record "Test Account Ltd".

And set the flag at creation, so the exclusion is reliable rather than retrospective.

52 A scheduled report stopped being relevant.Medium

Hard-coded dates, or a filter referencing something that changed. Relative dates prevent the first case.

Also review subscriptions periodically — scheduled reports nobody reads are a common form of organisational noise.

53 How do you report on records a user owns or shares?Medium

Scope filters ("My records", "My team's records") handle the common cases without custom filtering.

For more complex definitions you need a field on the record expressing the relationship, since reports cannot traverse sharing logic.

54 A filter needs to be dynamic per viewer.Medium

Scope filters, or a dynamic dashboard that runs as the viewer.

Standard dashboards show one running user's view to everyone, which is the most common cause of a manager seeing the wrong numbers.

55 Two filters that should overlap return nothing.Easy

They are ANDed, so mutually exclusive conditions return an empty set.

Set explicit filter logic with OR where that is the intent — this is the single most common filter mistake.

56 How do you build a data-quality report?Medium

Filter for the bad state: blank required-ish fields, field-to-field contradictions, records without expected children (cross filter).

Then group by owner, so the output is actionable rather than a number.

Dashboards & trending (57–78)

57 A manager sees the VP's numbers on a dashboard.Medium

A standard dashboard runs as one user and shows that user's data view to everyone. This is the number-one dashboard misunderstanding.

Use a dynamic dashboard so it runs as the viewer — noting they are limited in number by edition and cannot be subscribed to in the same way.

58 How many dashboard filters can you have?Easy

A small number per dashboard, each with a limited set of options.

Which means the dashboard should be designed around the two or three distinctions that matter, not every possible slice.

59 One dashboard must show "my team" and "everyone".Medium

Component-level filters let two components use the same report with different scopes, side by side.

That is cleaner than two dashboards that then drift apart.

60 A dashboard shows 20 metrics.Medium

Nobody acts on 20 numbers. Ask which three decisions it supports and build for those.

Also pair every throughput metric with a quality metric, or the dashboard drives the wrong behaviour — see paired metrics.

61 Users want the dashboard to refresh continuously.Medium

Dashboards run their reports on refresh, so continuous refresh means continuous query load — and there are concurrency limits org-wide.

Ask what decision depends on sub-hourly freshness; usually a scheduled refresh plus a "last refreshed" timestamp suffices.

62 A dashboard is slow to load.Medium

It runs every component's report. One unselective report over a large object makes the whole dashboard slow.

Fix the underlying reports' selectivity, reduce the component count, and avoid putting heavy dashboards on a record or home page.

63 How do you alert someone when a metric crosses a threshold?Medium

A report subscription with a conditional alert — it only emails when the condition is met.

Far more useful than a daily email nobody opens, and it is the cheapest monitoring available for business metrics.

64 The business wants last quarter's pipeline as it stood then.Hard

Live reports cannot do that — the records have changed. You need Historical Trending (built-in, limited objects and retention) or Reporting Snapshots.

Snapshots mean you design the schema and own the volume, which is the trade for full flexibility.

65 Which trending tool should you use?Medium

Historical Trending for a few objects and fields with zero setup and a bounded retention window. Reporting Snapshots when you need custom fields, longer history or a different grain.

Beyond either — multi-year, large volumes, blended sources — it is CRM Analytics or a warehouse.

66 A snapshot object is growing fast.Medium

You own the volume: a daily snapshot of 100,000 records is 36 million rows a year.

Snapshot at the grain you actually report on (weekly summaries rather than daily rows), and set a retention policy.

67 A snapshot stopped running.Medium

It is a scheduled job and fails quietly — a source report that changed, a field mapping that broke, or a limit.

Monitor for the expected row count each period and alert on absence, because a gap in trend data cannot be backfilled.

68 You need a chart on a record page.Easy

Embed a report chart filtered by the record — usually better than a custom component.

But it runs the report on page load, so the report's selectivity directly affects page performance.

69 Users cannot see a dashboard you built.Easy

Folder sharing — report and dashboard visibility comes from folder access, not record sharing.

And the data they see still obeys the running user's record access, which is a separate question.

70 How should report folders be organised?Medium

By audience and purpose, with sharing set per folder — and a convention for naming so people can find things.

A flat "Public Reports" folder with 400 items is where reports go to be rebuilt by the next person who needs one.

71 A dashboard needs to be emailed weekly.Easy

Dashboard subscriptions handle it, with the running-user caveat: recipients see the running user's data view.

For per-recipient data you need dynamic dashboards, which have different subscription behaviour.

72 How do you show a trend without snapshots?Medium

Group by a date field on the existing records — which shows when things were created or closed, not what the state was at each point.

That distinction matters: "opportunities created per month" is not "pipeline as it stood each month".

73 A dashboard component shows the wrong chart type.Easy

Chart types depend on the report's groupings and summaries — a chart needs the right grouping structure to be available.

Fix the report's groupings rather than fighting the component.

74 Two dashboards claim different revenue.Hard

Different running users, different filters, different date basis, or different currency conversion.

Agree one authoritative definition per metric, document it, and point other dashboards at the same report rather than reimplementing it.

75 How do you make a dashboard trustworthy?Medium

A documented definition per metric, a visible last-refreshed timestamp, a stated running user, and consistency with the source reports.

Trust comes from provenance, not from polish.

76 Dashboards deploy but look wrong.Medium

Running user, folder, and the underlying reports must all exist in the target org — and the running user may not be the same person.

Verify the running user and folder assignments after every deployment.

77 A dashboard is on the home page for 500 users.Medium

That is 500 report runs per load cycle. Make absolutely sure those reports are selective.

A heavy dashboard on a widely-used home page is one of the easiest ways to make an org feel slow.

78 Nobody uses the dashboard you built.Medium

Usually it does not answer a question they have, or it is not where they work.

Ask which decision it should support, and put it in their path — a dashboard nobody opens is a reporting requirement nobody actually had.

Performance, API & judgement (79–100)

79 A report times out.Medium

Selectivity. Filter on indexed fields, narrow the date range, and remove cross-object formula fields from filters.

Run the Query Plan tool on the equivalent SOQL: cost above roughly 1 means a table scan.

80 A report returns 400,000 rows to show 12 numbers.Medium

It is doing all the work to display almost none. Reduce the row count with filters before grouping.

Summary reports still process the underlying rows, so the filter — not the format — is what makes it fast.

81 Users export huge reports regularly.Medium

Ask what they do with it — usually it is a report that should exist, or an integration that should.

Also note exports are a security surface: Event Monitoring tracks them, and a Transaction Security policy can alert on large ones.

82 You need report data in an LWC.Medium

The Analytics (Reports) REST API runs a report and returns results as JSON, with filters applied at runtime.

That is better than re-implementing the query, because the definition stays in one place that admins can maintain.

83 An external dashboard needs Salesforce data.Medium

The Analytics API for report results, or a direct query via the REST API — and respect the daily API allocation.

A tool polling twenty reports every five minutes will consume a noticeable share of it.

84 Report concurrency limits are being hit.Medium

There are org-wide limits on concurrent report and dashboard runs. Heavy scheduled refreshes plus many users is the usual combination.

Stagger schedules, reduce dashboard component counts, and move genuinely analytical workloads off reports.

85 A report is the only documentation of a business rule.Medium

That happens, and it is fragile — the logic lives in filters nobody reviews.

Document the definition in the report description, and consider whether the rule belongs in a field or automation instead.

86 How do you stop report proliferation?Medium

Filter panels and dashboard filters instead of cloning, folder conventions with ownership, and a periodic review that deletes unused reports.

Usage data makes the deletion defensible; without it nobody dares remove anything.

87 Who should be able to create reports?Medium

Most users, in their own folders — restricting creation produces a queue and shadow spreadsheets.

Control the shared folders and the export permission instead, which is where the real risk is.

88 A report exposes data a user should not see.Hard

Reports respect sharing and FLS, so either the sharing model grants it or a dashboard's running user is wider than intended.

Check the running user first — that is the usual cause, and it looks like a reporting bug rather than a sharing one.

89 Report performance degrades as the org grows.Medium

Expected: filters that were selective stop being selective. The same report changes plan as data grows.

Review the heaviest reports periodically, and consider archiving so the working set stays bounded.

90 The business wants a report Salesforce cannot produce.Medium

Establish whether it is a join reports cannot do, a trend snapshots cannot hold, or a statistic reports do not compute.

Each has a different answer: a schema change, a snapshot, or CRM Analytics. Saying "not possible" without identifying which is unhelpful.

91 How do you migrate reports between orgs?Medium

They are metadata and deploy — but folders, folder sharing, running users and the underlying report types must exist in the target.

Verify after deployment. "Deployed but invisible" is the standard outcome of forgetting the folder.

92 A report needs to drive an action, not just inform.Medium

A conditional alert subscription, or a scheduled flow acting on the same criteria.

A report nobody acts on is a cost. Pair the metric with the decision it supports, or question why it exists.

93 Stakeholders disagree about a number.Medium

Usually a definition disagreement, not a data one. Compare the filters, date basis and denominators side by side.

Then agree one definition, document it, and make the other reports reference the same source — otherwise the meeting recurs.

94 How do you measure whether reporting is working?Medium

Usage data (which reports are actually run), the number of exports to spreadsheets, and how often the same question is asked in different forms.

Heavy spreadsheet export is the clearest signal that reporting is not meeting the need.

95 A manager wants a report built for every request.Medium

Teach the filter panel and give them a good report type — self-service scales and a build queue does not.

Reserve your effort for the report types, the metric definitions and the heavy reports.

96 Reports or CRM Analytics for this requirement?Medium

Reports unless you need to blend sources Salesforce cannot join, trend beyond what snapshots can hold, or handle multi-million-row datasets.

Reports are free, live, and buildable by anyone — which also makes them far cheaper to maintain.

97 A report is business-critical and undocumented.Medium

Document the definition in its description, note its owner, and make sure it is in version control via its metadata.

Critical reports built by someone who left, with filters nobody understands, are a common and avoidable risk.

98 How do you design a report someone will trust?Medium

A clear name stating the question, a documented definition, honest statistics (no averaged averages), relative dates, and a stated scope.

Trust is mostly about provenance and consistency, not presentation.

99 What is the most common reporting mistake?Hard

Averaging averages — followed by the dashboard running-user misunderstanding, and inner joins where an outer join was wanted.

All three produce confidently wrong numbers that nobody questions, which is the worst category of error.

100 One habit that most improves reporting?Hard

Writing the metric definition — numerator, denominator, date basis, exclusions — in the report description before building it.

It prevents averaged averages, settles disagreements before they happen, and makes the report maintainable by someone who was not in the original conversation.
