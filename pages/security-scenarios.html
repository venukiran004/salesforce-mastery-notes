Security & Sharing — 100 Scenarios

"Why can they see this?" and "why can't they?" — object and field permissions, OWD, hierarchy, sharing rules, Apex sharing, external access, encryption and incident response.

📚
How to use this Answer out loud in ninety seconds, then open the answer. Concepts on Security & Sharing and its Advanced section.

"Why can they see this?" (1–10)

1 A user can see a record you believe they should not. Walk your diagnosis.Hard

In order: object permissions (profile + permission sets), FLS for the fields in question, OWD, role hierarchy, sharing rules, manual and Apex shares (query the share object and read the RowCause), implicit parent sharing, team membership, territory, then any restriction rule narrowing it back.

And the one that is the answer more often than anyone expects: without sharing Apex or a system-context flow exposing the data through a component, bypassing everything above.

2 A user cannot see a record they should. Same question, other direction.Medium

Start at the top of the stack because the cheapest checks are first: do they have Read on the object at all, is the record type/layout hiding it, and is the record actually in a state your filter expects?

Then OWD and whether any grant exists: hierarchy (are they above the owner?), sharing rule criteria actually matching this record, team membership, sharing set for external users. Log in as them rather than reasoning — it takes thirty seconds and settles it.

3 Access to an Account unexpectedly grants access to its Cases.Medium

Implicit sharing — parent-to-child grants that exist automatically based on the org's settings, and are invisible in the sharing UI.

If you need child access to be independent, the child must not be master-detail, and you may need to tighten the Account's related-object access settings. Implicit sharing is the correct answer to a large share of "why can they see this" puzzles.

4 A share row exists but you did not create it. How do you find out why?Medium

Query the share object and read RowCause — it names the mechanism: Owner, Rule (a sharing rule), Manual, Team, Territory, ImplicitChild/ImplicitParent, or a custom Apex sharing reason.

That single field turns sharing archaeology into a lookup. It is also why Apex managed sharing should always use a custom RowCause, so your grants are identifiable later.

5 Removing a sharing rule does not immediately remove access.Medium

Share rows are materialised, and recalculation is asynchronous — potentially hours on a large org.

If the access must be revoked immediately for a security incident, do not wait: restrict at the object or profile level, or freeze the user. Sharing recalculation is not an incident-response tool.

6 A manual share vanished after the record changed owner.Easy

Expected: manual shares are deleted when ownership changes.

For durable grants use Apex managed sharing with a custom RowCause, which survives owner changes and can be reported on. If the access is rule-based rather than exceptional, a criteria-based sharing rule is better than either.

7 A report shows records a user cannot open.Medium

Check whether the report is on a dashboard with a running user — a standard dashboard shows one user's data view to everyone, which is the single most common dashboard misunderstanding.

If it is a report they ran themselves, the data respects their access, so the discrepancy is usually a cached view or a record whose sharing changed since. Dynamic dashboards run as the viewer and solve the first case.

8 An LWC shows data the user should not see.Hard

Its Apex is almost certainly running without sharing, or with sharing but not enforcing FLS — because with sharing controls record visibility only and never field-level security or object permissions.

Fix in Apex: WITH USER_MODE on queries, as user on DML, or Security.stripInaccessible. Hiding fields in the template is presentation, not security. See user-mode queries.

9 A user in a parent role cannot see a subordinate's records.Medium

Check "Grant Access Using Hierarchies" on the object — it can be disabled for custom objects, which stops hierarchy-based roll-up entirely.

Also confirm the role hierarchy is what you think (people are frequently in the wrong role), and that the records are owned by the subordinate rather than a queue or another user.

10 Everything looks correct but access is still wrong.Hard

Look for the things that are not in the sharing model: a restriction rule removing access that sharing granted, a scoping rule changing the default view (which looks like missing access but is not), or permission set muting inside a permission set group subtracting a permission.

Then check the user's actual permission set assignments rather than their profile — in a modern org most access comes from permission sets, and people reason about profiles out of habit.

OWD, hierarchy & sharing rules (11–20)

11 The business says "everyone should see everything". Do you set Public Read/Write?Medium

Challenge it, then document the decision. Open OWD is simple and fast, but it removes your ability to tighten later without a painful migration, and it is rarely what compliance actually agreed to.

Prefer Private or Public Read Only with sharing rules granting the openness — the same visible outcome with the ability to restrict one object or one population later. Going from open to private on a large object means a sharing redesign plus recalculation.

12 You need to change OWD from Public Read to Private on 20 million records.Hard

This triggers a full sharing recalculation that can run for a very long time and locks group membership while it does.

Plan it as a change: do it in a maintenance window, ask Salesforce about deferred sharing maintenance so you can batch the related role and rule changes and resume once, and rehearse in a Full sandbox to time it. Never do it piecemeal during business hours.

13 Criteria-based or owner-based sharing rule?Easy

Owner-based when access follows who owns the record (give the EMEA role's records to the EMEA support group). Criteria-based when access follows the record's data (all records where Region = EMEA).

Criteria-based rules recalculate when the criteria fields change, so they cost more at volume — and there are limits on how many you can have per object, which is a real constraint in a complex org.

14 You need sharing based on a field on the parent record.Hard

Criteria-based sharing rules evaluate fields on the record itself, so a parent field is not directly usable.

Patterns: a formula field on the child copying the parent value (but formula fields are not always usable in sharing criteria), automation stamping a plain field on the child, or Apex managed sharing which can evaluate anything you can query. Stamping a field is usually the cheapest and most debuggable.

15 Sharing rules hit the per-object limit.Hard

Consolidate: replace many narrow rules with fewer rules granting to public groups whose membership encodes the distinction, which is far more maintainable anyway.

If the model genuinely needs per-record decisions, move to Apex managed sharing with a custom RowCause, or reconsider whether the hierarchy and ownership design is doing its job. Hitting the limit is usually a symptom of sharing being used to express something ownership should.

16 Role hierarchy is 12 levels deep and performance is poor.Hard

Deep hierarchies multiply share rows and recalculation cost. The hierarchy should model access roll-up, not the HR org chart.

Flatten it: typically far fewer levels than the management structure, with public groups and sharing rules handling the exceptions. Reorganising a hierarchy is a heavy change, so plan it with deferred sharing maintenance and a sandbox rehearsal.

17 An executive needs read access to everything, without Modify All Data.Medium

View All on the relevant objects via a permission set — object-scoped read-everything, without the write and delete power of Modify All Data.

Prefer View All on specific objects over View All Data org-wide, and record the business justification; these are exactly the permissions a Health Check and an auditor will ask about.

18 A team needs access to one Account's records, including from other owners.Medium

Account teams (or Opportunity/Case teams) are built for exactly this, with per-member access levels, and they are maintainable by the account owner rather than an admin.

Alternative for a stable pattern: a criteria-based sharing rule on a field identifying the account tier, granting to a public group. Teams for exceptions and per-record variation; rules for patterns.

19 Territory management or role hierarchy for sales access?Hard

Role hierarchy when access follows management lines and ownership is stable. Enterprise Territory Management when access follows territory assignment that changes independently of management — and when you need territory-based forecasting and reporting.

Be explicit about the cost: territories are a second hierarchy to maintain alongside roles, with their own assignment rules and recalculation. Powerful and genuinely heavy. See Sales Cloud.

20 Can you share a master-detail child independently of its parent?Easy

No. Master-detail children have no share object and inherit access from the master entirely.

If independent sharing is required, the relationship must be a lookup with its own OWD — at the cost of roll-up summaries and cascade delete. That trade is a data-model decision to make before building, because converting later is a migration.

Profiles, permission sets & FLS (21–30)

21 You inherit 40 profiles. What is your plan?Hard

Freeze profile editing first — all new permissions go into permission sets from today, or you are chasing a moving target forever.

Then build permission sets around capabilities ("Approve Discounts", "Manage Knowledge"), compose them into permission set groups per role, use muting to subtract for exceptions, and strip profiles to the minimum (login hours, IP, defaults, layout and record type assignments). Verify per user with a before/after comparison and keep the evidence.

22 Permission set group grants something one population must not have.Medium

Use a muting permission set inside the group to subtract that permission, rather than cloning the entire group.

That is the whole point of muting: one group definition with targeted subtractions, instead of five near-identical groups that drift apart over time.

23 A user has a permission you cannot find the source of.Medium

Permissions are the union of profile, every assigned permission set, and every permission set group (minus muting). Check all of them — people reason about the profile and forget the other three.

Also check permission set licences, which can enable capability independently, and whether the permission comes from a managed package's own permission sets.

24 FLS hides a field but it appears in a report.Medium

FLS is enforced in reports, so if it appears, the user has Read on that field somewhere — check every permission set and group, not just the profile.

If it appears for a different user running the report on a dashboard, that is the running-user issue rather than FLS.

25 Does with sharing enforce field-level security?Easy

No — and this is the single most common misunderstanding in Salesforce security. with sharing controls which records are visible. FLS and object permissions are never enforced by it.

Enforce them explicitly: WITH USER_MODE, as user DML, Security.stripInaccessible, or field-level isAccessible() checks.

26 What is inherited sharing for?Medium

A reusable class that should take the sharing mode of whatever calls it — the correct default for library and service classes.

It is also the only safe-by-default choice when the class can be entered from a Visualforce page or a REST endpoint, where an unannotated class would run in system mode. Note inner classes do not inherit the outer class's declaration.

27 A developer used without sharing "because it was easier".Medium

Triage rather than rewrite: classify every usage as genuinely needing elevation (document why), should be with sharing, or should be inherited sharing.

Prioritise anything reachable from an @AuraEnabled method on a guest-accessible page or a REST endpoint — that is an exfiltration path, not a style issue. Keep deliberate elevation small, single-purpose and reviewed.

28 You need a permission for 200 users for two weeks only.Easy

A permission set with an expiration date on the assignment where available, or a dated assignment you remove via a scheduled job — and a calendar reminder regardless.

Temporary permissions that nobody removes are a standard audit finding. Build the removal into the same change as the grant.

29 How do you prove least privilege to an auditor?Hard

With artefacts, not assertions: Security Health Check scores over time, a documented permission model (capability-based permission sets composed into groups per role), a list of who holds Modify All Data / View All Data with justifications, and evidence of periodic access review.

Plus the change trail: permission changes going through pull requests, and Setup Audit Trail reviewed. "We think it's minimal" is not a control.

30 Profiles cause merge conflicts on every PR. Remove them from git?Medium

Usually yes, once they are minimal. A profile is one huge XML file so unrelated features both rewrite it, and people learn to resolve those diffs carelessly — including the ones that matter.

Move permissions to permission sets, .forceignore the profiles, and document that profiles are now managed deliberately per org. The trade must be explicit, or you have just created an unmanaged surface. See the merge problem.

Apex sharing & programmatic access (31–40)

31 You need to grant access programmatically based on a complex rule.Medium

Apex managed sharing: insert Object__Share rows with ParentId, UserOrGroupId, AccessLevel and — crucially — a custom RowCause created in Setup, so the grants survive ownership changes and are identifiable.

The class needs elevated context to insert shares, so keep it small and reviewed, and use Database.insert(shares, false) so one bad row does not lose the rest.

32 Your Apex shares disappeared after a sharing recalculation.Medium

You used the Manual RowCause, which the platform manages and removes. Custom Apex sharing reasons are preserved.

Re-create them with a custom reason, and add a reconciliation job that re-asserts expected shares — any programmatic sharing model needs a way to detect and repair divergence.

33 Stale Apex shares grant access long after the reason ended.Medium

Nothing cleans them up for you. Whatever creates shares must also delete them when the condition no longer holds, and a scheduled reconciliation should catch the gaps.

Stale shares are a common audit finding precisely because the grant path gets built and the revoke path does not.

34 You cannot share above the OWD. Why does that matter?Easy

Sharing only ever grants. If OWD is Public Read/Write, share rows achieve nothing — so a team building elaborate sharing on an open object is wasting effort.

Corollary: to tighten access you change OWD (and then grant back), or use a restriction rule, which is the only mechanism that removes access sharing has given.

35 An integration user needs broad access. How do you scope it?Medium

A dedicated integration user with a least-privilege permission set — only the objects and fields the integration touches, and View All only where genuinely required.

Never a named human's admin account: it breaks when they leave and makes every audit trail ambiguous. Add IP restrictions where the caller has stable egress, and scope the Connected App's OAuth scopes to the minimum.

36 A flow can see records the running user cannot. Is that a bug?Medium

No — record-triggered flows run in system context without sharing by default. It is powerful and it is a security review item.

Autolaunched flows let you choose the context explicitly; screen flows run as the user. Choose deliberately, write the choice in the flow description, and be especially careful with anything reachable by a guest user. See running context.

37 How do you enforce FLS on a dynamic SOQL query?Hard

Append WITH USER_MODE, or run the results through Security.stripInaccessible(AccessType.READABLE, records) and use getRecords().

And escape the dynamic parts: String.escapeSingleQuotes() on any user-supplied fragment, with bind variables wherever possible. Dynamic SOQL built by concatenation is both an injection risk and an FLS risk.

38 A test passes as admin and fails for real users.Medium

Tests run in system mode by default, so they never exercise the sharing and FLS your users experience.

Use System.runAs with a user created from a minimum-access profile plus only the permission set under test — not an admin. That is the test that finds the access bug before your users do. See testing permissions.

39 Should an @AuraEnabled method trust the client?Easy

Never. Every @AuraEnabled method is a callable endpoint for anyone who can load the component — including, on a public page, anonymous visitors.

Re-check CRUD, FLS and sharing server side, validate and bound every parameter, and never accept a filter expression or an object name from the client. Client-side checks are UX.

40 An Apex REST endpoint needs to be callable by a partner but see only their data.Hard

Authenticate as a user whose access is the restriction — a per-partner integration user or a per-user OAuth principal — and write the class with sharing so record access does the filtering.

Do not implement the filter as a WHERE clause on an elevated query; a bug in that clause becomes a data breach, whereas sharing failing closed is the safer default. Then log every request with a correlation id.

External & guest access (41–50)

41 100,000 community users need to see their own cases.Medium

High-volume Customer Community licences have no role hierarchy, so the mechanism is a Sharing Set matching the user's Contact or Account to a field on the Case.

For internal staff to see records those users own, you additionally need a Share Group — otherwise those records are invisible to everyone else. See external sharing.

42 Should External OWD be enabled?Easy

Yes — it gives external users a separate OWD so you can lock their access down without constraining internal users.

A single OWD for both populations is how community data leaks: an internal convenience setting silently becomes an external grant.

43 A guest user can read records you did not intend.Hard

Review the guest profile's object and field permissions first — FLS on the guest profile is the control that actually prevents exposure. Then check guest sharing rules (guests cannot be targets of ordinary sharing rules) and that "Secure guest user record access" is enabled.

Then audit code paths: any @AuraEnabled method or system-context flow reachable from a public page. Finally, test as the guest in an incognito window and try to read what you did not intend.

44 Guest users are creating spam records.Medium

A guest-writable object with no validation is a target. Add CAPTCHA and honeypots on the form, rate-limit at the web layer, validate server side, and route submissions to a review queue rather than into live data.

Also remember guest users cannot own records, so creations are reassigned to a default owner you must configure — and that owner can develop ownership skew if volumes are high.

45 Partners must see their own and their resellers' opportunities.Hard

Partner Community licences with partner roles under each account, Super User access for partner managers, and External Account Hierarchy for the distributor-to-reseller tier.

Verify the licence includes Opportunity — Customer Community does not. Then test as each persona, because multi-tier channel access is where external sharing models most often turn out to be wrong in one direction or the other.

46 A community user can see another customer's record.Hard

Treat it as an incident: contain first. Tighten the object permission or disable the page while you diagnose, rather than attempting an elegant fix live.

Then find the grant: an over-broad Sharing Set match field, a sharing rule that includes external users, an elevated Apex method, a system-context flow, or External OWD left open. Afterwards, assess exposure with Event Monitoring and write up what made it reachable.

47 Self-registration is creating users with too much access.Hard

The self-registration Apex handler is a public endpoint. Never trust supplied profile, role or permission values — assign them server side from a fixed, least-privilege configuration.

Add CAPTCHA, rate limiting and email verification, and review the default profile's permissions field by field. This handler is one of the most commonly exploited surfaces in Experience Cloud.

48 How do you review what anonymous visitors can reach?Hard

Five surfaces, with evidence for each: the guest profile's object and field permissions; the guest sharing rules; every @AuraEnabled method reachable from a public page; every flow running in system context on that page; and the self-registration handler.

Each site has its own guest user and profile, so hardening one does not harden the others. Then test it as the guest rather than reading configuration.

49 Contractors need access to only their own field service appointments.Medium

Experience Cloud with Sharing Sets matching the contractor's Contact to the Service Resource and Assigned Resource records — or dedicated contractor licences.

Test with a real contractor login, including the mobile app: under-sharing shows up as blank screens on the device, which looks like a mobile bug for days. See Field Service sharing.

50 A public Experience Cloud site needs to be indexed by Google but not leak data.Hard

Separate the content from the data. Public, indexable content (LWR for SEO and performance) should be CMS or Knowledge articles exposed deliberately via data category visibility — not records surfaced by a permissive guest profile.

Anything record-backed stays behind authentication. The failure mode is exposing a record-driven page to guests for SEO and discovering a search engine has indexed customer data.

Encryption, PII & compliance (51–60)

51 Legal asks you to "encrypt all PII".Hard

Clarify the threat model first, because Shield Platform Encryption protects data at rest from infrastructure-level access — it does not hide data from a user who has FLS on the field.

If the requirement is "staff must not see it", that is field-level security. If it is "it must be encrypted at rest for compliance", that is Shield — and it breaks filtering, sorting, some formulas and matching rules, so scope it to the fields that genuinely need it.

52 An encrypted field can no longer be used in a report filter.Medium

Expected: filtering and sorting on encrypted fields is restricted, and that is the main functional cost of Shield.

Design around it: keep a non-sensitive derived field for filtering (a hashed key, a bucketed value), or reconsider whether that field needs encryption. Discovering this after encrypting a field used in fifty reports is an expensive week.

53 Who holds the encryption key, and what happens if it is destroyed?Hard

With bring-your-own-key you do, which is the point and the risk: destroying a key makes the data permanently unreadable, and that is not recoverable by Salesforce.

So key management needs real process — custody, rotation schedule, documented recovery, and a named owner. Teams adopt BYOK for a compliance tick and then have no key-rotation runbook.

54 A customer invokes their right to be forgotten.Hard

Deletion must cascade further than people expect: the record, history, feeds, files, email logs, Big Objects, backups, sandboxes, and downstream systems you have fed.

Build it as a documented, repeatable process with a verification step rather than an ad-hoc query — and decide between deletion and anonymisation, since anonymisation often preserves reporting integrity while meeting the requirement.

55 Sandbox contains real customer data and developers have full access.Medium

That is a compliance exposure and usually a policy breach. Run Data Mask as part of the post-refresh checklist, before anyone logs in.

Also set email deliverability to System Email Only first — the masking conversation is often triggered by test emails reaching real customers, which is the more visible failure. See post-refresh.

56 You need to prove who exported a report containing PII.Medium

Event Monitoring — report export events are among the most valuable log types it provides, and it is the only retrospective answer.

Without Event Monitoring you cannot answer the question after the fact, which is itself worth knowing before an incident. Real-Time Event Monitoring plus a Transaction Security policy lets you alert on or block large exports as they happen.

57 Consent is recorded in three systems and they disagree.Hard

Nominate one system of record per channel and sync outward from it — Salesforce's Individual and consent objects, Account Engagement opt-out, Marketing Cloud subscriber status.

A preference centre that updates one system and not the others is a regulatory finding waiting to be found. Also record proof: the timestamp, source, and the exact wording shown. See consent architecture.

58 Field Audit Trail or Field History Tracking?Easy

Field History Tracking is a convenience: a limited number of fields per object and limited retention. Field Audit Trail (Shield) extends retention substantially and is the right answer when a regulator asks the question.

Decide from the requirement's retention period, not from the feature list — and remember neither is a reporting-friendly shape for trend analysis.

59 A Transaction Security policy could block a risky action. Should you use it?Medium

Yes for well-understood, high-signal cases: a very large report export, a login from an unexpected region, a mass data operation. Start in notify mode to measure false positives before you block anything.

Blocking first produces business disruption and a policy that gets switched off. Notify, tune, then enforce.

60 Security Health Check score dropped 20 points. What happened?Medium

Something was relaxed — usually a password policy, session timeout, or a "temporary" permission grant that became permanent.

Health Check scores drift downward because exceptions accumulate. Run it quarterly with a named owner, and treat each regression as a ticket with a justification or a fix. See platform health.

Incidents & investigation (61–70)

61 You suspect an account is compromised. First three actions?Hard

Freeze the user (instant and reversible, unlike deactivation), revoke their OAuth tokens and sessions, and preserve evidence — login history, Event Monitoring logs, Setup Audit Trail — before anything is overwritten or rotated.

Containment before diagnosis, diagnosis before elegance. Only then work out what was accessed and what needs changing.

62 Data was exfiltrated via the API. How do you find out what?Hard

Event Monitoring API and Apex execution events, plus login history for the source, and the Connected App's usage page for which app and which tokens.

Without Event Monitoring, you will not be able to answer this — which is the argument for having it before you need it. Build the query and the dashboard in advance, not during the incident.

63 A departing employee may have downloaded customer lists.Hard

Report export events in Event Monitoring, plus login history and any Data Loader usage. Freeze first if they are still active.

Preventatively: a Transaction Security policy on large exports, restricting export permissions by profile, and making report folder access deliberate. This is a predictable risk that most orgs only instrument after the first occurrence.

64 An integration user's credentials leaked.Hard

Revoke the tokens from the Connected App immediately (which is faster than rotating the user), then rotate the certificate or client secret, then redeploy the pipeline's secret.

Afterwards: move to JWT bearer with a certificate rather than a stored password, add IP restrictions where egress is stable, scope OAuth scopes to the minimum, and set refresh token policy to expire on inactivity rather than "until revoked". See token lifecycle.

65 A security researcher reports a vulnerability in your community.Hard

Acknowledge, contain, verify, then fix forward. Containment might be disabling a page or tightening a guest permission — accept the functionality loss while you diagnose.

Verify the claim yourself as the guest or external user before changing architecture, then fix through the hotfix path with a test that fails without the fix. And write up what made it reachable, because the same class of hole usually exists elsewhere.

66 How do you detect a permission change nobody authorised?Medium

Setup Audit Trail reviewed weekly, plus permission changes going through pull requests so there is an approved record — and drift detection flagging metadata that differs from main.

The detection is only useful with a named owner and a cadence. An unread audit trail is not a control. See drift detection.

67 Logs show a user accessing records at 3am from an unusual country.Medium

Verify before accusing — travel, VPNs and offshore teams are common explanations. Check login history for the IP, device and auth method, and whether MFA was satisfied.

Then prevention: login IP ranges, login hours, high-assurance sessions for sensitive operations, and a Transaction Security policy for anomalous logins. Investigation first, policy second.

68 You need to know every user who can see a specific record, today.Hard

Query the object's share table for that ParentId and resolve the UserOrGroupId values through group membership — plus everyone above the owner in the hierarchy, plus anyone with View All or Modify All on the object.

That last part is why the honest answer always includes "and all administrators". Produce it as a repeatable script, because this is a question auditors ask more than once.

69 An admin deleted 50,000 records by mistake.Hard

Check the recycle bin immediately — it has capacity limits and purges, so time matters. Restore in batches and verify counts.

If it was a hard delete or the bin has purged, you are into backup restore, and this is where "we have a backup we have never restored" becomes expensive. Afterwards: restrict delete permissions, and require bulk operations to go through a reviewed process.

70 What is the most common root cause of Salesforce data exposure?Hard

Elevated code reachable from an under-protected surface: an @AuraEnabled method or a system-context flow, running without sharing, exposed on a guest-accessible Experience Cloud page.

The sharing model is usually fine; the bypass around it is the problem. Which is why the review question is not "is our OWD private" but "what code can an anonymous visitor cause to run, and in whose context?"

Design decisions (71–85)

71 Design sharing for 500 internal, 200 partners, 100,000 customers.Hard

Three populations, three mechanisms. Internal: private OWD, role hierarchy for roll-up, criteria or owner-based rules for cross-team, teams for exceptions. Partners: Partner Community licences, partner roles under the account, Super User, External Account Hierarchy for tiers. Customers: high-volume licences, so Sharing Sets plus a Share Group for internal visibility.

Then External OWD separately, guest hardening if anything is public, and a plan for recalculation time at that volume.

72 Private OWD plus 40 sharing rules — is that a smell?Medium

Usually yes. Forty rules means sharing is being used to express something ownership or hierarchy should, and it will hit per-object limits and recalculation cost.

Consolidate: grant to public groups whose membership encodes the distinction, revisit whether the hierarchy models access correctly, and consider whether some populations belong in teams or territories instead.

73 Restriction rule or a tighter OWD?Medium

OWD plus grants is the primary model and scales. A restriction rule is for subtracting access that sharing legitimately granted — "support agents see only their region's cases" on top of an otherwise open model.

Remember restriction rules apply to reports and API too (which is the point), so an integration running as a restricted user will also be narrowed. Test that path explicitly.

74 Is a scoping rule a security control?Easy

No. Scoping rules change the default view — users can still reach the records.

They are a usability feature, and presenting one to an auditor as a control is a mistake that will be found. Restriction rules remove access; scoping rules tidy list views.

75 Sales must not see each other's opportunities, but managers must.Easy

Private OWD plus the role hierarchy — that is precisely what the hierarchy is for, and it requires no sharing rules.

Check "Grant Access Using Hierarchies" is on (it can be disabled for custom objects), and that managers are actually above their reports in the role hierarchy rather than just the HR org chart.

76 HR data must be invisible to everyone except HR, including admins.Hard

You cannot fully hide data from a system administrator — Modify All Data and View All Data exist, and so does the ability to grant themselves access.

What you can do: a separate object with private OWD and tightly scoped permissions, remove View All/Modify All from everyone who does not need it, enable Event Monitoring so access is detectable, and consider a separate org if the requirement is absolute. Be honest with the business about the difference between prevention and detection.

77 Should you use a permission set or a profile for a new capability?Easy

Permission set, always, for anything new. Profiles should hold only login hours, IP ranges, defaults, and layout and record type assignments.

Capability-based permission sets compose into permission set groups per role, which is maintainable, reviewable and mergeable — unlike profiles. See the migration.

78 An object needs different access for the same user depending on record state.Hard

Sharing is not state-aware in that way. Patterns: criteria-based sharing rules keyed on a status field (they recalculate when it changes), Apex managed sharing maintained by automation, or record-level ownership changes as the record moves through states.

Also consider whether the requirement is really about editability rather than visibility — a validation rule or a record-locking approval step may be the right control instead.

79 You need field-level access to differ by record, not by user.Hard

FLS is per user and per field — it cannot vary per record. There is no record-level field security.

Workarounds: move the sensitive data to a related record with its own sharing, or encode the distinction in record types plus separate fields. If someone proposes hiding a field conditionally on the layout, be clear that this is presentation only and the data remains available via API.

80 How do you design sharing you can still change in two years?Hard

Keep OWD tight and grant through public groups rather than roles or named users, so changing who has access is a membership change rather than a rule rewrite. Keep the role hierarchy shallow and about access, not HR.

Document the intent of every rule, and prefer a few general rules over many specific ones. Sharing models become unchangeable when nobody can tell which of forty rules is load-bearing.

81 A managed package requests broad permissions on install.Medium

Install in a sandbox and review what it actually adds: permission sets, objects it reads, and whether any of its Apex runs without sharing in paths you expose.

Check what data leaves your org and to where, for your own compliance position. A completed security review means it met a bar, not that its permission footprint suits your org. See ISV discipline.

82 You need to let a support engineer impersonate a user.Medium

Login As, granted deliberately via the "Administrators Can Log in as Any User" setting and restricted to the people who genuinely need it.

It is logged, so it is auditable — make sure someone reviews those logs. And it is the single most useful diagnostic tool for access problems, so the answer is usually "grant it narrowly" rather than "never".

83 MFA is mandatory but a service account cannot do it.Medium

Service accounts should not be logging in interactively at all — use JWT bearer or client credentials with a certificate, which sidesteps the question entirely.

If an account genuinely must have a password, it needs a documented exemption, IP restrictions, and a rotation schedule. An MFA exemption with no compensating control is an audit finding.

84 How do you handle a break-glass admin account?Hard

At least one administrator who can authenticate without the IdP — password plus MFA — because an SSO design with no break-glass path is one IdP outage away from nobody being able to fix it.

Controls: credentials in escrow, MFA on a shared hardware token, login alerting on the account, periodic verification that it still works, and an audit trail of every use. Test it on a schedule; an untested break-glass account is a belief.

85 Compliance wants a quarterly access review. How do you make it sustainable?Medium

Automate the evidence: a scheduled report or script producing who holds elevated permissions (Modify All, View All, Export, Login As), who has not logged in for 90 days, and what changed since last quarter.

Then the review is a decision meeting rather than a data-gathering project. A manual quarterly review built from scratch each time gets skipped by the third quarter.

Judgement & trade-offs (86–100)

86 A deadline is tomorrow and the secure design needs two more days.Hard

Offer a safe subset rather than a binary. Ship with the surface narrowed — one profile, internal users only, feature-flagged off for guests — and complete the full design next week.

State the residual risk explicitly in writing, and who is accepting it. "We shipped it insecurely because of the deadline" should never be an undocumented decision made by the developer alone.

87 A stakeholder insists hiding the field on the layout is sufficient.Easy

Demonstrate it: one REST call, or export the report, and show the data. Thirty seconds of evidence ends the argument more effectively than any explanation.

Then do it properly with field-level security, and note that component visibility and Dynamic Forms conditions are in the same category — presentation, not control.

88 You find a sharing hole that has existed for three years.Hard

Assess exposure before you close it — what was reachable, by whom, and is there evidence it was accessed (Event Monitoring, report exports, API logs)? Closing it first destroys your ability to answer that.

Then fix, notify whoever owns the compliance position, and review whether the same class of hole exists elsewhere. Age does not reduce severity; it increases the exposure window.

89 Security review flags 40 issues. How do you prioritise?Medium

By reachability and blast radius, not by the tool's severity label. Anything an anonymous or external user can reach comes first; then internal elevation; then hardening and hygiene.

Fix the categories, not the instances: if one @AuraEnabled method lacks FLS enforcement, the pattern probably repeats — fix the pattern and add a review checklist item.

90 Developers say enforcing FLS everywhere is too much work.Medium

Make it cheap rather than optional: WITH USER_MODE on queries and as user on DML are a few characters, and a selector layer centralises it so it is written once per object.

Add it to the PR checklist and to static analysis so it is caught automatically. Security that depends on individual diligence on every method will fail; security that is the default path will not.

91 An integration needs View All Data. Do you grant it?Medium

Not reflexively. Ask which objects and which records — usually the real need is View All on two objects, not org-wide.

Grant the minimum through a permission set on a dedicated integration user, document the justification, and review it periodically. "The vendor's documentation said to" is not a justification.

92 Two teams need opposite sharing on the same object.Hard

Set OWD to the tighter requirement and grant the looser one back through sharing rules to a public group. Sharing only ever grants, so the restrictive requirement must be the baseline.

If one team needs less than the baseline grants, that is a restriction rule — the only mechanism that subtracts.

93 Is Shield worth it?Medium

Depends which part. Event Monitoring is frequently the highest-value component — it is the only retrospective answer to "who accessed what", and most orgs cannot answer that today. Field Audit Trail is worth it when retention is a regulatory requirement.

Platform Encryption is worth it when the threat model genuinely requires at-rest encryption, and costly in functionality when adopted as a tick-box. Price the components separately against actual requirements.

94 The business wants to copy production data to a demo org.Medium

Mask it first, and check whether your policy or regulator permits it at all. A demo org is usually less controlled than a sandbox, with more people having access.

Better: generate synthetic data that demonstrates the same shapes. It is a day of work once and it removes a recurring compliance conversation permanently.

95 How do you security-review a flow?Medium

Three questions: what context does it run in (record-triggered flows default to system context without sharing); what can invoke it (is it reachable from a guest page or an external user); and what does it touch (which objects and fields, and does it return data to the client).

A system-context flow exposed to guests is the same risk class as without sharing Apex, and it is reviewed far less often.

96 You are asked to sign off a design you think is unsafe.Hard

State the specific risk, the realistic scenario, and the mitigation cost — in writing, in one page. Then let the accountable person decide; if they accept it, record the acceptance and move on.

Vague objections get overruled. A concrete "an authenticated customer can read other customers' invoices via this endpoint; two days to fix" either gets fixed or gets consciously owned, and both are better than an unresolved worry.

97 What is the first thing you check on a new org's security posture?Medium

Who has Modify All Data and View All Data, and why. It is the fastest signal of whether access is designed or accumulated.

Then Health Check, guest user profiles on any site, External OWD, and a grep for without sharing. Those five checks give you an accurate picture in under an hour.

98 How do you keep a sharing model documented without it rotting?Medium

Document intent in the metadata itself — the description field on every sharing rule, permission set and permission set group — so it travels with the configuration and appears in diffs.

Separate documents rot because they live elsewhere. A rule whose description says "granted for the 2023 EMEA support model" is one you can confidently delete in 2026; an undescribed rule is one nobody dares touch.

99 A permission was granted "temporarily" eighteen months ago.Easy

Remove it, or justify it as permanent and document that. Temporary grants that nobody revokes are the most common way least privilege erodes.

Prevention: expiration dates on permission set assignments where available, and a quarterly review that specifically lists grants older than their stated purpose.

100 One habit that prevents most security incidents here?Hard

Asking, of every piece of code and every flow: "who can cause this to run, and in whose context?" Almost every real Salesforce exposure is elevated logic reachable from an under-protected surface, not a misconfigured sharing rule.

Make it a required line in every pull request template. It costs nothing and it catches the category of bug that actually makes the news.
