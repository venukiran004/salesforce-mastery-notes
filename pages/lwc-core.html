Lightning Web Components — Core

Component anatomy, decorators, reactivity, getters and setters, conditional rendering, lists, lifecycle hooks and the Shadow DOM.

Component anatomy

LWC is built on modern web standards (ES modules, custom elements, Shadow DOM) with a thin Salesforce layer on top. A component is a folder whose files share the folder's name.

The component bundle
<template>
    <lightning-card title="Accounts" icon-name="standard:account">
        <div class="slds-var-m-around_medium">

            <lightning-input
                label="Search"
                value={searchTerm}
                onchange={handleSearchChange}>
            </lightning-input>

            <template lwc:if={hasAccounts}>
                <ul>
                    <template for:each={accounts} for:item="acc">
                        <li key={acc.Id} class="slds-var-p-vertical_xx-small">
                            {acc.Name} — {acc.Industry}
                        </li>
                    </template>
                </ul>
            </template>
            <template lwc:else>
                <p class="slds-text-color_weak">No accounts found.</p>
            </template>

        </div>
    </lightning-card>
</template>
import { LightningElement, api, wire } from 'lwc';
import getAccounts from '@salesforce/apex/AccountController.getAccounts';

export default class AccountList extends LightningElement {
    @api recordId;                 // public — set by the parent or the record page
    searchTerm = '';               // private, but still reactive
    accounts = [];
    error;

    @wire(getAccounts, { searchKey: '$searchTerm' })
    wiredAccounts({ data, error }) {
        if (data)  { this.accounts = data;  this.error = undefined; }
        if (error) { this.error = error;    this.accounts = []; }
    }

    get hasAccounts() {
        return this.accounts && this.accounts.length > 0;
    }

    handleSearchChange(event) {
        this.searchTerm = event.target.value;
    }
}

📛
Naming rules Folder/file: camelCase. In markup: <c-account-list> — the namespace prefix c- plus kebab-case. Attributes in markup are kebab-case (record-id) but camelCase in JS (recordId). The class must be the default export and extend LightningElement.

Properties & data binding

LWC uses one-way data binding: the template reads from the JS class. To change data you handle an event and assign in JavaScript — the template then re-renders automatically.

<template>
    <!-- Text interpolation -->
    <p>Hello {greeting}</p>

    <!-- Attribute binding -->
    <lightning-input value={greeting} onchange={handleChange}></lightning-input>
    <img src={imageUrl} alt={altText} />

    <!-- Nested property access IS allowed -->
    <p>{account.Name}</p>

    <!-- ❌ NOT allowed: expressions, function calls, operators -->
    <!-- {count + 1}  {items.length}  {getName()}  {a && b} -->
    <!-- ✅ Use a getter instead -->
    <p>{itemCount}</p>
</template>
import { LightningElement } from 'lwc';

export default class Binding extends LightningElement {
    greeting = 'World';
    items = ['a', 'b', 'c'];
    account = { Name: 'Acme' };

    get itemCount() {
        return this.items.length;     // computed values live in getters
    }

    handleChange(event) {
        this.greeting = event.target.value;   // assignment triggers re-render
    }
}

Reactivity — the rule that catches everyone

What actually triggers a re-render
import { LightningElement, track } from 'lwc';

export default class Reactivity extends LightningElement {
    // Reassignment is reactive without any decorator (since Spring '20)
    count = 0;
    items = [];

    // @track makes the INSIDE of an object/array reactive too
    @track state = { filters: { status: 'Open' }, page: 1 };

    addWrong(item) {
        this.items.push(item);                 // ❌ template won't update
    }
    addRight(item) {
        this.items = [...this.items, item];    // ✅ new array reference
    }
    updateNested() {
        this.state.filters.status = 'Closed';  // ✅ works because of @track
    }
}

Decorators

DecoratorImport fromPurpose
@apilwcMakes a property or method public — settable by a parent or by App Builder
@tracklwcMakes object/array internals deeply reactive. Rarely needed now
@wirelwcReads Salesforce data reactively — see Wire service
 
import { LightningElement, api } from 'lwc';

export default class Child extends LightningElement {
    // Public PROPERTY — parent sets <c-child record-id={id}>
    @api recordId;
    @api title = 'Default title';

    // Public METHOD — parent calls childCmp.refresh()
    @api
    refresh() {
        this.loadData();
    }

    // Public GETTER/SETTER pair — react to a value being set
    @api
    get selectedIds() {
        return this._selectedIds;
    }
    set selectedIds(value) {
        this._selectedIds = value ? [...value] : [];
        this.recalculate();
    }
    _selectedIds = [];
}
🚫
Never mutate an @api property inside the child Data flows down. If the child changes its own @api value, LWC throws "Invalid mutation: Cannot set … on … " in strict cases and the parent's state gets out of sync. Copy it into a private field first, and notify the parent with a custom event.

Getters & setters

Getters replace the template expressions LWC doesn't allow. Setters let you react to incoming values.

import { LightningElement, api } from 'lwc';

export default class ContactCard extends LightningElement {
    contacts = [];
    _filter = 'all';

    /* ---------- GETTERS: computed values for the template ---------- */
    get hasContacts()  { return this.contacts.length > 0; }
    get contactCount() { return this.contacts.length; }
    get cardTitle()    { return `Contacts (${this.contacts.length})`; }

    get filteredContacts() {
        if (this._filter === 'all') return this.contacts;
        return this.contacts.filter(c => c.Status__c === this._filter);
    }

    // Dynamic CSS classes — a very common getter use
    get containerClass() {
        return this.hasContacts
            ? 'slds-box slds-theme_success'
            : 'slds-box slds-theme_shade';
    }

    // Formatting for display
    get formattedRevenue() {
        return new Intl.NumberFormat('en-IN', {
            style: 'currency', currency: 'INR'
        }).format(this.revenue || 0);
    }

    /* ---------- SETTER: run logic when a parent sets a value ---------- */
    @api
    get filter() { return this._filter; }
    set filter(value) {
        this._filter = value || 'all';
        this.applyFilter();          // side effect on every set
    }
}
⚡
Getter performance A getter runs on every re-render. Keep it cheap — no loops over thousands of items, no JSON.parse, never a server call. If the computation is expensive, compute it once in connectedCallback or in the setter and store the result in a field.
🔗
The setter + @api ordering rule When you use @api with a getter/setter pair, put the decorator on the getter. Also note: the setter fires before connectedCallback, so don't rely on the DOM being ready inside it.

Conditional rendering

<template>
    <!-- ✅ MODERN (API 58+, Spring '23) -->
    <template lwc:if={isLoading}>
        <lightning-spinner alternative-text="Loading"></lightning-spinner>
    </template>
    <template lwc:elseif={hasError}>
        <p class="slds-text-color_error">{errorMessage}</p>
    </template>
    <template lwc:elseif={hasData}>
        <c-data-table records={records}></c-data-table>
    </template>
    <template lwc:else>
        <p>No results.</p>
    </template>

    <!-- ⚠️ LEGACY (still works, no else-if chain) -->
    <template if:true={isLoading}>…</template>
    <template if:false={isLoading}>…</template>

    <!-- You can also put the directive on a real element -->
    <div lwc:if={showPanel} class="slds-box">Panel content</div>
</template>

👻
Conditional rendering removes the element from the DOM It is not CSS hiding. That means this.template.querySelector() returns null for hidden branches, and child components are destroyed and recreated (losing their state) when the condition flips. Use CSS slds-hide if you need to preserve state.

Rendering lists

<template>
    <!-- for:each — the standard loop -->
    <template for:each={contacts} for:item="contact" for:index="idx">
        <div key={contact.Id} class="slds-box">
            {idx}: {contact.Name} — {contact.Email}
            <lightning-button
                label="Delete"
                data-id={contact.Id}
                onclick={handleDelete}>
            </lightning-button>
        </div>
    </template>

    <!-- iterator — when you need first/last flags -->
    <template iterator:it={contacts}>
        <li key={it.value.Id}
            class={it.first ? 'first-item' : ''}>
            {it.value.Name}
            <template lwc:if={it.last}><hr /></template>
        </li>
    </template>
</template>
handleDelete(event) {
    // dataset is how you get the row identity back
    const id = event.currentTarget.dataset.id;
    this.contacts = this.contacts.filter(c => c.Id !== id);
}
🔑
The key attribute is mandatory key must be on the first element inside the loop and must be a unique primitive (string/number) — never an object, and never the index if the list can be reordered. Without a stable key, LWC re-uses the wrong DOM nodes and you get bizarre bugs.

Lifecycle hooks

Lifecycle order — parent and child
HookWhenUse it forDon't
constructor()Instance createdInitialise private fieldsTouch the DOM, read @api values, or forget super() first
connectedCallback()Inserted into the DOMFetch data, subscribe to LMS/EMP, read @api values, set up listenersQuery the DOM (not rendered yet)
render()Before renderingReturn a different template conditionallySide effects or state changes
renderedCallback()After every renderDOM measurements, third-party library init, focus managementChange reactive state unguarded — infinite loop
disconnectedCallback()Removed from the DOMUnsubscribe, clear intervals, remove listenersAssume it always runs on page navigation
errorCallback(error, stack)A descendant throwsError boundary — show a friendly message, log itExpect it to catch errors in this component
 
import { LightningElement, api } from 'lwc';
import { subscribe, unsubscribe, MessageContext } from 'lightning/messageService';

export default class LifecycleDemo extends LightningElement {
    @api recordId;
    subscription = null;
    chartInitialised = false;
    intervalId;

    constructor() {
        super();                       // MUST be first
        this.internalState = {};       // @api values are NOT available yet
    }

    connectedCallback() {
        // recordId IS available here
        this.loadData(this.recordId);
        this.subscription = subscribe(this.messageContext, MY_CHANNEL, (m) => this.handle(m));
        this.intervalId = setInterval(() => this.poll(), 30000);
    }

    render() {
        return this.isEditMode ? editTemplate : viewTemplate;
    }

    renderedCallback() {
        // GUARD: this runs after EVERY render
        if (this.chartInitialised) return;
        const canvas = this.template.querySelector('canvas');
        if (canvas) {
            this.chartInitialised = true;
            this.drawChart(canvas);
        }
    }

    disconnectedCallback() {
        unsubscribe(this.subscription);
        this.subscription = null;
        clearInterval(this.intervalId);       // prevent memory leaks
    }

    errorCallback(error, stack) {
        this.hasError = true;
        this.errorMessage = error.message;
        console.error('Child component failed:', error, stack);
    }
}
♾️
The classic renderedCallback bug Changing a reactive property inside renderedCallback triggers a re-render, which calls renderedCallback again — an infinite loop that freezes the browser tab. Always guard with a boolean flag, or do the work in connectedCallback instead.

Shadow DOM

Each LWC renders into its own shadow tree — an encapsulated DOM attached to the component's host element. This is a browser standard, not a Salesforce invention.

Encapsulation boundary

Querying the DOM

// ✅ Inside your own shadow tree
const input  = this.template.querySelector('lightning-input');
const rows   = this.template.querySelectorAll('.row');

// ✅ Modern, faster and refactor-safe: lwc:ref (API 59+)
//    <lightning-input lwc:ref="nameInput"></lightning-input>
const nameInput = this.refs.nameInput;

// ✅ Elements you passed into a SLOT live in the light DOM
const slotted = this.querySelector('p');

// ❌ Never reach into a child component's shadow tree
// const childBtn = this.template.querySelector('c-child').shadowRoot.querySelector('button');

// ⚠️ Only after render — null in connectedCallback
renderedCallback() {
    this.template.querySelector('lightning-input')?.focus();
}
ConsequenceWhat it means for you
CSS isolationComponent styles never leak out or in. Use SLDS utility classes and CSS custom properties (--lwc-*) or :host for theming
DOM isolationdocument.querySelector can't see inside; use this.template
Event retargetingAn event crossing the boundary reports the host as its target, hiding internals
Third-party librariesLibraries that expect global DOM access (jQuery plugins, some chart libs) often need the element passed explicitly, or Light DOM
TestingJest tests query via element.shadowRoot.querySelector()

Synthetic vs native Shadow DOM

Salesforce originally polyfilled Shadow DOM ("synthetic shadow") for older browser support. Modern orgs can enable native shadow via the Lightning Web Security setting. Native is stricter: some CSS and DOM tricks that worked under synthetic will break, so test after switching.

Light DOM — opting out

import { LightningElement } from 'lwc';

export default class LightDomCmp extends LightningElement {
    static renderMode = 'light';    // renders into the parent's DOM, no shadow root
}
// In the template: <template lwc:render-mode="light"> … </template>
// Query with this.querySelector() instead of this.template.querySelector()

Use Light DOM for: global styling/theming requirements, third-party libraries that need DOM access, and accessibility tools that struggle with shadow boundaries. Cost: you lose encapsulation.

Styling & SLDS

  • Use SLDS utility classes for spacing/layout: slds-var-m-around_medium, slds-grid, slds-col, slds-text-heading_small.
  • Use base components (lightning-card, lightning-input, lightning-datatable) — they're accessible, responsive and styled for you.
  • Theme with CSS custom properties: var(--lwc-brandPrimary), or use SLDS Styling Hooks.
  • Static resources for images/fonts: import LOGO from '@salesforce/resourceUrl/CompanyLogo';
  • :host styles the component element; ::slotted() styles slotted content.

Debugging

  • Enable Debug Mode for your user (Setup → Debug Mode) — unminified JS and better stack traces.
  • Browser DevTools: the shadow root is inspectable in Elements; set breakpoints in Sources.
  • Install the Salesforce Lightning Inspector Chrome extension to see the component tree and event log.
  • console.log(JSON.parse(JSON.stringify(obj))) — wire results are read-only Proxies and log unhelpfully otherwise.
  • Write Jest tests with sfdx-lwc-jest; run npm run test:unit.

Interview questions

1 Why is LWC faster than Aura?Easy

Because it's built on web standards the browser implements natively — ES modules, custom elements, Shadow DOM, templates. Aura shipped its own component model, event system and rendering engine, all of which had to be downloaded and interpreted. LWC is a thin layer over the platform the browser already provides, so there is far less framework code between your markup and the DOM. Bonus answer: LWC also brings standard tooling — Jest, ES6+, npm — instead of framework-specific equivalents.

2 Explain the LWC reactivity rules.Medium

Fields are reactive on reassignment: this.name = 'x' and this.items = [...this.items, item] both re-render. Mutation is not tracked — this.items.push(x), this.obj.a = 1 and this.items[0].name = 'x' change nothing on screen because the reference is unchanged.

Decorating the field with @track makes the object or array deeply reactive, which is the only reason @track still exists — since Spring '20 plain fields are reactive on reassignment without it.

3 Give the lifecycle hooks in order for a parent containing a child.Medium

Parent constructor → parent connectedCallback → parent render → child constructor → child connectedCallback → child render → child renderedCallback → parent renderedCallback.

The rule to state explicitly: rendering flows top-down, renderedCallback fires bottom-up. So a parent cannot rely on child DOM in its own connectedCallback, but can in its renderedCallback.

4 Why is @api recordId undefined in the constructor?Medium

Public properties are set by the framework after construction — the constructor runs before the element has been inserted or configured. The constructor is only for initialising private fields, and super() must be its first statement.

Read @api values in connectedCallback, which runs once the element is in the DOM and the properties are populated. If you need to react every time the value changes, use an @api getter/setter pair instead.

5 Why does the browser freeze when I set a property in renderedCallback?Medium

Changing reactive state triggers a re-render, which calls renderedCallback again — an infinite loop. renderedCallback fires after every render, not once.

Guard it with a boolean (if (this.chartInitialised) return;) for one-time DOM work such as initialising a third-party library, or move the logic to connectedCallback if it doesn't need the rendered DOM.

6 What is Shadow DOM and name three practical consequences.Hard

An encapsulated DOM subtree attached to the component's host element — a browser standard, not a Salesforce invention.

  1. CSS isolation — your styles can't leak out and global CSS can't reach in. Theme with SLDS classes, CSS custom properties, :host and ::slotted().
  2. DOM isolation — document.querySelector returns null; use this.template.querySelector() or lwc:ref. Never reach into a child's shadowRoot.
  3. Event retargeting — an event crossing the boundary reports the host as its target, hiding internals.

Escape hatch: static renderMode = 'light' for third-party libraries that need global DOM access — at the cost of encapsulation.

7 Why can't you write {items.length} or {count + 1} in a template?Easy

LWC templates deliberately allow only property access, including dotted paths like {account.Name} — no expressions, operators, function calls or method invocations. This keeps templates declarative and lets the engine track dependencies precisely for efficient re-rendering.

Put the computation in a getter. Keep getters cheap: they run on every render, so no loops over thousands of items, no JSON.parse, and never a server call.

8 What are the rules for key in for:each, and why does it matter?Medium

It's mandatory, must sit on the first element inside the loop, and must be a unique primitive — a string or number, never an object. Avoid the array index if the list can reorder or have items removed.

The key is how the diffing algorithm matches virtual nodes to real DOM nodes between renders. With an unstable key, LWC reuses the wrong element — you get checkboxes ticked on the wrong row, or input values jumping between items.

9 lwc:if versus if:true — and what happens to hidden content?Medium

lwc:if / lwc:elseif / lwc:else (API 58+) supports proper else-if chains and evaluates the branches together, so it's faster; if:true / if:false is the legacy form with no else-if.

Crucially, both remove the element from the DOM — this is not CSS hiding. So this.template.querySelector() returns null for a hidden branch, and child components are destroyed and recreated (losing their internal state) when the condition flips. Use the SLDS slds-hide class when you need to preserve state.

Quick check

1. You do this.items.push(newItem) and the UI doesn't update. Why?
Reactivity is reference-based for fields. Either reassign, or decorate the field with @track for deep reactivity.
2. Where should you subscribe to a Lightning Message Service channel?
connectedCallback runs once when inserted into the DOM and @api values are available. renderedCallback runs on every render, so you'd subscribe repeatedly.
3. document.querySelector('.my-button') returns null for a button inside your LWC. Why?
The shadow boundary hides internal markup from the document. Query through this.template, or use lwc:ref.
